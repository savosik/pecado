    Заказы в резерве (v16.9.0, уточнение ключа строки — v16.9.1)¶

    Режим самообслуживания для клиентов-интернет-магазинов: заказ сразу создаётся в 1С с удержанием товара, а окно между «зарезервировал» и «подтвердил» клиент обслуживает сам — правит состав, отменяет или отправляет в отгрузку из кабинета сайта или через клиентский API, без звонка менеджеру.

    Протокол согласован в топике №5 Agent Hub (resolution 03.09.2026).

    Как резерв выражен в 1С¶

    Отдельного статуса «Резерв» в перечислении статусов заказа нет и не будет — резерв живёт на строке документа:

    Что Значение
    Реквизит строки ВариантОбеспечения СоСклада («Резервировать на складе»)
    Статус документа КОбеспечению («К выполнению / В резерве»)
    Регистр удержания ТоварыКОтгрузке, ресурс ВРезерве
    Публикуемый остаток уже за вычетом резерва (ЗапасыИПотребности)

    Следствия:

    • постановка в резерв сама снимает товар с витрины через обычный stock.updated;
    • на сайт резервный заказ приезжает со status: ready_for_shipment — режим различается только по полю reserve в order.created / order.updated;
    • расходный ордер не оформляется (ресурс КОтгрузке у резервной строки нулевой), поэтому заказ не уходит в сборку.

    Жизненный цикл¶

    оформление (reserve: true) ──► резерв в 1С (окно ожидания)
    │ клиент правит состав          │ order.updated (сайт → 1С)
    │ клиент отменяет               │ order.deleted, reason=client_cancelled
    │ срок истёк                    │ order.deleted, reason=reserve_expired
    └ клиент подтверждает ──────────► order.confirmed → «К отгрузке», обычный конвейер

    Правила¶

    1. Охват — только партнёры-участники: флаг reserve_allowed в partner.created / partner.updated, мастер — 1С (отдельный реквизит партнёра). Сайт показывает выбор резерва в чекауте только участникам и может точечно сузить охват, но не расширить.
    2. Срок удержания — reserved_until присылает сайт (обязателен при reserve: true, повторяется в каждом сообщении). У 1С — верхний предел удержания (настройка, стартово 24 часа от создания заказа): срок сверх предела урезается, в исходящих 1С reserved_until — всегда фактический срок, не эхо. Сайт показывает клиенту фактический срок.
    3. Рассинхрон флагов: reserve: true по неучастнику — обычный заказ, признак игнорируется, в ответном order.updated возвращается reserve: false; reserved_until в прошлом — трактуется как reserve: false.
    4. Неподтверждённый резерв в сборку не идёт — ни автоматически (авто-оформление отгрузки в 1С гейтится по признаку резерва), ни руками. Ручной перевод менеджером — аварийный путь: 1С шлёт order.updated с reserve: false, сайт убирает заказ из раздела резервов и закрывает клиентские правки.
    5. Правка состава (order.updated сайт → 1С) — только в окне резерва, состав целиком, в v1 только уменьшение (снизить количество, удалить строку). 1С применяет к проведённому документу (распровести → заменить → провести), пока нет расходного ордера и реализации.
    6. Ключ строки — пара items_version + line_number (уточнено в v16.9.1). line_number стабилен только в пределах версии состава: при физическом удалении строки платформа 1С перенумеровывает последующие. Поэтому состав всегда идёт и применяется целиком (snapshot), сопоставление строк — внутри одного сообщения, а любое изменение состава (включая перенумерацию) увеличивает items_version. Сайт со своей стороны требует версию состава от клиента (кабинет и клиентский API) и отклоняет правку с устаревшей версией до отправки в шину — проверка 1С остаётся вторым рубежом.
    7. Конфликты — оптимистичная блокировка по версии состава: сайт шлёт base_items_version (последний применённый items_version из сообщений 1С); при расхождении правка не применяется, 1С отвечает order.updated с актуальным составом, items_version и conflict {rejected_message_id, reason}. ⚠️ revision для блокировки не годится — это счётчик отправленных сообщений, он растёт и без изменения состава (перепроведение, эхо с номером, дренаж очереди).
    8. Отмена (order.deleted сайт → 1С) — строки помечаются отменёнными с причиной, статус «Закрыт», резерв освобождается. Пометка удаления не ставится.
    9. Таймаут — основной таймер у сайта: по истечении reserved_until сайт шлёт order.deleted с reason: reserve_expired. Страховочный регламент 1С снимает резерв при reserved_until + 6 часов грации — последний рубеж на случай потери сообщения, в норме не срабатывает.
    10. Идемпотентность — повторная доставка любого сообщения (по message_id / uuid) не меняет состояние повторно; повтор order.confirmed по подтверждённому заказу — успех без изменений.
    11. Раскатка — за флагами обеих сторон, включение по отдельному решению владельцев. Перед включением — поимённая сверка списков участников: сайт передаёт свои uuid партнёров-интернетчиков, 1С размечает reserve_allowed и возвращает фактический состав через partner.updated.

    События протокола¶

    Событие Направление Назначение
    order.created + reserve/reserved_until Сайт → 1С создать заказ в резерве
    order.updated + base_items_version Сайт → 1С правка состава клиентом
    order.deleted + reason Сайт → 1С отмена клиентом / снятие по таймауту
    order.confirmed Сайт → 1С отправить резерв в отгрузку
    order.created/order.updated + reserve, reserved_until, items_version, conflict 1С → Сайт состояние резерва, фактический срок, версия состава, отказ правки
    partner.created/partner.updated + reserve_allowed 1С → Сайт признак участника режима

    Payload-схемы: AsyncAPI, JSON Schemas order.updated.to_erp, order.deleted.to_erp, order.confirmed.to_erp в /docs/erp/schemas/.
