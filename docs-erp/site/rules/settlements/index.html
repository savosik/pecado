    Регистр взаиморасчётов¶

    JSON Schema: settlement.posted.json | settlement.reverted.json | settlement.opening_balance.json | settlement.checkpoint.json
    AsyncAPI: Полная спецификация

    Направление: 1С → Сайт | Очередь: erp_in.settlements | Версия: v16.0.0

    Движения регистра «Расчёты с клиентами» из 1С. Ядро мажорной версии 16.0.0: сайт перестаёт считать деньги и становится витриной регистра.

    Зачем понадобилось¶

    До v16.0.0 сайт выводил долг клиента из первичных документов: реализации минус платежи, разложенные по расшифровке, с поправкой на график оплат. Эта арифметика систематически не сходилась с 1С, потому что 1С гасит долг ещё и авансами по заказам, взаимозачётами и корректировками, которых сайт не видит.

    Что мерили Результат
    Доля денег, помещавшаяся в модель «платёж → реализация» 28,6 %
    Не помещалось 111 872 793,21 ₽
    Просрочка одного клиента: сайт против 1С 5,53 млн ₽ против 478 тыс ₽

    Итогом стало отключение денежного раздела в личном кабинете: показывать клиенту завышенный в десять раз долг оказалось хуже, чем не показывать никакого.

    Корень проблемы: сайт не может знать то, что знает только 1С. Регистр взаиморасчётов — единственное место, где долг посчитан правильно, и теперь он приезжает целиком.

    События¶

    Событие Описание
    settlement.posted Все движения одного документа. Полная замена
    settlement.reverted Отмена проведения: движения документа аннулируются
    settlement.opening_balance Сальдо на дату отсечки (01.01.2026), несверенное
    settlement.checkpoint Сверенное сальдо на дату закрытия периода (01.07.2026 и далее)

    ⚠️ Знаковое соглашение¶

    Самое опасное место контракта: перепутанный знак не ловится валидацией схемы — суммы правильные, а баланс инвертирован у всей базы.

    amount со знаком, «+» означает «в пользу клиента».

    type Знак Смысл
    shipment − Реализация: клиент стал должен больше
    payment_in + Поступление средств от клиента
    goods_return + Возврат товара от клиента (зачёт)
    payment_out − Возврат денег клиенту
    commission_sale − Продажа через комиссионера
    adjustment ± Взаимозачёт, корректировка задолженности или реализации

    Сумма всех движений равна балансу контрагента; отрицательный баланс означает, что клиент должен. Соглашение совпадает с current_balance в balance.updated.

    В 1С знак читается наоборот: их «Приход» (долг вырос) — это наш минус, их «Расход» — наш плюс. Инверсию применяет сторона 1С. Поле movement_kind (income / expense) приезжает дополнительно и в арифметике не участвует — оно нужно, чтобы при разборе спорной строки было видно, что стояло в регистре.

    Числовой пример¶

    Договор в рублях, на 01.01.2026 клиент должен 50 000 ₽.

    Дата Операция type amount
    01.01.2026 Начальное сальдо opening_balance −50 000,00
    15.01.2026 Реализация на 120 000 shipment −120 000,00
    20.01.2026 Поступило 100 000 payment_in +100 000,00
    25.01.2026 Возврат товара на 20 000 goods_return +20 000,00
    30.01.2026 Вернули клиенту 5 000 payment_out −5 000,00

    Итог −55 000: клиент должен 55 000 ₽. Через дебет и кредит акта сверки: дебет 175 000, кредит 120 000, сальдо −55 000. ✓

    Бизнес-правила¶

    • (v16.0.0) Единица сообщения — документ, а не движение. В 1С движения порождаются проведением документа, поэтому подписка на проведение даёт идемпотентность без ухищрений.
    • (v16.0.0) Движения документа заменяются целиком. settlement.posted вытесняет всё сохранённое по этому document_uuid. Досылать дельту нельзя: сайт не отличит «строки не изменились» от «строк больше нет». Пустой entries — валидное значение, означает, что движений у документа не осталось.
    • (v16.0.0) Все измерения регистра живут в строке, не в шапке. Замер боевой базы: 33 % документов двигают несколько объектов расчётов, у 27 документов расходится и ключ аналитики. Правило простое: всё, что берётся из ключа аналитики, живёт в entries[].
    • (v16.0.0) Объект расчётов — не то же, что документ-регистратор. Регистратор — кто породил движение; объект расчётов (ОбъектРасчетов) — по чему ведётся расчёт. Один платёж закрывает несколько заказов, и это норма.
    • (v16.0.0) Перечень type закрытый, перечень settlement_object_kind открытый. Неизвестный тип движения отбрасывает сообщение в DLQ: пропустить строку молча нельзя, баланс разъедется незаметно. Неизвестный вид объекта расчётов, наоборот, сохраняется как other — состав объекта на стороне 1С заранее не известен.
    • (v16.0.0) Строка самодостаточна. Реквизиты документа (document_number, document_date, document_kind) дублируются в сообщение намеренно: движение обязано читаться, даже если самого документа на сайте нет и не будет — например, отчёт комиссионера. Это снимает весь класс проблем «движение приехало раньше документа».
    • (v16.0.0) Только движения с ненулевой суммой. ЗаказКлиента двигает КОплате и КОтгрузке, но Сумма = 0,00 за весь год — заказы в ленту не попадают. Правило сформулировано как «ненулевой Сумма», а не «кроме заказов»: если заказ когда-нибудь начнёт двигать сумму, движение появится автоматически.
    • (v16.0.0) Рублёвый эквивалент приходит суммой, а не курсом. amount_rub — ресурс СуммаРегл, зафиксированный учётом на дату операции. Курс сайта может отставать, а посчитанный учётом эквивалент не разъедется с отчётами 1С.
    • (v16.0.0) Отбор контрагентов общий для движений, баланса и сальдо. Приезжает баланс — обязаны приезжать движения; исключён контрагент — исключён везде. Промежуточных состояний быть не должно, иначе акт сверки не сможет объяснить баланс.

    Две даты сальдо¶

    Дата отсечки — 01.01.2026, но период на неё в 1С не закрыт: даты запрета изменения стоят на 31.03, 30.04 и 30.06.2026. Поэтому точек две:

    Событие Дата Роль
    settlement.opening_balance 01.01.2026 Начало ленты, is_verified: false
    settlement.checkpoint 01.07.2026 Сверенная цифра, is_verified: true

    Инвариант: сальдо на 01.01 + движения за первое полугодие = checkpoint на 01.07. Сойдётся — история первого полугодия достоверна. Нет — расхождение известно точной величиной, и решение «показывать ли H1» принимается осознанно, а не по умолчанию.

    Это тот же принцип, что и во всём разделе: расхождение — сигнал, а не повод считать по-своему.

    Что считается из регистра¶

    Вопрос бизнеса Выражение
    Фактический баланс (акт сверки) SUM(amount) по nature='fact' на дату
    Сколько клиент должен сейчас непогашенный план с датой ≤ сегодня
    Текущая просрочка то же, дата < сегодня
    Поток по дням непогашенный план, дата > сегодня, группировка по дате
    Свободный аванс положительный фактический баланс

    Ось акта сверки¶

    Контрагент × организация × валюта — регистровый срез, который гарантированно сходится с balance.updated.

    Соглашение и договор осью не являются: соглашение 1С берёт из документа-регистратора, и при изменении задним числом группировка исторических движений может разъехаться; договор заполнен лишь у 2,2 % документов. Оба служат фильтром и группировкой внутри акта — см. Соглашения.

    Критерии приёмки¶

    • [ ] Сайт принимает все четыре события из очереди erp_in.settlements
    • [ ] Повторная доставка того же document_uuid не задваивает движения
    • [ ] settlement.posted заменяет набор движений целиком, пустой entries очищает
    • [ ] settlement.reverted гасит вклад документа, включая строки его графика
    • [ ] Движение с неизвестным type уходит в DLQ; неизвестный settlement_object_kind сохраняется как other
    • [ ] Движение, приехавшее раньше документа, сохраняется и читается по document_number
    • [ ] Устаревшая ревизия отбрасывается ErpRevisionGuard
    • [ ] Валютное движение сохраняет amount_rub из 1С, свой курс не подставляется
    • [ ] Сальдо 01.01 + движения первого полугодия сходятся с checkpoint 01.07
    • [ ] Сумма движений по контрагенту и организации совпадает с balance.updated
    • [ ] Знак по каждому type соответствует соглашению — проверяется командой сверки
