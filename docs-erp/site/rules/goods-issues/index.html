    Расходные ордера на товары¶

    JSON Schema: goods_issue.created.json | goods_issue.updated.json | goods_issue.deleted.json
    AsyncAPI: Полная спецификация
    Задание разработчику 1С: Расходные ордера: что сделать в 1С

    Направление: 1С → Сайт | Очередь: erp_in.warehouse | Появилось в: v15.15.0

    Зачем это нужно¶

    Реализация (shipment.*) отражает уже свершившийся факт отгрузки. Документ, по которому товар физически собирают, проверяют, упаковывают и грузят — «Расходный ордер на товары» — до v15.15.0 на сайте отсутствовал вовсе.

    Из-за этого склад не видел на сайте свою основную операционную единицу: что сейчас в отборе, что ждёт проверки, что зависло на этапе, сколько мест собрано и по каким заказам идёт ордер. Всё это жило только в толстом клиенте 1С.

    Главный потребитель данных — кабинет склада /wms: журнал ордеров с фильтрами, статусами, карточкой документа и выгрузкой в Excel.

    События¶

    Событие Описание
    goods_issue.created При первом проведении ордера
    goods_issue.updated При смене статуса, состава или реквизитов (структура идентична created, отличается event)
    goods_issue.deleted При отмене проведения или пометке на удаление

    Статусы¶

    Статус присылается машинным кодом, а не русским названием из 1С:

    Статус в 1С Код
    Подготовлен prepared
    К отбору to_pick
    К проверке to_check
    В процессе проверки checking
    Проверен checked
    К отгрузке to_ship
    Отгружен shipped

    Значение вне этого списка не принимается: сообщение отбрасывается целиком, попадает в erp_dlq.warehouse и фиксируется в журнале ошибок валидации.

    Строгий перечень выбран сознательно — в отличие от shipment.status, где 1С шлёт голые строки. Статус здесь главное, ради чего журнал склада существует: молча принять неизвестный код означало бы показать кладовщику ордер в состоянии, которого нет в его рабочем процессе.

    Сайт хранит не только текущий статус, но и журнал смен: по нему видно, сколько ордер простоял на каждом этапе, и находятся зависшие документы. Строка в журнал пишется только при фактическом изменении статуса — повторный goods_issue.updated с тем же статусом журнал не засоряет.

    Бизнес-правила¶

    • Один ордер может собираться сразу по нескольким заказам клиента. Поэтому заказ-распоряжение указывается в строке (items[].order_uuid), а не в шапке — так же, как у реализаций. Связь «ордер ↔ заказ» на сайте строится через строки.
    • Документ присылается целиком. Сайт удаляет прежние строки и упаковочные листы и создаёт их заново. Досылать отдельные изменившиеся строки нельзя — они продублируются.
    • Идемпотентность по uuid. Повторное сообщение по тому же документу не создаёт второй ордер, а перезаписывает существующий. Плюс транспортная идемпотентность по message_id: полный дубль сообщения отбрасывается до обработки.
    • recipient_name присылать нужно всегда. Получателем ордера бывает контрагент, которого в справочниках сайта нет вовсе (маркетплейс, внутреннее перемещение). Без строки-имени такой ордер в журнале склада останется безымянным.
    • Привязка к контрагенту — по общим правилам документов: приоритет contractor_uuid, fallback по tax_id в паре с partner_uuid. Не нашли — ордер сохраняется с пустым контрагентом, но с заполненным recipient_name и виден складу.
    • Неизвестный товар или заказ обработку не роняют. Строка сохраняется с пустой ссылкой, но с product_name и order_number из 1С: ордер по товару, которого нет в каталоге сайта, кладовщику всё равно нужно видеть.
    • packages: отсутствие ключа и пустой массив означают разное. Ключа нет — сайт не трогает сохранённые упаковочные листы; [] — очищает их полностью.
    • Неизвестный сайту склад автоматически не заводится: warehouse_uuid останется непривязанным, факт попадёт в лог. Склады заводятся в админке вручную.
    • Организация документа — по общим правилам, см. Организации.

    Что сайт не хранит¶

    • Цены, скидки, суммы. Ордер — складской документ, а не денежный: суммы приезжают реализацией. Если понадобится сверка «отгружено на сумму» — она строится по реализации.
    • Серии номенклатуры и штрихкоды маркировки («Честный знак»). Данные тяжёлые, а задач, которые на них опираются, у сайта сейчас нет. При необходимости — отдельная доработка контракта.
    • Состав упаковочных листов построчно. Хранится номер листа, число позиций в нём и (опционально) номер листа в строке товара — этого хватает для сверки при погрузке.

    Чего в документе 1С нет (v15.16.0)¶

    Уточнения после сверки контракта с реальным составом реквизитов документа.

    Доставка: delivery_type и delivery_address не заполнять. Таких реквизитов в расходном ордере физически нет — проверено по полному перечню 43 реквизитов. Присылайте delivery_order («Порядок доставки» из нижней части документа). Способ доставки и адрес сайт берёт из заказа и реализации, где они есть штатно. Оба поля оставлены в схеме ради совместимости и будут удалены, когда станет ясно, что их никто не шлёт.

    Отметки времени erp_created_at / erp_updated_at можно опускать. У документа в 1С отключена история данных, брать их неоткуда. Поля не входят в required, сообщение без них валидно, а отсутствие ключа не сбрасывает сохранённое значение. По той же причине у расходных ордеров не используется revision — см. Порядок доставки и свежесть.

    Ячейка (items[].cell) — необязательная строка (v15.17.0). Реквизит «Ячейка» табличной части приезжает как есть и показывается кладовщику в карточке ордера и в выгрузке. Сайт её не разбирает и не сверяет ни со справочником складов, ни с остатками: адресное хранение ведётся в 1С, сайт его только отражает.

    Поле можно не присылать вовсе, а можно прислать пустую строку — для сайта это одно и то же, ячейка остаётся незаполненной. Ограничение одно: не длиннее 255 символов, иначе сообщение не пройдёт валидацию.

    Номер места (items[].package_number) — приближение, и это нормально. Связи «конкретная строка ордера → конкретное место упаковки» в модели данных 1С нет. Номер восстанавливается по паре товар + характеристика; если товар лежит в нескольких местах, строка получает наименьший номер.

    Следствие, с которым сайт согласился: сумма строк с номером N может не совпасть с positions_count места N, и сайт эти величины не сверяет. Дробление одной строки по нескольким местам контракт выразить не позволяет — если это когда-нибудь понадобится, заведём отдельную структуру, а не будем менять смысл поля.

    Обратный поток¶

    Его нет: журнал на сайте read-only, статусами управляет 1С. Сайт не присылает в 1С ни смену статуса, ни отметки о сборке.

    Критерии приёмки¶

    • [ ] 1С присылает goods_issue.created при первом проведении ордера
    • [ ] 1С присылает goods_issue.updated при каждой смене статуса
    • [ ] Статус передаётся машинным кодом из таблицы выше
    • [ ] items[].order_uuid заполнен — иначе ордер не связывается с заказами
    • [ ] recipient_name заполнен всегда
    • [ ] message_id уникален для каждого сообщения
    • [ ] Выполнена первоначальная выгрузка незакрытых ордеров
    • [ ] Очередь erp_dlq.warehouse пуста после прогона
