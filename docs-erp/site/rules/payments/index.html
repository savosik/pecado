    Платежи¶

    JSON Schema: payment.created.json | payment.updated.json | payment.deleted.json
    AsyncAPI: Полная спецификация

    Направление: 1С → Сайт | Очередь: erp_in.payments

    Платёжные документы банка и кассы: поступления оплаты от клиентов и возвраты оплаты клиентам. Онлайн-эквайринг сайта по этой очереди не передаётся — это отдельная сущность.

    События¶

    Событие Описание
    payment.created При первом проведении платёжного документа
    payment.updated При перепроведении или изменении расшифровки
    payment.deleted При отмене проведения

    Бизнес-правила¶

    • (v15.11.0) Один платёж разносится на несколько реализаций, и одна реализация закрывается несколькими платежами. Разнесение приходит массивом allocations внутри самого сообщения — отдельного события для расшифровки нет
    • (v15.11.0) Разнесение заменяется целиком. Содержимое allocations полностью вытесняет то, что сохранено на сайте. Досылать только изменившиеся строки нельзя — сайт не умеет отличить «строки не изменились» от «строк больше нет»
    • (v15.11.0) Отсутствие ключа allocations и пустой массив означают разное. Ключа нет — сайт не трогает сохранённое разнесение (используйте, когда меняется только шапка документа). Пустой массив [] — сайт очищает разнесение полностью, платёж становится авансом. Различие критично: если 1С опустит ключ, подразумевая «разнеси заново на ноль», оплата останется на реализациях
    • (v15.11.0) Строка расшифровки связывается по uuid, а не по номеру. Документ может ещё не приехать на сайт: строка сохранится без привязки, а связь доклеится автоматически при его получении
    • (v15.16.0) Расшифровка не ограничена реализациями — см. раздел «Типы документов расшифровки» ниже
    • (v15.11.0) Направление передаётся явно полем direction (in — поступление от клиента, out — возврат клиенту). Сайт не выводит направление из текста операции: наименование операции меняется вместе с настройками учёта. При отсутствии поля платёж считается поступлением. Сумма amount всегда положительная — знак задаёт direction, а не сама сумма
    • (v15.11.0) operation_code — машинный код операции латиницей (customer_payment, customer_refund). operation_name — русское наименование как в 1С, показывается сотрудникам как есть и в логике не участвует
    • (v15.11.0) Привязка к контрагенту повторяет правило реализаций:
      • Приоритет — по contractor_uuid (Company.erp_id на сайте)
      • Fallback — по tax_id в паре с partner_uuid. Без partner_uuid fallback-поиск не выполняется (security-fix v13.2): иначе нашлась бы чужая Company с тем же ИНН
      • contractor_uuid сохраняется в платеже всегда, даже если контрагента на сайте ещё нет. По нему связь доклеивается позже
    • (v15.11.0) partner_uuid настоятельно рекомендуется. Без него платёж не привяжется к пользователю сайта, и клиент не увидит свою оплату в личном кабинете
    • (v15.11.0) Нераспределённый остаток = аванс. Разница между amount и суммой строк allocations хранится на сайте как нераспределённый остаток и показывается клиенту и менеджеру. Платёж вообще без allocations — целиком аванс, это легитимно
    • (v15.11.0) Оплата реализации считается только по совпадающей валюте. Платёж в валюте, отличной от валюты реализации, в оплату не засчитывается, и факт попадает в лог. Сложить рубли с тенге по неизвестному курсу сайт не вправе
    • (v15.11.0) Возврат (direction: "out"), разнесённый на реализацию, уменьшает её оплаченную сумму
    • (v15.11.0) payment.updated на неизвестный платёж создаёт его из полученного payload — структура updated полная. Потерянный payment.created означал бы потерянные деньги в отчётах; реализация в такой ситуации хотя бы видна в заказах, а платёж не виден нигде
    • (v15.11.0) payment.deleted не удаляет расшифровку. Платёж помечается удалённым и перестаёт учитываться в оплате реализаций, но строки разнесения сохраняются: повторное проведение того же документа вернёт их как было
    • (v15.11.0) Номер документа не уникален. Номера повторяются между организациями и годами, поэтому связь строится только по uuid. Поле bank_number (номер по банку) — отдельный номер, по которому клиент ищет платёж в своей выписке
    • (v15.11.0) Время в date значимо. Порядок платежей внутри дня определяет, каким из них закрыта реализация, поэтому date передаётся как datetime, а не как дата
    • (v15.11.0) Реквизиты платежа на сайте не редактируются. Мастер — 1С. Сотрудник сайта может добавить только комментарий и вложения; эти поля в 1С не уходят и из 1С не перезаписываются
    • (v15.16.0) Комментарий 1С хранится отдельно от комментария сотрудника. Поле comment из payload попадает в собственную колонку и не затирает заметку менеджера — иначе первая же доставка документа стирала бы её. Не путать с purpose: там назначение платежа из банковской выписки, это другое поле и другой смысл
    • (v15.16.0) organization_account — НАШ счёт, payer_account — счёт КЛИЕНТА. Состав полей у них одинаковый, различие только смысловое, и до v15.16.0 описания были дословно одинаковыми. Перепутав их, клиент увидел бы в кабинете собственный счёт вместо нашего и решил бы, что деньги ушли не туда

    Типы документов расшифровки (v15.16.0)¶

    До v15.16.0 строка расшифровки умела указывать только на реализацию: shipment_uuid был обязателен, target_type знал единственное значение shipment.

    Замер 1С на боевой базе за 2026 год показал, что это вмещает меньше трети денег:

    На что указывает строка Строк Доля строк
    Реализация 4 366 58%
    Заказ клиента (предоплата) 2 033 27%
    Первичный документ 880 12%
    Отчёт комиссионера 146 2%
    Прочее 111 1%

    В деньгах хуже: из 156 754 061,98 ₽ разнесения на реализации ложится 44 881 268,77 ₽, а 111 872 793,21 ₽ (71,4%) не помещалось. Не помещались именно крупные предоплаты по заказам: чем больше платёж, тем вероятнее, что реализации ещё нет.

    Правила¶

    target_type определяет, какое поле в строке обязательно:

    target_type Обязательное поле Что делает сайт
    shipment (или поле отсутствует) shipment_uuid Засчитывает оплату реализации
    order order_uuid Показывает предоплату в карточке заказа и закрывает ею график оплаты его реализаций
    other — (желательны target_uuid и target_name) Сохраняет строку и показывает её как есть
    • Отсутствие target_type и null означают shipment — обратная совместимость с v15.11.0.
    • Строка, не удовлетворяющая требованию своей колонки, пропускается с записью в лог. После v15.16.0 это должно стать редким исключением, а не системой.
    • Тип вне перечисления пропускается так же.

    Что закрывает накладную¶

    Оплату реализации (shipments.paid_amount) закрывают только строки shipment. Это поле — строгая проекция расшифровки платежа, и предоплата по заказу его не меняет: пока реализации нет, гасить нечего.

    Когда реализация появляется, 1С переразносит платёж и присылает его целиком заново — правило «разнесение заменяется целиком» не меняется. Досылать изменившиеся строки по-прежнему нельзя.

    Вариант «1С сама развернёт заказ в реализации» отвергнут обеими сторонами: на момент платежа реализации может не быть, а при её появлении пришлось бы досылать обновления по всем ранее отправленным платежам заказа.

    Что закрывает график оплаты (2026-08-09)¶

    График оплаты предоплата по заказу закрывает — в отличие от paid_amount. Строка графика со ссылкой order_uuid гасится авансом того же заказа.

    Так пришлось сделать, потому что на практике 1С разносит на заказы почти половину денег: на 2026-08-09 это 39,7 млн ₽ из 82,8 млн ₽ поступлений, а до июня 2026 — подавляющее большинство платежей. Без зачёта строка графика оставалась просроченной навсегда, и отчёт «когда придут деньги» показывал долг, которого в учёте нет: у одного клиента 5,53 млн ₽ против 478 тыс ₽ по данным самой 1С.

    Правила зачёта:

    • аванс раскладывается по строкам всех реализаций заказа в порядке FIFO (плановая дата, затем номер строки) — заказ отгружают частями, и зачесть его каждой реализации целиком значило бы погасить долг дважды;
    • прямое разнесение имеет приоритет: аванс закрывает лишь то, что не закрыто строками shipment;
    • зачтённая сумма хранится отдельно (shipment_payment_schedules.prepaid_amount), а не примешивается к paid_amount: у них разные источники и разные инварианты;
    • пересчёт идемпотентен — полная функция от состояния БД, как и остальные денежные агрегаты.

    Со стороны 1С ничего делать не нужно: контракт обмена не изменился.

    other — что увидит клиент¶

    Строки other сайт ни с чем не связывает. В расшифровке показывается target_name — представление документа строкой, как в 1С («Отчёт комиссионера 29УТ-000112 от 14.03.2026»). Если поле не заполнено, клиент увидит только сумму, поэтому заполнять его стоит осмысленно.

    Порядок первичной выгрузки¶

    Платежи выгружаются после реализаций. Иначе весь массив приедет с неразрешёнными shipment_uuid, и оплата проставится только по мере доезда реализаций. Порядок не критичен для корректности (связь доклеивается), но экономит часы на первичной заливке.

    • [x] (v15.11.0) contractor_uuid сохраняется даже когда контрагент на сайте отсутствует
    • [x] (v15.11.0) Повторная доставка того же uuid не создаёт второй платёж и не задваивает разнесение
    • [x] (v15.11.0) payment.updated без ключа allocations оставляет разнесение нетронутым; с пустым массивом — очищает
    • [x] (v15.11.0) Строка с неизвестным shipment_uuid сохраняется без привязки и доклеивается при получении реализации, после чего оплата реализации пересчитывается
    • [x] (v15.11.0) Нераспределённый остаток равен amount минус сумма строк разнесения
    • [x] (v15.11.0) Реализация, закрытая двумя платежами, получает суммарную оплату и статус «оплачена»
    • [x] (v15.11.0) Возврат (direction: "out") уменьшает оплаченную сумму реализации
    • [x] (v15.11.0) Платёж в валюте, отличной от валюты реализации, в оплату не засчитывается
    • [x] (v15.11.0) payment.deleted обнуляет вклад платежа в оплату реализаций, сохраняя строки расшифровки; повторное payment.created возвращает оплату
    • [x] (v15.11.0) Клиент видит свои оплаты в личном кабинете и разнесённые платежи в карточке реализации
    • [x] (v15.16.0) Строка с target_type: "order" и заполненным order_uuid сохраняется, а не пропускается
    • [x] (v15.16.0) Предоплата по заказу видна клиенту в карточке заказа и менеджеру в CRM
    • [x] (v15.16.0) Предоплата по заказу не засчитывается в оплату реализаций этого заказа
    • [x] (v15.16.0) Строка target_type: "other" сохраняется и показывается по target_name
    • [x] (v15.16.0) Строка order без order_uuid и строка shipment без shipment_uuid пропускаются с записью в лог
    • [x] (v15.16.0) Строка по заказу, приехавшая раньше самого заказа, доклеивается при его получении
    • [x] (2026-08-09) Предоплата по заказу закрывает строки графика оплаты его реализаций, не меняя shipments.paid_amount
    • [x] (2026-08-09) Аванс заказа делится между его реализациями и не засчитывается каждой целиком
    • [x] (2026-08-09) Прямое разнесение на реализацию имеет приоритет над зачётом аванса
    • [x] (2026-08-09) Повторный зачёт не меняет результат
