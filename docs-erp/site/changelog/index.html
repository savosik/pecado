    [15.6.0] — 2026-07-31¶

    Добавлено¶

    • Заказы промо-позиций (type: "promo" / type: "promo_sample", Сайт → 1С) — то, что выдала акция, уезжает отдельными документами. promo — подотчётные позиции со складов наличия региона, выписываются в накладную клиенту; promo_sample — рекламные образцы со склада «Москва реклама», в накладную не выписываются. Одно оформление на сайте теперь даёт до пяти документов: order, preorder, defect, promo, promo_sample.
      • final_price промо-позиции — цена из награды акции (может быть 0 или 0,01 ₽) и берётся авторитетно: пересчитывать сумму через discount_percent не нужно. Заказ с нулевой суммой — норма.
      • Схемы: order.created.to_erp.json (описание type, поля позиций is_promo / promo_kind); order.created.json и order.updated.json (входящие — те же поля позиций плюс опциональное type).
      • AsyncAPI: OrderCreatedPayload.type, OrderCreatedPayload.warehouse_uuids, OrderItem.is_promo, OrderItem.promo_kind.
      • Правила: rules/orders.md, раздел «order.created (Сайт → 1С)».
    • Позиция промо, добавленная менеджером вручную в 1С, принимается сайтом и переживает последующие order.updated — сайт не пытается сопоставить её с правилом акции.

    [15.5.0] — 2026-07-22¶

    Добавлено¶

    • Заказ уценки (type: "defect", Сайт → 1С) — некондиция с сайта уходит отдельным заказом. warehouse_uuids содержит UUID склада некондиции (флаг is_defect на сайте), final_price позиций — цена уценки (задаёт закупщик), discount_percent = 0. Структура payload не меняется — расширен только перечень значений type.
      • Схемы: order.created.to_erp.json (описание type / warehouse_uuids); AsyncAPI: OrderCreatedPayload.type.
      • Правила: rules/orders.md, раздел «order.created (Сайт → 1С)».
    • Списание партии некондиции по реализации — если shipment.created относится к заказу уценки, сайт уменьшает количество партии на отгруженное; при нуле партия закрывается. Идемпотентно по uuid реализации — повторная доставка не списывает дважды. Связь заказ↔партия сайт держит у себя, 1С передаёт обычную реализацию.
      • Правила: rules/shipments.md.

    [15.4.0] — 2026-07-15¶

    Добавлено¶

    • Самовосстановление заказа при order.updated (1С → Сайт) — если заказа с таким uuid на сайте нет, сайт создаёт его из payload вместо того, чтобы молча проигнорировать сообщение.
      • Требуются partner_uuid и непустой items. Если их нет — заказ не создаётся, сообщение помечается failed с текстом причины и видно в админке.
      • Восстановленное сообщение получает статус recovered в логе шины ERP.
      • Восстановление идемпотентно, обратно в 1С заказ не публикуется.
      • Правила: rules/orders.md, раздел «Самовосстановление заказа».
    • partner_uuid и contractor в order.updated (1С → Сайт) — поля задокументированы в спецификации. 1С присылала их фактически с самого начала, но в схеме они описаны не были и проходили через additionalProperties. Оба опциональны, обратная совместимость не нарушена. Используются только при самовосстановлении: для существующего заказа контрагент не переназначается.
      • Схемы: order.updated.json; AsyncAPI: OrderUpdatedPayload.
    • Статус recovered в логе шины ERP (erp_bus_messages.status) — рядом с success и failed. Означает: сообщение обработано, но потребовало восстановления сущности. Это сигнал о потере события на стороне 1С, а не штатный режим.

    Исправлено¶

    • order.updated по несуществующему заказу больше не «теряется» молча. Раньше обработчик выходил через return, а сообщение помечалось success; единственный след писался через Log::info, который на проде отфильтрован (LOG_LEVEL=warning). Сбой был невидим с обеих сторон. За 1–15 июля 2026 так потерялось 40 заказов (≈3.5% от всех обновляемых) — обнаружено только по жалобе менеджеров. Теперь такие случаи либо восстанавливаются, либо видны в админке как ошибки.

    [15.3.0] — 2026-07-11¶

    Добавлено¶

    • delivery_method в order.created / order.updated (оба направления) — способ доставки: delivery (доставка по адресу) | pickup (самовывоз). Опциональное поле, обратная совместимость сохранена: отсутствие поля = delivery.
      • order.created (Сайт → 1С): при pickup поле delivery_address = null — 1С не должна требовать адрес доставки.
      • order.created (1С → Сайт): для нового заказа отсутствие поля = delivery; при upsert существующего заказа отсутствие поля не сбрасывает сохранённый способ.
      • order.updated (1С → Сайт): отсутствие ключа или null — способ доставки не меняется.
      • Схемы: order.created.to_erp.json, order.created.json, order.updated.json; AsyncAPI: OrderCreatedPayload, OrderUpdatedPayload.
      • На сайте хранится в orders.delivery_method; выбор доступен на оформлении заказа и в клиентском API (POST /orders, поле delivery_method).

    Исправлено¶

    • AsyncAPI OrderUpdatedPayload синхронизирован с JSON-схемой order.updated.json: добавлено ранее отсутствовавшее в спецификации поле delivery_address (v12.1).
    • info.version AsyncAPI выровнена с changelog (была 15.1.0 при актуальной 15.2.1).

    [15.2.1] — 2026-07-05¶

    Исправлено¶

    • partner.created: e-mail нормализуется в нижний регистр при создании и поиске партнёра (HandlePartnerCreated) + на уровне модели User. Раньше e-mail с заглавными буквами сохранялся как есть, из-за чего temporary_password (crc32 от e-mail) расходился с паролем, который 1С генерирует от e-mail в нижнем регистре — партнёр не мог войти по выданному временному паролю. Контракт payload не изменился (e-mail остаётся строкой); затронута только серверная обработка. Ранее заведённые партнёры с рассинхроном (60 шт. из импорта 2026-05-10) поправлены разово на проде.

    Удалено¶

    • Очередь external.remains_for_website и её потребитель на стороне сайта. Сайт больше не принимает внешние остатки с московского ESB. Изменения:
      • Очередь отвязана от fanout external.remains (убрана из EXTERNAL_FANOUTS) и удаляется в php artisan rabbitmq:setup (новый список DELETED_QUEUES, queue_delete идемпотентен — 404 на отсутствующей очереди не роняет setup).
      • Снят supervisor-процесс [program:external-remains-consumer] (docker/supervisor/conf.d/worker.conf).
      • Очередь убрана из мониторинга rabbitmq:status и админ-страницы «Шина ERP».
    • Не затронуто: fanout external.remains и очередь external.remains_for_erp сохранены — 1С продолжает получать остатки с московского ESB без изменений. Shovel moscow-remains и policy external-remains-ttl остаются.

    Примечания¶

    • Код потребителя сайта (ExternalRemainsJob, HandleExternalProductQuantityUpdated, JSON Schema external.product_quantity_updated.json, connection rabbitmq-external-remains, config erp.external_remains) оставлен в репозитории на случай возврата. Инструкция по реактивации — в правилах внешних остатков.
    • Покрыто интеграционным тестом ExternalRemainsTopologyIntegrationTest: после rabbitmq:setup очередь external.remains_for_website отсутствует, а external.remains_for_erp по-прежнему получает копии из fanout.

    [15.1.0] — 2026-06-05¶

    Добавлено¶

    • partner.updated — поддержка поля manager (обработчик HandlePartnerUpdated). Поведение аналогично partner.created: объект {uuid, name} — привязывает/создаёт PersonalManager по erp_uuid; null — сбрасывает personal_manager_id; отсутствие ключа — менеджер не меняется. Логика вынесена в общий трейт ResolvesPersonalManager, используемый обоими обработчиками.

    [15.0.0] — 2026-05-12¶

    BREAKING: Выравнивание перечисления статусов возврата с справочником 1С:КА2. До v15 на сайте было 5 статусов (pending, confirmed, ready_to_ship, closed, cancelled), при этом ключ confirmed сворачивал два разных этапа 1С — «КОбеспечению/В резерве» и «КВозврату/К возврату» — в одно значение. Менеджер не мог увидеть, на каком из двух шагов находится заявка. Аналогично PR v14 (OrderStatus).

    Изменено (BREAKING)¶
