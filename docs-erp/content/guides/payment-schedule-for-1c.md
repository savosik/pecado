# Промт для ИИ-агента 1С: выгрузка графика оплат (протокол v15.12.0)

> Скопируйте всё, что ниже разделителя, в ИИ-агента, который дорабатывает обмен на стороне
> 1С:КА2. Промт самодостаточен: в нём есть контракт, правила, порядок работ и критерии приёмки.

---

## Роль и задача

Ты — разработчик 1С:Комплексная автоматизация 2, дорабатывающий обмен данными с сайтом
`pecado.ru` через RabbitMQ.

**Задача:** начать выгружать на сайт **график оплаты реализаций** — табличную часть
**«Правила оплаты»** документа *Реализация товаров и услуг*. Сайт уже принимает эти данные:
доработка нужна только на стороне 1С.

**Зачем это бизнесу.** Сайт уже знает *факт* оплаты (кто и сколько заплатил) — это
предыдущая версия протокола. Сейчас он не знает *плана*: когда клиент **должен** заплатить.
Из графика строятся два экрана:

- **клиенту** в личном кабинете — календарь оплат: когда и сколько он должен перечислить;
- **менеджеру** в CRM — календарь поступления денег: план на каждый день против факта,
  плюс список просроченных платежей.

Пока 1С не начнёт присылать график, оба календаря пустые.

## Что уже сделано на стороне сайта

Ничего менять и согласовывать не нужно — приём готов и выкачен в бой:

- поле `payment_schedule` принимается в существующих сообщениях `shipment.created`
  и `shipment.updated` (очередь `erp_in.documents`);
- **новой очереди и нового события нет** — график едет внутри самого документа реализации;
- сайт сам сопоставляет строки графика с фактическими платежами (методом FIFO
  по плановой дате) и считает остаток по каждой дате.

реализация при этом не обновится вообще, а не «обновится без графика».

## Формат данных

В payload реализации добавляется необязательный массив `payment_schedule`.
Одна строка массива = одна строка табличной части «Правила оплаты».

```json
{
  "event": "shipment.created",
  "message_id": "msg-shipment-a1b2c3",
  "uuid": "8e1c3a52-6f4b-4b1e-9d0a-2c7f5a8b1d34",
  "number": "29УТ-006915",
  "contractor_uuid": "…",
  "tax_id": "…",
  "date": "2026-07-28",
  "status": "completed",
  "currency_code": "RUB",
  "items": [ /* … как раньше … */ ],

  "payment_schedule": [
    {
      "line_number": 1,
      "due_date": "2026-08-27",
      "amount": 2325.20,
      "percent": 100,
      "term_days": 30,
      "basis": "shipment_date",
      "basis_name": "от даты отгрузки",
      "stage": "credit",
      "stage_name": "Оплата после отгрузки",
      "order_uuid": "…"
    }
  ]
}
```

### Соответствие полям формы «Правила оплаты»

| Поле JSON | Колонка / реквизит в 1С | Обязательно | Комментарий |
|---|---|---|---|
| `due_date` | **Дата платежа** | **да** | Формат `ГГГГ-ММ-ДД`. Без неё строка не сохранится |
| `amount` | **Сумма платежа** | **да** | Число, в валюте документа. Не строка, без пробелов-разделителей |
| `line_number` | **N** | нет | Порядок показа. Если не передать — нумерация по порядку в массиве |
| `percent` | **% платежа** | нет | Справочно. Расчёты сайт ведёт по `amount` |
| `term_days` | **Срок (дни)** | нет | Справочно: дата уже посчитана в 1С и приезжает в `due_date` |
| `basis` | **Вариант отсчёта** (код) | нет | Только: `shipment_date`, `order_date`, `invoice_date` |
| `basis_name` | **Вариант отсчёта** (текст) | нет | Как в 1С: «от даты отгрузки» |
| `stage` | **Контроль** (код) | нет | Только: `prepayment`, `advance`, `credit` |
| `stage_name` | **Контроль** (текст) | нет | Как в 1С: «Оплата после отгрузки» |
| `order_uuid` | **Заказ** | нет | UUID заказа клиента из строки |

### Что передавать НЕ нужно

Из шапки «Правил оплаты» сайту **не нужны и не принимаются**: «Расчёты», «Форма оплаты»,
«Касса», «Банковский счёт», «УИП» и «Сумма к оплате». УИП уже приходит в платёжном
документе, сумма документа у сайта есть, остальное на календарь оплат не влияет.
Не добавляй их «на всякий случай».

### Соответствие кодов

`basis` и `stage` — **латинские коды**, а не русский текст. Сопоставь их с типами значений
1С один раз в общем модуле:

| Код | Смысл |
|---|---|
| `basis` = `shipment_date` | отсчёт от даты отгрузки |
| `basis` = `order_date` | отсчёт от даты заказа |
| `basis` = `invoice_date` | отсчёт от даты счёта |
| `stage` = `prepayment` | предоплата до отгрузки |
| `stage` = `advance` | аванс |
| `stage` = `credit` | оплата после отгрузки (кредит) |

**Почему нельзя обойтись русским наименованием:** оно меняется вместе с настройками учёта
и переводом конфигурации, а на код опирается логика сайта (что считать предоплатой,
от чего отсчитывать просрочку). Русский текст передавай **дополнительно**, в полях
`*_name` — он показывается клиенту и менеджеру как есть.

Незнакомый код сайт обнулит и запишет предупреждение в лог, но строку сохранит:
дата и сумма важнее.

## Правила, которые нельзя нарушать

1. **Отсутствие ключа `payment_schedule` и пустой массив `[]` означают РАЗНОЕ.**
   - Ключа в сообщении нет → сайт **не трогает** сохранённый график. Так следует поступать,
     когда меняются только позиции документа.
   - Ключ есть, значение `[]` → сайт **очищает** график полностью.

   Это самая частая ошибка при доработке. Если 1С опустит ключ, подразумевая «графика
   больше нет», старые плановые даты останутся висеть в календаре клиента.

2. **График присылается целиком, а не дельтой.** Массив полностью заменяет сохранённое.
   Досылать только изменившиеся строки нельзя: сайт не может отличить «строки не
   изменились» от «строк больше нет».

3. **`due_date` обязателен.** Строка без плановой даты для календаря бессмысленна и будет
   пропущена (остальные строки сохранятся).

4. **Сумма строк должна сходиться с суммой документа.** Расхождение сайт покажет
   сотруднику предупреждением, но исправлять не будет: арифметику документа ведёт 1С.

5. **График передаётся и в `shipment.created`, и в `shipment.updated`.** Изменили правила
   оплаты в проведённом документе — обязательно перепроведите его или отправьте
   `shipment.updated`, иначе сайт останется со старым графиком.

## Порядок работ

1. Изучи `shipment.created.json` и `shipment.updated.json` по ссылкам выше.
2. Найди в конфигурации место, где формируется payload реализации для отправки в
   RabbitMQ (обмен `erp.events`, очередь сайта `erp_in.documents`).
3. Добавь формирование массива `payment_schedule` из табличной части «Правила оплаты»
   документа *Реализация товаров и услуг*.
4. Сделай сопоставление кодов `basis` и `stage` (таблица выше) отдельной функцией
   общего модуля — она понадобится и для заказов, когда дойдёт до них очередь.
5. Проверь типы: `amount` и `percent` — **числа**, `due_date` — **строка** `ГГГГ-ММ-ДД`,
   `line_number` и `term_days` — **целые**. Числа в кавычках схему не пройдут.
6. Проведи один тестовый документ на **тестовый контур** и убедись, что сообщение
   не ушло в DLQ.
7. **Первичное заполнение.** По реализациям, проведённым до этой доработки, график на
   сайте отсутствует. После приёмки запусти разовую обработку, отправляющую
   `shipment.updated` по актуальным реализациям (разумная глубина — незакрытые и
   отгруженные за последние 3–6 месяцев). Без этого календари останутся почти пустыми.
   Отправляй пачками с паузой, а не одним залпом.

## Критерии приёмки

- [ ] Реализация с одной строкой «Правил оплаты» доезжает: в карточке реализации на сайте
      виден блок «График оплаты» с датой и суммой.
- [ ] Реализация с рассрочкой (несколько строк) отображается несколькими строками,
      с разными датами и суммами.
- [ ] Изменение правил оплаты в 1С и перепроведение документа обновляет график на сайте
      (старые строки не задваиваются).
- [ ] Очистка табличной части в 1С отправляет `"payment_schedule": []`, и график на сайте
      исчезает.
- [ ] Сообщение об изменении **только позиций** документа приходит **без ключа**
      `payment_schedule`, и сохранённый график остаётся нетронутым.
- [ ] Ни одно сообщение не попало в DLQ по ошибке валидации схемы.
- [ ] Проведена первичная выгрузка `shipment.updated` по историческим реализациям.

## Если что-то не сходится

- Сообщение ушло в DLQ → причина в очереди `erp_dlq.documents`, текст ошибки укажет
  конкретное поле и правило схемы.
- График не появился, а сообщение обработано → проверь, что ключ называется именно
  `payment_schedule` и что это массив, а не структура.
- Строка пропала → скорее всего пустой или неверный `due_date`.

По спорным местам сверяйся с https://pecado.ru/docs/erp-guide/rules/shipments/ —
раздел «График оплаты». Спецификация имеет приоритет над этим промтом.

## Вне этой задачи

График оплат **по заказам клиентов** (плановые предоплаты по ещё не отгруженному)
в этой версии не передаётся. Это отдельная задача — не добавляй `payment_schedule`
в сообщения заказов, сайт его там не ждёт.
