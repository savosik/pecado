# Промт для ИИ-агента 1С: печатные формы документов для личного кабинета (протокол v16.1.0)

> Скопируйте всё, что ниже разделителя, в ИИ-агента, который дорабатывает обмен на стороне
> 1С:КА2. Промт самодостаточен: в нём есть контракт, правила, порядок работ и критерии приёмки.

---

## Роль и задача

Ты — разработчик 1С:Комплексная автоматизация 2, дорабатывающий обмен данными с сайтом
`pecado.ru` через RabbitMQ.

**Задача:** начать выгружать на сайт **готовые печатные формы документов в PDF** — счета
на оплату, счета-фактуры, УПД, акты сверки, договоры. Сам файл кладётся в обменный бакет S3,
а по шине отправляется запись о документе двумя новыми сообщениями: `printed_document.published`
и `printed_document.deleted`.

Сайт уже принимает эти данные: доработка нужна только на стороне 1С.

**Зачем это бизнесу.** Сегодня клиент получает свои документы единственным способом: пишет
или звонит менеджеру, менеджер идёт в 1С, печатает форму, сохраняет в PDF и отправляет почтой.
Поток идёт через отдел продаж целиком и целиком вручную. Раздел «Документы» в личном кабинете
снимает его: клиент сам находит нужный счёт по типу, дате и своему юрлицу и скачивает.

## Что уже сделано на стороне сайта

Ничего согласовывать и настраивать не нужно — приём готов:

- заведена очередь `erp_in.printed_documents`, привязанная к обменнику `erp.events`
  по routing key `printed_document.*`, с очередью недоставленных `erp_dlq.printed_documents`;
- создан **обменный бакет** `documents-exchange` в MinIO, доступ на запись выдан 1С;
- заведена таблица документов, приватное хранилище файлов, раздел в кабинете клиента
  и витрина для менеджеров;
- работает перенос файла: сайт забирает PDF из обменного бакета и удаляет исходник.

## ⚠️ Идентификатор печатной формы — самое опасное место

**Прочитай этот раздел до всего остального и вернись к нему перед сдачей работы.**

В КА2 печатная форма не является объектом информационной базы: у неё нет ссылки, нет GUID,
она существует только в момент печати. А контракту нужен `uuid`, по которому сайт отличает
«та же форма, обновлённая» от «другая форма».

### Что требуется

Завести **регистр сведений «ПечатныеФормыДляСайта»**:

| Роль | Реквизит |
|---|---|
| Измерение | ДокументОснование (ДокументСсылка) |
| Измерение | ВидФормы (перечисление или строка-код) |
| Ресурс | UUID (УникальныйИдентификатор, генерируется **один раз** при первой записи) |
| Ресурс | Ревизия (число, +1 при каждом перевыставлении) |
| Ресурс | ИмяФайла, Хеш, ДатаВыгрузки |

Альтернатива, если регистр невозможен: вычислять `uuid` **детерминированно** из пары
(GUID документа-основания, код вида формы) — например, UUIDv5 с фиксированным namespace.
Требование то же: одинаковый вход всегда даёт одинаковый `uuid`.

### Почему это критично

`uuid` обязан быть **стабильным между перевыставлениями**. Если при повторной печати того же
счёта сгенерировать новый `uuid`, сайт посчитает это другим документом, и клиент увидит
**два счёта** вместо одного обновлённого. Разобраться, какой из них актуальный, он не сможет.

И главное: **валидацией схемы это не ловится.** Сообщение с новым `uuid` полностью корректно —
все поля на месте, типы верные, оно спокойно пройдёт и запишется. Ошибка проявится только
как жалоба клиента через недели, когда в разделе накопятся дубли. Проверить это можно
единственным способом: напечатать одну и ту же форму дважды и убедиться, что на сайте
по-прежнему один документ.

## Формат сообщения

**Обменник:** `erp.events` (topic, durable) — тот же, что для всех остальных сообщений.
**Routing key:** `printed_document.published` / `printed_document.deleted`
**Очередь-получатель:** `erp_in.printed_documents` (настроена на стороне сайта).

### `printed_document.published`

```json
{
  "event": "printed_document.published",
  "message_id": "msg-pdoc-b3f1c0a2-7d4e-4a11-9f2c-1e5a7b9d0c33",
  "timestamp": "2026-08-13T10:15:00+03:00",
  "revision": 3,

  "uuid": "3f2504e0-4f89-11d3-9a0c-0305e82c3301",
  "type_code": "tax_invoice",
  "type_name": "Счёт-фактура",

  "number": "29УТ-002488",
  "date": "2026-08-12",
  "title": "Счёт-фактура № 29УТ-002488 от 12.08.2026",

  "file_url": "s3://documents-exchange/2026/08/3f2504e0-4f89-11d3-9a0c-0305e82c3301.pdf",
  "file_name": "Счет-фактура_29УТ-002488.pdf",
  "file_size": 184320,
  "file_checksum": "9b74c9897bac770ffc029102a200c5de1c4f8e6a3f7b1e2d0c9a8b7f6e5d4c3b",
  "mime_type": "application/pdf",

  "partner_uuid": "a1b2c3d4-0000-4000-a000-000000000001",
  "contractor_uuid": "a1b2c3d4-0000-4000-a000-000000000002",
  "tax_id": "7701234567",
  "organization_uuid": "a1b2c3d4-0000-4000-a000-000000000003",

  "base_document_kind": "shipment",
  "order_uuid": null,
  "shipment_uuid": "a1b2c3d4-0000-4000-a000-000000000004",

  "erp_created_at": "2026-08-12T18:40:11+03:00",
  "erp_updated_at": "2026-08-13T10:14:52+03:00"

```

| Поле | Тип | Обяз. | Соответствие в КА2 |
|---|---|:--:|---|
| `event` | строка | ✅ | Всегда `printed_document.published` |
| `message_id` | строка | ✅ | Уникален на каждое сообщение. По нему сайт отбрасывает дубли |
| `uuid` | UUID | ✅ | Ресурс UUID регистра «ПечатныеФормыДляСайта» |
| `type_code` | строка | ✅ | Латинский код вида формы — таблица ниже |
| `file_url` | строка | ✅ | `s3://documents-exchange/<ключ>` |
| `date` | дата | ✅ | Дата документа-основания |
| `revision` | целое | ⬜* | Ресурс Ревизия регистра. *Обязателен бизнес-правилом |
| `type_name` | строка | ⬜ | Русское наименование вида формы |
| `number` | строка | ⬜ | Номер документа-основания |
| `title` | строка | ⬜ | Готовый заголовок. Не передан — сайт соберёт сам |
| `file_name` | строка | ⬜ | Человекочитаемое имя, основа имени при скачивании |
| `file_size` | целое | ⬜ | Размер в байтах |
| `file_checksum` | строка | ⬜ | SHA-256 в нижнем регистре, 64 hex-символа |
| `mime_type` | строка | ⬜ | Только `application/pdf` |
| `partner_uuid` | UUID | ⬜ | GUID элемента справочника «Партнёры» |
| `contractor_uuid` | UUID | ⬜* | GUID «Контрагенты». *Обязателен бизнес-правилом |
| `tax_id` | строка | ⬜ | ИНН контрагента |
| `organization_uuid` | UUID | ⬜ | GUID элемента справочника «Организации» |
| `base_document_kind` | `order`/`shipment`/null | ⬜ | Вид документа-основания |
| `order_uuid` | UUID/null | ⬜ | GUID «Заказ клиента» |
| `shipment_uuid` | UUID/null | ⬜ | GUID «Реализация товаров и услуг» |
| `erp_created_at` | datetime | ⬜ | Когда форма сформирована |
| `erp_updated_at` | datetime | ⬜ | Когда переформирована |

Формат дат и времени — как во всех остальных сообщениях, см.
[метки времени для 1С](erp-timestamps-for-1c.md).

### `printed_document.deleted`

```json
{
  "event": "printed_document.deleted",
  "message_id": "msg-pdoc-del-7c1e0a44",
  "timestamp": "2026-08-14T09:02:00+03:00",
  "revision": 4,
  "uuid": "3f2504e0-4f89-11d3-9a0c-0305e82c3301",
  "reason": "Документ помечен на удаление в 1С"
}
```

Обязательны `event`, `message_id`, `uuid`. `revision` присылать так же, как в публикации:
без неё обогнавшее удаление сотрёт уже применённую свежую версию формы.

## Что именно класть в S3

1. **Только PDF.** Не ZIP, не архив, не офисный формат, не комплект из нескольких файлов.
   Всё остальное сайт помечает как отклонённое и клиенту не показывает. Раздел обещает
   документ, который открывается в браузере одним кликом.
2. **Один файл = одна печатная форма.** Если по реализации нужны и УПД, и счёт-фактура —
   это два объекта, два `uuid` и два сообщения.
3. **Размер до 50 МБ.** Больше — отклоняется.
4. **Имя объекта:** `<ГГГГ>/<ММ>/<uuid>.pdf`, где год и месяц взяты из **даты документа**,
   а `uuid` — из регистра, строчными буквами, без фигурных скобок.
   Пример: `2026/08/3f2504e0-4f89-11d3-9a0c-0305e82c3301.pdf`.
   Никакой кириллицы, пробелов и номеров документов в ключе — человекочитаемое имя
   передаётся отдельным полем `file_name`.
5. **Файл выкладывается ДО отправки сообщения.** Сайт читает его сразу после получения.
   Если объекта нет, документ помечается «файл отсутствует», и повторного опроса не будет —
   придётся присылать сообщение заново.
6. **Из бакета ничего не удалять и не перезаписывать.** Сайт заберёт файл и удалит его сам.
   Перезапись того же ключа в промежутке между отправкой сообщения и приёмом даст клиенту
   не тот PDF, и обнаружить это будет невозможно.
7. **Бакет — для обмена, а не для хранения.** Срок жизни объектов 7 дней; всё, что сайт
   не успел забрать, удаляется. Долговременное хранение — на стороне сайта, в отдельном
   приватном хранилище, куда доступа у 1С нет.

## Коды видов печатных форм

| Код | Русское название | Печатная форма КА2 |
|---|---|---|
| `contract` | Договор | Договор с клиентом |
| `agreement` | Соглашение об условиях продаж | Соглашение с клиентом |
| `invoice` | Счёт на оплату | Счёт на оплату клиенту |
| `tax_invoice` | Счёт-фактура | Счёт-фактура выданный |
| `correction_invoice` | Корректировочный счёт-фактура | Корректировочный счёт-фактура выданный |
| `upd` | УПД | Универсальный передаточный документ |
| `ukd` | УКД | Универсальный корректировочный документ |
| `waybill` | Товарная накладная | ТОРГ-12 |
| `consignment_note` | Транспортная накладная | Транспортная накладная |
| `act` | Акт выполненных работ | Акт об оказании услуг |
| `reconciliation_act` | Акт сверки взаиморасчётов | Акт сверки взаиморасчётов |
| `specification` | Спецификация | Спецификация к договору |
| `price_list` | Прайс-лист | Прайс-лист |

**Формы нет в таблице.** Присылай свой `type_code` латиницей **и обязательно** `type_name`
по-русски. Сайт положит документ в раздел «Прочее», покажет клиенту твоё название и не
потеряет файл; по накопившимся кодам мы заведём новые виды.

**Чужой код придумывать нельзя.** Если отправить акт сверки под кодом `act`, он уедет
в «Акты выполненных работ» и потеряется среди них. Лучше `other` с точным названием,
чем похожий по смыслу чужой код.

## Когда слать

- При **сохранении формы в регистр** «ПечатныеФормыДляСайта», а не при каждом открытии
  печати менеджером. Открытие предпросмотра сообщением быть не должно.
- Только по документам, которые клиент **имеет право видеть**. Внутренние перемещения,
  документы себестоимости, служебные формы в кабинет не отправляются.
- Отдельным сообщением на каждую форму. Сообщение маленькое, батчить не нужно.
- Досылать неизменившиеся формы не нужно, но и не вредно: обработка идемпотентна
  по `message_id`, а совпавший хеш файла отменяет повторное копирование.

## Перевыставленный или исправленный документ

Три разных случая, и правила у них **разные**. Перепутать их — вторая по вероятности ошибка
внедрения после нестабильного `uuid`.

### 1. Переформировали ту же форму

Исправили реквизиты, реквизиты организации, ошибку в адресе — номер документа тот же.

→ Тот же `uuid`, `revision + 1`, новый файл по тому же ключу в бакете.
Сайт перезапишет запись и PDF. У клиента остаётся **один** документ, всегда актуальный.

### 2. Корректировочный или исправительный документ

Корректировочный счёт-фактура, УКД, исправление к отгруженной реализации.

→ Это **другой документ 1С**: **новый** `uuid`, свой `type_code` (`correction_invoice`,
`ukd`), ссылка на то же основание тем же `shipment_uuid`.
Старую форму оставить: у клиента должны быть обе, этого требует учёт.

**Не** присылать корректировку под `uuid` исходного счёта-фактуры — она затрёт оригинал,
и клиент лишится документа, который обязан хранить.

### 3. Документ отменён или помечен на удаление

→ `printed_document.deleted` с тем же `uuid`. Файл повторно не выкладывать.
Сайт убирает документ из кабинета, но файл на диске сохраняет: снятие пометки удаления
в 1С — обычная операция, а перезалить PDF потом неоткуда.

## Ревизия и порядок доставки

`revision` — номер версии печатной формы, монотонно растущий при каждом перевыставлении.
Начинается с 1 (или 0) и **никогда не уменьшается**.

Почему без неё нельзя: у сайта несколько параллельных потребителей, и RabbitMQ не гарантирует
порядок между сообщениями. Менеджер перепечатал счёт дважды подряд — два сообщения с разными
`message_id` и `erp_updated_at`, совпадающим до секунды. Если второе доставится раньше
первого, клиент получит **устаревший PDF**, а система об этом не узнает: оба сообщения
корректны.

Сайт сравнивает `revision` с уже применённой и отбрасывает не большую.
См. [Порядок сообщений](../rules/message-ordering.md).

---

## Идемпотентность

- **`message_id` уникален для каждого сообщения.** Не переиспользуй его при повторной
  отправке с изменённым содержимым: сайт посчитает такое сообщение дублем и молча отбросит.
- **`uuid` — ключ документа.** Повтор того же `uuid` обновляет существующую запись.

Эти два поля решают разные задачи и путать их нельзя: `message_id` защищает от повторной
доставки одного и того же сообщения, `uuid` связывает разные сообщения об одном документе.

---

## Привязка к сторонам

- **`contractor_uuid` — обязателен по бизнес-правилу.** Видимость документа в кабинете
  строится по контрагенту: без него документ не увидит ни один клиент.
  В `required` схемы он не вынесен намеренно — иначе такое сообщение ушло бы в DLQ,
  а печатную форму терять нельзя. Сайт документ примет, сохранит и покажет менеджеру
  в списке «без контрагента».
- `partner_uuid`, `organization_uuid`, `tax_id` — желательны.
- `order_uuid` / `shipment_uuid` — если форма относится к заказу или реализации.
  Договор и акт сверки основания не имеют: `base_document_kind: null`.

**Документ, приехавший раньше своих сторон, не теряется.** Если контрагента, заказа или
реализации на сайте ещё нет, UUID сохраняется, а связь доклеивается автоматически, когда
сущность приедет. Специально подгадывать порядок не нужно — но при первичной выгрузке он
экономит время, см. ниже.

---

## Порядок первичной выгрузки

1. **Согласовать глубину.** Предложение — с 01.01.2026. Нужна оценка: сколько форм и какой
   суммарный вес.
2. **Одна тестовая форма каждого вида** → сверка на dev-стенде. Проверяем тип, номер, дату,
   контрагента, организацию и то, что PDF открывается.
3. **Пачка на одном контрагенте** → проверка полноты и связей.
4. **История.** Печатные формы выгружаются **после** контрагентов, заказов и реализаций,
   иначе документы приедут без связей и будут ждать доклейки. Темп — **не быстрее 20–30
   сообщений в секунду** и **не более 5 000 файлов в бакете единовременно**: сайт забирает
   и удаляет асинхронно, обменный бакет не должен раздуться.
5. **Новые формы** — потоком, сразу после сохранения в регистр.

## Критерии приёмки

- [ ] Заведён регистр «ПечатныеФормыДляСайта» (или согласован детерминированный алгоритм `uuid`)
- [ ] Файл появляется в бакете **до** отправки сообщения
- [ ] Ключ объекта имеет вид `<ГГГГ>/<ММ>/<uuid>.pdf`, без кириллицы и пробелов
- [ ] Сообщение проходит валидацию по JSON Schema
- [ ] Документ виден в CRM сайта с правильным типом, номером, датой, контрагентом и организацией
- [ ] PDF скачивается и открывается
- [ ] **Повторная печать той же формы обновила документ, а не создала второй**
- [ ] Корректировочный счёт-фактура приехал отдельным документом, оригинал остался на месте
- [ ] `printed_document.deleted` убрал документ из кабинета

## Если что-то не сходится

Очередь недоставленных — `erp_dlq.printed_documents`. Туда попадают сообщения, не прошедшие
валидацию по схеме. Типовые причины:

| Симптом | Причина |
|---|---|
| Сообщение в DLQ | Не заполнено одно из обязательных полей (`uuid`, `type_code`, `file_url`, `date`) либо `event` написан иначе |
| Документ есть, файла нет («файл отсутствует») | Объекта по `file_url` в бакете не оказалось: сообщение ушло раньше загрузки, ключ не тот, либо файл уже кем-то удалён |
| Документ есть, файл отклонён | Не PDF или больше 50 МБ |
| Файл не найден, хотя он точно в бакете | В `file_url` указан **чужой бакет**. Сайт бакет из URL игнорирует и всегда читает свой обменный — путь внутри бакета должен быть верным |
| У клиента два одинаковых счёта | **Нестабильный `uuid`** — самая частая ошибка. Каждая печать генерирует новый идентификатор |
| Документ не виден клиенту, но виден менеджеру | Не передан `contractor_uuid`, либо контрагента с таким UUID на сайте ещё нет |
| Клиент видит старую версию | Не растёт `revision`, и сайт отбросил сообщение как обогнавшее |

## Вопросы, на которые нужен ответ

1. **Возможен ли регистр «ПечатныеФормыДляСайта» со стабильным `uuid`?** Если нет — какой
   детерминированный алгоритм вычисления вы предлагаете?
2. **Полный список видов печатных форм**, которые вы можете отдавать, с русскими названиями.
   Сверьте с таблицей кодов выше и допишите недостающее.
3. **Отдаёте ли SHA-256 файла?** Он позволяет пропускать повторное копирование неизменившихся
   форм — экономия на первичной выгрузке.

5. **Умеете ли ставить `revision`,** монотонно растущую при каждом перевыставлении?
6. **Как в КА2 выражен «исправительный» документ** — отдельный объект или реквизит
   существующего? От этого зависит, попадёт он в случай 2 или в случай 1.

   будет ли он обновляться (тот же `uuid`, растущая ревизия) или каждый раз это новый
   документ.
9. **С какой глубины истории** начинать выгрузку? Предложение — с 01.01.2026.
