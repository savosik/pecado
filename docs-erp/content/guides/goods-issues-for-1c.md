# Промт для ИИ-агента 1С: выгрузка расходных ордеров (протокол v15.15.0)

> Скопируйте всё, что ниже разделителя, в ИИ-агента, который дорабатывает обмен на стороне
> 1С:КА2. Промт самодостаточен: в нём есть контракт, правила, порядок работ и критерии приёмки.

---

## Роль и задача

Ты — разработчик 1С:Комплексная автоматизация 2, дорабатывающий обмен данными с сайтом
`pecado.ru` через RabbitMQ.

**Задача:** начать выгружать на сайт документ **«Расходный ордер на товары»** тремя новыми
сообщениями — `goods_issue.created`, `goods_issue.updated`, `goods_issue.deleted`.
Сайт уже принимает эти данные: доработка нужна только на стороне 1С.

**Зачем это бизнесу.** Сайт получает из 1С реализации, но реализация отражает **уже
свершившийся** факт отгрузки. Документ, по которому склад физически собирает, проверяет,
упаковывает и грузит товар, на сайте отсутствовал вовсе. Из-за этого кладовщики и начальник
склада вынуждены держать открытым толстый клиент 1С: в кабинете склада не видно ни что
сейчас в отборе, ни что зависло на этапе, ни сколько мест собрано, ни по каким заказам
идёт ордер.

## Что уже сделано на стороне сайта

Ничего менять и согласовывать не нужно — приём готов:

- заведена **новая очередь** `erp_in.warehouse` с routing key `goods_issue.*`
  и очередь недоставленных `erp_dlq.warehouse`;
- сайт хранит ордер целиком: шапку, товары по распоряжениям, упаковочные листы;
- сайт **сам ведёт журнал смены статусов** — вам достаточно присылать текущий статус;
- в кабинете склада `/wms/goods-issues` работает журнал с фильтрами, карточкой документа
  и выгрузкой в Excel.

## Формат сообщения

**Обменник:** `erp.events` (topic, durable) — тот же, что для всех остальных сообщений.
**Routing keys:** `goods_issue.created`, `goods_issue.updated`, `goods_issue.deleted`
**Очередь-получатель:** `erp_in.warehouse` (привязана на стороне сайта, настраивать не нужно).

### Поля шапки

| Поле | Тип | Обязательно | Соответствие в 1С |
|---|---|---|---|
| `event` | строка | да | `goods_issue.created` / `.updated` / `.deleted` |
| `message_id` | строка | да | Уникальный идентификатор сообщения. По нему сайт отбрасывает дубли |
| `uuid` | UUID | да | GUID документа «Расходный ордер на товары» |
| `number` | строка | да | Номер, например `УТ-00009419` |
| `date` | дата-время | да | Дата документа («от» в шапке) |
| `shipment_date` | дата-время | нет | Дата отгрузки |
| `status` | код | да | Статус — **только машинным кодом**, см. таблицу ниже |
| `operation` | строка | нет | Операция, например `Отгрузка клиенту` |
| `warehouse_uuid` | UUID | нет | Склад |
| `organization` | объект | нет | Организация, достаточно `uuid` |
| `contractor_uuid` | UUID | нет | Контрагент-получатель |
| `partner_uuid` | UUID | нет | Партнёр-владелец |
| `tax_id` | строка | нет | ИНН получателя |
| `recipient_name` | строка | нет* | Получатель строкой. *Формально необязателен, но присылать нужно всегда — см. правило 3 |
| `responsible` | строка | нет | Ответственный, например `Отгрузка 3 Москва` |
| `priority` | код | нет | `low` — Низкий, `normal` — Средний, `high` — Высокий |
| `comment` | строка | нет | Комментарий |
| `delivery_type` | код | нет | `pickup` — Самовывоз, `delivery` — Доставка |
| `delivery_address` | строка | нет | Адрес доставки |
| `delivery_order` | строка | нет | Порядок доставки |
| `erp_created_at` / `erp_updated_at` | дата-время | нет | Аудит-метки 1С |
| `items` | массив | да | Табличная часть «Товары по распоряжениям», минимум одна строка |
| `packages` | массив | нет | Упаковочные листы |

### Статусы — таблица соответствия

| Статус в 1С | Код для передачи |
|---|---|
| Подготовлен | `prepared` |
| К отбору | `to_pick` |
| К проверке | `to_check` |
| Проверен | `checked` |
| К отгрузке | `to_ship` |
| Отгружен | `shipped` |

**Передавать нужно именно код.** Русское название («Отгружен») сайт не принимает: сообщение
отбрасывается целиком и уходит в `erp_dlq.warehouse`.

### Строка `items[]`

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `line_number` | целое | нет | Номер строки табличной части |
| `product_uuid` | UUID | да | GUID номенклатуры — тот же, что в `price.updated` и `stock.updated` |
| `product_name` | строка | нет* | Наименование. *Присылать нужно — см. правило 4 |
| `order_uuid` | UUID | нет* | GUID заказа-распоряжения. *Без него ордер не связывается с заказом — см. правило 2 |
| `order_number` | строка | нет | Номер заказа, например `30УТ-000213` |
| `order_date` | дата-время | нет | Дата заказа |
| `quantity` | число ≥ 0 | да | Количество к отгрузке |
| `unit` | строка | нет | Единица измерения |
| `package_number` | целое | нет | Номер упаковочного листа для этой строки |

### Строка `packages[]`

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `number` | целое | да | Номер упаковочного листа |
| `positions_count` | целое | нет | Сколько позиций в составе листа |
| `weight` / `volume` | число | нет | Вес и объём места, если ведутся |

### Удаление

```json
{
  "event": "goods_issue.deleted",
  "message_id": "msg-gi-del-a1b2c3d4",
  "uuid": "7f3d9c10-4b21-4e8a-9c55-1a2b3c4d5e6f"
}
```

## Правила выгрузки

1. **Слать при каждом изменении.** `goods_issue.created` — при первом проведении,
   `goods_issue.updated` — **на каждую смену статуса** и при изменении состава или
   реквизитов, `goods_issue.deleted` — при отмене проведения или пометке на удаление.
   Без сообщений на смену статуса журнал склада показывает ордер в том состоянии,
   в котором он приехал впервые, и весь смысл раздела теряется.

2. **Заказ указывается в строке, а не в шапке.** Один расходный ордер может собираться
   сразу по нескольким заказам клиента, поэтому `order_uuid` живёт в `items[]` — та же
   модель, что у реализаций. Если не заполнить `order_uuid`, ордер попадёт на сайт,
   но не свяжется ни с одним заказом, и склад не увидит, что именно он комплектует.

3. **`recipient_name` заполнять всегда.** Получателем ордера бывает контрагент, которого
   в справочниках сайта нет вовсе (маркетплейс, внутреннее перемещение). Сайт не сможет
   подставить имя из своей базы — и ордер в журнале останется безымянным.

4. **`product_name` заполнять всегда.** Товара может не быть в каталоге сайта (снят
   с публикации, не выгружался). Без наименования строка нечитаема для кладовщика.

5. **Документ присылается целиком.** Сайт удаляет прежние строки и упаковочные листы
   и создаёт их заново. Досылать только изменившиеся строки нельзя — они продублируются.

6. **`packages`: отсутствие ключа и пустой массив означают разное.** Ключа нет — сайт
   не трогает сохранённые упаковочные листы (используйте, когда меняется только статус);
   `[]` — очищает их полностью. Та же ловушка, что с графиком оплат в v15.12.0.

7. **`message_id` должен быть уникальным для каждого сообщения.** Если переиспользовать
   один и тот же идентификатор, сайт посчитает второе сообщение дублем и не применит его.
   Особенно важно при смене статуса: `uuid` документа тот же, а `message_id` обязан
   отличаться.

8. **Цены, суммы, серии и штрихкоды маркировки присылать не нужно.** Ордер — складской
   документ; денежные данные сайт берёт из реализации. Лишние поля сообщение не ломают
   (сайт их игнорирует), но и смысла в них нет.

9. **Первоначальная выгрузка.** Разово выгрузить **незакрытые** ордера (все, кроме давно
   отгруженных) — иначе журнал склада будет пустым до первого нового проведения. Глубину
   истории согласуйте со складом; по отгруженным ордерам за прошлые периоды практической
   ценности мало. Порядок и приоритеты — см. [Первоначальная выгрузка](../initial-load.md).

## Критерии приёмки

- [ ] В 1С реализована выгрузка `goods_issue.created` при первом проведении ордера
- [ ] Реализована выгрузка `goods_issue.updated` на **каждую** смену статуса
- [ ] Реализована выгрузка `goods_issue.deleted` при отмене проведения
- [ ] Статус передаётся машинным кодом из таблицы соответствия
- [ ] `product_uuid` совпадает с GUID номенклатуры, который уже используется
      в `price.updated` и `stock.updated`
- [ ] `items[].order_uuid` заполнен для всех строк, у которых есть распоряжение
- [ ] `recipient_name` и `product_name` заполнены всегда
- [ ] `message_id` уникален для каждого сообщения
- [ ] Выполнена первоначальная выгрузка незакрытых ордеров
- [ ] В кабинете склада сайта ордер виден со своим статусом, позициями и упаковочными листами
- [ ] Очередь недоставленных `erp_dlq.warehouse` пуста после прогона
