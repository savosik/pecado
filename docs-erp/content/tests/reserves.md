# Тест-план: Заказы в резерве (v16.9.0; совместная отгрузка — v16.11.0; рабочие дни — v16.12.1)

Критерии приёмки режима резерва. Обязательные интеграционные прогоны перед включением
(раскатка за флагами обеих сторон, см. правила: [Заказы в резерве](../rules/order-reserves.md)).

## Р-1. Создание резерва

- [ ] `order.created` с `reserve: true`, `reserved_until` (в пределах предела 1С) → в 1С
  документ со строками «Резервировать на складе», статус «К выполнению»; ответный
  `order.updated` несёт `reserve: true`, тот же `reserved_until`, `items_version`.
- [ ] `reserved_until` дальше предела 1С → удержание до предела, в ответе
  **фактический** (урезанный) `reserved_until`.
- [ ] `reserve: true` по партнёру-неучастнику (`reserve_allowed: false`) → обычный
  заказ, ответ с `reserve: false`.
- [ ] `reserved_until` в прошлом → обычный заказ (`reserve: false`).
- [ ] `reserve: true` без `reserved_until` → сообщение не проходит валидацию схемы
  на сайте, в шину не публикуется.
- [ ] Остаток: после постановки в резерв `stock.updated` уменьшает публикуемый
  остаток на зарезервированное количество.

## Р-2. Правка состава

- [ ] `order.updated` (сайт → 1С) с уменьшением количества и актуальным
  `base_items_version` → состав в 1С заменён, ответный `order.updated` с новым
  `items_version`.
- [ ] Удаление строки → строка исчезает из документа, резерв по ней освобождён.
- [ ] Отставший `base_items_version` (менеджер успел изменить состав в 1С) → правка
  НЕ применена, ответ с актуальным составом, `items_version` и
  `conflict.rejected_message_id` = message_id отклонённого сообщения.
- [ ] Повторная доставка того же `order.updated` (тот же `message_id`) → состояние
  не меняется повторно.

## Р-3. Отмена

- [ ] `order.deleted` с `reason: client_cancelled` → строки отменены, статус «Закрыт»,
  пометки удаления НЕТ, резерв освобождён, остаток вернулся в `stock.updated`.
- [ ] `order.deleted` с `reason: reserve_expired` — то же, причина отмены строк
  различима в 1С.
- [ ] Повтор `order.deleted` по отменённому заказу → успех без изменений.

## Р-4. Подтверждение

- [ ] `order.confirmed` → строки «Отгрузить», статус «К отгрузке», заказ уходит в
  обычный конвейер (при включённом авто-оформлении — расходный ордер).
- [ ] Повтор `order.confirmed` по подтверждённому заказу → успех без изменений.
- [ ] `order.confirmed` по заказу, уже отменённому по таймауту (гонка) → заказ
  остаётся отменённым, сайт получает актуальное состояние ответным сообщением.

## Р-5. Гейты и аварийные пути

- [ ] Авто-оформление отгрузки НЕ подхватывает резервный заказ до `order.confirmed`
  (контрагент с включённым авто-оформлением).
- [ ] Ручной перевод резервного заказа менеджером в 1С → сайт получает
  `order.updated` с `reserve: false`, убирает заказ из раздела резервов, клиентские
  правки закрыты.
- [ ] Страховочный регламент 1С: заказ с `reserved_until` + 6 ч в прошлом и без
  отмены от сайта → резерв снят регламентом, сайт получает `order.deleted` или
  `order.updated` с `reserve: false`.

## Р-6. Охват

- [ ] `partner.updated` с `reserve_allowed: true` → сайт открывает выбор резерва
  в чекауте партнёру; с `false` — закрывает (висящие резервы доживают штатно).
- [ ] Поимённая сверка: список uuid от сайта → 1С размечает реквизит → сайт получил
  `partner.updated` по каждому размеченному партнёру.

## Р-7. Совместная отгрузка (v16.11.0)

Правила: [Совместная отгрузка резервов](../rules/order-reserves.md#совместная-отгрузка-резервов-v16110).
Прогон совместный — сайт шлёт реальные `order.confirmed`, 1С отвечает реальными `order.updated`.

- [ ] Группа из 2–3 резервов одного контрагента, один склад → по каждому заказу
  `order.confirmed` с одинаковыми `ship_together_key` и `ship_together_order_uuids`;
  1С по полному составу подтверждает все заказы, приходит `order.updated` по каждому с
  `reserve: false`, «К отгрузке», `ship_together_status: confirmed`; далее одна реализация
  и один расходный ордер, заказы — в строках (`items[].order_uuid`).
- [ ] Полная группа обрабатывается сразу, без ожидания 15 минут.
- [ ] Один `order.confirmed` группы не доставлен (имитация) → через 15 минут от первого
  сохранённого сообщения все заказы получают `conflict.reason: timeout`, `reserve: true`
  без изменений, документов нет; сайт вернул заказы в резерв и показал причину.
- [ ] Сообщения группы с разными манифестами (один ключ) → `manifest_mismatch`; опорный —
  первый валидный манифест, итог по его заказам и по конфликтующему.
- [ ] Один заказ группы уже подтверждён/отменён в 1С до сбора группы → `not_reserved` с
  `order_uuid` виновного, остальные заказы остаются в резерве.
- [ ] Разные соглашения/организации у заказов группы → `incompatible`; флаг запрета
  объединения у партнёра → `merge_forbidden`.
- [ ] Недобор по одному заказу на предконтроле → `shortage`, ни один заказ не потерял
  резерв, `goods_issue.*` / `shipment.*` не публикуются.
- [ ] Товар разных владельцев в группе → группа успешна, реализаций две, ордер один;
  сайт показывает фактические документы.
- [ ] Повторная доставка `order.confirmed` группы (те же `message_id`) после итога →
  повторных документов нет, итог не меняется.
- [ ] Поздний `order.confirmed` с ключом закрытой группы → тот же итог, группа не
  открывается заново.
- [ ] Повтор после отказа с новым ключом и новыми `message_id` → штатная новая группа.
- [ ] Сайт до публикации отклоняет группу: разные склады, разные контрагенты, разные
  способы доставки, заказ не в резерве — в шину ничего не уходит.
- [ ] Пока группа собирается, правка состава и отмена заказов группы на сайте закрыты.
- [ ] Старый `order.confirmed` без полей группы → прежнее поведение по одному заказу.

## Р-8. Срок в рабочих днях клиента (v16.12.1)

Расчёт сайта (интеграционные тесты сайта, окно 24 ч, если не указано иное):

- [ ] чт 01.10.2026 17:00 → пт 02.10 17:00 (24 ч).
- [ ] пт 02.10.2026 17:00 → пн 05.10 17:00 (72 ч).
- [ ] сб 03.10.2026 10:00 → пн 05.10 10:00 (48 ч); вс 04.10 22:00 → пн 05.10 22:00 (24 ч).
- [ ] пт 31.10.2025 17:00 при рабочей субботе 01.11.2025 → сб 01.11 17:00 (24 ч);
  сб 01.11.2025 17:00 → ср 05.11 17:00 (96 ч, 03–04.11 нерабочие).
- [ ] вт 03.11.2026 17:00 → чт 05.11 17:00 (48 ч); чт 30.04.2026 17:00 → пн 04.05 17:00 (96 ч).
- [ ] Окно 120 ч: чт 01.10.2026 17:00 → чт 08.10 17:00 (168 ч).
- [ ] Окно 168 ч: пт 02.10.2026 17:00 → расчёт вт 13.10 (264 ч) → срез по потолку на
  **пн 12.10 17:00** (240 ч).
- [ ] Новый год: вт 29.12.2026 17:00 → ср 30.12 17:00; ср 30.12.2026 17:00 и
  пн 04.01.2027 12:00 → резерв не предлагается (чекаут и клиентский API отклоняют выбор
  резерва с причиной, обычный заказ доступен); вс 10.01.2027 20:00 → пн 11.01 20:00.
- [ ] В каждом `order.created` с `reserve: true`: `reserved_until − date <= 240 ч`.

Совместная проверка на боевом контуре (тестовый партнёр, предел 1С = 240):

- [ ] Резерв, созданный в пятницу 17:00, → ответный `order.updated` с фактическим
  `reserved_until` = понедельник 17:00 (1С не урезала).
- [ ] В субботу и воскресенье резерв не снят ни сайтом (`reserve:release-expired`), ни
  страховкой 1С.
- [ ] В понедельник до 17:00 `order.confirmed` проходит штатно.
- [ ] Резерв пятницы и резерв понедельника отправляются в отгрузку одной группой
  (совместная отгрузка), без `incompatible` по дате отгрузки.
