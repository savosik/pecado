# Заказы в резерве (v16.9.0; ключ строки — v16.9.1; авторитетность reserve — v16.9.2; совместная отгрузка — v16.11.0)

Режим самообслуживания для клиентов-интернет-магазинов: заказ сразу создаётся в 1С
с удержанием товара, а окно между «зарезервировал» и «подтвердил» клиент обслуживает
сам — правит состав, отменяет или отправляет в отгрузку из кабинета сайта или через
клиентский API, без звонка менеджеру.

Протокол согласован в топике №5 Agent Hub (resolution 03.09.2026).

## Как резерв выражен в 1С

Отдельного статуса «Резерв» в перечислении статусов заказа **нет и не будет** —
резерв живёт на строке документа:

| Что | Значение |
|---|---|
| Реквизит строки `ВариантОбеспечения` | `СоСклада` («Резервировать на складе») |
| Статус документа | `КОбеспечению` («К выполнению / В резерве») |
| Регистр удержания | `ТоварыКОтгрузке`, ресурс `ВРезерве` |
| Публикуемый остаток | уже за вычетом резерва (`ЗапасыИПотребности`) |

Следствия:

- постановка в резерв **сама** снимает товар с витрины через обычный `stock.updated`;
- на сайт резервный заказ приезжает со `status: ready_for_shipment` — режим
  различается **только** по полю `reserve` в `order.created` / `order.updated`;
- расходный ордер не оформляется (ресурс `КОтгрузке` у резервной строки нулевой),
  поэтому заказ не уходит в сборку.

## Обеспечение по флагу `reserve` на `order.created` (v16.9.2)

Согласовано в топике №6 Agent Hub (09.09.2026). Поле `reserve` на `order.created` —
**авторитетный признак обеспечения**, а не подсказка. Сайт присылает явный Boolean
во **всех** новых `order.created` (не только по участникам режима).

| `reserve` | Статус документа в 1С | Вариант обеспечения строк | Резерв |
|---|---|---|---|
| `true` (режим вкл ∧ участник ∧ срок валиден) | `КОбеспечению` | `СоСклада` + `Доп_ЗаказВРезерве` | да, срок из `reserved_until` |
| `false` | `КОтгрузке` | `Отгрузить` | нет |
| поле отсутствует / `null` | `КОтгрузке` (fallback как `false`) | `Отгрузить` | нет |

- **Резерв по умолчанию НЕ ставится.** Только валидный `reserve: true` переводит
  заказ в обеспечение; при `false` и отсутствии поля обычный заказ идёт сразу под
  отгрузку.
- Право на резерв всё равно гейтит 1С: режим включён ∧ партнёр помечен участником
  (`reserve_allowed`) ∧ срок валиден. По неучастнику `reserve: true` игнорируется и
  в ответном `order.updated` возвращается `reserve: false` (см. правило 3).
- Совместимость: `absent = false` сохраняет поведение старых отправителей и
  неучастников — они и раньше не подразумевали резерв.
- Предзаказы и аварийные типы (`defect` / `promo` / `promo_sample`) сохраняют своё
  текущее поведение независимо от `reserve`.

> **История дефекта (до v16.9.2):** сайт слал `reserve` только при `true`, а 1С
> трактовала отсутствие/`false` как «резервировать по умолчанию» — заказу до проверки
> флага уже проставлялся `КОбеспечению`/`СоСклада`. Клиент, выбравший «к отгрузке»,
> фактически получал резерв. Исправлено с двух сторон: сайт шлёт явный `reserve`,
> 1С делает флаг авторитетным (default-path готовит `КОтгрузке`, резерв — только по
> валидному `true`).

## Жизненный цикл

```
оформление (reserve: true) ──► резерв в 1С (окно ожидания)
    │ клиент правит состав          │ order.updated (сайт → 1С)
    │ клиент отменяет               │ order.deleted, reason=client_cancelled
    │ срок истёк                    │ order.deleted, reason=reserve_expired
    └ клиент подтверждает ──────────► order.confirmed → «К отгрузке», обычный конвейер
```

## Правила

1. **Охват** — только партнёры-участники: флаг `reserve_allowed` в
   `partner.created` / `partner.updated`, **мастер — 1С** (отдельный реквизит
   партнёра). Сайт показывает выбор резерва в чекауте только участникам и может
   точечно сузить охват, но не расширить.
2. **Срок удержания** — `reserved_until` присылает сайт (обязателен при
   `reserve: true`, повторяется в каждом сообщении). У 1С — верхний предел удержания
   (настройка, стартово **24 часа** от создания заказа): срок сверх предела урезается,
   в исходящих 1С `reserved_until` — всегда **фактический** срок, не эхо. Сайт
   показывает клиенту фактический срок.
3. **Рассинхрон флагов**: `reserve: true` по неучастнику — обычный заказ, признак
   игнорируется, в ответном `order.updated` возвращается `reserve: false`;
   `reserved_until` в прошлом — трактуется как `reserve: false`.
4. **Неподтверждённый резерв в сборку не идёт** — ни автоматически (авто-оформление
   отгрузки в 1С гейтится по признаку резерва), ни руками. Ручной перевод менеджером —
   аварийный путь: 1С шлёт `order.updated` с `reserve: false`, сайт убирает заказ из
   раздела резервов и закрывает клиентские правки.
5. **Правка состава** (`order.updated` сайт → 1С) — только в окне резерва, состав
   целиком, в v1 **только уменьшение** (снизить количество, удалить строку).
   1С применяет к проведённому документу (распровести → заменить → провести), пока
   нет расходного ордера и реализации.
6. **Ключ строки — пара `items_version` + `line_number`** (уточнено в v16.9.1).
   `line_number` стабилен только в пределах версии состава: при физическом удалении
   строки платформа 1С перенумеровывает последующие. Поэтому состав всегда идёт и
   применяется целиком (snapshot), сопоставление строк — внутри одного сообщения,
   а **любое** изменение состава (включая перенумерацию) увеличивает `items_version`.
   Сайт со своей стороны требует версию состава от клиента (кабинет и клиентский API)
   и отклоняет правку с устаревшей версией **до** отправки в шину — проверка 1С
   остаётся вторым рубежом.
7. **Конфликты** — оптимистичная блокировка по версии состава: сайт шлёт
   `base_items_version` (последний применённый `items_version` из сообщений 1С);
   при расхождении правка не применяется, 1С отвечает `order.updated` с актуальным
   составом, `items_version` и `conflict {rejected_message_id, reason}`.
   ⚠️ `revision` для блокировки не годится — это счётчик отправленных сообщений,
   он растёт и без изменения состава (перепроведение, эхо с номером, дренаж очереди).
8. **Отмена** (`order.deleted` сайт → 1С) — строки помечаются отменёнными с причиной,
   статус «Закрыт», резерв освобождается. **Пометка удаления не ставится.**
9. **Таймаут** — основной таймер у сайта: по истечении `reserved_until` сайт шлёт
   `order.deleted` с `reason: reserve_expired`. Страховочный регламент 1С снимает
   резерв при `reserved_until` + **6 часов** грации — последний рубеж на случай
   потери сообщения, в норме не срабатывает.
10. **Идемпотентность** — повторная доставка любого сообщения (по `message_id` /
   `uuid`) не меняет состояние повторно; повтор `order.confirmed` по подтверждённому
   заказу — успех без изменений.
11. **Раскатка** — за флагами обеих сторон, включение по отдельному решению
    владельцев. Перед включением — поимённая сверка списков участников: сайт передаёт
    свои uuid партнёров-интернетчиков, 1С размечает `reserve_allowed` и возвращает
    фактический состав через `partner.updated`.

## Совместная отгрузка резервов (v16.11.0)

Согласовано в топике №7 Agent Hub (resolution 18.09.2026). Интернет-магазины держат
по нескольку резервов и отправляют их в отгрузку сразу, одним курьером; клиент хочет
**одну реализацию**, склад — **один расходный ордер**. Слить заказы средствами сайта
нельзя (правка резерва только на уменьшение, «новый заказ + отмена резервов» даёт гонку
за остаток), поэтому **объединяется отгрузка, а не заказы**: заказы остаются отдельными
документами, 1С оформляет по группе минимальный комплект реализаций и расходных ордеров.

### Контракт

| Событие | Поля | Смысл |
|---|---|---|
| `order.confirmed` (Сайт → 1С) | `ship_together_key`, `ship_together_order_uuids` | ключ группы и манифест — все заказы группы |
| `order.updated` (1С → Сайт) | `ship_together_key`, `ship_together_status`, `ship_together_conflict` | терминальный итог группы |

Поля необязательны и **аддитивны**: без них `order.confirmed` работает по-прежнему,
по одному заказу. Пара полей в `order.confirmed` присутствует только вместе.
`ship_together_size` и срок ожидания в контракт **не входят** (счётчик не позволяет
понять, какой заказ потерян; абсолютный срок истекал бы при отставании потребителя).

### Правила

1. **Манифест** — UUID всех заказов группы: уникальные, минимум 2, одинаковый состав
   и порядок во всех сообщениях группы, `uuid` текущего заказа входит в массив.
   Все `order.confirmed` группы сайт публикует в одной транзакции.
2. **Проверки сайта до публикации** (то, что сайт знает о заказе): один партнёр, один
   контрагент, одна валюта, **ровно один склад** (расходный ордер живёт на одном складе),
   один способ доставки, один адрес доставки (при самовывозе — все самовывоз), все заказы —
   действующие резервы, ранее не подтверждённые и не отменённые. Не прошло — группа
   не отправляется, клиенту предлагается разбить её.
3. **Предконтроль 1С** (то, чего сайт не знает): заказ действительно в резерве в 1С,
   организация, соглашение, договор, флаги запрета объединения у партнёра и соглашения,
   получатель, дата отгрузки, складская операция, транспортное назначение, доступность
   остатков. Проверяется под одной групповой блокировкой по полному составу.
4. **Состояния группы в 1С** — `collecting → confirmed | conflict`. До полного состава
   1С ничего не меняет и наружу не шлёт. **Тайм-аут — 15 минут с момента, когда 1С впервые
   сохранила валидное сообщение группы**; задержка доставки до 1С на срок не влияет.
   Полная группа обрабатывается сразу, ждать 15 минут не нужно.
5. **Успех** — 1С подтверждает все заказы группы и передаёт их **одним групповым вызовом**
   в движки реализации и ордеров (поштучный автоордер для группы подавлен). Успех = создан
   и проведён **минимальный** комплект документов по всем заказам. Несколько реализаций
   (разные владельцы товара, налоговый режим) или несколько ордеров (складские ключи) —
   **не конфликт**; фактические документы сайт получает обычными `shipment.created` /
   `goods_issue.created` (заказ — в строке, `items[].order_uuid`).
6. **Отказ — по всей группе.** Резервы и статусы всех заказов остаются без изменений,
   частичного оформления нет. Ошибка или частичный результат ордерного движка откатывает
   изменения всей группы; наружу частичные `goods_issue.*` / `shipment.*` не публикуются.
7. **Итог** приходит в `order.updated`: на успех — по каждому заказу группы `reserve: false`,
   статус «К отгрузке», `ship_together_status: confirmed`; на отказ — по каждому разрешимому
   заказу опорного (первого валидного) манифеста и по текущему конфликтующему заказу: прежний
   `reserve: true`, `ship_together_status: conflict`, обязательный `ship_together_conflict
   {reason, message, order_uuid}`. `order_uuid` заполняется только при одном однозначном
   виновном заказе. Коды `reason`: `timeout`, `manifest_mismatch`, `not_reserved`,
   `incompatible`, `merge_forbidden`, `shortage`, `processing_error`.
8. **Окончательность и идемпотентность** — на один `ship_together_key` 1С публикует один
   терминальный итог; поздние сообщения с тем же ключом группу не открывают и получают тот
   же итог; повторная доставка входящих не создаёт повторных документов. Повтор после
   отказа — **новый ключ и новые `message_id`**. При `manifest_mismatch` опорным считается
   первый валидный манифест.
9. **Поведение сайта** — после отправки группы сайт **не снимает резерв локально**,
   показывает клиенту «отправлено, ждём подтверждения склада» и закрывает правки и отмену
   заказов группы до итога. Итог применяется по `order.updated` (`reserve` авторитетен).
   После отказа клиент видит причину, заказы снова в резерве, можно повторить группу или
   отправить заказы по одному прежним способом.
10. **Включение** — за флагами обеих сторон, по отдельному решению владельцев после
    совместных испытаний на dev с реальными сообщениями обеих сторон.

## События протокола

| Событие | Направление | Назначение |
|---|---|---|
| `order.created` + `reserve`/`reserved_until` | Сайт → 1С | создать заказ в резерве |
| `order.updated` + `base_items_version` | Сайт → 1С | правка состава клиентом |
| `order.deleted` + `reason` | Сайт → 1С | отмена клиентом / снятие по таймауту |
| `order.confirmed` | Сайт → 1С | отправить резерв в отгрузку |
| `order.confirmed` + `ship_together_key`, `ship_together_order_uuids` | Сайт → 1С | совместная отгрузка группы резервов (v16.11.0) |
| `order.created`/`order.updated` + `reserve`, `reserved_until`, `items_version`, `conflict` | 1С → Сайт | состояние резерва, фактический срок, версия состава, отказ правки |
| `order.updated` + `ship_together_key`, `ship_together_status`, `ship_together_conflict` | 1С → Сайт | итог группы совместной отгрузки (v16.11.0) |
| `partner.created`/`partner.updated` + `reserve_allowed` | 1С → Сайт | признак участника режима |

Payload-схемы: [AsyncAPI](/docs/erp/spec.yaml), JSON Schemas `order.updated.to_erp`,
`order.deleted.to_erp`, `order.confirmed.to_erp` в [/docs/erp/schemas/](/docs/erp/schemas/).
