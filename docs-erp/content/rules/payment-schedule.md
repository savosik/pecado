# График оплаты

> **JSON Schema:** [`payment_schedule.updated.json`](/docs/erp/schemas/payment_schedule.updated.json)  
> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.settlements` | **Версия:** v16.7.0

Плановые платежи документа вместе с закрытой частью. Из этого строятся два экрана: календарь
оплат клиента в кабинете и план поступления денег в CRM.

## Что изменилось в v16.0.0

График переехал из массива `payment_schedule` внутри `shipment.created`/`shipment.updated`
в собственное событие. Причина не в структуре, а в одном поле.

**Раньше 1С присылала только план.** Факт сайт сопоставлял с планом сам, методом FIFO
по плановой дате. Это не работало: 1С разносит на заказы почти половину денег, гасит долг
авансами и зачётами, и самодельная раскладка ошибалась в разы — **у одного клиента 5,53 млн ₽
просрочки против 478 тыс ₽ по данным учёта**.

**Теперь остаток приходит из 1С.** Источник — регистр `РасчетыСКлиентамиПоСрокам`, ресурсы
`Долг` и `Предоплата`. Сайт больше **не раскладывает платежи**: ни FIFO, ни как-либо ещё.

## События

| Событие | Описание |
|---|---|
| `payment_schedule.updated` | Актуальный график документа. Полная замена |

Отдельного события удаления нет: пустой массив `lines` очищает график, а
[`settlement.reverted`](settlements.md) удаляет график вместе с движениями документа.

## ⚠️ Реализации и заказы устроены по-разному

Это главная асимметрия раздела, и она вынужденная.

| | Реализация | Заказ | Первичный документ |
|---|---|---|---|
| `document_kind` | `shipment` | `order` | `initial` (v16.7.0) |
| Источник плана | Регистр по срокам | Табличная часть `ЭтапыГрафикаОплаты` | Регистр по срокам |
| `settled_amount` в строке | **есть** | **нет** | **есть** |
| `document_settled_amount` в шапке | не требуется | **единственный источник факта** | не требуется |
| Считается просрочкой | да | **никогда** | да |

**Почему по заказам нет построчного остатка.** Замер 1С: в регистре `РасчетыСКлиентамиПоСрокам`
**ноль строк с объектом расчётов «заказ клиента»** — ни в движениях, ни в остатках. Регистр
отвечает на вопрос «сколько осталось закрыть» по отгруженному, а не «сколько клиент должен
внести вперёд». Предоплату там двигает служебный «Регистратор расчётов», и строка появляется
в момент зачёта аванса, а не в момент возникновения обязательства.

План предоплат при этом существует: `ЭтапыГрафикаОплаты` заказа даёт 5 917 строк
на 85 915 586,15 ₽ за 2026 год и сходится с ресурсом `КОплате` заказов (85 737 178,94 ₽)
с точностью до сотых долей процента.

А факт оплаты по заказу берётся из ресурса `Оплачивается` — но **только по заказу целиком**,
без разложения по этапам.

## Правило разнесения оплаты заказа

Записано в контракт дословно, потому что здесь легко скатиться обратно к прежней болезни:

> Оплаченная сумма заказа берётся из `document_settled_amount` и **никогда не вычисляется**.
> Разнесение этой суммы по этапам графика выполняется только для отображения календаря,
> помечается производной величиной и **не участвует ни в балансе, ни в сверке**.

Почему это не возврат к FIFO. Прежний механизм раскладывал платежи **между документами**:
аванс по заказу гасил строки графика чужих реализаций, ошибка накапливалась и давала
расхождение в разы. Здесь авторитетное число делится **внутри одного заказа**, обычно
по одному-двум этапам. Итог по заказу верен по построению; неточной может быть только
дата внутри заказа, и на баланс это не влияет вовсе.

Вариант с поэтапным остатком по заказам рассматривался и отклонён: в 1С его нет, а заводить
ради уточнения даты внутри документа новую учётную логику не окупается.

## Бизнес-правила

- **(v16.0.0) График присылается целиком, а не дельтой.** Массив `lines` полностью вытесняет
  сохранённое. Пустой массив очищает график.
- **(v16.0.0) Ключ строки — `uuid`, а не номер строки.** Для реализаций он собирается из пары
  «расчётный документ + дата планового погашения»: именно она является ключом в регистре
  по срокам. `line_number` приезжает справочно, логика на нём не строится.
- **(v16.0.0) `due_date` обязательна, и строка без неё отбраковывает сообщение целиком.**
  График — единое целое. Сохранив его частично, сайт показал бы календарь, не сходящийся
  с суммой документа, и просрочку, посчитанную по неполному плану, — причём молча.
  Дата к тому же входит в ключ строки, так что строки без неё в 1С не существует.
- **(v16.0.0) Суммы в строках положительные.** Это «сколько клиент должен заплатить»; знак
  для реестра движений сайт разворачивает сам. Этим строки графика отличаются от `entries`
  в [`settlement.posted`](settlements.md), где знак содержательный.
- **(v16.0.0) `settled_amount` больше `amount` — легитимно.** Это переплата по строке.
  Остаток на сайте клампится в ноль и отрицательным не бывает.
- **(v16.0.0) Статус строки не хранится.** «Ожидается / частично / оплачена» и признак
  просрочки — функции от `settled_amount` и текущей даты, а не самостоятельные поля.
- **(v16.0.0) Сумма строк должна сходиться с суммой документа.** Расхождение сайт показывает
  сотруднику предупреждением, но не исправляет: арифметику документа ведёт 1С.
- **(v16.7.0) График заказа — план платежа, а не долг.** Долг создаёт отгрузка. Строки
  `document_kind: order` сайт **не считает просрочкой ни на одной поверхности** — ни в CRM,
  ни в кабинете клиента; они остаются в плане поступлений и календаре как ожидаемые платежи.
  Причина — круг 12: заказ с этапом «оплата после отгрузки» оставался «просроченным» навсегда
  (у клиента с авансом висел фантомный долг 1,14 млн ₽), потому что регистр по срокам
  заказы не ведёт и погашение по ним физически не публикуется.
- **(v16.7.0) Исполненный план снимается.** При полной отгрузке или закрытии заказа 1С
  публикует ревизию графика заказа с пустым `lines: []`. Критерий полноты — нулевой остаток
  регистра `ТоварыКОтгрузке` при наличии проведённой реализации, а **не статус заказа**:
  статус ставится руками и отстаёт. Частичная отгрузка график не трогает — план ещё
  актуален на невыполненную часть.
- **(v16.7.0) `initial` — «Первичный документ» переноса остатков.** Реальная дебиторка
  внешних клиентов, заведённая при переносе остатков между базами. Ведёт себя как
  реализация: построчный `settled_amount` из регистра по срокам, участвует в просрочке.
  Шлётся **только по внешним контрагентам** — расчёты между своими юрлицами
  (~6 млн ₽ на момент круга 12) в обмен не входят.

## Что строится из графика

| Экран | Что показывает |
|---|---|
| Календарь оплат в кабинете | Когда и сколько клиент должен перечислить |
| План поступлений в CRM | Ожидаемые деньги по дням, план против факта |
| Просрочка | Непогашенные строки с датой раньше сегодняшней |
| Кому звонить | Просрочка, сгруппированная по клиентам менеджера |

## Критерии приёмки

- [ ] График реализации приходит с заполненным `settled_amount`, значение меняется по мере оплаты
- [ ] График заказа приходит без `settled_amount`, но с `document_settled_amount` в шапке
- [ ] Повторная доставка не задваивает строки
- [ ] Пустой `lines` очищает график документа
- [ ] Строка без `due_date` отбраковывает сообщение целиком, частичный график не сохраняется
- [ ] `settled_amount` больше `amount` не ломает расчёт остатка
- [ ] Оплата заказа не раскладывается по этапам ни в балансе, ни в сверке
- [ ] Расхождение суммы строк с суммой документа показывается предупреждением
- [ ] Просроченная строка заказа не попадает в просрочку ни в CRM, ни в кабинете, но видна в плане
- [ ] После полной отгрузки заказа приходит ревизия с пустым `lines`, строки исчезают из плана
- [ ] График `initial` принимается, участвует в просрочке и подписывается «Первичный документ»
