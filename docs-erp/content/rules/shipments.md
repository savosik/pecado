# Реализации

> **JSON Schema:** [`shipment.created.json`](/docs/erp/schemas/shipment.created.json) | [`shipment.updated.json`](/docs/erp/schemas/shipment.updated.json) | [`shipment.deleted.json`](/docs/erp/schemas/shipment.deleted.json)  
> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.documents`

## События

| Событие | Описание |
|---|---|
| `shipment.created` | При первом проведении реализации |
| `shipment.updated` | При перепроведении (структура идентична `created`, отличается `event`) |
| `shipment.deleted` | При отмене проведения |

## Бизнес-правила

- Одна реализация может включать позиции из **нескольких заказов**
- Связь с заказами через `order_uuid` в каждой позиции
- Расчёт задолженности ведётся по реализациям, не по заказам
- Привязка к контрагенту:
    - **(v13.2)** Приоритет — по `contractor_uuid` (опциональное поле, `Company.erp_id` на сайте). Глобально уникальный идентификатор, не ломается при правке ИНН в 1С
    - **Fallback** — по `tax_id` (ИНН) **в паре с `partner_uuid`**. `partner_uuid` нужен для резолва `user_id` и фильтра Company по владельцу. Без `partner_uuid` fallback-поиск не выполняется (security-fix v13.2)
- **(v12.3)** Если передан `number` — сайт сохраняет его как `erp_number`. Это номер реализации из 1С, который отображается пользователю
- **(v15.8.0)** 1С присылает **организацию и склад** реализации: `organization` (достаточно `uuid`) и `warehouse_uuid`. Оба поля опциональны. Реализация — самое заметное для клиента место: именно по накладной он сверяет, какое юрлицо ему продало. Организация реализации может **отличаться** от организации её заказа — это легитимно, 1С могла переоформить документ. Подробности — [Организации](organizations.md)
- **(v12.10)** У `shipment.updated` **собственная JSON Schema** (`shipment.updated.json`), отделённая от `shipment.created.json`. Пока структуры payload-ов идентичны; разделение выполнено на вырост — для независимой эволюции `updated` при появлении у него собственных полей
- **(v12.11) `number` обязательно для `shipment.created` и `shipment.updated`.** 1С обязана передавать номер реализации непустой строкой. Сообщения без `number` отклоняются валидатором и отправляются в DLQ. Причина: без ERP-номера покупатель в ЛК видит только технический `id` сайта, а менеджер в 1С — ERP-номер; это ломает коммуникацию клиент-менеджер при обсуждении отгрузки
- **(v13.7)** Опциональные аудит-метки `erp_created_at` / `erp_updated_at` (ISO-8601 datetime с TZ) — момент создания/изменения документа на стороне 1С. Сохраняются в `shipments.erp_created_at` / `shipments.erp_updated_at` и отображаются в админке. **Не путать** с бизнес-полем `date` — это дата проведения реализации (день отгрузки), а аудит-метки фиксируют момент действия в учётной системе. При `shipment.updated` достаточно передавать только `erp_updated_at`. Подробнее: [«Аудит-метки 1С: erp_created_at / erp_updated_at»](../guides/erp-timestamps-for-1c.md)
- **(v15.5) Списание уценки.** Если реализация относится к заказу уценки (`type: "defect"`), сайт списывает соответствующую партию некондиции: количество партии уменьшается на отгруженное, при достижении нуля партия закрывается (перестаёт продаваться). Списание **идемпотентно по `uuid` реализации** — повторная доставка того же документа не списывает партию дважды. Структура payload не меняется: связь заказ↔партия сайт держит у себя, 1С передаёт обычную реализацию с `order_uuid` заказа уценки
- **(v15.9.2) Отмена реализации возвращает партию уценки в продажу.** Сайт распознаёт **три** способа отмены и по любому из них пересчитывает партию: `shipment.deleted` (снятие проведения), `shipment.updated` со `status: "cancelled"` (документ остаётся, отгрузки по нему нет) и `order.deleted` по самому заказу уценки. Пересчёт работает и когда заказ уценки уже помечен удалённым — типичный случай, когда в 1С отменяют разом и заказ, и реализацию. Партия, **списанная кладовщиком вручную** (утилизация, пересорт), автоматикой не открывается никогда

## График оплаты (v15.12.0)

Табличная часть **«Правила оплаты»** реализации приезжает массивом `payment_schedule`
внутри `shipment.created` / `shipment.updated`. Отдельного события и отдельной очереди нет:
график — часть документа, и присылать его отдельно значило бы создать гонку
«график приехал раньше реализации».

Из формы 1С сайт берёт только значимое для календаря оплат. **Не передаются и не нужны:**
«Расчёты», «Форма оплаты», «Касса», «Банковский счёт» и УИП (УИП уже приходит в платеже),
а «Сумма к оплате» — это сумма самого документа, она у сайта уже есть.

| Поле | Соответствие в 1С | Обязательность |
|---|---|---|
| `due_date` | Дата платежа | **да** |
| `amount` | Сумма платежа | **да** |
| `percent` | % платежа | нет |
| `line_number` | N | нет |
| `term_days` | Срок (дни) | нет |
| `basis` / `basis_name` | Вариант отсчёта | нет |
| `stage` / `stage_name` | Контроль | нет |
| `order_uuid` | Заказ | нет |

### Бизнес-правила

- **(v15.12.0) Отсутствие ключа `payment_schedule` и пустой массив означают разное.** Ключа нет — сайт **не трогает** сохранённый график (используйте, когда меняются только позиции документа). Пустой массив `[]` — сайт **очищает** график полностью. Различие критично: если 1С опустит ключ, подразумевая «графика больше нет», старые плановые даты останутся в календаре клиента
- **(v15.12.0) График присылается целиком**, а не досылается изменившимися строками: сайт не умеет отличить «строки не изменились» от «строк больше нет». Замена выполняется delete-and-recreate, как у позиций документа
- **(v15.12.0) Строка без `due_date` пропускается.** Плановая дата — единственное, ради чего график забирается: без неё строка не попадает ни в календарь, ни в расчёт ближайшего платежа. Факт пропуска записывается в лог
- **(v15.12.0) Пары «код + наименование» разведены намеренно.** Логика сайта (что считать предоплатой, от чего считать просрочку) опирается **только** на латинские `basis` и `stage`; `basis_name` и `stage_name` показываются сотруднику и клиенту как есть. Причина та же, что у `operation_code` в платежах: русское наименование в 1С меняется вместе с настройками учёта
- **(v15.12.0) Строки графика гасятся фактическими платежами по FIFO.** 1С разносит платёж по **реализациям**, а не по строкам графика, поэтому связку «какая строка оплачена» строит сайт: оплаченная сумма реализации (`shipments.paid_amount`, см. [Платежи](payments.md)) распределяется по строкам в порядке `due_date`, затем `line_number`. Первая непокрытая строка становится ближайшей датой платежа реализации
- **(v15.12.0) Пересчёт идемпотентен.** Раскладка — полная функция от суммы оплаты и состава графика, а не инкремент: повторная доставка того же сообщения даёт тот же результат. Пересчёт запускается и при изменении графика, и при изменении оплаты (`payment.*`)
- **(v15.12.0) Статус строки не хранится.** «Ожидается / частично / оплачена» и признак просрочки вычисляются на лету из погашенной суммы и текущей даты — хранимый статус пришлось бы обновлять ночным заданием, и он врал бы до следующего запуска
- **(v15.12.0) Сумма строк должна сходиться с суммой реализации.** Расхождение сайт показывает сотруднику, но не исправляет: арифметику документа ведёт 1С
- **(v15.12.0) График — план, а не факт просрочки.** Не путать с `overdue_details` в [Балансах](balances.md): там 1С сообщает уже случившуюся просроченную задолженность, здесь — плановые даты. Календари строятся по графику, баланс остаётся независимой сверкой
- **(v15.12.0)** График по **заказам** (предоплата по неотгруженному) в этой версии не передаётся — только по реализациям

> **Разработчику 1С:** пошаговое задание с форматом, кодами и критериями приёмки —
> [«График оплат: что сделать в 1С»](../guides/payment-schedule-for-1c.md).

### Первичное заполнение

По документам, проведённым до v15.12.0, график приедет при **следующем перепроведении**
реализации в 1С. Чтобы календарь заполнился сразу, 1С делает повторную выгрузку
`shipment.updated` по актуальным реализациям. До неё календарь пуст — это ожидаемо,
ошибкой не является.

## Критерии приёмки

- [ ] Сайт принимает `shipment.created`, `shipment.updated`, `shipment.deleted`
- [ ] **(v13.2)** Company находится сначала по `contractor_uuid`, затем fallback по `tax_id + user_id` (резолв через `partner_uuid`). Поиск без `partner_uuid` / `user_id` не выполняется — иначе можно найти чужую Company с тем же ИНН
- [ ] Позиции связаны с заказами через `order_uuid`
- [ ] Реализация отображается в ЛК
- [ ] **(v12.10)** Валидация `shipment.updated` использует схему `shipment.updated.json` (поле `event` = `shipment.updated`)
- [ ] **(v12.11)** `shipment.created` / `shipment.updated` без поля `number` или с пустой строкой отклоняются на стадии валидации и не создают/не обновляют реализацию
- [ ] **(v15.5)** Реализация по заказу уценки списывает партию некондиции; повторная доставка того же `uuid` не списывает повторно; при нулевом остатке партия закрывается
- [ ] **(v15.9.2)** Партия уценки возвращается в продажу после `shipment.deleted`, после `shipment.updated` со `status: "cancelled"` и после `order.deleted` по заказу уценки — в том числе когда заказ удалён раньше реализации; партия со статусом «Списана» при этом не открывается
- [x] **(v15.12.0)** Массив `payment_schedule` сохраняется в график оплаты реализации; повторная доставка того же `uuid` не задваивает строки
- [x] **(v15.12.0)** Сообщение **без ключа** `payment_schedule` оставляет сохранённый график нетронутым; с пустым массивом — очищает
- [x] **(v15.12.0)** Строка без `due_date` пропускается, остальные строки сохраняются
- [x] **(v15.12.0)** Оплата реализации гасит строки графика по FIFO: частичная закрывает первые строки и делит очередную, полная закрывает все и обнуляет ближайшую дату платежа
- [x] **(v15.12.0)** Возврат (`direction: "out"`) уменьшает оплату и снова открывает погашенные строки
- [x] **(v15.12.0)** Клиент видит календарь оплат в личном кабинете, менеджер — календарь поступления денег в CRM с планом и фактом по дням
