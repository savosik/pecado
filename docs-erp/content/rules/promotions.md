## Модель данных на сайте

| Сущность | Таблица | Назначение |
|---|---|---|
| `ErpPromotion` | `erp_promotions` | UUID промо-группы + тип (`new`/`bestseller`/`liquidation`) |
| Привязка товаров | `erp_promotion_product` | Связь промо ↔ товар (many-to-many) |
| Флаг на товаре | `products.is_new` / `is_bestseller` / `is_liquidation` | Агрегированный признак для витрины и фильтров |

**Агрегация:** флаг товара устанавливается в `true`, если товар состоит хотя бы в одной `ErpPromotion` соответствующего `type`. В `false` — если ни в одной.

Таким образом, один товар может находиться в нескольких промо одного типа одновременно (например, «Летние новинки» и «Новинки бренда X»). Удаление одного из промо не снимает флаг, пока остаётся хотя бы одно активное.

---

## Тип промо-флага

В поле `type` допустимы только три значения (латиница):

| Значение | Русское соответствие | Колонка товара |
|---|---|---|
| `new` | Новинка | `products.is_new` |
| `bestseller` | Бестселлер | `products.is_bestseller` |
| `liquidation` | Ликвидация | `products.is_liquidation` |

Другие значения приводят к отклонению сообщения на этапе JSON Schema-валидации (`ErpMessageValidator`).

## promotion.created — создание промо-группы

### Бизнес-правила

- `uuid` промо-группы — идемпотентный ключ. Повторная отправка с тем же `uuid` ведёт себя как `promotion.updated` (upsert).
- `items[]` — **полный** состав товаров на момент создания. Товары, не найденные по `external_id`, игнорируются (с записью в лог), валидация сообщения не падает.
- Флаги на товарах пересчитываются в рамках одной транзакции после изменения привязок.

### Критерии приёмки

- [ ] При получении `promotion.created` с `type=new` у всех товаров из `items[]` (найденных по UUID) `products.is_new = 1`.
- [ ] Повторная отправка того же `uuid` с новым составом заменяет привязки и пересчитывает флаги у добавленных и удалённых товаров.
- [ ] Повторная отправка с тем же `uuid` и `message_id` в пределах одного цикла обработки — **no-op** (идемпотентность по `message_id`).
- [ ] Товары, не найденные по `external_id`, в лог попадают, но сообщение обрабатывается успешно.

## promotion.updated — обновление состава и/или type

### Бизнес-правила

- `items[]` — **полный снимок** актуального состава. Сайт выполняет полную замену привязок (`BelongsToMany::sync`).
- Если промо-группа с таким `uuid` не найдена — создаётся (**upsert**).
- При смене `type` (например, `new` → `bestseller`) флаги пересчитываются для **обоих типов** — предыдущего и нового.

### Критерии приёмки

- [ ] Товары, которых больше нет в `items[]`, **освобождаются** от привязки; если они не состоят в других промо того же `type` — соответствующий флаг снимается.
- [ ] Товары, добавленные в `items[]`, получают соответствующий флаг (если ещё не имели).
- [ ] При смене `type` у всех товаров (и добавленных, и удалённых, и оставшихся) флаги обоих типов корректно пересчитываются.
- [ ] Отсутствие промо-группы по `uuid` не приводит к ошибке — сайт создаёт группу.

---

## promotion.deleted — удаление промо-группы

### Бизнес-правила

- Удаляются запись `ErpPromotion` и все её привязки в `erp_promotion_product`.
- У каждого освободившегося товара флаг **снимается только если** он больше не состоит ни в одной другой `ErpPromotion` того же `type`.
- Если промо-группы с таким `uuid` не существует — событие логируется как информационное и обработка завершается успешно.

### Критерии приёмки

- [ ] После `promotion.deleted` запись из `erp_promotions` удалена, связанные строки `erp_promotion_product` — тоже.
- [ ] У товаров, состоящих **только** в удалённой группе — соответствующий флаг снят.
- [ ] У товаров, состоящих также в других промо того же `type` — флаг **остаётся**.
- [ ] Удаление несуществующей промо-группы не считается ошибкой.

## Ошибки и диагностика

| Сценарий | Поведение |
|---|---|
| Отсутствует `uuid` или `type` | Сообщение отклоняется JSON Schema, запись в `erp_validation_errors` |
| `type` не из enum | Аналогично: отклонение схемой |
| Товары из `items[]` не найдены | Логируется количество `missing`, обработка успешна |
| Ошибка БД внутри транзакции | Транзакция откатывается, сообщение уходит в retry (backoff=15 с) |

Идемпотентность гарантируется таблицей `erp_processed_messages` по `message_id`.
