# Порядок доставки и свежесть данных

> **Версия протокола:** v15.16.0
> **Затронутые каналы:** заказы, реализации, платежи, возвраты

## Проблема

Порядок доставки сообщений **не гарантирован**:

- между очередями — у каждой свой connection и свой набор воркеров;
- внутри одной очереди — там, где воркеров больше одного (`numprocs > 1`;
  например, у цен их 12).

До v15.16.0 у сайта не было способа отличить свежее сообщение от устаревшего.

**Дедупликация по `message_id` эту задачу не решает.** Она защищает ровно от
одного сценария — повторной доставки **того же** сообщения брокером. Два разных
сообщения по одному документу имеют разные `message_id`, и оба будут применены
в том порядке, в каком доехали.

!!! note "Почему `message_id` требуется контрактом, но не проверяется рантаймом"
    В спецификации поле стоит в `required` — присылать его обязательно.
    Рантайм-валидатор (JSON Schema) его **намеренно не требует**, и это
    осознанное расхождение, а не недосмотр:

    - обработчики идемпотентны по `uuid` документа — повторная доставка
      переприменяет данные, а не задваивает их. `message_id` здесь вторая линия
      защиты, а не первая;
    - сделать поле обязательным в рантайме означало бы, что сообщение без него
      уходит в очередь недоставленных. Обмен встал бы там, где данные приехали
      бы корректно.

    Практический вывод для 1С: присылайте `message_id` всегда — без него сайт
    лишний раз перезапишет документ. Но забытое поле обмен не сломает.

**`erp_updated_at` тоже не решает.** Вот две отправки подряд по заказу
29УТ-012045 из журнала исходящих 1С:

```
[4609584] событие 15:41:28  →  1 строка: 5 шт, не отменено       (УСТАРЕВШИЕ данные)
[4609585] событие 15:41:28  →  2 строки: 2 активно + 3 отменено  (актуальные)
```

Метка совпадает до секунды. Применись они в обратном порядке — сайт записал бы
устаревшее состояние и никак этого не заметил.

---

## Решение: `revision`

Документные сообщения получают поле `revision` — номер ревизии документа в 1С.

```json
{
  "event": "order.updated",
  "uuid": "…",
  "revision": 7,
  "…": "…"
}
```

### Требования к значению

| Требование | Пояснение |
|---|---|
| Целое, ≥ 0 | Тип `integer`, отрицательные значения не принимаются |
| Монотонно возрастает **в рамках одного `uuid`** | Каждое изменение документа увеличивает номер |
| Глобальная монотонность **не нужна** | Номера разных документов между собой не сравниваются |
| Постоянство не требуется | Достаточно, чтобы каждое следующее сообщение по документу имело номер больше предыдущего |

### Поведение сайта

1. На документе хранится `applied_revision` — ревизия последнего применённого
   сообщения.
2. Сообщение с `revision` **меньше или равным** `applied_revision` отбрасывается
   как устаревшее. Обработчик не вызывается, данные не меняются.
3. Отброшенное сообщение попадает в журнал шины (**Админка → Шина ERP → Сообщения**)
   со статусом **«Устаревшее»** и пояснением, какая ревизия пришла и какая уже
   применена. Молча ничего не теряется.
4. Сообщение **без** `revision` применяется как раньше, без проверки.

Пункт 4 существенен: он позволяет 1С включать поле по одному каналу за раз,
а не одномоментно по всем.

### Что считается «применённым»

`applied_revision` записывается **после успешной обработки** сообщения. Если
обработчик упал и сообщение вернулось в очередь, ревизия не сдвигается —
повторная попытка пройдёт проверку.

---

## Где поле поддерживается

| Канал | События |
|---|---|
| Заказы | `order.created`, `order.updated`, `order.deleted` |
| Реализации | `shipment.created`, `shipment.updated`, `shipment.deleted` |
| Платежи | `payment.created`, `payment.updated`, `payment.deleted` |
| Возвраты | `return.updated`, `return.deleted` |

Справочники (товары, цены, остатки, контрагенты, партнёры) поле не используют:
там нет документа с жизненным циклом, а последнее пришедшее значение и есть
правильное.

**Расходные ордера (`goods_issue.*`) исключены намеренно:** у документа в 1С
отключена история данных, и брать номер ревизии неоткуда. Это тот же корень,
по которому у них не заполняются `erp_created_at` / `erp_updated_at`.

---

## Что это значит для 1С

- **Дубли сообщений перестают быть опасными.** Если по одному изменению уходит
  3–5 сообщений, лишние будут отброшены по ревизии, а не применены поверх.
  Чинить дубли всё равно стоит — они грузят шину, — но данные они уже не портят.
- **Номер обязан расти.** Если 1С пришлёт документ с той же ревизией, но другими
  данными, сайт сообщение отбросит: с его точки зрения это повтор.
- **Если ревизии у документа нет — не присылайте поле вовсе.** Отсутствие лучше
  нуля: нуль означает «ревизия 0», и следующее сообщение с нулём будет отброшено.

---

## Критерии приёмки

- [ ] Два сообщения по одному документу, применённые в обратном порядке, оставляют
      на сайте состояние из **более свежего**
- [ ] Сообщение с равной ревизией отбрасывается
- [ ] Сообщение без `revision` применяется
- [ ] Отброшенное сообщение видно в админке со статусом «Устаревшее»
- [ ] Упавшая обработка не сдвигает `applied_revision`
