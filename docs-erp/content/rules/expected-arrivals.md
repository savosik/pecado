# Ожидаемые поступления

> **JSON Schema:** [`product.expected_arrivals.updated.json`](/docs/erp/schemas/product.expected_arrivals.updated.json)  
> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.expected_arrivals` | **Routing key:** `product.expected_arrivals.*`

!!! warning "v16.16.0 — проект, согласуется (топик №16 Agent Hub)"
    Схема опубликована и уже зарегистрирована в валидаторе сайта, но **приём не включён**:
    очередь не объявлена, обработчика нет. Сайт включит приём вторым этапом, после
    замечаний 1С к этому проекту. Пока очереди нет, брокер сообщения с этим ключом
    никуда не доставляет — это безопасно: первая же полная выгрузка после включения
    привезёт всё, что закупки успели внести.

## Зачем

Менеджер должен видеть, когда ожидается товар, которого сейчас нет: дату и количество
к поступлению по складу. Закупки вносят ожидаемые даты в 1С (отчёт «Ожидаемые
поступления»), с 01.10.2026. До v16.16.0 в контракте такого поля не было.

## Кто видит

**В этом круге — только менеджеры (CRM).** Клиентам на витрине, в карточке товара,
в корзине, в личном кабинете и в клиентском API ожидания **не показываются** (решение
заказчика). В шину при этом идут полные данные — даты и количества, — чтобы позже открыть
их клиентам без доработок 1С.

## Единица данных — полный снимок по товару

- Одно сообщение — **один товар** (`product_uuid`) и **все** его ожидания по складам сайта
  (`warehouses[]`). Это не дельта: сообщение целиком заменяет всё, что сайт знал об
  ожиданиях товара.
- Склад, которого нет в новом снимке, у товара **очищается**.
- **Пустой `warehouses` = «ожиданий нет»**: сайт удаляет все ожидания товара. Это
  нормальное сообщение, а не ошибка.
- Склад перечисляется не больше одного раза. Склад без ожиданий не перечисляется —
  `arrivals` у перечисленного склада всегда непустой (иначе сообщение не пройдёт схему).
- Строки с одинаковыми `date` и `source` в одном складе 1С сворачивает в одну. Если всё же
  придут две — сайт их **сложит**, а не перезапишет одну другой.

### Когда 1С шлёт

1. **При каждом изменении** ожиданий товара — полный снимок по этому товару.
2. **Раз в сутки — контрольная полная выгрузка** тем же событием по всем товарам, у которых
   есть ожидания или были вчера. Она убирает даты, ушедшие в прошлое, и чинит всё, что
   могло потеряться (сообщение до включения приёма, товар, пришедший на сайт позже).

    !!! tip "Как очистить товар, у которого ожидания пропали"
        Ожидания пропадают, когда поступление оприходовано или отменено. 1С шлёт по такому
        товару снимок с пустым `warehouses` — один раз, при изменении. Если он потерялся,
        суточная выгрузка должна повторить пустой снимок; иначе у сайта останутся старые
        строки. Поэтому в контрольную выгрузку входят и товары, у которых ожидания были
        в предыдущей выгрузке.

## Поля строки ожидания

| Поле | Смысл |
|---|---|
| `date` | Ожидаемая дата поступления, `yyyy-MM-dd`. Сегодня или будущее |
| `date: null` | Поступление ожидается, **дата уточняется** — закупки её ещё не внесли |
| `quantity` | Количество к поступлению в **базовой единице** товара, строго `> 0` |
| `source` | `purchase` — поступление от поставщика; `import` — импортный заказ (зарезервирован, сейчас 1С таких строк не шлёт) |

- **Даты в прошлом 1С не шлёт.** Если такая всё же придёт, сайт её сохранит, но не покажет:
  «сегодня» сайт считает по московскому времени. Суточная выгрузка такие строки уберёт.
- **Строки без даты** — `date: null`. Менеджер видит их как «дата уточняется».
- **Горизонт не ограничен**: 1С шлёт всё будущее. Если понадобится отсечка, её делает сайт.
- **Заказы поставщику без настоящей даты** (дата = дата заказа) 1С **не шлёт**, пока закупки
  не внесут дату. Перемещения и возвраты — не источник ожиданий до отдельного решения.
- Поставщики и документы-источники наружу не передаются.

## Защита от перестановки — `calculated_at`

Снимки по одному товару могут прийти не в том порядке, в каком собраны (повтор доставки,
суточная выгрузка параллельно с изменением). Поэтому каждое сообщение несёт момент сборки
снимка `calculated_at` — ISO-8601 **с обязательным смещением** (для 1С — `+03:00`):

- снимок с `calculated_at` **раньше** сохранённого по товару — отбрасывается как устаревший;
- **равный или более поздний** — применяется (повтор того же снимка безвреден);
- время без смещения не проходит схему: иначе сайт сравнивал бы моменты в разных поясах.

Защита работает по товару целиком, а не по складу: снимок всегда полный.

## Неизвестные товар и склад

- **Склад, не заведённый на сайте, пропускается молча** — как в [`stock.updated`](stocks.md).
  Остальные склады снимка применяются. Склады сайта на 01.10.2026: «Москва Основной»,
  «Москва Персональный», «Тюмень Основной».
- **Товар, которого нет на сайте**, пропускается без ошибки и без очереди недоставленных.
  Следующая суточная выгрузка привезёт его ожидания, когда карточка появится.

## Отличие от остатков

Ожидания — **отдельное событие**, а не поле в `stock.updated`:

- у остатков другой ритм — около 30 тыс. сообщений в сутки, пересчёт на каждый заказ;
- другая семантика — `stock.updated` несёт **свободный** остаток сейчас, а ожидание — товар,
  которого ещё нет физически. Свободный остаток ожидания не увеличивают, к заказу они не
  доступны.

## Критерии приёмки

- [ ] Схема `product.expected_arrivals.updated` валидирует снимок, очистку пустым
      `warehouses`, `date: null`; отклоняет `calculated_at` без смещения, `quantity ≤ 0`,
      неизвестный `source`, склад с пустым `arrivals`
- [ ] Снимок целиком заменяет прежние ожидания товара; склад вне снимка очищается
- [ ] Пустой `warehouses` удаляет все ожидания товара
- [ ] Снимок с более ранним `calculated_at` отброшен, данные не изменились
- [ ] Неизвестный склад пропущен, остальные склады снимка применены
- [ ] Неизвестный товар пропущен без ошибки и без DLQ
- [ ] Дата в прошлом сохранена, но менеджеру не показана
- [ ] Менеджер в CRM видит дату (или «дата уточняется») и количество по складу
- [ ] Клиент ожиданий не видит нигде: витрина, карточка, корзина, кабинет, клиентский API
