> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)

## Базовые цены (price.updated)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.prices`

### Бизнес-правила

- Выгрузка цен использует вид цен из `ОсновнойВидЦен` настроек
- Если товара с UUID на сайте ещё нет, цена **откладывается** и применяется в момент
  `product.created` этого товара (v16.12.3). Из нескольких отложенных цен действует
  последняя принятая. Раньше такое событие игнорировалось, и цена терялась навсегда
- `product.created` и `product.updated` базовую цену **не меняют** — её меняет только `price.updated`
- Сайт **не** отправляет обновления цен в 1С
- **Базовая цена карточки на сайте живёт только из `price.updated`.** `product.created` заводит товар с нулевой базовой ценой и никогда её не меняет. Пока по товару не пришёл ни один `price.updated`, базовая цена на сайте — 0, даже если в 1С цена назначена. Продаваться товар при этом может: клиентская цена приезжает отдельным каналом (см. [Индивидуальные цены](individual-prices.md)). Последствие для заказов — см. [Заказы → order.created](orders.md): сайт подставляет `base_price = final_price`, чтобы строка документа не встала нулём

#### ⚠️ Цена присылается агрегатом, без разреза по организациям

**Требование контракта** (зафиксировано в v15.8.0, подтверждено стороной 1С).

Сообщение `price.updated` содержит одну — лучшую — цену товара. Раздельные цены
по нашим организациям на один товар **не передаются**: сайт хранит одну цену на товар
и перезаписывает её каждым сообщением, поэтому второе значение молча затёрло бы первое.

Разрез по организациям существует только в документах и взаиморасчётах, см.
[Организации](organizations.md). То же требование для остатков — см.
[Остатки](stocks.md).

#### Цена пришла раньше карточки (v16.12.3)

`price.updated` и `product.created` идут разными очередями (`erp_in.prices`,
`erp_in.catalog`) с параллельными воркерами, поэтому порядок их обработки
[не гарантирован](message-ordering.md). 1С публикует цену нового товара одновременно
с его карточкой: сообщения приходят в одну секунду, и цена нередко обрабатывается
первой. До v16.12.3 сайт такую цену выбрасывал, и карточка оставалась с нулевой
базой до следующего изменения цены в 1С (топик №12, товары 955067-L и 955077-S,
сентябрь 2026).

Теперь сайт сохраняет цену по неизвестному UUID в `erp_pending_prices`. Применяет
её та из двух сторон, которая завершилась второй: `product.created` после создания
карточки или сам `price.updated`, если карточка появилась, пока цена сохранялась.
Со стороны 1С **ничего менять не нужно**: порядок отправки, состав и формат
сообщений прежние.

#### Дата вступления цены в силу (v16.13.0)

Коммерческий отдел проводит установку цен **будущей датой**: акции, плановые переоценки,
смена прайса с первого числа. До v16.13.0 сайт применял любое `price.updated` в момент
получения и показывал новую цену раньше срока. 27.09.2026 документ датой 28.09 00:00 ушёл
на витрину за сутки (топик №15 Agent Hub, пример — 9015108: 3 845 → 2 295). Заказ уходит
в 1С с ценой витрины, и регистр цен 1С при приёме не читается, поэтому все заказы до даты
действия пришли бы по новой цене.

**Поля `price.updated`:**

| Поле | Смысл |
|---|---|
| `effective_from` | Момент, с которого цена действует: дата документа установки цен = период записи в регистре цен. ISO-8601 **с обязательным смещением** (`2026-09-28T00:00:00+03:00`); без смещения сообщение отклоняется. |
| `document_uuid` | GUID документа установки цен. Вместе с `product_uuid` — ключ отложенной цены. |
| `document_number` | Номер документа — только для разбора, логика на нём не строится. |

`effective_from` и `document_uuid` передаются **вместе**: одно без другого отклоняется
валидацией. Сообщение без обоих — прежний формат.

**Правила приёма на сайте:**

- `effective_from` не позже текущего момента сайта — цена применяется сразу, как раньше;
- `effective_from` в будущем — цена сохраняется **отложенной**. До этого момента витрина,
  корзина, поиск, выгрузки и расчёт заказа работают по действующей цене;
- планировщик сайта раз в минуту включает отложенные цены с наступившей датой, по
  возрастанию `effective_from`. Задержка после `effective_from` — не больше минуты.
  Включение — та же запись базовой цены, что и обычный `price.updated`: поисковый индекс
  и данные выгрузок обновляются вместе с ней, готовые файлы фидов — следующим прогревом;
- ключ отложенной цены — пара `product_uuid` + `document_uuid`. Новое сообщение с той же
  парой заменяет запись целиком, в том числе дату (документ перепровели другим числом);
  если новая дата уже наступила — цена применяется сразу, а отложенная запись снимается;
- у товара может лежать несколько отложенных цен разных документов;
- цены с прошедшей датой между собой **не сравниваются**: последняя принятая побеждает,
  как и раньше. На этом держится откат: после отмены вступившего документа 1С шлёт
  действующую цену с датой более раннего документа, и она должна лечь;
- сообщение без `effective_from` применяется сразу (прежний формат, переходный период);
- будущая цена по товару, которого на сайте ещё нет, не теряется: включается в свой срок,
  а если карточка появилась позже срока — при её создании (как в v16.12.3).

**Отмена — `price.cancelled`.** Документ будущей датой распровели, удалили или перепровели
без части строк до наступления даты. 1С отправляет `document_uuid` и список `product_uuids`;
сайт удаляет отложенные цены этого документа по перечисленным товарам, товар без такой
записи пропускается без ошибки. Действующую цену сообщение не меняет: если цена документа
уже вступила в силу, 1С дополнительно присылает `price.updated` с ценой, действующей после
отмены. Если документ перепровели, убрав из него строки, `price.cancelled` нужен и по
убранным товарам — иначе их отложенные цены останутся.

**Полная выгрузка цен** (`RMQ_ВыгрузитьВсеЦены`) отдаёт действующую цену каждого товара с
`effective_from` = период записи в регистре (дата в прошлом — применится сразу) и все
будущие записи регистра по основному виду цены, каждую своим `price.updated`. Будущие
записи работают как upsert по паре `product_uuid` + `document_uuid`: восстанавливают
потерянное, но **ничего не удаляют**. Выгрузка не эталон расписания — неполная выгрузка
(обрыв, сбой задания) иначе снесла бы запланированные цены. Снимает отложенную цену
только `price.cancelled`.

**Заказ** фиксирует цену в строке в момент оформления на сайте и уходит в 1С через секунды.
Заказ, оформленный до `effective_from`, идёт по цене, которую видел клиент; 1С строки при
приёме по регистру не пересчитывает.

**Вне v16.13.0:** будущая цена клиенту не показывается (решение коммерческого отдела,
контракт позволит без доработок обмена); отложенные индивидуальные цены
(`individual_prices.ready`) — отдельным кругом.

### Критерии приёмки

- [ ] Сайт принимает `price.updated` и обновляет цену товара по UUID
- [ ] Если товара ещё нет — событие принимается без ошибок, цена откладывается
- [ ] `product.created` после отложенной цены создаёт карточку сразу с этой ценой
- [ ] Порядок `price.updated` и `product.created` не важен: цена не теряется ни в каком порядке
- [ ] `product.created` по существующей карточке базовую цену не трогает
- [ ] По каждому товару, которому в 1С назначена цена, `price.updated` приходит хотя бы один раз — иначе базовая цена на сайте останется нулевой
- [ ] `price.updated` с будущей `effective_from` не меняет цену до срока и включается не позже минуты после него (v16.13.0)
- [ ] Повтор с тем же `document_uuid` заменяет отложенную цену и дату, отложенная запись по паре одна
- [ ] `price.cancelled` снимает отложенную цену документа и не трогает действующую
- [ ] `price.updated` без `effective_from` применяется сразу
- [ ] `effective_from` без смещения, `effective_from` без `document_uuid` — отклоняются валидацией

## Курсы валют (exchange_rate.updated)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.prices`

### Бизнес-правила

- Все цены хранятся в базовой валюте (`RUB`)
- Сайт **не** обновляет курсы из сторонних источников — только из 1С
- `ВыгрузитьВсеКурсыВалют` выгружает **все валюты** из справочника

### Критерии приёмки

- [ ] Сайт сохраняет все три значения: `official_rate`, `rate_coefficient`, `rate`
- [ ] Курсы обновляются только через 1С
