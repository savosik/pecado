# Платежи

> **JSON Schema:** [`payment.created.json`](/docs/erp/schemas/payment.created.json) | [`payment.updated.json`](/docs/erp/schemas/payment.updated.json) | [`payment.deleted.json`](/docs/erp/schemas/payment.deleted.json)  
> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.payments`

Платёжные документы банка и кассы: поступления оплаты от клиентов и возвраты оплаты клиентам.
Онлайн-эквайринг сайта по этой очереди **не передаётся** — это отдельная сущность.

## ⚠️ Что изменилось в v16.0.0

**Расшифровка платежа (`allocations`) удалена из контракта.**

Разнесение теперь выражается движениями регистра взаиморасчётов — см.
[Регистр взаиморасчётов](settlements.md). Формировать `allocations` на стороне 1С больше
не нужно; это была самая сложная часть выгрузки, и она всё равно не покрывала реальность:
из 156 754 061,98 ₽ разнесения на реализации ложилось 44 881 268,77 ₽, а **111 872 793,21 ₽
(71,4 %) не помещалось**.

Поле, присланное по инерции, **игнорируется** — сообщение обрабатывается целиком и в очередь
недоставленных не уходит. `additionalProperties: true` оставлен намеренно, чтобы переключение
сторон не роняло обмен.

**Сам документ платежа остаётся.** Клиенту нужен ответ на вопрос «дошёл ли мой платёж»,
и отвечает на него именно журнал платежей: дата, сумма, номер по банку, наш счёт.

**(v16.8.0) Сайт больше не хранит разнесение.** Таблица расшифровки и колонки
`allocated_amount` / `unallocated_amount` удалены вместе со старым счётным ядром:
для платежей, пришедших после v16.0.0, они были пусты всегда, и колонка «Разнесение»
в журнале показывала бы всем «аванс». Связь «платёж → что он закрыл» видна в акте
сверки и в движениях регистра.

## События

| Событие | Описание |
|---|---|
| `payment.created` | При первом проведении платёжного документа |
| `payment.updated` | При перепроведении или изменении реквизитов |
| `payment.deleted` | При отмене проведения |

## Бизнес-правила

- **(v15.11.0) Направление передаётся явно** полем `direction` (`in` — поступление от клиента,
  `out` — возврат клиенту). Сайт не выводит направление из текста операции: наименование
  меняется вместе с настройками учёта. При отсутствии поля платёж считается поступлением.
  Сумма `amount` всегда положительная — знак задаёт `direction`, а не сама сумма.
- **(v15.11.0)** `operation_code` — машинный код операции латиницей (`customer_payment`,
  `customer_refund`). `operation_name` — русское наименование как в 1С, показывается
  сотрудникам как есть и в логике не участвует.
- **(v15.11.0) Привязка к контрагенту:**
    - приоритет — по `contractor_uuid` (`Company.erp_id` на сайте);
    - **fallback** — по `tax_id` **в паре с `partner_uuid`**. Без `partner_uuid` fallback-поиск
      не выполняется (security-fix v13.2): иначе нашлась бы чужая Company с тем же ИНН;
    - `contractor_uuid` сохраняется **всегда**, даже если контрагента на сайте ещё нет.
      По нему связь доклеивается позже.
- **(v16.0.0) У одного партнёра может быть несколько контрагентов с одним ИНН.** Проверено
  на боевых данных: у партнёра «Яндекс.Лавка» три записи с ИНН 9718101499 и разными UUID,
  причём документы приезжали на один, а баланс — на другой, и они никогда не встречались.
  Документы, движения и баланс одного контрагента обязаны приезжать **на один и тот же UUID**.
- **(v15.11.0) `partner_uuid` настоятельно рекомендуется.** Без него платёж не привяжется
  к пользователю сайта, и клиент **не увидит свою оплату** в личном кабинете.
- **(v15.11.0) `payment.updated` на неизвестный платёж создаёт его** из полученного payload —
  структура `updated` полная. Потерянный `payment.created` означал бы потерянные деньги
  в отчётах; реализация в такой ситуации хотя бы видна в заказах, а платёж не виден нигде.
- **(v15.11.0) Номер документа не уникален.** Номера повторяются между организациями и годами,
  поэтому связь строится только по `uuid`. Поле `bank_number` — отдельный номер, по которому
  клиент ищет платёж в своей выписке.
- **(v15.11.0) Время в `date` значимо** и передаётся как datetime: порядок платежей внутри дня
  имеет значение при разборе.
- **(v15.11.0) Реквизиты платежа на сайте не редактируются.** Мастер — 1С. Сотрудник сайта
  может добавить только комментарий и вложения; эти поля в 1С не уходят и из 1С
  не перезаписываются.
- **(v15.16.0) Комментарий 1С хранится отдельно от комментария сотрудника.** Поле `comment`
  попадает в собственную колонку и **не затирает** заметку менеджера — иначе первая же доставка
  документа стирала бы её. Не путать с `purpose`: там назначение платежа из банковской выписки.
- **(v15.16.0) `organization_account` — НАШ счёт, `payer_account` — счёт КЛИЕНТА.** Состав полей
  одинаковый, различие смысловое. Перепутав их, клиент увидел бы в кабинете собственный счёт
  вместо нашего и решил бы, что деньги ушли не туда.
- **(v15.11.0) `payment.deleted` — мягкое удаление.** Платёж помечается удалённым и перестаёт
  учитываться; повторное проведение того же документа возвращает его.

## Порядок первичной выгрузки

Платежи выгружаются **после реализаций**. Порядок не критичен для корректности, но экономит
часы на первичной заливке.

Движения регистра по платежам идут отдельным потоком — см.
[порядок выгрузки](../initial-load.md) и [Регистр взаиморасчётов](settlements.md).

## Критерии приёмки

- [x] **(v15.11.0)** Сайт принимает `payment.created`, `payment.updated`, `payment.deleted`
- [x] **(v15.11.0)** Company находится сначала по `contractor_uuid`, затем fallback
      по `tax_id + partner_uuid`; поиск без `partner_uuid` не выполняется
- [x] **(v15.11.0)** `contractor_uuid` сохраняется даже когда контрагента на сайте нет
- [x] **(v15.11.0)** Повторная доставка того же `uuid` не создаёт второй платёж
- [x] **(v15.11.0)** `payment.updated` на неизвестный платёж создаёт документ
- [x] **(v15.11.0)** Возврат (`direction: "out"`) отражается как возврат, а не как поступление
- [x] **(v15.11.0)** Клиент видит свои оплаты в личном кабинете
- [x] **(v15.16.0)** Комментарий из 1С не затирает заметку менеджера
- [x] **(v16.0.0)** Сообщение с присланным по инерции `allocations` обрабатывается без ошибки,
      поле игнорируется
- [x] **(v16.0.0)** Оплата документов отражается движениями регистра, а не расшифровкой платежа
- [x] **(v16.8.0)** Расшифровка на сайте не хранится: приём `allocations` снят целиком
