# Платежи

> **JSON Schema:** [`payment.created.json`](/docs/erp/schemas/payment.created.json) | [`payment.updated.json`](/docs/erp/schemas/payment.updated.json) | [`payment.deleted.json`](/docs/erp/schemas/payment.deleted.json)  
> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.payments`

Платёжные документы банка и кассы: поступления оплаты от клиентов и возвраты оплаты клиентам.
Онлайн-эквайринг сайта по этой очереди **не передаётся** — это отдельная сущность.

## События

| Событие | Описание |
|---|---|
| `payment.created` | При первом проведении платёжного документа |
| `payment.updated` | При перепроведении или изменении расшифровки |
| `payment.deleted` | При отмене проведения |

## Бизнес-правила

- **(v15.11.0)** Один платёж разносится на **несколько реализаций**, и одна реализация закрывается **несколькими платежами**. Разнесение приходит массивом `allocations` внутри самого сообщения — отдельного события для расшифровки нет
- **(v15.11.0) Разнесение заменяется целиком.** Содержимое `allocations` полностью вытесняет то, что сохранено на сайте. Досылать только изменившиеся строки нельзя — сайт не умеет отличить «строки не изменились» от «строк больше нет»
- **(v15.11.0) Отсутствие ключа `allocations` и пустой массив означают разное.** Ключа нет — сайт **не трогает** сохранённое разнесение (используйте, когда меняется только шапка документа). Пустой массив `[]` — сайт **очищает** разнесение полностью, платёж становится авансом. Различие критично: если 1С опустит ключ, подразумевая «разнеси заново на ноль», оплата останется на реализациях
- **(v15.11.0) Строка расшифровки связывается по `shipment_uuid`, а не по номеру.** Реализация может ещё не приехать на сайт: строка сохранится без привязки, а связь доклеится автоматически при получении `shipment.created` / `shipment.updated` с этим uuid. Строка без `shipment_uuid` пропускается — она бессмысленна
- **(v15.11.0)** Поле `target_type` заведено на вырост. Сейчас поддерживается только `shipment`; строки с другим значением сайт пропускает и пишет предупреждение в лог. Отсутствие поля равнозначно `shipment`
- **(v15.11.0) Направление передаётся явно** полем `direction` (`in` — поступление от клиента, `out` — возврат клиенту). Сайт не выводит направление из текста операции: наименование операции меняется вместе с настройками учёта. При отсутствии поля платёж считается поступлением. Сумма `amount` всегда положительная — знак задаёт `direction`, а не сама сумма
- **(v15.11.0)** `operation_code` — машинный код операции латиницей (`customer_payment`, `customer_refund`). `operation_name` — русское наименование как в 1С, показывается сотрудникам как есть и в логике не участвует
- **(v15.11.0) Привязка к контрагенту** повторяет правило реализаций:
    - Приоритет — по `contractor_uuid` (`Company.erp_id` на сайте)
    - **Fallback** — по `tax_id` **в паре с `partner_uuid`**. Без `partner_uuid` fallback-поиск не выполняется (security-fix v13.2): иначе нашлась бы чужая Company с тем же ИНН
    - `contractor_uuid` сохраняется в платеже **всегда**, даже если контрагента на сайте ещё нет. По нему связь доклеивается позже
- **(v15.11.0) `partner_uuid` настоятельно рекомендуется.** Без него платёж не привяжется к пользователю сайта, и клиент **не увидит свою оплату** в личном кабинете
- **(v15.11.0) Нераспределённый остаток = аванс.** Разница между `amount` и суммой строк `allocations` хранится на сайте как нераспределённый остаток и показывается клиенту и менеджеру. Платёж вообще без `allocations` — целиком аванс, это легитимно
- **(v15.11.0) Оплата реализации считается только по совпадающей валюте.** Платёж в валюте, отличной от валюты реализации, в оплату не засчитывается, и факт попадает в лог. Сложить рубли с тенге по неизвестному курсу сайт не вправе
- **(v15.11.0)** Возврат (`direction: "out"`), разнесённый на реализацию, **уменьшает** её оплаченную сумму
- **(v15.11.0) `payment.updated` на неизвестный платёж создаёт его** из полученного payload — структура `updated` полная. Потерянный `payment.created` означал бы потерянные деньги в отчётах; реализация в такой ситуации хотя бы видна в заказах, а платёж не виден нигде
- **(v15.11.0) `payment.deleted` не удаляет расшифровку.** Платёж помечается удалённым и перестаёт учитываться в оплате реализаций, но строки разнесения сохраняются: повторное проведение того же документа вернёт их как было
- **(v15.11.0) Номер документа не уникален.** Номера повторяются между организациями и годами, поэтому связь строится только по `uuid`. Поле `bank_number` (номер по банку) — отдельный номер, по которому клиент ищет платёж в своей выписке
- **(v15.11.0) Время в `date` значимо.** Порядок платежей внутри дня определяет, каким из них закрыта реализация, поэтому `date` передаётся как datetime, а не как дата
- **(v15.11.0) Реквизиты платежа на сайте не редактируются.** Мастер — 1С. Сотрудник сайта может добавить только комментарий и вложения; эти поля в 1С не уходят и из 1С не перезаписываются

## Порядок первичной выгрузки

Платежи выгружаются **после реализаций**. Иначе весь массив приедет с неразрешёнными `shipment_uuid`,
и оплата проставится только по мере доезда реализаций. Порядок не критичен для корректности
(связь доклеивается), но экономит часы на первичной заливке.

## Критерии приёмки

- [x] **(v15.11.0)** Сайт принимает `payment.created`, `payment.updated`, `payment.deleted` из очереди `erp_in.payments`
- [x] **(v15.11.0)** Company находится сначала по `contractor_uuid`, затем fallback по `tax_id + partner_uuid`; поиск без `partner_uuid` не выполняется
- [x] **(v15.11.0)** `contractor_uuid` сохраняется даже когда контрагент на сайте отсутствует
- [x] **(v15.11.0)** Повторная доставка того же `uuid` не создаёт второй платёж и не задваивает разнесение
- [x] **(v15.11.0)** `payment.updated` **без ключа** `allocations` оставляет разнесение нетронутым; с пустым массивом — очищает
- [x] **(v15.11.0)** Строка с неизвестным `shipment_uuid` сохраняется без привязки и доклеивается при получении реализации, после чего оплата реализации пересчитывается
- [x] **(v15.11.0)** Нераспределённый остаток равен `amount` минус сумма строк разнесения
- [x] **(v15.11.0)** Реализация, закрытая двумя платежами, получает суммарную оплату и статус «оплачена»
- [x] **(v15.11.0)** Возврат (`direction: "out"`) уменьшает оплаченную сумму реализации
- [x] **(v15.11.0)** Платёж в валюте, отличной от валюты реализации, в оплату не засчитывается
- [x] **(v15.11.0)** `payment.deleted` обнуляет вклад платежа в оплату реализаций, сохраняя строки расшифровки; повторное `payment.created` возвращает оплату
- [x] **(v15.11.0)** Клиент видит свои оплаты в личном кабинете и разнесённые платежи в карточке реализации
