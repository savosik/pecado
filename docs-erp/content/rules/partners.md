## partner.created (1С → Сайт)

### Бизнес-правила

- Партнёры без email **не выгружаются** (пропускаются)
- `country` никогда не `null` — фолбэк на `СтранаПоУмолчанию` из настроек (по умолчанию `"RU"`)
- `password` = десятичное число CRC32 от email партнёра
- `currency` всегда `"RUB"`
- При первом входе пользователь **обязан сменить пароль**

### Версионные изменения

- **(v8)** Поля `first_name`, `last_name`, `middle_name` удалены. Единое поле `name` (НаименованиеПолное)
- **(v10)** Поле `is_active` (boolean) — активность партнёра. `false` → пользователь не может оформлять заказы
- **(v11)** Поле `client_status` — произвольная строка, код статуса клиента (уровень лояльности). Резолвится через `ClientStatus.external_id`. Примеры: `silver`, `gold`, `diamond`, `individual`
- **(v12.7.5)** Поле `password` — тип изменён с `integer` на `string`, `maxLength` увеличен до 32. 1С передаёт CRC32 как строку длиной до 10 символов
- **(v15.10)** Поле `name` пишется в `users.erp_name` (рабочее наименование). Для **нового** пользователя оно дополнительно становится стартовым `users.name`; у существующего личное имя не трогается
- **(v15)** Поле `manager` — объект `{ uuid, name }` или `null`. Основной менеджер партнёра в 1С.
    - `manager.uuid` — UUID пользователя 1С (Справочник «Пользователи»), **не** UUID партнёра/контрагента
    - `manager.name` — ФИО/наименование для отображения на сайте
    - Сайт ищет `PersonalManager` по `erp_uuid`; если не найден — создаёт новую запись с `name` из payload
    - `manager = null` — менеджер не назначен; сайт сбрасывает `user.personal_manager_id = null`
    - Отсутствие ключа `manager` в payload — менеджер не меняется (идемпотентность)

### Критерии приёмки

- [ ] 1С публикует `partner.created` через `erp.events` → `erp_in.partners`
- [ ] Сайт создаёт/обновляет пользователя с `name` как единое поле
- [ ] **(v15.10)** `name` сохраняется в `users.erp_name` во всех трёх сценариях (поиск по `erp_id`, по email, создание)
- [ ] **(v15.10)** У существующего пользователя `users.name` не перезаписывается
- [ ] При первом входе — обязательная смена пароля (`must_change_password`)
- [ ] Партнёры без email пропускаются при выгрузке
- [ ] **(v15)** Поле `manager` обрабатывается: новый менеджер создаётся или привязывается по `erp_uuid`
- [ ] **(v15)** `manager = null` сбрасывает `personal_manager_id` пользователя

## partner.updated (1С → Сайт)

### Бизнес-правила

- Событие предназначено для **обновления атрибутов** существующего партнёра
- **Не создаёт** нового пользователя — если партнёр не найден, событие игнорируется с предупреждением
- Поиск пользователя: сначала по `erp_id` (UUID), фолбэк — по `email`/`login`
- При нахождении по email — привязывает `erp_id` к пользователю
- Поле `password` **не передаётся** — пароль не изменяется
- **Частичное обновление**: обновляются только переданные поля

### Обновляемые атрибуты

| Поле payload | Поле User | Описание |
|---|---|---|
| `name` | `erp_name` | **Рабочее наименование** — наименование карточки партнёра в 1С. С v15.10 приезжает в отдельное поле, личное `users.name` не перезаписывается |
| `phone` | `phone` | Телефон |
| `city` | `city` | Город |
| `country` | `country` | ISO alpha-2 код страны (нормализация) |
| `is_active` | `status` | `true` → ACTIVE, `false` → BLOCKED |
| `client_status` | `client_status_id` | Код → `ClientStatus.external_id` |
| `manager` | `personal_manager_id` | `{uuid,name}` → `PersonalManager.erp_uuid`; `null` → сброс |

!!! warning "Рабочее наименование и личное имя — разные поля (v15.10)"
    Клиент вправе переименовать себя в личном кабинете, поэтому `users.name`
    принадлежит клиенту и из 1С **не перезаписывается**. Наименование из
    `partner.created` / `partner.updated` сохраняется в `users.erp_name` —
    рабочее наименование, по которому менеджеры сличают отчёты сайта и 1С.

    Сотрудникам (CRM, админка) клиент показывается по `erp_name`; личное имя
    выводится рядом, только когда отличается. Клиент в кабинете и письма ему
    по-прежнему используют `name`.

    Мастер рабочего наименования — 1С: на сайте поле только для чтения.

!!! info "Поля, не передаваемые в partner.updated"
    `currency` — определяется через регион пользователя, не передаётся из 1С.
    `region` — 1С не присылает регион, привязка региона выполняется на стороне сайта.

### Версионные изменения

- **(v12)** Новое событие `partner.updated` — выделено из `partner.created` как самостоятельное событие для обновления атрибутов
- **(v12)** Удалены поля `currency` и `region` из входящих событий партнёра
- **(v15.1)** Поле `manager` (опциональное) — при наличии обрабатывается аналогично `partner.created`: сайт ищет `PersonalManager` по `erp_uuid`, при отсутствии — создаёт. `null` — сбрасывает привязку. Отсутствие ключа — не меняет
- **(v15.10)** Поле `name` теперь пишется в `users.erp_name` (рабочее наименование), а не в `users.name`. Структура payload не изменилась — изменился приёмник на стороне сайта

### Критерии приёмки

- [ ] 1С публикует `partner.updated` через `erp.events` → `erp_in.partners`
- [ ] Сайт обновляет атрибуты пользователя (phone, city, country, region, status, client_status)
- [ ] **(v15.10)** `name` из payload попадает в `users.erp_name`
- [ ] **(v15.10)** `users.name` после `partner.updated` не меняется — имя, заданное клиентом в кабинете, сохраняется
- [ ] При совпадении email — привязывает `erp_id` к существующему пользователю
- [ ] При `client_status = null` — сброс `client_status_id` пользователя
- [ ] При неизвестном `client_status` — логирование предупреждения, текущий статус не меняется
- [ ] При `is_active = false` — пользователь блокируется
- [ ] Если пользователь не найден ни по `erp_id`, ни по `email` — событие игнорируется с логом
- [ ] **(v15.1)** При `manager` в payload — привязывает/создаёт `PersonalManager` по `erp_uuid`
- [ ] **(v15.1)** При `manager = null` — сбрасывает `personal_manager_id` пользователя
- [ ] **(v15.1)** При отсутствии ключа `manager` — менеджер не меняется

## partner.created (Сайт → 1С)

### Бизнес-правила

- Событие публикуется при **регистрации** нового пользователя (событие `UserCreated`), не при активации
- Новый пользователь получает статус **PROCESSING** — `is_active` всегда `false` при первой отправке
- Поле `comment` содержит **секретную ссылку** на превью-страницу (`/preview/user/{token}`) — только по URL с токеном, без авторизации
  - Ссылка предназначена для менеджеров, не имеющих доступа к админке, чтобы ознакомиться с данными нового партнёра
- При регистрации пользователю автоматически назначается регион по умолчанию (первый по id)
- 1С ищет партнёра по email (`EmailПартнера`); если не найден — создаёт нового
- 1С **не использует** UUID из payload как свой идентификатор — генерирует свой UUID платформой

### Версионные изменения

- **(v12.8)** Триггер изменён с `UserUpdated` (активация) на `UserCreated` (регистрация)
- **(v12.8)** Добавлено поле `is_active` (boolean) — всегда `false` при первой регистрации (статус PROCESSING)
- **(v12.8)** Добавлено поле `comment` (string|null) — секретная ссылка на превью-страницу пользователя

### Критерии приёмки

- [ ] Сайт публикует `partner.created` с данными партнёра через `erp_out.partners` при регистрации
- [ ] Payload содержит: `event`, `message_id`, `uuid`, `login`, `name`, `email`, `is_active`, `comment`
- [ ] `login = email`
- [ ] `is_active = false` (новый пользователь в статусе PROCESSING)
- [ ] `comment` содержит валидный URL вида `/preview/user/{token}`
- [ ] Превью-страница открывается без авторизации, показывает данные пользователя и анкету (если заполнена)

## partner.deleted (1С → Сайт)

### Бизнес-правила

- Пользователь переводится в статус «Не активен» (`is_active = false`)
- Пользователь не может авторизоваться и оформлять заказы

### Критерии приёмки

- [ ] Сайт принимает `partner.deleted` и деактивирует пользователя
