# Расходные ордера на товары

> **JSON Schema:** [`goods_issue.created.json`](/docs/erp/schemas/goods_issue.created.json) | [`goods_issue.updated.json`](/docs/erp/schemas/goods_issue.updated.json) | [`goods_issue.deleted.json`](/docs/erp/schemas/goods_issue.deleted.json)  
> **AsyncAPI:** [Полная спецификация](/docs/erp/spec.yaml)  
> **Задание разработчику 1С:** [Расходные ордера: что сделать в 1С](../guides/goods-issues-for-1c.md)

**Направление:** 1С → Сайт | **Очередь:** `erp_in.warehouse` | **Появилось в:** v15.15.0

## Зачем это нужно

Реализация (`shipment.*`) отражает **уже свершившийся** факт отгрузки. Документ, по которому
товар физически собирают, проверяют, упаковывают и грузят — «Расходный ордер на товары» —
до v15.15.0 на сайте отсутствовал вовсе.

Из-за этого склад не видел на сайте свою основную операционную единицу: что сейчас в отборе,
что ждёт проверки, что зависло на этапе, сколько мест собрано и по каким заказам идёт ордер.
Всё это жило только в толстом клиенте 1С.

Главный потребитель данных — **кабинет склада `/wms`**: журнал ордеров с фильтрами,
статусами, карточкой документа и выгрузкой в Excel.

## События

| Событие | Описание |
|---|---|
| `goods_issue.created` | При первом проведении ордера |
| `goods_issue.updated` | При смене статуса, состава или реквизитов (структура идентична `created`, отличается `event`) |
| `goods_issue.deleted` | При отмене проведения или пометке на удаление |

## Статусы

Статус присылается **машинным кодом**, а не русским названием из 1С:

| Статус в 1С | Код |
|---|---|
| Подготовлен | `prepared` |
| К отбору | `to_pick` |
| К проверке | `to_check` |
| В процессе проверки | `checking` |
| Проверен | `checked` |
| К отгрузке | `to_ship` |
| Отгружен | `shipped` |

**Значение вне этого списка не принимается:** сообщение отбрасывается целиком, попадает
в `erp_dlq.warehouse` и фиксируется в журнале ошибок валидации.

Строгий перечень выбран сознательно — в отличие от `shipment.status`, где 1С шлёт голые
строки. Статус здесь главное, ради чего журнал склада существует: молча принять неизвестный
код означало бы показать кладовщику ордер в состоянии, которого нет в его рабочем процессе.

Сайт хранит не только текущий статус, но и **журнал смен**: по нему видно, сколько ордер
простоял на каждом этапе, и находятся зависшие документы. Строка в журнал пишется только
при фактическом изменении статуса — повторный `goods_issue.updated` с тем же статусом
журнал не засоряет.

## Бизнес-правила

- **Совместная отгрузка (v16.11.0).** Группа резервов, отправленная клиентом в отгрузку
  вместе (`order.confirmed` с `ship_together_key`), оформляется в 1С одним групповым вызовом
  ордерного движка: ожидаемый результат при одном складе и совместимых складских ключах —
  один расходный ордер по всем заказам группы. Несколько ордеров — не ошибка, сайт узнаёт
  фактический состав из `goods_issue.created`. Частичный ордер по группе наружу не
  публикуется: ошибка движка откатывает всю группу. Подробно —
  [Заказы в резерве → Совместная отгрузка](order-reserves.md#совместная-отгрузка-резервов-v16110).
- **Один ордер может собираться сразу по нескольким заказам клиента.** Поэтому
  заказ-распоряжение указывается в строке (`items[].order_uuid`), а не в шапке — так же,
  как у реализаций. Связь «ордер ↔ заказ» на сайте строится через строки.
- **Документ присылается целиком.** Сайт удаляет прежние строки и создаёт их заново;
  упаковочные листы с v16.14.0 сверяются по `uuid` (см. ниже). Досылать отдельные изменившиеся строки нельзя — они продублируются.
  Единственное исключение — отгруженный без товара ордер (`shipped` + `items: []`, v16.15.0):
  прежние строки сайт сохраняет, см. [Полный недобор](#empty-shipped).
- **Идемпотентность по `uuid`.** Повторное сообщение по тому же документу не создаёт
  второй ордер, а перезаписывает существующий. Плюс транспортная идемпотентность
  по `message_id`: полный дубль сообщения отбрасывается до обработки.
- **`recipient_name` присылать нужно всегда.** Получателем ордера бывает контрагент,
  которого в справочниках сайта нет вовсе (маркетплейс, внутреннее перемещение).
  Без строки-имени такой ордер в журнале склада останется безымянным.
- Привязка к контрагенту — по общим правилам документов: приоритет `contractor_uuid`,
  fallback по `tax_id` **в паре с `partner_uuid`**. Не нашли — ордер сохраняется
  с пустым контрагентом, но с заполненным `recipient_name` и виден складу.
- **Неизвестный товар или заказ обработку не роняют.** Строка сохраняется с пустой
  ссылкой, но с `product_name` и `order_number` из 1С: ордер по товару, которого нет
  в каталоге сайта, кладовщику всё равно нужно видеть.
- **`packages`: отсутствие ключа и пустой массив означают разное.** Ключа нет — сайт
  не трогает сохранённые упаковочные листы; `[]` — очищает их полностью.
- Неизвестный сайту склад автоматически не заводится: `warehouse_uuid` останется
  непривязанным, факт попадёт в лог. Склады заводятся в админке вручную.
- Организация документа — по общим правилам, см. [Организации](organizations.md).

## Полный недобор: ордер отгружен без товара (v16.15.0) {#empty-shipped}

Топик Agent Hub №19. Упаковщик в РМУ нажал «Груз собран» → «Оформить недобор», а собрано
**ничего**: весь товар оказался некондицией, браком или его не нашли. 1С отменяет строки
заказа («Нет остатка», приходит `order.updated`), перемещает товар на склады причин и
проводит расходный ордер **без строк** в «Товарах по распоряжениям».

**Что присылает 1С** — финальное `goods_issue.updated`:

- `status: shipped`, `items: []`, `packages: []`;
- если ордер уже идёт с `revision` — `measurement` с `required: false`, `state: not_required`,
  `measured_at`/`measured_by` = `null` (мест нет — обмерять нечего).

**Что проверяет схема:**

- пустой `items` допустим **только** в `goods_issue.updated` и **только** при `status: shipped`;
  в `goods_issue.created` и в любом другом статусе — ошибка валидации, сообщение уходит в
  `erp_dlq.warehouse`;
- при пустом `items` массив `packages` пуст или отсутствует, а `measurement` (если передан) —
  только `not_required`. `done` и `pending` отклоняются.

**Что делает сайт:**

- **строки прошлых снимков не удаляет.** Связь ордера с заказом на сайте живёт только в строках
  (`items[].order_uuid`), поэтому строки последней сборки (`to_check` и т. п.) остаются как
  история: ордер по-прежнему виден в карточке заказа, а отменённые позиции в журнале недоборов
  получают подсказку «Похоже на склад»;
- помечает ордер **«Отгружен без товара»** — так он и показывается в журнале склада;
- стадия заказа для клиента и менеджера — **«Сборка не состоялась»**, а не «Собран, ждёт выдачи»;
- письмо клиенту «заказ собран и ждёт выдачи» **не уходит**, ордер не встаёт в очередь выдачи
  самовывоза, не попадает в напоминания «не забрали» и в утреннюю сводку как «собран»;
- если позже придёт `goods_issue.updated` со строками (например, документ перепровели с товаром),
  пометка снимается, строки заменяются по общему правилу.

Почему не другие варианты: строки с `quantity: 0` — позиции, которых в документе 1С уже нет,
и на сайте они неотличимы от собранного ордера (клиент получил бы «заказ собран»);
`goods_issue.deleted` исказил бы историю: документ в 1С проведён и отгружен.

## Что сайт не хранит

- **Цены, скидки, суммы.** Ордер — складской документ, а не денежный: суммы приезжают
  реализацией. Если понадобится сверка «отгружено на сумму» — она строится по реализации.
- **Серии номенклатуры и штрихкоды маркировки** («Честный знак»). Данные тяжёлые,
  а задач, которые на них опираются, у сайта сейчас нет. При необходимости — отдельная
  доработка контракта.
- **Состав упаковочных листов построчно.** Хранится номер листа, число позиций в нём
  и (опционально) номер листа в строке товара — этого хватает для сверки при погрузке.

## Чего в документе 1С нет (v15.16.0)

Уточнения после сверки контракта с реальным составом реквизитов документа.

**Доставка: `delivery_type` и `delivery_address` не заполнять.** Таких реквизитов
в расходном ордере физически нет — проверено по полному перечню 43 реквизитов.
Присылайте `delivery_order` («Порядок доставки» из нижней части документа).
Способ доставки и адрес сайт берёт из заказа и реализации, где они есть штатно.
Оба поля оставлены в схеме ради совместимости и будут удалены, когда станет ясно,
что их никто не шлёт.

**Отметки времени `erp_created_at` / `erp_updated_at` можно опускать.** У документа
в 1С отключена история данных, брать их неоткуда. Поля не входят в `required`,
сообщение без них валидно, а отсутствие ключа не сбрасывает сохранённое значение.
По той же причине до v16.14.0 у расходных ордеров не было `revision`; с v16.14.0 номер
ведёт собственный счётчик 1С — см. раздел «Обмер грузовых мест» ниже.

**Ячейка (`items[].cell`) — необязательная строка (v15.17.0).** Реквизит «Ячейка»
табличной части приезжает как есть и показывается кладовщику в карточке ордера
и в выгрузке. Сайт её **не разбирает и не сверяет** ни со справочником складов,
ни с остатками: адресное хранение ведётся в 1С, сайт его только отражает.

Поле можно не присылать вовсе, а можно прислать пустую строку — для сайта это одно
и то же, ячейка остаётся незаполненной. Ограничение одно: не длиннее 255 символов,
иначе сообщение не пройдёт валидацию.

**Номер места (`items[].package_number`) — приближение, и это нормально.** Связи
«конкретная строка ордера → конкретное место упаковки» в модели данных 1С нет.
Номер восстанавливается по паре товар + характеристика; если товар лежит
в нескольких местах, строка получает наименьший номер.

Следствие, с которым сайт согласился: **сумма строк с номером N может не совпасть
с `positions_count` места N**, и сайт эти величины не сверяет. Дробление одной
строки по нескольким местам контракт выразить не позволяет — если это когда-нибудь
понадобится, заведём отдельную структуру, а не будем менять смысл поля.

## Обмер грузовых мест (v16.14.0, проект)

> **Статус: проект контракта, согласуется в топике Agent Hub №13.** Поля уже принимаются
> валидатором, но сайт их пока не применяет; 1С начинает слать их одним выпуском после
> приёмки. До этого действуют правила выше.

### Зачем

Клиент сам отдаёт собранный заказ транспортной компании в личном кабинете: выбирает ТК,
тариф, пункт выдачи. Расчёт у любого перевозчика начинается с веса и габаритов **мест**,
а вывести их из карточек товара нельзя: ТК тарифицирует по объёмному весу, а коробка —
это пустоты и нестандартная укладка. Поэтому место обмеряет упаковщик руками.

### Что такое место

**Один элемент `packages[]` = одно грузовое место = один УпаковочныйЛист**, созданный
командой «Закрыть коробку» рабочего места упаковщика (`Обработка.Андрей_РабочееМестоУпаковщика`).
Подтверждено 1С по коду и боевым данным (с 28.06.2026 все 3 821 лист имеют профиль РМУ,
вложенных листов и «нескольких коробок одним листом» нет). Реквизит листа `ВсегоМест` —
сумма упаковок товаров, числом мест не является и в контракт не входит.

Обмер делается при закрытии коробки, пока она перед упаковщиком. Лист, к которому не
записались товары (сбой записи коробки), в `packages[]` как готовое место не попадает.

### Способ доставки — `shipping_mode`

Реквизита способа в ордере нет, 1С определяет его по уникальным заказам-распоряжениям строк:

| Значение | Когда | Обмер | Расчёт доставки на сайте (целевое, блок логистики) |
|---|---|---|---|
| `pickup` | все распоряжения — подтверждённый самовывоз | `not_required` | нет |
| `delivery` | все — доставка | `pending` → `done` | да, при `done` |
| `mixed` | сочетание самовывоза и доставки | все места, `pending` → `done` | **да, по всем местам ордера**: коробки общие, к перевозчику уходит весь ордер, включая заказы на самовывоз; клиент это видит |
| `null` | способ неизвестен, распоряжения не-заказы, нет прав | `pending` | нет, «обратитесь к менеджеру»; самовывозом не считается |

Сайт сверяет `shipping_mode` со способом своих заказов ордера (связь по `items[].order_uuid`).
Расхождение `pickup` ↔ доставка и `shipping_mode = null` пишутся в журнал шины оговоркой к
принятому сообщению. Автоматического разделения ордера по способам нет.

!!! note "Расчёт доставки сейчас не блокируется (решение заказчика 01.10.2026)"
    Сайт **сохраняет обмер и способ доставки**; в расчёте доставки они будут учтены в блоке
    логистики. Сейчас расчёт не блокируется ни при `pending`, ни при `null`, ни при расхождении
    способа: склад считает доставку по местам, введённым вручную, а состояние обмера видит
    справкой (готовый обмер подставляется в форму отправки). Колонка «Расчёт доставки на сайте»
    в таблице выше описывает целевое поведение блока логистики: расчёт **по ордеру**, а не по
    заказу — одно место дважды не посчитается.

Смена способа доставки в заказе пересчитывает `shipping_mode`/`measurement` и публикует
актуальный снимок всех связанных ордеров.

### Состояние обмера — `measurement.state`

- **`done`** ставит только отдельная команда завершения — после упаковки всего фактического
  состава, закрытия всех коробок и полного валидного обмера каждого непустого места. Четыре
  заполненных числа сами по себе завершением не являются.
- **`pending`** — обмер нужен, но не завершён или сброшен. Частичные данные мест передаются,
  сайт их хранит, но готовым обмером не считает.
- **Сброс `done` → `pending`** делает 1С на сервере по отпечатку физического состава: добавление,
  удаление, пересоздание места, перенос товара между местами при неизменном общем количестве,
  недобор, пересборка, смена способа доставки в заказе. Техническое перепроведение и смена
  статуса ордера без изменения состава `done` **не** сбрасывают.
- `measured_at` (со смещением) и `measured_by` заполнены только при `done`, иначе `null`.
- Сохранение и сброс обмера **сами публикуют** полный `goods_issue.updated`, не дожидаясь
  смены статуса ордера, атомарно с сохранением.

Условия `done` проверяет JSON Schema, и нарушение отклоняет сообщение целиком (DLQ + журнал
ошибок валидации), как неизвестный статус: `done` при `packages = []`, место без `weight`
или с `weight = 0`, место без `dimensions` или со стороной < 1, `done` без `measured_at`/`measured_by`.

### Единицы и поля места

| Поле | Единица / смысл |
|---|---|
| `dimensions.length/width/height` | **сантиметры, целые**, внешние, округление вверх, ≥ 1 |
| `weight` | **килограммы брутто**, до трёх знаков, > 0 при `done`. Расчётный вес по карточкам товара сюда не передаётся |
| `volume` | м³; **в v16.14.0 не передаётся**, сайт считает Д×Ш×В/1 000 000 |
| `package_type` | `box` / `pallet` / `bag` / `roll` / `other`; нет значения = `other` |
| `uuid` | GUID УпаковочногоЛиста — ключ идентичности места; обязателен при `revision` |
| `barcode` | Code128 с печатной формы листа: GUID без дефисов как hex → десятичная строка **без ведущих нулей**; длина переменная (до 39 цифр), префиксов и контрольного символа нет |
| `number` | только отображение, может перенумероваться |

**`barcode` сравнивается как строка.** 1С кладёт в поле результат той же функции, что печатает
наклейку, поэтому скан и сообщение совпадают символ в символ. Если старшие шестнадцатеричные
цифры GUID нулевые, строка короче 39 знаков — сайт хранит её как пришла: к числу не приводит,
нулями не дополняет и не обрезает. Пример: `200683171295922156459098038718576216010`.

**Места сверяются по `uuid`**, а не удаляются и вставляются заново: место из снимка
обновляется, отсутствующее удаляется, новое создаётся. Это сохранит будущую связь
«место → трек-номер ТК». Места старого формата без `uuid` при первом новом снимке заменяются целиком.

### Защита от перестановки — `revision`

С v16.14.0 расходные ордера входят в общее правило ревизий
([Порядок доставки и свежесть](message-ordering.md)), со своим счётчиком 1С и двумя
особенностями:

- после первой применённой ревизии сообщение **без** `revision` по тому же `uuid`
  отбрасывается как устаревшее;
- `measurement.state = done` из сообщения без `revision` сайт не принимает: ордер считается
  `pending`, факт пишется в журнал.

Если `revision` есть, схема требует `measurement`, `packages` и `packages[].uuid`.

### Порядок выката

1. Сайт принимает новые поля и правила (обратно совместимо: без `revision` всё как раньше).
2. 1С включает `revision` + `shipping_mode` + `measurement` + `packages[].uuid` **одним
   выпуском**, без промежуточного состояния.
3. Совместная проверка на боевом контуре по тест-плану 1.22 F–M.

### Чего в этом круге нет

- Обратного канала (клиент выбрал ТК, тариф, ПВЗ → 1С): сайт по обмеру в шину ничего
  не публикует.
- Подключения весов к РМУ — ввод вручную.
- Разделения `mixed`-ордера по способам.

## Обратный поток

Его нет: журнал на сайте **read-only**, статусами управляет 1С. Сайт не присылает
в 1С ни смену статуса, ни отметки о сборке.
