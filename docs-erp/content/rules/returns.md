## Допустимые статусы (v15)

Перечисление статусов заявки на возврат на сайте и в шине RabbitMQ
полностью соответствует справочнику 1С:КА2. Шесть значений в порядке
жизненного цикла:

| № | Канонический ключ | Название в 1С | Лейбл на сайте | Цвет |
|---|---|---|---|---|
| 1 | `pending_approval` | На согласовании | На согласовании | yellow |
| 2 | `for_return` | К возврату | К возврату | orange |
| 3 | `in_reserve` | В резерве | В резерве | blue |
| 4 | `ready_for_shipment` | К отгрузке | К отгрузке | purple |
| 5 | `completed` | Выполнена | Выполнена | green |
| 6 | `rejected` | Отклонена | Отклонена | red |

Источник истины на стороне сайта — `App\Enums\ReturnStatus`. Маппинг
русских названий и legacy-ключей до v15 — в
`App\Services\Erp\Support\ReturnStatusMapper`.

### Legacy (v13.12.x → v15)

Сохранены для обратной совместимости — переходный период. Сайт переводит
их в канонические ключи без ошибок.

| Legacy-ключ | Канонический ключ v15 |
|---|---|
| `pending` | `pending_approval` |
| `confirmed` | `in_reserve` (КОбеспечению — более ранний этап) |
| `ready_to_ship` | `ready_for_shipment` |
| `closed` | `completed` |
| `cancelled` | `rejected` |

До v15 ключ `confirmed` объединял два этапа 1С — «КОбеспечению/В резерве»
и «КВозврату/К возврату». При миграции данных все `confirmed` уходят в
`in_reserve`; если для конкретной заявки правильным является `for_return`,
менеджер 1С переведёт её туда вручную.

## return.created (Сайт → 1С)

### Бизнес-правила

- **(v12.13)** Возврат формируется на основании **реализаций (shipments)**, а не заказов. Возвращать можно только то, что физически отгружено.
- Одна заявка на возврат может содержать позиции из разных реализаций — привязка хранится на уровне позиции возврата (`return_items.shipment_item_id`).
- Цена каждой позиции фиксируется как **snapshot** из `ShipmentItem.price` в момент создания возврата. Последующие переоценки реализации со стороны 1С цену возврата не меняют.
- Валюта возврата совпадает с валютой реализации — передаётся полем `currency_code`.
- Поле `order_uuid` в корне сообщения **удалено** (v12.13, BREAKING). Если 1С нужно связать возврат с заказом, она делает это через цепочку `shipment_uuid → shipment.order_uuid`.
- Сайт публикует заявку в статусе `pending_approval` — она ждёт согласования менеджером в 1С.

### Обязательные поля позиции

| Поле | Тип | Описание |
|---|---|---|
| `product_uuid` | uuid | UUID товара (ERP) |
| `shipment_uuid` | uuid | UUID реализации, из которой возвращается позиция |
| `shipment_number` | string | Человекочитаемый номер реализации (shipments.number), с v12.12 обязателен |
| `quantity` | number ≥ 1 | Количество к возврату (не больше отгруженного и не возвращённого ранее) |
| `price` | number ≥ 0 | Цена одной единицы — snapshot из ShipmentItem |
| `currency_code` | string | Код валюты реализации (например, `RUB`) |

Опциональные: `subtotal` (price × quantity), `reason`.

### Валидация сайта при создании возврата

- `ShipmentItem.shipment.user_id` должен совпадать с пользователем, от имени которого создаётся возврат (иначе 403).
- `sum(return_items.quantity)` по одной `shipment_item_id` не может превышать `ShipmentItem.quantity` (иначе 422 с сообщением «Доступно к возврату: N»).

## return.updated (1С → Сайт)

### Бизнес-правила

- Обновляет статус и/или `erp_number` заявки на возврат по UUID.
- **(v12.3)** Если передан `number` — сайт сохраняет его как `erp_number`. Это номер возврата из 1С, который отображается пользователю для коммуникации с менеджером.
- **(v15)** Поле `status` приводится к каноническому ключу через `ReturnStatusMapper`. Поддерживаются:
    - канонические английские ключи (см. раздел «Допустимые статусы»);
    - русские названия 1С (`«На согласовании»`, `«К возврату»`, `«В резерве»`, …);
    - legacy-ключи до v15 (`pending`, `confirmed`, `ready_to_ship`, `closed`, `cancelled`) — для переходного периода.
- Неизвестные значения игнорируются с записью `Log::warning`, статус возврата при этом не меняется.
- **(v15.8.0)** Опциональное поле `organization` — **справочное**. Клиент оформляет возврат по реализациям, а организация реализации сайту известна, поэтому сайт выводит её сам; значение от 1С приоритетнее, если пришло. Если возврат опирается на реализации **разных** организаций, сайт оставляет поле пустым и документ не дробит: раскладывать возврат по основаниям — задача 1С. В `return.created` (Сайт → 1С) организация **не передаётся**. Подробности — [Организации](organizations.md).

## return.deleted (1С → Сайт)

### Бизнес-правила

- Заявка помечается soft-delete (`returns.deleted_at` = `NOW()`). Физическая запись сохраняется для аудита.
- Статус заявки явно не переписывается — её последнее зафиксированное состояние остаётся в БД и доступно в админке через фильтр «Удалённые».

## Критерии приёмки

- [ ] Сайт публикует `return.created` после успешного оформления возврата клиентом — статус заявки `pending_approval` (v15)
- [ ] Сайт принимает `return.updated` со всеми 6 каноническими ключами enum (v15)
- [ ] `return.updated` распознаёт русские названия 1С (например `«В резерве»`) и legacy-ключи (`confirmed` → `in_reserve`) через `ReturnStatusMapper` (v15)
- [ ] `return.deleted` делает soft-delete без потери последнего зафиксированного статуса
- [ ] Каждая позиция содержит `shipment_uuid`, `shipment_number`, `price`, `currency_code` (v12.13, v12.12)
- [ ] Корневое `order_uuid` не передаётся (v12.13 BREAKING)
