# 01. Доменная модель

## Назначение

Перевод терминов Положения в сущности информационной системы: что уже существует и переиспользуется,
что заводится заново, как хранится и в каком объёме.

## Область

Входит: глоссарий, состав новых таблиц с эскизами структуры, правила хранения и заморозки, объёмы.
Не входит: формулы (раздел 02), происхождение исходных величин (раздел 03), экраны (разделы 05–06).

## Основания

Положение — разделы 2, 5, 7, 8, 11; действующий домен `sal-00`
(`app/Services/Payroll/**`, миграции `database/migrations/2026_08_30_*`);
объёмы — [приложение «Профиль данных»](prilozhenie-profil-dannyh.md).

## 3. Что меняется в домене `payroll`

1. **Новый компонент-контейнер `VariablePartComponent`.** Владеет П1, П2, П3 и К1, знает порядок их
   применения, потолок переменной части и правило неотрицательности — на **сумме**, а не на отдельном
   слагаемом (п. 6.6). Устроен так же, как действующий `KpiBonusComponent` владеет тремя факторами:
   семантика формулы остаётся в классе, схема остаётся таблицей параметров.
2. **`PayrollCalculator` не изменяется.** Он по-прежнему складывает только компоненты вида
   `ComponentKind::AMOUNT`; вся внутренняя механика переменной части скрыта в контейнере.
3. **Схема v2** — новая строка в `payroll_schemes` с датой начала действия. Значения по умолчанию
   в `config/payroll.php` не трогаются: на них опирается контрольный тест действующей формулы.
   `KpiBonusComponent` остаётся в каталоге компонентов и в схеме v2 выключен.
4. **Новые компоненты** переменной части: `BaseSalesComponent` (П1), `NewPartnersComponent` (П2),
   `FocusProductsComponent` (П3), `OverdueDebtFactor` (К1), `TransitionGuaranteeComponent` (п. 12.3).
5. **Расширение `PayrollInputs`** новыми величинами (отгрузки новых партнёров, отгрузки фокус-позиций,
   база начисления К1, состав фокус-перечня на период). Существующий контракт допускает отсутствующие
   ключи, поэтому ранее сохранённые снимки продолжают читаться.

## 4. Новые сущности

Общие правила: все таблицы и колонки снабжаются комментариями на русском; префикс `motivation_`
исключается из выдачи BI-агенту; денежные величины — `decimal(15,2)`, доли — `decimal(8,5)`.

### 4.1. `motivation_parameter_orders` — переменные Положения

Приказ, вводящий значения Приложения № 1 с определённой даты. Ранее изданные приказы не правятся:
расчёт за прошлый период читается по приказу, действовавшему в том периоде.

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `effective_from` | date | первый расчётный период действия (всегда первое число месяца) |
| `order_number` | varchar(64), null | номер приказа |
| `order_date` | date, null | дата приказа |
| `values` | json | значения всех параметров: ставки, пороги, ступени, сроки, сезонные коэффициенты |
| `comment` | varchar(500), null | основание изменения |
| `author_id` | bigint → users | кто ввёл |
| `created_at` / `updated_at` | timestamp | |

Уникальность по `effective_from`. Действующий набор — приказ с максимальной датой, не превышающей
расчётный период. Объём: одна стартовая запись, далее одна–четыре в год.

Хранение значений одним JSON, а не строками «параметр — значение», выбрано осознанно: набор
параметров меняется целиком приказом, и версия должна быть атомарной; отдельные строки допускали бы
полуприменённое состояние.

Объём: единицы правил. Одно правило `brand → Pecado` покрывает 277 товаров.

### 4.3. `motivation_focus_snapshot_items` — состав перечня на период

Развёрнутый состав перечня на конкретный расчётный период. Нужен, чтобы расчёт прошлого месяца
воспроизводился после любых изменений правил.

| Колонка | Тип | Назначение |
|---|---|---|
| `period_month` | date | расчётный период |
| `product_id` | bigint → products | позиция |
| `rule_id` | bigint → motivation_focus_rules | по какому правилу попала |
| `rate` | decimal(8,5) | действовавшая ставка |
| `created_at` | timestamp | |

Уникальность по паре `period_month` + `product_id`. Объём: около 1 000 строк в год при нынешнем
перечне (83 позиции в месяц), в предельном случае — 7 240 позиций × 12 месяцев.

### 4.4. `motivation_partner_novelty` — новизна партнёра

Кэш, отвечающий на вопрос «является ли партнёр новым и до какого периода». Пересчитывается заданием,
но в снимок расчёта попадает зафиксированным.

| Колонка | Тип | Назначение |
|---|---|---|
| `user_id` | bigint → users | партнёр, первичный ключ |
| `first_shipment_on` | date, null | первая отгрузка в доступной истории |
| `last_shipment_before_gap_on` | date, null | последняя отгрузка перед перерывом |
| `gap_days` | int, null | длительность перерыва в днях |
| `novelty_started_on` | date, null | начало Периода новизны |
| `novelty_ends_on` | date, null | конец Периода новизны |
| `source` | varchar(20), null | откуда пришёл: `pool`, `own`, `unknown` |
| `history_incomplete` | boolean | признак, что перерыв не может быть подтверждён из-за глубины истории |
| `computed_at` | timestamp | |

**Принятое определение** (решение заказчика от 08.09.2026): норма в двенадцать месяцев применяется
к доступной истории, отсутствие партнёра в истории отгрузок приравнивается к отсутствию закупок.
Партнёр без единой отгрузки при первой покупке признаётся Новым. Круг потенциально Новых
партнёров — 722: 108 закреплённых, ни разу не покупавших, и 614 в общем списке.

Флаг `history_incomplete` остаётся: партнёр с первой отгрузкой в первом месяце выгрузки неотличим
от партнёра с многолетней историей. На начисление он не влияет, но экран обязан различать
«новый» и «выглядит новым, но проверить нельзя».

Объём: одна строка на партнёра, 742 сейчас.

### 4.5. `motivation_partner_assignments` — история закрепления

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `user_id` | bigint → users | партнёр |
| `personal_manager_id` | bigint → personal_managers, null | за кем закреплён; null — Пул |
| `starts_on` | date | дата записи в реестре |
| `ends_on` | date, null | до какой даты действовало |
| `reason` | varchar(20) | основание: `initial`, `pool_package`, `transfer`, `return_to_pool`, `absence` |
| `plan_delta` | decimal(15,2), null | изменение Личного плана по п. 5.5 |
| `comment` | varchar(500), null | |
| `author_id` | bigint → users, null | |
| `created_at` / `updated_at` | timestamp | |

Заводится бэкфиллом текущего состояния (742 записи), далее пополняется при каждом изменении.
`users.personal_manager_id` остаётся действующим значением — реестр не подменяет его, а хранит историю.

**Атрибуция при передаче** (решение заказчика от 08.09.2026): весь месяц, в котором внесена запись,
партнёр учитывается за прежним работником; переход действует с первого числа следующего расчётного
периода. Отгрузки внутри месяца не дробятся — это делает снимок расчёта воспроизводимым.

### 4.6. `motivation_pool_packages` и `motivation_pool_package_items`

Пакет партнёров, переданных работнику из Пула (п. 8.2–8.4).

`motivation_pool_packages`: `id`, `personal_manager_id`, `issued_on`, `issued_by`, `comment`,
`contact_due_on` (срок фиксации первого контакта), `shipment_due_on` (срок первой отгрузки),
`status` (`active`, `closed`, `blocked_by_tap` — не выдан по правилу крана), timestamps.

`motivation_pool_package_items`: `package_id`, `user_id`, `first_contact_at`, `first_shipment_at`,
`returned_to_pool_at`, `outcome` (`in_progress`, `converted`, `returned`).

Объём: до двадцати строк на пакет, один–три пакета в месяц.

### 4.7. Квартал: `motivation_quarterly_bonuses` и `motivation_quarterly_qualifications`

Квартальная премия начисляется на отдел и, согласно пп. 3.4 и 7.6, не влияет на месячный доход
работника. Поэтому она живёт отдельными таблицами, а не внутри месячного снимка.

`motivation_quarterly_bonuses`: `id`, `quarter_start` (первое число первого месяца квартала, unique),
`qualified_count`, `step_reached`, `amount`, `status` (`draft`, `approved`, `paid`), `snapshot` (json —
состав квалифицированных партнёров и параметры на момент расчёта), `approved_by` / `approved_at`,
`paid_by` / `paid_at`, timestamps.

`motivation_quarterly_qualifications`: `quarter_start`, `user_id`, `personal_manager_id`,
`shipments_amount`, `returns_amount`, `qualified` (boolean), `computed_at`; уникальность по паре
`quarter_start` + `user_id`.

`motivation_quarterly_shares` — распределение премии по работникам (решение заказчика от 08.09.2026,
пункт 7.5): `bonus_id`, `personal_manager_id`, `amount`, `reason`, `author_id`, timestamps.
Сумма долей обязана равняться сумме премии; распределение возможно только после утверждения итога
квартала и попадает в расчётный лист работника отдельной строкой за последний месяц квартала.

Зачёт проверяется по каждому партнёру отдельно (п. 7.3); хранение построчно делает это проверяемым
и исключает деление совокупного объёма на количество.

Объём: четыре записи премии в год, от пяти до тридцати строк квалификации в квартал.

### 4.9. `motivation_debt_exclusions` — исключения задолженности из базы начисления

Заведена по решению заказчика от 08.09.2026: старая задолженность расчищается до введения системы —
безнадёжная списывается, по остальной ведётся претензионная работа. И то, и другое должно
исключать долг из базы начисления К1, иначе показатель продолжает начисляться на задолженность,
которой работник уже не занимается.

Признака такого рода в данных нет: система различает только «оплачено» и «не оплачено».

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | bigint | первичный ключ |
| `shipment_id` | bigint → shipments, null | документ отгрузки; null — исключение по партнёру целиком |
| `user_id` | bigint → users | партнёр |
| `reason` | varchar(20) | основание: `written_off` — списан безнадёжным, `legal` — передан в претензионную работу, `disputed` — оспаривается партнёром, `other` |
| `excluded_from` | date | с какого дня долг не участвует в начислении |
| `excluded_until` | date, null | до какого дня; null — бессрочно |
| `amount` | decimal(15,2), null | сумма, если исключается часть долга |
| `document_ref` | varchar(255), null | ссылка на основание: приказ о списании, номер претензии |
| `comment` | varchar(500), null | |
| `author_id` | bigint → users | кто исключил |
| `created_at` / `updated_at` | timestamp | |

**Правила.** Исключение действует с указанной даты и не меняет уже утверждённые расчёты.
Возврат долга в базу начисления (партнёр признал долг, платёж пошёл) оформляется закрытием
исключения датой, а не удалением записи: история должна сохраняться.

Право на исключение — только у руководителя. Работник видит исключённые долги на своём экране
отдельным разделом с указанием основания: он должен понимать, почему по этому долгу вычет
прекратился, и не считать это ошибкой.

**Объём.** Стартовая расчистка — 53 накладные у 11 партнёров на 1 524 тыс ₽ (42 у шести партнёров
на 1 464 тыс ₽ и 11 у пяти на 60 тыс ₽). Далее — единицы записей в месяц.

## 5. Заморозка и воспроизводимость

Снимок расчёта обязан воспроизводиться спустя год. Для этого в `payroll_calculations.inputs`
дополнительно фиксируются: действовавший приказ параметров, состав фокус-перечня периода,
статус новизны каждого партнёра, состав закреплённой базы и база начисления К1 по документам.

Изменение приказа, правила фокус-перечня или закрепления партнёра **не пересчитывает** утверждённые
периоды. Черновик текущего периода пересчитывается, как и сейчас, по событию с задержкой.
