# Roadmap инициативы «Прокачка CRM»

Документ описывает **порядок** реализации, **состав** волн и **стратегию безопасной доставки**
инициативы по превращению `/crm/` из read-only витрины в рабочее место отдела продаж
с гейтом для ИИ-агентов менеджеров.

Содержательные требования не дублируются — они в карточках задач.

## Суть в одном абзаце

Сегодня `/crm/` показывает клиентов, команду и отчёт продаж — и ничего не позволяет **делать**.
Инициатива добавляет то, чем менеджер живёт: профиль клиента, управляемый жизненный статус,
планы продаж с выполнением и burndown, «грядки» как визуальный пульт, сквозные комментарии,
задачи, почту с журналом. Поверх всего — REST `/api/crm/*` и MCP `/mcp/crm`, через которые
те же операции делает ИИ-агент менеджера, не заходя в интерфейс.

## Принципы безопасной доставки

1. **Никаких вторых движков расчёта.** Факт продаж, разрезы, ABC/XYZ и gap-анализ уже посчитаны
   в `app/Services/Analytics/*`. Планы, «грядки» и «возможности» строятся **поверх**
   `ShipmentAnalyticsService` через `AnalyticsContext::forScope()`. Расхождение цифр между
   `/crm/analytics` и `/crm/plans` — баг по определению.
2. **Границы владения данными.** `users` — зона 1С (`HandlePartnerCreated/Updated` пишут туда).
   Все CRM-поля живут в своих таблицах `crm_*`. Статус лояльности `users.client_status_id`
   в CRM **только читается**.
3. **Шина данных не затрагивается.** Ни одного нового события AsyncAPI/RabbitMQ во всей
   инициативе — правило обязательных ERP-интеграционных тестов здесь не применяется.
4. **Один PR — одна карточка** (или один её этап). Волны не смешиваются в одном PR.
5. **Миграции только новые**, с комментариями к таблице и каждому столбцу (правило проекта).
   FK-колонкам комментарий ставится отдельным `->change()` — см. миграцию `analytics_tokens`.
6. **`bi:sync-grants` после каждой миграции с новой таблицей**, иначе аналитический MCP-агент
   менеджеров новых таблиц не увидит.
7. **Права — только префикс `crm-`** и действия `view|create|edit|delete`:
   `RoleController::buildPermissionTree()` и `PermissionMatrix.jsx` хардкодят этот набор,
   кастомное действие молча выпало бы из UI ролей.
8. **Фича-флаги там, где меняется внешнее поведение**: отправка почты
   (`MAIL_FEATURE_CRM_OUTBOUND`), уведомления по задачам (`MAIL_FEATURE_CRM_TASKS`).
   Дефолт на prod — `false`, как у всех почтовых фич проекта.
9. **Раскатка**: push в `dev` → CI/CD → визуальная проверка на `https://dev.pecado.ru` →
   `git push origin dev:main` на prod.
10. **План отката**: код без флага — `git revert` + redeploy; фичи с флагом — `.env=false`
    + `config:clear` (мгновенно, без revert). Таблицы аддитивны, откат миграций не требуется.

## Волна 1 — Фундамент

**Цель:** два сквозных примитива, на которых стоят волны 2, 3 и частично 5. Без них
комментарии и вложения пришлось бы городить отдельно в каждой сущности.

| Карточка | Что делается |
|---|---|
| `crm-01-comments` | Полиморфные комментарии + сквозная лента клиента (`ClientTimelineService`) |
| `crm-02-attachments` | Вложения через существующую MediaLibrary, коллекция `crm-attachments` |

**Два решения волны, определяющих всё дальнейшее:**

1. **`CrmEntityMap`** — одна карта привязываемых сущностей на комментарии, вложения и задачи.
   Все три полиморфны одинаково; новая сущность добавляется одной строкой, а не тремя правками.
2. **Денормализованный `client_user_id`** во всех «ленточных» таблицах. Требование «в карточке
   клиента видны все комментарии, где бы их ни оставили» становится одним индексированным
   запросом вместо обхода заказов и реализаций. Записи, не сводящиеся к клиенту, живут при
   своей сущности с `null`.

**Стратегия:** чисто аддитивно, без флагов. Существующие страницы получают врезки-компоненты,
ничего не переписывается.

## Волна 2 — Карточка клиента

**Цель:** менеджеру есть что записать о клиенте и чем управлять.

| Карточка | Что делается |
|---|---|
| `crm-03-client-profile` | `crm_client_profiles`: структурированные поля + Markdown-заметки с историей версий |
| `crm-04-lifecycle` | Жизненный статус (лид → в работе → активен → спящий → закрылся), журнал смен, лояльность из 1С read-only |

**Зависимости:** `crm-03` независима; `crm-04` кладёт колонку в таблицу из `crm-03`.

**Грабля, зафиксированная заранее:** статус лояльности перезаписывается обработчиком
`HandlePartnerUpdated` при каждом `partner.updated`. Всё, что менеджер выставил бы там руками,
затёрлось бы следующим сообщением из 1С — поэтому управляемым делается отдельное поле сайта.

## Волна 3 — Работа менеджера

**Цель:** задачи и переписка перестают жить в мессенджерах.

| Карточка | Что делается |
|---|---|
| `crm-09-tasks` | Задачи себе и коллегам: дедлайны, исполнитель, полиморфная привязка, отдельный раздел с полным списком |
| `crm-14-proactive-coverage` | Закрытие задачи с отчётом и следующим шагом; клиенты без задач видны менеджеру |
| `crm-10-email` | Отправка HTML-писем из CRM с вложениями + журнал отправок |

**Зависимости:** обе требуют волну 1 (комментарии и вложения).

**Стратегия доставки почты:** `MAIL_FEATURE_CRM_OUTBOUND=false` до тех пор, пока на dev
не проверен весь путь через Mailpit. `From` — ящик отдела, `Reply-To` — менеджер:
это не требует хранить пароли личных ящиков и работает на текущем SMTP сразу.

## Волна 4 — Планы и аналитика (идёт параллельно волнам 1–3)

**Цель:** видно, кто сколько должен продать, сколько продал и кому продавать дальше.

| Карточка | Что делается |
|---|---|
| `crm-05-plans` | `crm_sales_plans`: план на месяц по клиенту / менеджеру / отделу |
| `crm-06-plan-analytics` | Выполнение, прогноз, burndown, разрез по менеджерам |
| `crm-07-opportunities` | «Кому продать»: ранжирование поверх `GapAnalysisService` |
| `crm-08-beds` | «Грядки» — treemap плана с провалом в аналитику клиента |

**Зависимости:** строго последовательно `05 → 06 → 07 → 08`. От волн 1–3 не зависит,
кроме кнопок «поставить задачу» / «написать письмо» в `crm-07` — они добавляются последними
и только если волна 3 уже готова.

**Факт продаж** во всей волне — отгрузки в ₽ по бизнес-дате `erp_created_at`
(`AnalyticsContext::forScope($clientIds, DATE_ERP, null)`), ровно как в текущем `/crm/analytics`.

## Волна 6 — Рабочее место менеджера

**Цель:** список клиентов и карточка перестают быть витриной. Менеджер работает
из строки таблицы и из ленты, не переходя между экранами.

| Карточка | Что делается |
|---|---|
| `crm-16-clients-table` | Действия в ячейках (письмо, звонок, задача, стадия), срок ближайшей задачи с просрочкой, план/факт, поиск по задачам и переписке, личные отборы |
| `crm-17-client-feed` | Лента-чат как главная вкладка карточки: composer снизу, заказы и реализации в общей хронологии; компактный блок описания клиента |
| `crm-18-calls` | Журнал звонков с заделом под АТС, звонок в ленте, шлифовка |

**Зависимости:** волны 1–4 целиком (комментарии, вложения, задачи, письма, статусы, планы).
Внутри волны строго `16 → 17 → 18`.

**Три решения, определяющих волну:**

1. **Менеджер остаётся зоной 1С.** Смены менеджера из CRM нет: `HandlePartnerUpdated`
   перезаписывает `personal_manager_id` при каждом `partner.updated`, и любая правка
   в интерфейсе затиралась бы следующим сообщением из шины.
2. **Лента расширяется, а не переписывается.** `ClientTimelineService` получает источники
   (заказы, реализации, звонки) в той же форме записи — существующие потребители ленты
   продолжают работать без правок.
3. **Телефония поэтапно.** Сначала собственный журнал звонков (запись результата,
   следующий шаг), интеграция с АТС — отдельной картой, когда будет выбран провайдер.
   Колонки-задел (`provider`, `external_id`, `recording_url`) заводятся сразу, чтобы
   не мигрировать таблицу второй раз.

## Волна 5 — Гейт для ИИ-агентов

**Цель:** менеджер решает те же задачи через своего ИИ-агента, не открывая CRM.

| Карточка | Что делается |
|---|---|
| `crm-11-agent-api` | `OperationRegistry` + REST `/api/crm/*` + Scramble-документ + discovery `GET /api/crm/me` |
| `crm-12-mcp` | `/mcp/crm` с записью: токен → менеджер, тулы `catalog / describe / call` + ярлыки, аудит |
| `crm-13-tokens-ui` | Выпуск и отзыв агентских токенов (команда + экран) |

**Зависимости:** идёт последней, объём определяется тем, что реализовано к этому моменту.
Внутри волны строго `11 → 12 → 13`.

**Два решения, определяющих волну:**

1. **Токен превращается в менеджера.** `AuthenticateCrmAgent` делает `Auth::setUser($manager)`,
   после чего работают существующие `permission`-middleware, политики и скоуп
   `User::visibleInCrm($actor)`. Агент физически не может больше своего менеджера — и это
   не требует второй копии правил доступа, которая неизбежно разошлась бы с первой.
2. **Реестр операций — один источник для REST, discovery и MCP.** Методов станет много, поэтому
   MCP отдаёт не N тулов, а три (`crm-catalog`, `crm-describe`, `crm-call`) — тот же паттерн
   `list-tables / describe-table / run-query`, к которому агенты менеджеров уже приучены
   на `/mcp/analytics`. Плюс несколько «горячих» ярлыков для частых сценариев.
   Хардкод списка эндпоинтов не повторяем: в `/api/content/me` он уже разошёлся с роутами.
