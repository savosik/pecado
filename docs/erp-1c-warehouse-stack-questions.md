# Вопросы стороне 1С: режим стопки складов (спека v16.5.0)

Контекст: сайт вводит «стопку складов» — приоритетную последовательность складов
региона. По каждому товару клиенту действуют остаток и цена самого верхнего склада
стопки, где товар в наличии; нижние склады — фолбэк по позициям, которых нет выше.
Цель — торговля для отдельных клиентов с отдельных складов по иным ценам
(индивидуальные цены и так приходят в разрезе складов в CSV).

Для 1С меняется одно: заказы таких регионов приходят **уже разбитыми по складам**,
и в `warehouse_uuids` каждого документа ровно один UUID — зафиксированный сайтом
склад. Схема сообщения не меняется (поле остаётся массивом), меняется семантика.
Полное описание: `docs-erp/content/rules/orders.md`, раздел «Фиксация склада сайтом»,
changelog v16.5.0.

Фиксация склада в исходящих сообщениях закрыта переходным флагом
`ERP_STACK_WAREHOUSE_PINNING_ENABLED` (по умолчанию выключен): до ответов на
вопросы 1–3 сообщения уходят в прежнем легаси-формате (перечисление складов
региона, 1С выбирает сама), даже если стопка включена у региона на сайте.
Организация (вопрос 5) закрыта отдельным флагом `ERP_ORGANIZATION_UUID_ENABLED`
(тоже по умолчанию выключен) — независимо от флага складов. Ничего на стороне
1С до включения флагов дорабатывать не нужно, текущий приёмник продолжает
работать без изменений.

## Блокирующие вопросы (этап заказов)

1. **Строгое проведение по указанному складу.** Если `warehouse_uuids` содержит
   один склад — 1С проведёт заказ строго по нему? Сейчас правило «1С выбирает
   первый найденный» формально даёт нужный результат — подтвердите, что оно
   не изменится. Отдельно: фолбэк «если склад не найден — ОсновнойСклад» для
   таких заказов нужно **отключить** (неизвестный UUID — ошибка конфигурации,
   а не повод молча провести с другого склада). Возможно ли?

2. **Нехватка остатка на зафиксированном складе.** Что делает 1С, если к моменту
   обеспечения на указанном складе товара уже нет: отклоняет заказ, ждёт,
   самовольно меняет склад? Если меняет — сайт увидит расхождение по
   `warehouse_uuid` в `order.updated` и запишет предупреждение; нужен ли
   вам встречный алерт/регламент?

3. **Число документов.** Одно оформление на сайте сможет давать больше пяти
   документов (по числу складов стопки с позициями). Есть ли ограничения
   в документообороте/нумерации на вашей стороне?

## Неблокирующие вопросы

4. **Индивидуальные цены.** Бывают ли в выгрузке CSV строки «без склада» или
   «на все склады» (пустой/специальный `warehouse_uuid`)? Сайт начинает читать
   цену строго по складу, выигравшему по остаткам; строки без склада сейчас
   молча пропускаются при загрузке.

5. **Организация в заказе — реализовано на сайте, ждёт подтверждения.**
   Привязка склад → организация уже сделана (`warehouses.organization_id`,
   заводится в админке; UUID организаций у нас на проде уже есть). Готов
   передавать `organization_uuid` опциональным полем в `order.created`
   (Сайт → 1С) — сейчас закрыто переходным флагом
   `ERP_ORGANIZATION_UUID_ENABLED` (по умолчанию выключен), включим только
   после вашего подтверждения. Вопросы:
   - Умеет ли приёмник безопасно игнорировать незнакомое опциональное поле
     в `order.created`, или новое поле в схеме требует доработки на вашей
     стороне до включения?
   - Если поле придёт — учитываете ли вы его при выборе организации, или
     организацию по-прежнему полностью определяет 1С (для нас это ок в любом
     случае — поле задумано как подсказка, не как директива)?
   - Полный список UUID всех наших организаций для сверки справочника на
     сайте (эпик org-11) — можно ли выгрузить?
