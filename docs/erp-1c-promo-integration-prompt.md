# Промт для ИИ-агента на стороне 1С: промо-документы (акции сайта Pecado)

> Файл — **задание исполнителю на стороне 1С**. Скопируйте его целиком в контекст
> ИИ-агента, который дорабатывает конфигурацию. Всё, что ниже, написано для него.
>
> Актуально для версии контракта **15.7.1** (2026-08-01).

---

## Роль и контекст

Ты дорабатываешь конфигурацию **1С:Предприятие 8.3 (КА2)**, обменивающуюся с сайтом
Pecado через **RabbitMQ** (AMQP, JSON-сообщения). На сайте запущен конструктор акций:
движок сам начисляет клиенту подарки, товары по промо-цене и пробники. Эти начисления
приезжают в 1С **отдельными документами заказа**.

Сайт свою часть уже реализовал, покрыл интеграционными тестами и выкатил в бой. Твоя
задача — сторона 1С: корректно **принимать** новые документы, разложить их по нужным
организациям и складам, и корректно **отдавать** данные обратно.

## Что изменилось в контракте

Раньше одно оформление на сайте давало до трёх документов: `order`, `preorder`, `defect`.
Теперь — **до пяти**: добавились `promo` и `promo_sample`.

| `type` | Что это | Накладная клиенту |
|---|---|---|
| `order` | обычный заказ | выписывается |
| `preorder` | предзаказ | выписывается |
| `defect` | уценка/некондиция | выписывается |
| **`promo`** | **подотчётные промо-позиции (подарки, товар по промо-цене)** | **выписывается** |
| **`promo_sample`** | **рекламные образцы: пробники и прочая раздача не под подотчёт** | **НЕ выписывается** |

Каждый документ приходит **отдельным сообщением** `order.created` в очередь
`erp_out.orders` (routing key `order.created`), со своим `uuid` и своим `number`.
Связи «родитель–потомок» между документами одного оформления в payload **нет** — их
объединяет только партнёр, момент времени и (при желании) комментарий.

Позиции промо-документов несут два дополнительных поля:

- `is_promo: true` — позиция выдана акцией, а не куплена клиентом;
- `promo_kind` — `"accountable"` (подотчётная, в накладную) либо `"sample"`
  (рекламный образец, в накладную не идёт).

Оба поля присутствуют **только** в документах `promo` / `promo_sample`. В обычных
заказах их в payload нет вообще (не `false`, не `null` — ключа нет).

## 🔴 Маппинг организаций и складов — целиком на стороне 1С

**Организация в payload не передаётся и передаваться не будет.** Сайт не знает про
организации, это внутреннее понятие 1С. Определяй организацию по `type` документа:

| `type` | Организация | Склад |
|---|---|---|
| `promo` (подотчётные промо-позиции) | **ООО «Пекадо»** | из `warehouse_uuids` заказа; **если склад не указан или не найден — «Москва основной»** |
| `promo_sample` (рекламные образцы) | **«Реклама»** | **«Москва подарки»** — UUID `9da1768a-40d4-11e1-a692-001e6711ed1d` |

Пояснения:

- Для `promo` сайт передаёт в `warehouse_uuids` склады наличия региона клиента — ровно
  те же, что и для обычного заказа. Приоритет за ними; «Москва основной» — fallback,
  который уже действует по общему правилу («если ни один склад из `warehouse_uuids`
  не найден — используется `ОсновнойСклад`»).
- Для `promo_sample` сайт всегда передаёт единственный UUID склада «Москва подарки».
  Организация «Реклама» подставляется 1С безусловно — на сайте она никак не отражена.
- Правило маппинга должно быть **параметризуемым** (константа или регистр сведений,
  а не зашитая в код ссылка): состав организаций и складов может измениться без
  изменения контракта обмена.

### Пример входящего сообщения (Сайт → 1С), `type: "promo"`

```json
{
  "event": "order.created",
  "message_id": "9f1c3b20-...-a1",
  "uuid": "3b6f0f2e-...-77",
  "number": "П-000123-2",
  "status": "pending_approval",
  "type": "promo",
  "partner_uuid": "a41c...-9b",
  "warehouse_uuids": ["8e2b...-01"],
  "currency_code": "RUB",
  "exchange_rate": 1,
  "rate_coefficient": 1,
  "delivery_method": "delivery",
  "comment": "",
  "manager_comment": null,
```

в позициях.

## Требования к приёму (1С получает от сайта)

1. **Распознавать `type` = `promo` и `promo_sample`**, подставлять организацию и склад
   по таблице выше. Отдельный вид документа заводить не нужно, если этого не требует
   учётная политика, — но признак промо должен быть виден менеджеру и складу.

2. **`final_price` авторитетна и не пересчитывается.** Это главное правило. Для
   промо-позиции равенство `final_price = base_price × (1 − discount_percent / 100)`
   **не выполняется**: `final_price` — цена из награды акции, а `discount_percent`
   передаётся только для наглядности в печатной форме. Любой пересчёт суммы через
   `discount_percent` даст расхождение (особенно при цене 0,01 ₽).

3. **Нулевая цена и нулевая сумма документа — норма.** Позиция по `0` (подарок) или
   `0.01` ₽ (учётная копейка) валидна. Документ, все позиции которого по 0 ₽,
   принимается и проводится как обычный: он подтверждает, что именно и в каком
   количестве отгружено по акции. Проверки вида «сумма заказа должна быть > 0» для этих
   типов должны быть отключены.

4. **`promo_sample` не попадает в накладную клиенту.** Товар списывается со склада
   «Москва подарки» по организации «Реклама» как обычный товар, но в отгрузочных
   документах клиента не фигурирует. Уточни у бухгалтерии, каким документом оформляется
   списание по организации «Реклама», и реализуй именно его.

5. **`warehouse_comment` содержит лист отбора** — по строке на позицию:
   `арт. {артикул} — {название} — {N} шт. — по акции «{название акции}»`, с заголовком,
   различающим виды («Промо-позиции — отобрать с обычного склада вместе с заказом:» /
   «Рекламные образцы — отобрать со склада «Москва подарки»:»). Поле пишется в реквизит
   `Доп_КомментарийДляСклада` — **как есть, без обрезки переносов строк**, и
   **обязательно должно попадать в печатную форму отбора**: кладовщик собирает по бумаге,
   в интерфейс сайта он не заходит. Комментарий клиента в этом же поле не затирается —
   лист дописывается ниже через пустую строку. Дедупликация версионируемого журнала
   комментариев — на стороне 1С, как и раньше.

6. **До пяти документов на одно оформление.** Проверь, что ничто в обработке не
   предполагает «один заказ с сайта = одно оформление»: нумерация, уведомления менеджеру,
   автосогласование, контроль дублей по партнёру и времени. Учти, что документы одного
   оформления могут оказаться **в разных организациях** — «ООО Пекадо» и «Реклама».

7. **Идемпотентность по `message_id`** — как и для остальных событий. Повторная доставка
   того же сообщения не должна создавать второй документ и задваивать позиции.

8. **Склад «Москва подарки» должен корректно выгружаться в остатках** (`stock.updated`)
   под UUID `9da1768a-40d4-11e1-a692-001e6711ed1d`. Сайт считает фонд пробников именно по
   остаткам этого склада, поэтому **без корректной передачи остатков по нему акции
   с пробниками не сработают вообще**: движок сочтёт фонд нулевым и не покажет акцию
   клиенту. На сайте склад намеренно не входит ни в один регион, поэтому его остатки не
   попадают в витринное наличие — пробник выдаёт только движок акций.

## Требования к отдаче (1С отправляет на сайт)

1. **`order.updated` / `order.created` (1С → Сайт).** Поле `type` 1С передавать
   **не обязана** — сайт хранит свой тип. Но если передаёшь, значение должно быть из enum
   (`order`, `preorder`, `defect`, `promo`, `promo_sample`) и **соответствовать реальному
   типу документа**; неверный `type` перезапишет тип на сайте. Отсутствие ключа — тип
   на сайте не меняется, это безопасный вариант. Организацию в payload **не добавлять** —
   контракт её не содержит.

2. **Промо-позиция, добавленная менеджером вручную в 1С, — штатный сценарий.** Интерфейса
   выдачи промо на сайте у менеджера нет, поэтому такие позиции заводятся в 1С. При
   отправке `order.updated` такую позицию нужно помечать `is_promo: true` и `promo_kind`
   (`accountable` / `sample`) — сайт сохранит её, не пытаясь сопоставить с правилом акции,
   и не удалит при следующем обновлении. Без этих полей позиция приедет на сайт как
   обычная покупка и исказит отчёты.

3. **Не терять промо-признак при обратной синхронизации.** `order.updated` пересоздаёт
   состав позиций на сайте. Сайт со своей стороны защищён (сохраняет привязку к правилу
   акции), но `is_promo` / `promo_kind` по позициям, которые 1С отдаёт обратно,
   **передавать нужно** — иначе смысл документа теряется.

4. **`shipment.created` (реализация) по промо-заказам приходит на общих основаниях.**
   Обязательны `number` (номер реализации) и `order_uuid` в позициях — сайт по нему
   связывает отгрузку с заказом и понимает, что она промо. Цены позиций реализации могут
   быть `0` / `0.01` — не блокируй выгрузку такой реализации. Реализация по `promo_sample`
   (организация «Реклама») тоже отправляется: физическое движение товара со склада
   «Москва подарки» сайту нужно видеть.

5. **Возвраты.** Промо-позиции возвращаются по общим правилам возвратов (v12.13: возврат
   формируется на основании реализаций, каждая позиция несёт `shipment_uuid`). Отдельного
   контракта нет — убедись, что нулевая цена не ломает формирование возврата.

## Вне задачи (не путать)

Очередь `erp_in.promotions` с событиями `promotion.created` / `promotion.updated` /
`promotion.deleted` — это **другая функциональность** (US-16): маркерные группы товаров
`new` / `bestseller` / `liquidation`, которые сайт показывает бейджами в каталоге.
К конструктору акций и промо-документам она отношения не имеет и в этой задаче
не изменяется.

Скидочные механики самой 1С (соглашения, скидки-наценки) в промо-документах
**не применяются**: индивидуальные цены и скидки к промо-цене не пересчитываются, цена
приходит готовой.

## Чек-лист приёмки

Проверить на тестовом контуре, каждый пункт — с фактическим сообщением в шине:

- [ ] Оформление с подарком: приходят два сообщения `order.created` — `order` и `promo`.
      Оба документа созданы, ни одно сообщение не отклонено валидацией.
- [ ] Документ `promo` создан **по организации ООО «Пекадо»**; склад взят из
      `warehouse_uuids`.
- [ ] Документ `promo` с пустым или ненайденным `warehouse_uuids` встаёт на склад
      **«Москва основной»**, а не отбраковывается.
- [ ] Документ `promo_sample` создан **по организации «Реклама»**, склад
      **«Москва подарки»**, и **не попадает в накладную клиенту**.
- [ ] Документ `promo` с единственной позицией по 0 ₽ проводится; сумма документа 0 —
      ошибок и предупреждений нет.
- [ ] Позиция с `base_price: 500`, `discount_percent: 92`, `final_price: 40` даёт
      в документе цену **ровно 40**, а не пересчитанную от базы.
- [ ] Позиция с `final_price: 0.01` не округляется до 0 и не «исправляется» до базовой цены.
- [ ] `warehouse_comment` с листом отбора виден в печатной форме склада целиком,
      с сохранением переносов строк, и не затирает комментарий клиента.
- [ ] Повторная доставка того же `message_id` не создаёт второй документ.
- [ ] Оформление с наличием + предзаказом + уценкой + промо + образцами даёт пять
      документов, корректных типов и по двум разным организациям.
- [ ] Менеджер добавил промо-позицию вручную → `order.updated` уходит с `is_promo: true`
      и корректным `promo_kind`.
- [ ] `shipment.created` по промо-заказу уходит с `number` и `order_uuid`, позиции
      с нулевой ценой не блокируют выгрузку.
- [ ] Остатки склада «Москва подарки» приходят на сайт в `stock.updated` под UUID
      `9da1768a-40d4-11e1-a692-001e6711ed1d`.

## Вопрос, требующий подтверждения до начала работ

UUID `9da1768a-40d4-11e1-a692-001e6711ed1d` был передан сайту как склад для рекламных
образцов. **Подтверди, что это UUID именно склада «Москва подарки»**, и если нет — сообщи
корректный: сайт хранит его в конфигурации, и без совпадения документы `promo_sample`
в шину не уйдут вообще (сработает защитный гейт — документ создастся на сайте, но
не отправится).
