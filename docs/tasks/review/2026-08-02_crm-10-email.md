# crm-10 · Отправка писем из CRM с вложениями + журнал отправок

**Приоритет:** средний
**Создано:** 2026-08-02
**Эпик:** [crm-00](2026-08-02_crm-00-epic.md)
**Волна:** 3 (работа менеджера)
**Зависимости:** `crm-02` (вложения), желательно `crm-01` (лента)

## Описание

Менеджер и РОП пишут клиенту письмо прямо из CRM: тело в HTML, вложения, отправка через почту
сайта. Каждая отправка логируется — кто, кому, когда, что, чем закончилось.

Сейчас в проекте нет ни одного Mailable-класса (всё на `Notifications`) и нет журнала отправок:
единственный след писем — Telescope, который на проде в `dont-discover`.

## Решение по отправителю

`From` — общий ящик отдела (`MAIL_FROM_ADDRESS`), `Reply-To` — личная почта менеджера.
Ответ клиента приходит менеджеру, при этом не нужно хранить пароли личных ящиков и обрабатывать
сбои SPF/DKIM по каждому из них. Личные SMTP-ящики — сознательно вне скоупа эпика.

## Что делаем

**Миграция `crm_emails`** (комментарии к таблице и всем столбцам):

```php
$table->comment('Журнал писем, отправленных менеджерами из CRM');
$table->id();
$table->foreignId('user_id')->constrained()->cascadeOnDelete();          // автор
$table->foreignId('client_user_id')->nullable()->constrained('users')->nullOnDelete();
$table->nullableMorphs('related');                                       // Order | Shipment | User
$table->json('to')->comment('Получатели: массив адресов');
$table->json('cc')->nullable()->comment('Копия: массив адресов');
$table->string('reply_to')->nullable()->comment('Обратный адрес — личная почта менеджера');
$table->string('subject')->comment('Тема письма');
$table->longText('body_html')->comment('Тело письма в HTML, как его составил менеджер');
$table->string('status', 20)->default('queued')
      ->comment("Статус: 'draft' — черновик, 'queued' — в очереди, 'sent' — отправлено, 'failed' — ошибка");
$table->timestamp('sent_at')->nullable()->comment('Момент фактической отправки через SMTP');
$table->string('message_id')->nullable()->comment('Message-ID из SMTP — для поиска письма в логах почтового сервера');
$table->text('error')->nullable()->comment('Текст ошибки, если отправка не удалась');
$table->timestamps();
$table->index(['client_user_id', 'created_at'], 'crm_emails_client_created_idx');
```

Статус `draft` нужен по технической причине: вложение прикрепляется только к сохранённой
записи (`MediaService::upload()` не умеет загрузку «в никуда»), поэтому форма создаёт черновик
первым шагом, а «Отправить» переводит его в `queued`.

**Модель `App\Models\CrmEmail`** — `HasCrmAttachments` (из `crm-02`), связи `author()`,
`client()`, `related()`.

**Mailable `App\Mail\CrmManagerMail`** — первый Mailable в проекте (всё остальное на
`Notifications`; здесь Notification не подходит — получатель не наш пользователь, а произвольный
адрес, и тело задаёт человек, а не шаблон). Собирает `from` из конфига, `replyTo` из записи,
вложения — из медиа-коллекции.

**Job `SendCrmEmailJob`** — очередь, `tries = 3`. Успех → `status = sent`, `sent_at`.
Провал (`failed()`) → `status = failed` + текст ошибки в `error`. Письмо не должно молча
исчезать: менеджер обязан видеть, что оно не ушло.

**Слушатель на `Illuminate\Mail\Events\MessageSent`** — дописывает `message_id` в запись
(связка через заголовок `X-Crm-Email-Id`, который Mailable проставляет сам).

**Фича-флаг** `config('notifications.mail.features.crm_outbound')` ← `MAIL_FEATURE_CRM_OUTBOUND`,
дефолт `false` — как все почтовые фичи проекта. При выключенном флаге черновики создаются
и сохраняются, кнопка «Отправить» заблокирована с пояснением.

**Роуты** в `routes/crm.php` под `permission:crm-emails.view`:

```
GET    /crm/emails                 — журнал: фильтры по клиенту, автору, статусу, периоду
GET    /crm/emails/{email}         — просмотр отправленного
POST   /crm/emails                 — создать черновик
PATCH  /crm/emails/{email}         — правка черновика
POST   /crm/emails/{email}/send    — отправить
DELETE /crm/emails/{email}         — удалить черновик
```

Отправка на адрес клиента разрешена только если клиент виден в `User::visibleInCrm($actor)`;
для писем без привязки к клиенту — свободный ввод адреса под тем же правом.

**Безопасность HTML.** Тело хранится как есть (его составил доверенный сотрудник, и почтовый
клиент получателя должен получить именно его). Опасность — **не в письме, а в нашем UI**:
при показе черновика и записи журнала HTML прогоняется через `dompurify` (уже в зависимостях)
на фронте. Новый PHP-санитайзер в зависимости не добавляем.

**Шаблоны писем** (`crm_email_templates`: `name`, `subject`, `body_html`, `is_active`) —
заготовки с подстановками `{{client_name}}`, `{{manager_name}}`. Экономят менеджеру время
и делают письма единообразными.

**Фронтенд:**
- `Crm/Pages/Emails/Index.jsx` — журнал со статусами и фильтрами;
- `Crm/Pages/Emails/components/ComposeDialog.jsx` — редактор на `tiptap` (уже в проекте),
  выбор шаблона, получатели, вложения через `AttachmentPanel`, предпросмотр;
- кнопка «Написать письмо» в карточке клиента, в строке заказа и в панели «Возможности»
  (`crm-07`) — открывает диалог с подставленным адресом и привязкой;
- письма в ленте клиента (`ClientTimelineService` расширяется типом `email`).

**Права**: ресурс `crm-emails`, действия `view, create, edit, delete`, метка «CRM: Письма».
Выдать `sales-manager`, `sales-manager-crm`, `sales-head`.

## Границы

- Приём входящей почты и переписка тредами — не делаем. Ответы клиента идут менеджеру в его
  почтовый клиент.
- Массовые рассылки не делаем: это другая механика (отписки, репутация домена, троттлинг).
  Письмо адресуется конкретному клиенту.
- Личные SMTP-ящики менеджеров — вне скоупа (см. эпик).

### Решения, принятые по ходу

**Редактор — `SimpleWysiwyg`, а не tiptap.** В карточке был записан tiptap, но он тянет
за собой связку с ИИ-ассистентом и слэш-меню, которые в письме не нужны. `SimpleWysiwyg`
отдаёт ровно то, чем письмо и является, — HTML, и не утяжеляет бандл CRM.

**Скоуп писем шире скоупа задач.** Задача — поручение конкретному человеку, поэтому её видят
только участники. Письмо клиенту — факт из его истории, поэтому его видит любой, кому виден
клиент. Править и отправлять при этом может только автор: чужое письмо, ушедшее от твоего
имени, — это не совместная работа.

**Отправленное письмо неизменяемо.** Журнал, который можно переписать задним числом,
бесполезен как журнал. Править и удалять можно только черновики и то, что не ушло.

**Правка после сбоя возвращает письмо в черновики.** Иначе оно так и висело бы «с ошибкой»,
хотя причину уже устранили.

**В ленту клиента идут только отправленные письма.** Черновик — ещё не событие в жизни клиента.

**Выключенный флаг — это 422 с текстом, а не 403.** Сотрудник ничего не нарушил, просто
отправка ещё не включена администратором; 403 читался бы как «вам нельзя».

**HTML санитайзится на фронте, а не в PHP.** Получателю тело письма нужно ровно таким, каким
его составил сотрудник, — опасность не в письме, а в показе этого HTML в нашем интерфейсе.
`dompurify` уже в зависимостях, новый PHP-санитайзер не понадобился.
