# crm-04 · Жизненный статус клиента + лояльность из 1С (read-only)

**Приоритет:** высокий
**Создано:** 2026-08-02
**Эпик:** [crm-00](2026-08-02_crm-00-epic.md)
**Волна:** 2 (карточка клиента)
**Зависимости:** `crm-03` (колонка кладётся в `crm_client_profiles`)

## Описание

Дать менеджеру управляемый **жизненный статус** клиента (лид → в работе → активен → спящий →
закрылся) и показать рядом **статус лояльности** (basic/vip/gold), который приходит из 1С.
Каждая смена статуса фиксируется: кто, когда, с чем на что, почему.

## Ключевая находка: лояльностью владеет 1С

`users.client_status_id` (справочник `client_statuses` с `external_id` из 1С) **перезаписывается**
в `App\Services\Erp\Handlers\HandlePartnerUpdated` при каждом сообщении `partner.updated`.
Статус, выставленный менеджером в CRM, был бы затёрт следующим сообщением — молча и без следа.

Поэтому:
- **лояльность в CRM — только чтение**, с явной подписью «источник: 1С»;
- **управляемое — отдельное поле сайта** `lifecycle_status`, о котором 1С не знает.

Отдавать лояльность в 1С через шину — отдельная задача со spec-first порядком (JSON Schema →
AsyncAPI → MkDocs → код) и договорённостью на стороне 1С. В этот эпик не входит.

## Что делаем

**Миграция** — добавляет в `crm_client_profiles` (таблица из `crm-03`):

```php
$table->string('lifecycle_status', 20)->default('active')
      ->comment("Жизненный статус: 'lead' — лид, 'in_work' — в работе, 'active' — активен, 'sleeping' — спящий, 'churned' — закрылся/ушёл");
$table->timestamp('lifecycle_changed_at')->nullable()->comment('Когда статус менялся в последний раз');
$table->foreignId('lifecycle_changed_by')->nullable()->constrained('users')->nullOnDelete();
$table->index('lifecycle_status');
```

**Миграция `crm_client_status_changes`** — журнал смен:

```php
$table->comment('Журнал смен статусов клиента в CRM: кто, когда, с чего на что и почему');
$table->foreignId('client_user_id')->constrained('users')->cascadeOnDelete();
$table->string('field', 30)->comment("Что менялось: 'lifecycle' — жизненный статус (лояльностью владеет 1С)");
$table->string('from_value', 30)->nullable()->comment('Значение до смены; null — статус ставился впервые');
$table->string('to_value', 30)->comment('Значение после смены');
$table->foreignId('user_id')->nullable()->constrained()->nullOnDelete();
$table->string('reason')->nullable()->comment('Причина словами: «не отвечает третий месяц»');
$table->timestamps();
$table->index(['client_user_id', 'created_at']);
```

Колонка `field` заведена сразу, хотя значение пока одно: если лояльность когда-нибудь станет
управляться сайтом, журнал не придётся мигрировать.

**Enum `App\Enums\Crm\ClientLifecycleStatus`** — с русскими метками (`label()`) и цветом бейджа
(`color()`), по образцу существующих `App\Enums\OrderStatus` / `UserStatus`.

Дефолт `active` для существующих клиентов: на проде почти у всех есть менеджер, и объявлять
их всех лидами было бы неверно. Реальную раскладку менеджеры проставят сами, опираясь
на подсказки (ниже).

**Сервис `ClientLifecycleService::change(User $client, ClientLifecycleStatus $to, User $actor, ?string $reason)`** —
пишет профиль + журнал в одной транзакции. Единственная точка смены статуса; ею же пользуется
ИИ-агент из волны 5.

**Команда `crm:lifecycle-hints`** (ежедневно по расписанию) — **не меняет** статусы, а формирует
подсказки: активный клиент без отгрузок 90 дней → «похоже, спящий»; спящий с отгрузкой за
последние 30 дней → «похоже, снова активен». Порог — в `config/crm.php`.

Почему не авто-смена: статус — управленческое решение менеджера («договорились, что он вернётся
в марте»), и молчаливая ночная перезапись этого решения хуже, чем его отсутствие. Подсказка
показывается в карточке и в списке клиентов бейджем «есть предложение», применяется одним кликом.

Давность отгрузок берём по бизнес-дате `shipments.erp_created_at` — по `created_at` вся
историческая база выглядит купленной в мае 2026 (импорт истории 1С при запуске прода).

**Фронтенд:**
- бейдж жизненного статуса в списке клиентов `Crm/Pages/Clients/Index.jsx` + фильтр по нему;
- в карточке — блок «Статусы»: жизненный статус (селект + поле причины), рядом лояльность
  как **read-only** плашка с подписью «из 1С», и раскрывающаяся история смен.

**Права**: действие `edit` на существующем ресурсе `crm-profile` (отдельный ресурс не заводим —
статус живёт в профиле, а ресурсов в матрице ролей и так много).

## Границы

- Лояльность не редактируется и не отправляется в 1С.
- Видимость клиентов не меняется: `User::visibleInCrm()` по-прежнему показывает только тех,
  у кого есть менеджер. Статус `lead` — стадия работы с уже закреплённым клиентом, а не режим
  видимости самозарегистрировавшихся пользователей.
- Автоматической смены статуса нет — только подсказки.

### Решения, принятые по ходу

**Подсказка хранится в профиле, а не считается на лету.** Иначе бейдж «есть предложение» в списке
клиентов означал бы пересчёт давности отгрузок на каждую страницу списка.

**Ночной прогон не трогает профили, у которых предложение не изменилось.** Иначе `updated_at`
переписывался бы всей клиентской базе каждую ночь.

**Смена статуса снимает подсказку.** Её приняли или пошли своим путём — в обоих случаях висеть
бейджем поверх уже принятого решения она не должна.

**Клиент без профиля читается как активный** — и в карточке, и в фильтре списка. Дефолт колонки
и поведение интерфейса совпадают; без этого фильтр «Активен» прятал бы почти всю базу.

**«Никогда не отгружался» подсказку даёт не всегда.** Свежая регистрация — это «ещё не начал»,
а не «уснул»: порог применяется к дате регистрации.

**Отправка из подсказки идёт через `transform()`, а не `setData()`.** `setData` асинхронен,
и кнопка «Применить» уехала бы со старым значением селекта.

**Лояльность из 1С показана рядом read-only с подписью источника**, и убрана из блока «Основная
информация», чтобы не дублироваться. Ручки записи у неё нет вовсе — это закреплено тестом.
