## Описание

Экран, отвечающий на вопрос «почему клиенту ничего не пришло» без обращения к разработчику.
До эпика ответ требовал чтения кода маршрутизации, то есть был предположением, а не фактом.

Ключевая ценность — журнал показывает и **отрицательные** решения: письмо не ушло, потому что
адрес в стоп-листе / сработал троттлинг / не совпало ни одно правило. Существующий `sent_emails`
на такие вопросы не отвечает по построению: он пишется по факту отправки.

## Что делаем

### `Deliveries.jsx` — журнал доставок

Роут `GET /crm/notifications/deliveries` под `permission:crm-notifications.view`,
пункт меню «Журнал уведомлений» в группе «Продажи».

Колонки: дата, событие, партнёр, контрагент, адрес, правило, статус, причина пропуска,
тема письма, ссылка на запись `sent_emails`, ссылка на трассу сигнала.

Фильтры по всему перечисленному плюс период. Скоуп видимости — как в пульте:
без `crm-notifications-all.view` менеджер видит доставки только своих клиентов.

Статусы и причины пропуска показываются по-русски бейджами: «Отправлено», «В очереди»,
«Пропущено: адрес отписан», «Пропущено: слишком часто», «Ошибка отправки».

**Плашка вверху:** «Письма, написанные менеджером вручную, живут в разделе „Письма“»
со ссылкой на `/crm/emails` — иначе менеджер будет искать здесь свою переписку.

### `SignalTrace.jsx` — трасса сигнала

Роут `GET /crm/notifications/signals/{uuid}`. Показывает:

- контекст сигнала: событие, партнёр, контрагент, ссылка на заказ/документ, поля `data`
  человекочитаемой таблицей;
- **все рассмотренные правила** по порядку разбора, с отметкой «совпало» / «не совпало» и
  указанием, какое именно условие не выполнилось;
- где сработал `stop` и какие правила из-за этого не рассматривались;
- итоговых адресатов с указанием правила и отсеянных с причинами.

Это тот самый экран, ради которого заводились `notification_signals`.

### Вкладка «Уведомления» на карточках

На `/crm/partners/{user}` и `/crm/contractors/{company}` — рядом с вкладкой «Контакты»
из `notif-01`:

- правила этой области;
- унаследованные глобальные и системные — серым, с пометкой «глобальное» / «системное»;
- кнопка «Добавить правило» (область подставлена) и «Применить пресет» (заглушка до `notif-11`);
- последние доставки по этому партнёру;
- плашка «Уведомления не настроены» с одной кнопкой, если правил нет.

### Лента партнёра

`app/Services/Crm/ClientTimelineService.php` — доставки пульта попадают в сквозную ленту
карточки. Дешевле обогатить существующий `TYPE_SYSTEM_EMAIL` названием правила, чем заводить
новый тип: запись уже строится из `sent_emails`, а связь `notification_delivery_id` появилась
в `notif-02`. Решение принять при реализации, второй вариант — новый `TYPE_PULSE_DELIVERY`.

### Ретенция

Прецедент свеж: таблицы Pulse занимали 5,8 ГБ из 6,6 ГБ боевой базы и растягивали pre-deploy
бэкап. `notification_signals` пишется на **каждое** событие, поэтому ретенция обязательна.

- `NotificationSignal` — `Prunable`, 30 дней (`PULSE_SIGNAL_RETENTION_DAYS`).
- `NotificationDelivery` — `Prunable`, 365 дней (`PULSE_DELIVERY_RETENTION_DAYS`).
  Дольше, чем `sent_emails` (180): «когда мы перестали слать этому бухгалтеру» спрашивают
  через год, а тела письма журнал не хранит — строка компактная.
- `data` и `view` обрезаются по размеру при записи сигнала.
- `routes/console.php` — добавить модели в существующую строку `model:prune` рядом с `SentEmail`
  (05:10) либо отдельной строкой.
