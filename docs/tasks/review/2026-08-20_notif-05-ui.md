# notif-05 · Пульт в CRM: список правил и конструктор

**Приоритет:** высокий
**Создано:** 2026-08-20
**Эпик:** [notif-00](2026-08-20_notif-00-epic.md)
**Волна:** 1 (ядро и заказы)
**Зависимости:** [notif-03](2026-08-20_notif-03-engine.md)
**Оценка:** ~4 дня

## Описание

Экран, ради которого затевался эпик: РОП и менеджер собирают правила сами, без разработчика.
Раздел `/crm/notifications` — «Пульт уведомлений», рядом с уже существующим «Пультом платежей».

Главный риск карточки — не техника, а понятность. Sieve-логика мощная, но неочевидная:
если менеджер не понимает, почему письмо ушло не туда, он вернётся в мессенджеры. Поэтому
«лестница разбора» и предпросмотр — не украшения, а обязательные пункты.

## Что делаем

### Права — три реестра

| Ресурс | Действия | Метка | Кому |
|---|---|---|---|
| `crm-notifications` | `view, create, edit, delete` | «CRM: Пульт уведомлений» | `sales-manager`, `sales-manager-crm`, `sales-head` |
| `crm-notifications-all` | `view, edit` | «CRM: Все и системные правила уведомлений» | только `sales-head` |

Обязательны все три места, иначе валится `tests/Feature/Crm/PermissionNamingTest.php`:

1. `database/seeders/RolesAndPermissionsSeeder.php` — `$resources` (CRM-блок), `$resourceLabels`,
   раздача ролям в match-блоках.
2. `app/Http/Controllers/Admin/RoleController.php` — `$permissionGroups['CRM']`, `$resourceLabels`.
3. `resources/js/Crm/config/menuConfig.ts` — группа «Продажи», после «Письма»:
   `{ label: "Пульт уведомлений", icon: LuBellRing, path: "/crm/notifications", permission: "crm-notifications.view" }`.

Плюс миграция выдачи прав на прод по образцу
`database/migrations/2026_08_10_110000_grant_crm_contractor_permissions.php`.

**Скоуп видимости.** Без `crm-notifications-all.view` менеджер видит и правит только правила,
чья область — его клиент или контрагент его клиента (через `User::scopeVisibleInCrm($actor)`),
а глобальные и системные видит в режиме чтения. Глобальное правило может создать только
держатель `crm-notifications-all.edit` — иначе один менеджер разошлёт письма по всей базе.

### Роуты (`routes/crm.php`)

```

POST   /crm/notifications/{rule}/toggle
POST   /crm/notifications/{rule}/duplicate
POST   /crm/notifications/{rule}/override     переопределить системное
POST   /crm/notifications/reorder             drag-n-drop приоритетов
POST   /crm/notifications/preview             «кто получит» — dry-run без сохранения
POST   /crm/notifications/{rule}/test-send    тестовое письмо ТОЛЬКО на адрес актора
```

Чужое правило → **404, не 403**.

### `Index.jsx` — список с лестницей разбора

Правила сгруппированы по событию, внутри группы отсортированы по приоритету, с визуальной
«лестницей»: видно, где сработает `stop` и какие правила ниже он отрежет.

```
Смена статуса заказа
  50   ▸ Закрытие → директору Залупкину            [СТОП] ──┐
  100  ▸ Любой статус → email клиента              ⌐ отрезано при status=closed
  500  ▸ [системное] Статусы 1С → клиенту          ⌐ отрезано при status=closed
```

Фильтры: домен, событие, область, статус, «только системные». Строка правила: название, область
(клиент/контрагент со ссылкой на карточку), условия человеческим текстом, чипсы получателей,
тумблер, счётчик срабатываний, дата последнего.

Правило с 0 совпадений за 60 дней помечается «мёртвое». Правила, заведённые клиентом из кабинета
(после `notif-09`), — с бейджем «Завёл клиент», доступен только тумблер.

### Два сценария настройки — политика и исключение

Это главное решение по интерфейсу. Поштучная настройка 800 клиентов × 6 событий = 4800 правил
означала бы, что менеджер вернётся в мессенджеры на второй день.

**Основной сценарий — правило-политика.** Одно правило на всю базу, получатель задан ролью,
а не человеком:

> Просрочка больше 30 дней → **бухгалтеру этого контрагента**

Система сама подставит нужного бухгалтера для каждого клиента. Таких правил нужно 5–8 штук
на весь отдел, заводит их РОП один раз. Ни одного персонального правила при этом не создаётся.

**Второй сценарий — исключение.** «Пупкину закрытие заказа шлём директору, он так попросил».
Заводится кнопкой с карточки контрагента, область подставлена. Таких единицы, а не сотни.

Список правил разделён на две вкладки — «Политика отдела» и «Исключения», — чтобы разница
была видна с первого экрана и никто не начал настраивать поштучно.

### `Form.jsx` — конструктор в шесть шагов

1. **Событие** — выпадающий список, **сгруппированный по смыслу** (Заказы / Документы /
   Оплаты), с русскими названиями из `label()` и подсказкой из `description()`.
   Никаких технических ключей: менеджер видит «Просрочка выросла», а не `finance.overdue_grew`.
2. **Область** — «Все партнёры» / «Партнёр…» / «Контрагент…» / «Клиенты менеджера…».
   Открыто с карточки — подставлено автоматически. «Все партнёры» доступно только
   под `crm-notifications-all.edit`.
3. **Условия** — строки «поле → оператор → значение», контрол значения зависит от типа поля
   (селект для enum со списком из самого enum'а, число, диапазон дат, мультиселект).
   Группы И/ИЛИ. Внизу живой пересказ: «Если статус = Закрыт и сумма ≥ 100 000 ₽».

   Значения **всегда выбираются из подсказки, не набираются руками** — опечатка в ИНН или
   статусе иначе даст молчаливо не работающее правило, которое никто не найдёт.

   Метки из `notif-02` менеджеру как метки **не показываются**: их полторы тысячи (по одной
   на контрагента), и список был бы свалкой. «Про кого» задаётся шагом 2, «про что» — шагом 1
   и условиями. Режим, где условия видны как есть, доступен только под
   `crm-notifications-all.view` — для разбора «почему сработало».
4. **Получатели** — чипсы с автодополнением из адресной книги контрагента (ФИО, роль, email),
   плюс «Клиент (email аккаунта)», «Персональный менеджер», «Все бухгалтеры контрагента»,
   «Произвольный адрес», «Резервный список из настроек». Флаги «только если некому больше»
   и «копия / скрытая копия». Если у контрагента нет контакта нужной роли — плашка
   «Добавить контакт» прямо в форме, без ухода со страницы.
5. **Порядок и остановка** — приоритет и тумблер «Не обрабатывать следующие правила»
   с предупреждением перед сохранением: **«Это правило остановит N правил ниже: …»** со списком.
6. **Предпросмотр** — «Кто получит»: движок в dry-run прогоняет 5 последних реальных сигналов
   этого типа из `notification_signals` по этой области и показывает таблицу
   «событие → адресаты → по какому правилу». Плюс кнопка «Отправить тест себе».

### Валидация

`StoreNotificationRuleRequest` / `UpdateNotificationRuleRequest` — переиспользуют
`ConditionValidator` из `notif-02`. Все сообщения на русском.

Отдельные правила валидации:
- `kind=contact` в глобальном правиле запрещён — контакт конкретного контрагента бессмыслен
  в правиле «для всех партнёров»;
- `kind=config_list` принимает только ключи из белого списка;
- у правила должен быть хотя бы один получатель, не считая `suppress`.

## Проверка на живом менеджере — до вёрстки

Три экрана (правило-политика, правило с карточки, журнал) собираются эскизами и показываются
Сухову или Курочкиной **до** реализации. Полчаса разговора покажут, где путаница, а переделать
картинку стоит ничего. Результат — короткая запись в комментарии к карточке: что поправили.

Это не формальность: Sieve-логика мощная, но неочевидная, и если менеджер не понимает,
почему письмо ушло не туда, он вернётся в мессенджеры — ровно как случилось с клиентской
подпиской, которой никто не воспользовался.
