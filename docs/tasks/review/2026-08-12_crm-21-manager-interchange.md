# crm-21 · Взаимозаменяемость менеджеров: право отдела и галочка «только мои»

**Приоритет:** высокий
**Создано:** 2026-08-12
**Эпик:** [crm-00](../backlog/2026-08-02_crm-00-epic.md)
**Волна:** 7 (взаимозаменяемость и охват), этап 1 — фундамент волны
**Зависимости:** нет; блокирует `crm-22`, `crm-23`, `crm-24`, `crm-26`

## Описание

Организационное изменение: менеджеры должны стать **взаимозаменяемыми** — видеть и вести не
только своих клиентов, но и чужих, видеть чужие задачи и помогать их выполнять.

Текущая модель это прямо запрещает. `User::scopeVisibleInCrm()`
([app/Models/User.php:721](../../../app/Models/User.php#L721)) режет менеджера до
`personal_manager_id = его карточка`, весь отдел видит только РОП по праву `crm-clients-all.view`.
Чужой партнёр отдаёт **404, а не 403** — по всей CRM принято соглашение «чужой записи для тебя
не существует».

Просто снять ограничение нельзя: если вывалить менеджеру весь скоуп, он утонет в чужих задачах,
клиентах и планах. Поэтому расширение видимости идёт **в комплекте с фокусировкой** — глобальной
галочкой «только мои», включённой по умолчанию и запоминающейся отдельно по каждому разделу.

## Главная проблема: право `crm-clients-all.view` склеивает четыре полномочия

Выдать его менеджерам «как есть» **нельзя**. Проверено по всем использованиям — вместе
с «вижу отдел» приедет вот это:

| Что откроется | Где | Оценка |
|---|---|---|
| **План отдела и планы других менеджеров становятся редактируемыми любым менеджером** | `SalesPlanService::canManage()` ([:81](../../../app/Services/Crm/SalesPlanService.php#L81)) | недопустимо: общая цель портится без аудита |
| Выручка по менеджерам: `/crm/plans/by-manager`, блок `by_manager` в аналитике и в её экспорте, фильтр по менеджерам в финансах | [routes/crm.php:292](../../../routes/crm.php#L292), `AnalyticsController:490,570`, `FinanceController:552,554` | не входит в задачу «взаимозаменяемость» |
| **Удаление любого чужого вложения**, без отката | `AttachmentController` [:110](../../../app/Http/Controllers/Crm/AttachmentController.php#L110), `:164` | деструктивно; сейчас защищено тестами |
| **Чужие черновики писем**, включая письма на свободные адреса | `CrmEmailService::visibleTo()` ([:38](../../../app/Services/Crm/CrmEmailService.php#L38)) — возвращает `$query` без ограничений | побочное |
| Все звонки коллег, включая беспривязочные | `CrmCallService::visibleTo()` ([:38](../../../app/Services/Crm/CrmCallService.php#L38)) | побочное |
| **Вообще все компании базы** — не «юрлица отдела», а включая юрлица лидов и сотрудников | `Company::scopeVisibleInCrm()` ([:218](../../../app/Models/Company.php#L218)) | переширено |
| Токен ИИ-агента менеджера получает `sees_all: true` | `CrmApiController:61,67` | ломает инвариант `CrmAgentToken`: «агент физически не может больше своего менеджера» |
| Импорт листа продаж по всему отделу через агента | `CrmImportSalesSheet:102` | побочное |
| Правка/удаление чужих комментариев, звонков, писем | `CrmCommentPolicy:57`, `CrmCallPolicy:61`, `CrmEmailPolicy:74` | правка — желаемое, **удаление — нет** |
| Вход в личный кабинет **любого партнёра отдела** | `ImpersonationController:37` резолвит через `visibleInCrm` | **решено 2026-08-12: принимаем**, см. ниже |

**Ловушка в сидере:** ресурс, указанный роли без сужения (`'crm-clients-all'`), выдаёт **все**
объявленные действия — и `view`, и `edit`. `crm-clients-all.edit` управляет сменой типа аккаунта
([routes/crm.php:147](../../../routes/crm.php#L147)). Указывать только нужные действия явно.

## Решение: расщепить право на три уровня

| Право | Смысл | Кому |
|---|---|---|
| `crm-department.view` | вижу записи всего отдела (чтение) | менеджеры |
| `crm-department.edit` | действую с чужими записями | менеджеры, отдельным этапом |
| `crm-clients-all.view` | разрез по менеджерам, чужая выручка, план отдела | **остаётся только РОПу** |

Граница между первым и третьим: «вижу карточку партнёра коллеги» и «вижу, сколько коллега
продал» — качественно разные вещи, и вторая в запрос не входила.

**Соответствие правилам проекта** (проверено): префикс `crm-` = `User::CRM_PERMISSION_PREFIX`
([app/Models/User.php:153](../../../app/Models/User.php#L153)); действия только
`view|create|edit|delete` — жёстко зашито в `RoleController:182`, кастомное молча выпало бы
из UI ролей. Новый ресурс обязан появиться **в трёх местах**, иначе падает `PermissionNamingTest`:
`RolesAndPermissionsSeeder::$resources`, `RoleController::$permissionGroups['CRM']`,
`RoleController::$resourceLabels`.

Отвергнуто: флаг или JSON-колонка на `users` — выпадает из матрицы ролей, невидим при аудите,
дублирует spatie.

## Галочка «только мои»

**Источник истины — сервер.** Параметр `scope=mine|department`, **отсутствие параметра = `mine`**.
Иначе любой запрос без параметра — curl, старая закладка, экспорт, ИИ-агент — отдаёт весь отдел.
`scope=department` без права `crm-department.view` молча схлопывается в `mine` — тот же приём,
которым уже гасится `managerId` в
[ClientListFilters](../../../app/Support/Crm/ClientListFilters.php) и чужой `scope_id`
в `PlanScopeResolver:40`.

**Три слоя:**

1. **Сервер** — поле `scope` в `ClientListFilters` + маленький общий `App\Support\Crm\CrmScope`
   для остальных разделов.
2. **URL** — Inertia-визит несёт `?scope=department`: ссылка шарится, «назад» работает,
   значение видно в тестах.
3. **Клиент** — `localStorage['crm.scope.<section>']`, читается при монтировании; при расхождении
   с URL — `router.reload`. Прецедент такого хранения в проекте уже есть:
   [Analytics/Index.jsx](../../../resources/js/Crm/Pages/Analytics/Index.jsx).

**Почему не таблица настроек:** один бит на раздел, меняется десятки раз в день, кросс-девайсной
и аудитной ценности нет. Таблица = миграция + контроллер + запись в БД на каждый клик.

**Почему не пресеты:** `CrmClientFilterPreset` — именованный явный снимок, который пользователь
создаёт сам; галочка — неявный липкий дефолт, другая природа. Но `scope` **кладём в `payload`
пресета**, чтобы сохранённый отбор фиксировал разрез.

**Оговорка:** localStorage переживает смену роли — при 403 или схлопывании ответа клиент чистит ключ.

### Импersonation следует за видимостью (решено 2026-08-12)

Менеджер может войти в кабинет **любого партнёра, которого видит**. Отдельного ограничения
не вводим: `ImpersonationController:37` резолвит через `visibleInCrm` и поедет за расширением
скоупа автоматически — это и есть желаемое поведение. Подменяя коллегу, менеджер должен видеть
кабинет клиента глазами клиента, иначе взаимозаменяемость упирается в «а цены посмотреть
не могу».

Два следствия, которые надо держать в голове:

- Граница проходит по **праву** (`crm-department.view`), а не по галочке. Импersonation —
  show-роут, а галочка это фильтр списка; сфокусировавшись на своих, менеджер не теряет
  возможность войти под клиентом коллеги, если открыл его карточку.
- Расширяется охват действия, которое и так привилегированное (`crm-impersonate.use`, есть
  у всех трёх ролей менеджеров). Журналирование входов должно оставаться на месте —
  при взаимозаменяемости «кто заходил под клиентом» становится важнее, чем было.

### Где применяется и на что сужает

| Раздел | Сужает до |
|---|---|
| `/crm` дашборд | мои клиенты + мои задачи и покрытие |
| `/crm/partners` | `personal_manager_id = мой профиль`, **и** производные колонки задач |
| `/crm/contractors` | юрлица моих клиентов |
| `/crm/orders｜shipments｜payments` | документы моих клиентов |
| `/crm/tasks` | **моё участие** (автор или исполнитель) — так `visibleTo` работает сегодня и так менеджер понимает «мои задачи» |
| `/crm/calls`, `/crm/emails` | записи моих клиентов + мои беспривязочные |
| `/crm/plans` | строки партнёров. Сетка менеджеров и `by-manager` галочке **не** подчиняются — остаются РОПовскими |
| `/crm/opportunities`, `/crm/beds`, `/crm/finance` | мои клиенты |
| `/crm/analytics` | набор клиентов в `resolveContext`; при `mine` блок `by_manager` **скрыть** — он бессмыслен |

**Не применяется:** `/crm/team` (справочник, измерения «моё» нет), `/crm/agent-tokens`,
**все show-роуты** (карточка партнёра, задачи, звонка, лента, скачивание вложения, старт
импersonation) и CRUD пресетов. Галочка — фильтр списка, а не контроль доступа; пускать её
в show-роуты значит делать безопасность через UI-состояние.

Семантика колонки «Задачи» в списке партнёров (`ClientListService` `nextTaskDueSub:652`,
`activeTasksConstraint:675`) меняется с «мой следующий шаг» на «чей-нибудь» — она обязана
следовать за **галочкой**, а не за правом.

## Этапы

1. **Расщепление права, поведение неизменно.** Новый ресурс `crm-department` в трёх местах;
   идемпотентная миграция-грант по образцу
   `2026_08_04_120100_grant_crm_roster_permissions.php` — выдать `crm-department.*` тем, у кого
   уже есть `crm-clients-all.view` (`super-admin`, `sales-head`). Перевести ~45 call-sites.
   **Ни одна роль ничего нового не получает.** Самый рискованный PR — в нём не должно быть
   ничего, кроме рефакторинга.
2. **Серверный `scope` с дефолтом `mine`.** Никто ничего нового не видит; весь набор
   `manager_*`-тестов обязан остаться зелёным без правок. Это страховочная сетка для этапа 4.
3. **Фронт: галочка + localStorage по разделам.** В шапках самих страниц-списков, **не**
   в [shared/Panel/PanelLayout.jsx](../../../resources/js/shared/Panel/PanelLayout.jsx) —
   он общий с Admin и WMS.
4. **Выдать `crm-department.view` ролям** `sales-manager` и `sales-manager-crm`. Одновременно
   закрыть побочки: сузить `Company::scopeVisibleInCrm`, не отдавать чужие беспривязочные звонки
   и **черновики писем**, снять `sees_all` у агентского токена.
5. **`crm-department.edit` менеджерам** — отдельно, чтобы откатывалось само по себе.
   Удаление чужих вложений и чужих черновиков **не включать**: деструктивно и без отката.

## Регрессии тестов — отдельный пункт, не формальность

Расширение видимости массово переворачивает `assertNotFound` → `assertOk` по всему
`tests/Feature/Crm/`. Затронуты как минимум: `CrmClientVisibilityTest`, `ClientProfileTest`,
`ClientTimelineTest`, `ClientPassportTest`, `ClientLifecycleTest`, `ClientDocumentsTest`,
`CallsTest`, `AttachmentsTest`, `ImpersonationTest`, `SalesPlansTest`, `PlanProgressTest`,
`ClientPlanFactTest`, `OpportunitiesTest`, `DocumentFiltersTest`, `TasksTest`, `EmailsTest`,
`CommentsTest`, `ContractorsTest`, `ClientListTest`, `BedsTest`.

Отдельно `PermissionNamingTest:176` — `assertFalse($manager->can('crm-clients-all.view'))`:
падает сразу, если право выдать роли, и остаётся зелёным при новом ресурсе `crm-department`.

Тесты, которые дают актору право напрямую (`givePermissionTo('crm-clients-all.view')`), от смены
ролей не страдают, но ломаются от переезда call-site: `FinanceScopeTest`, `AnalyticsScopeTest`,
`GapAnalysisTest`, `AnalyticsExportTest`, `FinanceReconciliationTest`, `Api/Crm/CrmApiTest:179`,
`Crm/Mcp/CrmMcpTest:137,228` — последние два ассертят **текст сообщения** с именем права.

**Каждый переворот 404 → 200 — продуктовое решение.** Тест **переименовывать**, а не молча
менять ассерт: иначе через полгода не отличить намеренное от регрессии.

Новые тесты, обязательные на этапе 4: «без параметра `scope` менеджер видит только своих»,
«`scope=department` показывает клиентов коллеги», «менеджер по-прежнему не видит выручку
по менеджерам», «`scope=department` без права схлопывается в `mine`».

## Что сделано

Право расщеплено на `crm-department.view|edit`; серверный `scope` с дефолтом `mine`; галочка с памятью по разделам; право выдано менеджерам двумя миграциями. Изоляция сохранена как настраиваемая — трейт `RestrictsManagersToOwnClients`.
