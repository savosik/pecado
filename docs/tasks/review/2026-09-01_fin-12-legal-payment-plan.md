# fin-12 · План поступлений на юридическом графике 1С

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-09-01

## Описание

Финансист отверг `/crm/finance/plan`: раздел был вероятностной моделью —
`CollectionForecastService` взвешивал график 1С на «платёжную дисциплину» партнёра,
строил коридор сценариев взвешенной регрессией по своей истории и досчитывал
«сверх графика» за горизонтом. Для бюджета такое число бесполезно: в бюджет
переносят обязательство, а не матожидание.

Требование заказчика: **план поступлений = график платежей, который присылает 1С**.
Реализовали — план платежей и есть план поступлений. Оплаты — фактические. Плюс
ответ на «сколько ждём с даты по дату», календарь с расшифровкой дня (кто, сколько,
по каким реализациям) и финансовое состояние партнёра рядом с каждым его упоминанием.

## Что сделано

**Счётное ядро** — `app/Services/Crm/Finance/PaymentPlanService.php`: `summary()`,
`byPartner()`, `overdueBefore()`, `horizon()`, `days()`, `dayPlan()`, `dayFacts()`.
Строится поверх `PaymentForecast::plannedQuery()`, ничего не предсказывает.

**Реализации и счета на предоплату разведены.** Основная сумма — реализации
(`shipment`, `service_sale`, `initial`), счета по заказам — отдельным числом. Причина
не только юридическая: 1С **не публикует оплату заказов вовсе** (`settled_amount` и
`document_settled_amount` у всех 633 строк — ноль константой, регистр
«РасчетыСКлиентамиПоСрокам» заказы не ведёт), поэтому колонка «оплачено» для них
не показывается — иначе оплаченный счёт выглядел бы вечно неоплаченным.

**Виджет партнёра** — `PartnerFinanceSnapshot` + `PartnerFinanceCell.jsx`: долг,
доля просрочки градусником, дата и сумма последнего платежа; в поповере — корзины
возраста и ступень дебиторки с пояснением, почему числа расходятся (здесь строгий
счёт, там льгота 5 банковских дней и отсечка 5 000 ₽). Четыре агрегата на страницу
независимо от числа партнёров.

**«По каким реализациям» для факта.** `settlement_object_uuid` с `shipments.uuid`
не совпадает никогда — это разные сущности 1С. Мост — номер внутри
`settlement_object_name`, сравнение через готовый `InvoiceNumberNormalizer`
(снимает ведущие нули, латинскую/кириллическую «А», регистр). Текст документа
показывается всегда, ссылка — когда найден: на свежих датах это ~99 %, на старых
подпись объясняет, что документ до 19.01.2026 и карточки на сайте нет.

**Два вида в одном разделе.** Переключатель «Период» / «Календарь»; день календаря
раскрывается боковой панелью «Ожидается» / «Поступило», сгруппированной
партнёр → документы (в пиковый день 114 строк поступлений пришлись на 12 партнёров).
Горизонт графика объявлен плашкой, дни за ним приглушены: пусто там — отсутствие
данных, а не ноль поступлений.

**Побочно закрыто расхождение экранов.** `PaymentCalendarService` исключал заказы, а
`plannedQuery()` их включал — два экрана раздела расходились на 3,1 млн ₽, оба
называя себя графиком из 1С. Теперь источник один.

**Снесено:** `CollectionForecastService` (743 строки), `PaymentCalendarService`,
`ForecastChart.jsx`, `PaymentCalendar.jsx`, `FinanceForecastTest`, `PaymentCalendarTest`,
метод `DocumentController::paymentsCalendar()` со спутниками. Вместе с ними ушли три
дефекта: мёртвая серия графика (`dataKey="expected"` против точек `by_discipline`),
вечно нулевой `overdue_expected`, о котором страница печатала фразу, и список строк,
не связанный с выбранной датой. Пульт `/crm/finance` показывает «ждём за 30 дней»
из того же ядра. `/crm/payments/calendar` редиректит в раздел.

## Критерии готовности

- [x] План равен непогашенному остатку графика 1С, без поправок
- [x] Реализации и счета на предоплату считаются раздельно
- [x] Просроченное вынесено из ожиданий периода отдельным блоком

- [x] Суммы по партнёрам и по дням сходятся с итогом; плитка пульта равна экрану
- [x] Календарь: расшифровка дня партнёр → документы, план и факт
- [x] Виджет партнёра: долг, доля просрочки, градусник, последний платёж с суммой
- [x] Горизонт графика объявлен явно
- [x] Изоляция по менеджеру во всех блоках
- [x] `FinancePlanTest` — 17 тестов; затронутые наборы (524 теста) зелёные
- [x] ESLint чист, сборка Vite проходит, Pint применён
- [x] Весь интерфейс на русском
- [ ] Визуальная проверка на dev
