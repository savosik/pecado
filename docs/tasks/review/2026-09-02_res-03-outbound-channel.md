# res-03 · Исходящий канал: order.updated / order.deleted сайт → 1С

**Приоритет:** высокий
**Создано:** 2026-09-02
**Эпик:** [res-00](2026-09-02_res-00-epic.md)
**Зависимости:** res-02 (схемы и AsyncAPI зафиксированы)
**Волна:** 1
**Блокирует:** res-04, res-08

## Описание

Технически канал наполовину готов: `app/Listeners/PublishOrderToErp.php` подписан на
`OrderUpdated`/`OrderDeleted` и уже маппит их в `order.updated`/`order.deleted` для
`erp_out.orders`. Но контракт этого не знает, а валидация — заглушка:
`ErpMessageValidator::OUTBOUND_SCHEMA_MAP` содержит только `order.created`, для остальных
`validateOutbound()` возвращает `valid => true` без проверки.

### Что сделать

- Включить новые исходящие схемы в `OUTBOUND_SCHEMA_MAP` — честная runtime-валидация
  вместо пропуска.
- Провериться, что `fromErp`-заглушка надёжно гасит эхо (сообщение из 1С не должно
  породить обратную публикацию) — включая пути через `saveQuietly()`/массовые операции.
- Убедиться, что публикация уходит **только** для изменений, инициированных клиентом или
  админкой сайта, и не сыплется от технических апдейтов модели (например, пересчёт
  `prepaid_amount` проектором взаиморасчётов не должен публиковать `order.updated`).
- `revision` в исходящем сообщении — по договорённости из resolution.

### Интеграционные тесты (обязательны — правило проекта)

- Отмена заказа на сайте → в `erp_out.orders` уходит валидный `order.deleted`.
- Правка состава → валидный `order.updated` с полным составом и `revision`.
- Входящее сообщение из 1С не порождает эхо-публикацию.
- Невалидный payload не публикуется и логируется.

## Ход работ

- **03.09.2026** — реализовано. Ключевое решение: события окна резерва публикуются
  **не из модельных событий Eloquent, а явно** — новый сервис
  `App\Services\Erp\OrderReservePublisher` (`publishUpdated(order, baseItemsVersion)`,
  `publishDeleted(order, reason)`, `publishConfirmed(order)`), поверх универсальной
  `PublishOrderToErpJob` (валидация + pushRaw в `erp_out.orders`). Его будут дёргать
  res-04/07/08/09 из действий клиента. Эхо-защита — по построению: обработчики
  входящих publisher не вызывают.
- Регистрации `OrderUpdated`/`OrderDeleted` → `PublishOrderToErp` сняты
  (AppServiceProvider): 1С молча теряла такие order.updated (гейт проведённых),
  order.deleted у неё не было вовсе, а по новой схеме старые payload невалидны
  (нет base_items_version/reason) — засоряли бы журнал ошибок при каждой правке
  в админке. Листенер дополнительно гейтится `instanceof OrderCreated`.
- `OUTBOUND_SCHEMA_MAP` + три схемы; if/then `reserve → reserved_until` в
  order.created.to_erp покрыт тестом.
- Тесты: `tests/Feature/Erp/OrderReservePublishTest.php` (7 шт: валидные payload всех
  трёх событий против схем, отказ по чужому reason и без base_items_version, if/then
  резерва, модельные события не публикуют); два старых теста листенера переписаны
  под новый контракт. Смежный прогон Erp/Listeners/Order — 415 зелёных; Pint чистый;
  PHPStan по изменённым файлам новых ошибок не даёт (6 замечаний в листенере — старые).
