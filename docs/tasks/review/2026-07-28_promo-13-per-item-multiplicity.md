## Контекст — что вскрылось на обкатке

На dev воспроизвели боевую акцию
[«Lovense: Lush 4 в подарок»](https://dev.pecado.ru/promotions/lovense-lush-4-v-podarok-za-zakupku-akcionnyx-pozicii).
У неё пятнадцать акционных SKU, и **у каждого своя кратность**: LE-22 — 1 шт., LE-60 — 2,
LE-62/LE-37/LE-13/LE-47 — 4, LE-49/LE-32/LE-36 — 5, остальные — 6. Лендинг прямо говорит:
«кратности разных SKU считаются отдельно».

Текущая модель это выразить не может: `per_value` живёт **в награде**, а награда одна на
правило. Пришлось завести **15 правил** — по одному на SKU. Работает и считает верно, но:

- смена подарка = правка пятнадцати правил;
- список правил забит однотипными строками, акция как целое в нём не читается;
- «выключить акцию» = пятнадцать переключателей.

## Рядом лежал отдельный дефект

Множитель считался по первому условию правила, а не по сработавшему. Починен
отдельно — [promo-bugfix-multiplier-first-condition](2026-07-28_promo-bugfix-multiplier-first-condition.md),
семантики сведены: если позиции условия задают шаги, множитель складывается по
сработавшим; если нет — работает прежний путь через шаг в награде.

## Решение — вариант A

Из двух рассматривавшихся направлений взят **A: кратность в позиции условия**.
Он единственный убирает разбиение акции на правила, ради чего карточка и заводилась.
Вариант B (`multiply_from` — ссылка награды на индекс условия) не реализован:
после A связка перестала быть неявной — шаг виден прямо в той позиции, к которой
относится, и лишний способ сказать то же самое только запутал бы форму.

`conditions.items[]` получил необязательный `per_value`. Награда с
`multiply: per_threshold` считает множитель как **сумму** вкладов по сработавшим
позициям, у которых шаг задан (`floor(набрано / шаг)`), и обрезает результат
потолком. Максимум вместо суммы отвергнут: лендинг Lovense прямо обещает, что
кратности разных артикулов считаются отдельно и складываются.

Выполнено при этом:

- старые правила работают без миграции данных — шаг в награде остался запасным
  путём и применяется, когда ни одна позиция условия шага не задаёт;
- потолок (`max_multiplier`) остался обязательным;
- позиции условия, которые **не** выполнены, в кратность не идут: иначе половина
  набранного порога засчиталась бы как кратность.

## Нюансы

- **Таблица SKU → кратность вводится руками.** Сделана вставка пачкой: кнопка
  «Вставить список из Excel» на вкладке «Условия», разбор на бэкенде
  (`POST admin/promotion-rules/parse-sku-table`), каждая строка становится
  условием «за каждые N штук этого артикула». Разделители — табуляция, `;`, `,`
  или пробелы; кратность необязательна (по умолчанию «за каждую штуку»);
  дубли артикулов схлопываются, ненайденные показываются отдельным списком.
  При вставке нескольких строк режим проверки переключается на «Достаточно
  любого» — иначе правило потребовало бы все артикулы разом.
- **Материализация участников** (`promotion_rule_product`) не пострадала —
  она раскрывает селекторы, а не кратность.
- **Описание правила** (`PromotionRuleDescriber`) сворачивается начиная с четырёх
  позиций: «15 условий (достаточно любого), количество 1–6 шт., кратность 1–6 шт.».
  Названия товаров в свёрнутый вид не идут — пятнадцать наименований не читаются
  ни в какой ячейке.
- **Производительность.** Правило с пятнадцатью позициями стоило бы пятнадцати
  запросов на каждый рендер корзины: раскрытие селектора запросом включалось для
  любого правила с несколькими условиями. Добавлен быстрый путь — селектор из
  одних товаров пересекается со строками корзины в памяти, без запроса.

## Критерии готовности

- [x] Акция Lovense собирается **одним** правилом и даёт те же подарки, что и 15
      отдельных — тест `test_single_rule_matches_fifteen_separate_rules` прогоняет
      оба варианта по одинаковым корзинам и сравнивает выдачу.
- [x] Существующие правила работают без правки данных (весь прежний набор тестов
      промо-домена зелёный без изменений).
- [x] Ввод таблицы «артикул → кратность» пачкой, с отчётом о нераспознанном
      (`sku_table_is_parsed_into_products_and_steps`).
- [x] Описание правила в списке остаётся читаемым при 15+ позициях
      (`long_condition_list_is_collapsed_into_a_summary`).

|---|---|
