## Описание

Карточка, ради которой в задаче стоит «забрать рутину у менеджеров».

Дать конструктор недостаточно — об это уже разбилась клиентская подписка: механизм работал,
но собирать правила руками никто не стал. Если менеджеру придётся заводить по шесть правил
на каждого из своих 100+ клиентов, он останется в мессенджерах.

Настройка типового контрагента должна занимать одну кнопку.

## Что делаем

### Пресеты

Живут в `config/notification_pulse.php` → `presets`, версионируются вместе с релизом
(не в БД: набор правил — это решение команды о том, как ведётся клиент, а не пользовательские данные).

| Пресет | Состав |
|---|---|
| **Полный контроль заказов** | состав заказа и недоборы → закупщику; статусы → пользователю; закрытие заказа → директору |
| **Бухгалтерия** | акты сверки и УПД → бухгалтеру; срок оплаты + счёт вложением → бухгалтеру; просрочка → бухгалтеру и директору; порог блокировки → директору |
| **Логистика** | отгрузка, ТТН, транспортная накладная → логисту |
| **Только критичное** | недоборы и блокировки, ничего больше |

Каждое созданное правило получает `preset_key` — по нему повторное применение не плодит дубли
и видно, что правило пришло из пресета, а не собрано руками.

### Применение на карточке

Кнопка «Применить пресет» на вкладке «Уведомления» карточки партнёра и контрагента.
Диалог показывает состав пресета и **что получится конкретно здесь**:

```
Пресет «Бухгалтерия» для ООО «Ромашка»

✓ Акты сверки → Жопкин А.А. (бухгалтер)
✓ Срок оплаты + счёт → Жопкин А.А. (бухгалтер)
✓ Просрочка → Жопкин А.А., Залупкин В.В. (директор)
✗ Порог блокировки → у контрагента нет контакта с ролью «директор»
                     [Добавить контакт]

Будет создано 3 правила, 1 пропущено.
```

Недостающие роли **подсвечиваются, а не пропускаются молча** — иначе менеджер будет уверен,
что настроил, а письмо не уйдёт.

### Массовое применение

На списках `/crm/partners` и `/crm/contractors` — выбор строк или «все по текущему фильтру»
→ «Применить пресет уведомлений».

Обязательный предпросмотр **до** выполнения: сколько правил создастся, к скольким контрагентам,
сколько пропущено из-за отсутствия контактов и каких именно ролей.

Доступно только под `crm-notifications-all.edit` (РОП) — массовая операция по всей базе
не должна быть в руках одного менеджера.

Выполнение — очередью, с отчётом по завершении. Идемпотентно по `(preset_key, scope, event_key)`.

### Автозаполнение контактов

Развитие импорта из `notif-01`:

- подсказки адресов из `sent_emails` и `crm_emails`: «на эти адреса вы уже писали этому
  контрагенту» — самый достоверный источник, это реальная переписка менеджера;
- при применении пресета контакты роли подставляются автоматически, `is_primary` первым.

### Экран покрытия — где дыра

Главный риск всего эпика не интерфейс правил, а **пустая адресная книга**: правило
«бухгалтеру этого контрагента» молчит, если бухгалтеров не завели. Движок будет исправно
работать и ничего не отправлять, а выяснится это через жалобу клиента.

Экран «Покрытие» в пульте отвечает на это цифрой:

```
Политика отдела: 6 правил

Просрочка → бухгалтеру          покрыто 312 из 780 контрагентов   [показать непокрытых]
Акты сверки → бухгалтеру        покрыто 312 из 780
Недоборы → закупщику            покрыто  94 из 780
Блокировка → директору          покрыто  41 из 780

Не хватает контактов: бухгалтер — 468, закупщик — 686, директор — 739
```

«Показать непокрытых» открывает список клиентов с кнопкой добавления контакта. Так заполнение
адресной книги превращается из абстрактной задачи в конкретный список на разбор — и видно,
что оно движется.

### Обратная связь о сломанных правилах

Правило, давшее 0 получателей три раза подряд (контакт удалён, адрес в стоп-листе, бухгалтер
уволился), ставит менеджеру задачу через существующий `CrmTaskService`:
«Проверьте уведомления контрагента X — правило Y не находит получателей».

Сейчас такое не замечает никто: письмо просто не уходит, и узнают об этом от клиента.
