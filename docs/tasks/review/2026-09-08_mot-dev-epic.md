## Что строим

Раздел `/crm/motivation` — рабочее место менеджера (11 экранов) и руководителя (12 экранов),
обслуживающее систему оплаты труда отдела продаж редакции 2.2. Формула:

```
Переменная = min(потолок, max(0, П1 + П2 + П3 − К1))
```

П1 — 1,9 % от базы сверх порога 60 % плана, П2 — 3 % по Новым партнёрам, П3 — 1 % по
Фокус-перечню, К1 — 0,05 % за календарный день от остатка просроченной задолженности.

## Архитектура: три места в ядре `payroll`

1. **`VariablePartComponent`** — компонент-контейнер по образцу `KpiBonusComponent`: владеет
   П1/П2/П3/К1, знает порядок, потолок и неотрицательность **на сумме** (п. 6.6 применяет их
   к П1+П2+П3−К1, а не к слагаемому). `PayrollCalculator` не трогаем — он по-прежнему суммирует
   только `ComponentKind::AMOUNT`. Расширить `KpiBonusComponent` нельзя: там зашита семантика
   «база × выполнение».
2. **Квартал — рядом, а не внутри.** `payroll_calculations` уникален по `(менеджер, месяц, версия)`;
   квартальная премия — на отдел, за квартал, с поклиентным зачётом. Отдельные таблицы, из месячного
   снимка только справочная ссылка (пп. 3.4 и 7.6 требуют невлияния на месяц).
3. **Схема v2 — новая строка в `payroll_schemes`** с `effective_from` = месяц запуска.
   `config/payroll.php['default_scheme']` не трогаем: на него завязан `PayrollCalculatorGoldenTest`
   (125 075,20), он обязан оставаться зелёным. `KpiBonusComponent` и `ActiveClientsMultiplier`
   остаются в каталоге и выключены в v2.

**К1 — это не `DisciplinePenaltyFactor`.** Тот считает задержку закрывающего платежа в рабочих
днях; К1 — интеграл остатка долга по календарным дням месяца. Источник — `debt_states` /
`DebtOverview::rows()` / `contractor_balances.overdue_debt`; мост `payroll_invoice_settlements`
нужен только ради срока оплаты по документу и льготного периода. Считать К1 по остатку на конец
периода нельзя: это наказывает за долги, которые работник как раз собрал (грубая оценка давала
44 640 ₽ вместо честных 27 098 ₽).

**Второго движка выручки нет.** Только `ShipmentAnalyticsService`; план и темп —
`PlanProgressService` / `ClientPlanFactService`; сигналы по партнёрам —
`OpportunityService::signals()`; рабочие дни — `Payroll\Support\WorkingCalendar` и
`config/production_calendar.php`; отсутствия — `manager_absences`.

## Решения, влияющие на код

| Решение | Следствие для разработки |
|---|---|
| Потолка К1 нет | ограничителя в компоненте не требуется; сверху вычет ничем не ограничен, кроме неотрицательности переменной части |
| Прогрессивной ставки П1 нет | П1 исчисляется от суммы базы за период; поклиентная разбивка — только объяснение на экране |
| Отдельная должность = персональные отклонения | у оклада, надбавок и всех четырёх ставок обязателен слой работника, а не только слой схемы |
| Автоматической заморозки расчёта нет | 5-го числа задача руководителю, месяц остаётся черновиком до утверждения |
| Раздел скрыт от менеджеров до ввода системы | свои права `crm-motivation.view/.edit`; на время разработки и параллельного расчёта право у руководителя, менеджеры видят только действующую «Мою зарплату» |
| Новым не признаётся тот, чей перерыв не подтверждается | флаг `history_incomplete` выводит партнёра из П2; снимается ключом `motivation.novelty.requires_confirmed_history`, когда историю 2024–2025 догрузят из 1С |
| Возвраты учитываются | инвариант «выручка = `/crm/plans`» ослаблен до «с точностью до возвратов периода», подсказка на обоих экранах |
| Новый партнёр — по доступной истории | кэш новизны с флагом неполноты; партнёр без отгрузок Новый при первой покупке |
| Передача партнёра — с 1-го числа следующего месяца | история закрепления, атрибуция внутри месяца не дробится |
| Знаменатель дней — рабочие везде | `/crm/plans` приводится к тому же (`mot-41`) |
