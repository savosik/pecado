# US-22 Идентификатор строки и признак отмены в позициях заказа (протокол v15.16.0)

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-08-08
**Основание:** сверка спецификации 15.15.0 разработчиком 1С, вопрос 2
**Ответ отправлен:** `docs/erp-answers-2026-08-08.txt`

## Описание

Корень истории со «скачущими» суммами заказа в личном кабинете, которую разбирали
на встрече. **Баг наш, не 1С.**

Когда упаковщик оформляет недобор, строка заказа дробится: часть остаётся,
часть отменяется. В сообщении получаются две строки, у которых совпадает всё
контрактное — `product_uuid`, `base_price`, `discount_percent`, `final_price`.
Различаются только `quantity` и внеконтрактный `cancelled`.

Живое сообщение 4609585, заказ 29УТ-012045, гель, базовая 5090, скидка 25%,
конечная 3817,50:

```
строка 1: quantity 2, total 7635,    cancelled false
строка 2: quantity 3, total 11452.5, cancelled true
```

Отсюда три числа, которые видит Елена: 7 635 (только активная),
11 452,50 (только отменённая), 19 087,50 (сумма обеих).

Проверено по коду: **`cancelled` сайт не читает ни в одном обработчике.**
Отменённая строка попадает в позиции наравне с активной, и её сумма входит
в `total_amount`. Третье число — целиком наше.

`line_number` в контракте уже есть — он описан в реализациях, складских ордерах,
расшифровке платежа и правилах оплаты. В заказах его нет ни разу. Это недосмотр,
а не решение.

## Второе следствие — снятие двух костылей

Из-за отсутствия ключа строки `HandleOrderCreated` и `HandleOrderUpdated` при
каждом обновлении **удаляют все позиции и создают заново**. Складские привязки
(партия брака, промо-правило) сайт держит сам, 1С их не присылает — поэтому
появились два трейта-костыля:

- `PreservesDefectItemLinks`
- `PreservesPromoItemLinks`

Они снимают привязки перед удалением и пытаются приклеить обратно по `product_id`.
Один такой баг уже уезжал на прод (см. `project_erp_wipes_defect_links_bug`).
С `line_number` позиции переводятся на честный upsert по `(order_id, line_number)`,
и оба трейта снимаются.

## Решение по контракту

```
order.items[].line_number — integer, min 1, необязательное в схеме.
                            1С просят слать всегда; при отсутствии сайт
                            подставляет порядковый индекс (деградация, не режим)
order.items[].cancelled   — boolean, default false. Начинаем читать
```

**Повтор `product_uuid` внутри одного сообщения разрешён, агрегации нет.**
Каждый элемент `items[]` — отдельная строка заказа. `uniqueItems` не ставим
намеренно: недобор — ровно тот случай, где две строки на один товар осмысленны.
Это войдёт в контракт явной формулировкой — сейчас он молчит.

`cancellation_reason` не берём: у 1С там константа «Нет остатка». Вернёмся,
если текст станет осмысленным (в частности, про уценку).

## Что сделано

**Контракт (spec-first):**

- JSON Schema — `order.created.json`, `order.updated.json`: `items[].line_number`,
  `items[].cancelled`, описание массива `items` с правилом про повторяющийся товар.
  `order.created.to_erp.json` — `line_number` в исходящем заказе: поле двунаправленное.
- AsyncAPI `15.15.0` → **`15.16.0`**: схема `OrderItem` расширена двумя полями,
  описания `items` в `OrderCreatedPayload` и `OrderUpdatedPayload`.
- MkDocs: новый раздел «Строки заказа: `line_number` и отмена» в `rules/orders.md`
  с таблицей живого случая, changelog `[15.16.0]` с блоком «Требуется от 1С».

**Ключевое решение — единый `OrderItemsSynchronizer`.**

Вместо двух реализаций синхронизации позиций (по одной в каждом обработчике)
и двух трейтов-костылей — один сервис. Сопоставление строк:

1. по `line_number` — основной путь;
2. FIFO по `product_id` среди несопоставленных — переходный путь для заказов
   до v15.16.0 и для случая, когда 1С перенумеровала строки.

Складские привязки (партия некондиции, промо-правило) наследуются по товару
из снимка «до»: при дроблении строки **обе половины** обязаны ссылаться на ту же
партию. `PreservesDefectItemLinks` и `PreservesPromoItemLinks` удалены — их
эвристика поглощена сервисом и стала запасным путём, а не единственным.

**Найдено по ходу — вторая причина бага.** `HandleOrderUpdated::parseNewItems()`
складывал позиции в массив с ключом `product_uuid`. Две строки на один товар
схлопывались, и побеждала последняя — отменённая. Отсюда второе из трёх чисел
(11 452,50), которое видела Елена. В карточке была описана только первая причина
(непрочитанный `cancelled`, дававший 19 087,50).

**Третья точка того же бага — журнал изменений.** `OrderChangeLogger::snapshotItems()`
тоже ключевал по товару. Теперь при повторе товара ключ получает суффикс с номером
строки; просто ключевать по номеру нельзя — у позиций до v15.16.0 его нет, и первое
же обновление дало бы ложную пару «удалено + добавлено». Отмена строки попала
в diff и в текст: «Отменено при сборке: «…» — 3 шт., позиция отменена в 1С».

**Унификация поведения.** `order.updated` раньше молча выбрасывал позиции
с неизвестным сайту товаром, а `order.created` их сохранял — состав заказа зависел
от того, какое событие приехало последним. Теперь оба сохраняют строку со снимком имени.

**Нумерация на своей стороне.** `OrderAssembler` проставляет `line_number` позициям
заказа, оформленного на сайте, а `PublishOrderToErp` отправляет его в 1С. Roundtrip
своего заказа сопоставляется по номерам, а не эвристикой.

**Защита от регрессии через админку.** Сохранение заказа в админке пересчитывало
`total_amount` по всем строкам формы. Признак `cancelled` теперь едет туда-обратно,
исключается из суммы (и на бэкенде, и в итоге редактора позиций) — иначе первое же
открытие заказа менеджером вернуло бы отменённый недобор в сумму.

**Интерфейсы:** ЛК клиента (счётчик активных позиций + бейдж «N отменено»,
приглушённая строка, зачёркнутая сумма, пометка «Отменена — нет в наличии»),
админка (карточка + редактор позиций), CRM (карточка документа), выгрузка XLSX
в кабинете — новый столбец «Статус строки». Счётчик «повторить заказ» считает
уникальные товары, а не строки: при дроблении повтор всё равно складывает количество.
