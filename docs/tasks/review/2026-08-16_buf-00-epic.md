# ЭПИК: страховой запас — «интернетчики видят только гарантированный остаток»

**Приоритет:** высокий
**Создано:** 2026-08-16
**Карточки:** `buf-01` … `buf-06`
**Флаг:** `STOCK_BUFFER_ENABLED` (включается после buf-04, до этого вся инфраструктура спит)
**Смежная серия:** доработка замен `sub-10` … `sub-13` (тот же бизнес-контекст, отдельный домен)

| Волна | Карточки | Что даёт |
|---|---|---|
| 0 — фундамент | `buf-01`, `buf-02` | Расчётная модель буфера по рисковым SKU + галочка на клиенте в CRM. Ничего не меняется на витрине |
| 1 — рефакторинг | `buf-03` | SQL остатков переезжает в одну точку (`StockService`). Отдельно выкатываемый рефакторинг без изменения поведения |
| 2 — применение | `buf-04`, `buf-05` | Занижение включается на всех поверхностях: сайт, корзина, выгрузки, client-api |
| 3 — управление | `buf-06` | WMS-консоль: ручные пометки склада, отчёт «что скрыто», метрика отмен |

## Суть в одном абзаце

Дропшипперы и интернет-магазины «с колёс» транслируют наши остатки на свои витрины
и продают конечнику раньше, чем мы собрали их заказ. Когда на сборке попадается брак,
1С молча режет строки (`order.updated` → `order_items.cancelled = 1`) — клиент узнаёт
из коробки, уже взяв предоплату со своего покупателя. Эпик добавляет **виртуальный
страховой буфер**: клиентам с явной галочкой показываем по рисковым товарам остаток,
заниженный на 1–2 штуки, чтобы их заказы никогда не претендовали на последние
экземпляры на полке — у кладовщика всегда остаётся выбор лучшей единицы. Буфер
не пишется в `product_warehouse` и не резервирует ничего физически: офлайн-розница,
опт и розничные покупатели видят и выкупают всё. Протокол обмена с 1С не меняется
ни на байт.

## Данные, на которых стоит дизайн (prod, срез 2026-08-16)

| Факт | Число | Следствие для дизайна |
|---|---|---|
| Отменённые строки за ~2,5 мес | 101 строка / 77 товаров / 428 шт / 48 заказов | Проблема реальна, но концентрирована: буфер нужен десяткам SKU, не каталогу |
| Повторные отмены | топ: «Андрогерон» ×6, «JO WARMING» ×5, дальше ×1–3 | Частота отмен — главный автоматический сигнал риска |
| Партии брака (`product_defects`) | ~30 SKU, топ: набор TOYFA Theatre 206 шт / 6 партий | Второй сигнал; «Сменный рукав Max 2» светится в обоих списках |
| Позиции «Москва Основной» с остатком 1–2 шт | 530 из 1 581 (треть) | Тупое «−2 всем» спрятало бы треть ассортимента — буфер только по рисковым SKU |
| Причина отмены строки в протоколе | не передаётся (брак/недобор/пересорт неразличимы) | Считаем по факту отмены; типизация — после отпуска 1С |
| Сроки годности партий в БД | отсутствуют; только атрибут товара `srok-godnosti-goden-do` | «Затесавшийся старый экземпляр» алгоритмически не виден — закрывается буфером и ручной пометкой склада |
| Сегмент | `crm_client_profiles.business_type`: 44 online + 4 seller (21 с маркетплейсами) | Кандидаты на галочку известны, но включение — только руками менеджера |

## Принципы

**1. Буфер виртуальный и посегментный.** Ничего не замораживаем и не резервируем:
занижается только *показ* для клиентов с галочкой `users.stock_buffer_enabled`.
Остальные клиенты и витрина видят полный остаток. Цена сервиса — ~1–2 % единиц
склада, скрытых от ~50 клиентов, а не заморозка остатков.

**2. Только рисковые SKU, размер — из сигналов.** Отмены строк за 90 дней, партии
брака, близкий срок годности, ручная пометка склада. Размер:
`clamp(f(сигналы), 0, min(2, 10 % остатка))`. Для рискового SKU с остатком 1–2 шт
буфер честно даёт ноль — если единственный экземпляр может быть браком, выбора
у кладовщика всё равно нет.

**3. Буфер — производная, не поле остатка.** По прецеденту `PromoStockService` и
`DefectStockService`: `product_warehouse.quantity` остаётся абсолютным значением
из 1С, вычитание происходит при чтении. Никаких записей в pivot, ничего не ломается
при следующем `stock.updated`.

**4. Все поверхности показывают одно число.** Карточка, листинг, поиск, корзина,
выгрузка, client-api — клиент с галочкой нигде не должен увидеть расхождение,
иначе перестанет верить всем числам сразу. Отсюда предварительный рефакторинг
`buf-03`: SQL остатков в одной точке.

**5. Протокол 1С неприкосновенен.** Разработчики 1С в отпуске: ни схем, ни спеки,
ни новых полей. Всё считается из данных, которые уже приходят.

**6. Preorder не занижается.** Риск брака относится к товару на полке; предзаказный
остаток — обещание прихода, его буфер не трогает.

**7. Не медленнее ни для кого — и это доказывается замером.** Горячий путь
(гости, клиенты без галочки) не получает ни одного лишнего SQL-запроса; рефакторинг
buf-03 принимается только с таблицей замеров «до/после» (запросы + p95) по каталогу,
поиску, избранному, карточке и главной; кеши (выгрузки, главная) инвалидируются
только при реальном изменении данных, а не по расписанию пересчёта.

## Сигналы риска (buf-01)

| Сигнал | Источник | Вес |
|---|---|---|
| Отмены строк при сборке | `order_items.cancelled = 1` за скользящие 90 дней, GROUP BY `product_id` | Основной: повторная отмена — почти гарантия проблемной полки |
| Партии брака | `product_defects` по товару (открытые и закрытые за 180 дней) | Подтверждённый физический брак этого SKU |
| Срок годности | атрибут `srok-godnosti-goden-do` ближе порога (конфиг, старт — 6 мес) | Риск «старой» единицы среди свежих |
| Ручная пометка | `product_stock_buffers.manual_qty` из WMS (`buf-06`) | Абсолютный приоритет над расчётом |

## Порядок и зависимости

`buf-01` → (`buf-02` ∥ `buf-03`) → `buf-04` → (`buf-05` ∥ `buf-06`)

`buf-03` — самостоятельный рефакторинг без изменения поведения, его можно выкатить
и проверить до любого занижения. Флаг `STOCK_BUFFER_ENABLED` включается после
`buf-04`; до этого расчёт буфера работает «вхолостую» и виден только в отчёте.

Метрика успеха эпика: доля заказов клиентов сегмента с отменёнными строками
(база: 48 заказов с отменами за квартал по всем клиентам) и отсутствие жалоб
на расхождение чисел между поверхностями.
