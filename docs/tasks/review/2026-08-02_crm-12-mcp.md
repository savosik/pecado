# crm-12 · MCP `/mcp/crm`: запись от имени менеджера, каталог операций, аудит

**Приоритет:** высокий
**Создано:** 2026-08-02
**Эпик:** [crm-00](../backlog/2026-08-02_crm-00-epic.md)
**Волна:** 5 (гейт для ИИ-агентов)
**Зависимости:** `crm-11` (реестр операций и сервисы)

## Описание

Дать ИИ-агентам менеджеров возможность **делать** работу в CRM, а не только читать отчёты:
оставить комментарий, поставить задачу, обновить профиль, задать план, отправить письмо —
не заходя в интерфейс.

Менеджеры уже ходят в `/mcp/analytics` (read-only BI поверх `bi_agent`, только SELECT).
Добавлять запись туда **нельзя**: весь смысл того сервера в том, что даже с валидным токеном
писать в БД невозможно на уровне СУБД. Пишущий гейт — отдельный сервер с отдельными токенами.

## Ключевое решение: токен превращается в менеджера

```php
class AuthenticateCrmAgent
{
    public function handle(Request $request, Closure $next): Response
    {
        $token = CrmAgentToken::where('token', $request->bearerToken())
            ->where('is_active', true)->first();
        // нет токена или отозван → 401 с одинаковым текстом
        Auth::setUser($token->user);   // ← агент = его менеджер
        ...
    }
}
```

После `Auth::setUser()` работают уже существующие `permission`-middleware, политики и скоуп
`User::visibleInCrm($actor)`. Агент физически не может больше своего менеджера — и это
не требует второй копии правил доступа, которая неизбежно разошлась бы с первой.

`user_id` в токене — **обязателен** (в отличие от `analytics_tokens`, где он nullable):
запись без установленного автора недопустима, «кто это сделал» должно быть в каждой строке.

## Что делаем

**Миграция `crm_agent_tokens`** (комментарии к таблице и всем столбцам):

```php
$table->comment('Токены ИИ-агентов менеджеров для пишущего доступа в CRM (/mcp/crm, /api/crm)');
$table->id();
$table->string('name')->comment('Кому выдан — попадает в аудит каждой операции');
$table->foreignId('user_id')->constrained()->cascadeOnDelete();   // обязателен
$table->string('token', 64)->unique()
      ->comment('Секрет для Bearer-аутентификации; хранится как есть — его нужно уметь показать владельцу');
$table->boolean('is_active')->default(true)->comment('false — отозван, доступ закрыт без удаления записи');
$table->timestamp('last_used_at')->nullable()->comment('Последнее обращение; обновляется не чаще раза в минуту');
$table->timestamps();
```

**Отдельная таблица, не `analytics_tokens` и не `api_tokens`** — по тому же обоснованию, что
записано в шапке миграции `analytics_tokens`: разные резолверы = граница, которую нельзя
перешагнуть по недосмотру. Здесь граница ещё существеннее: у этих токенов есть право записи.

**Сервер `App\Mcp\Servers\CrmServer`** (`Laravel\Mcp\Server`) с `$instructions` в духе
`AnalyticsServer`: порядок работы, бизнес-правила (клиент = пользователь с
`personal_manager_id`; факт продаж = отгрузки по `erp_created_at`; лояльностью владеет 1С
и меняется только там; жизненный статус — поле сайта), и явное предупреждение, что операции
записи необратимы и выполняются от имени менеджера.

**Инструменты — каталог вместо N тулов.** Операций уже десятки и станет больше; выкладывать
их по одному туду означало бы раздувать список инструментов до нечитаемости:

| Тул | Назначение |
|---|---|
| `crm-catalog` | Список операций с фильтром по разделу; отдаёт id, назначение и доступность |
| `crm-describe` | Полная схема аргументов одной операции |
| `crm-call` | Выполнить операцию по id с аргументами |

Это ровно тот же паттерн `list-tables → describe-table → run-query`, к которому агенты
менеджеров уже приучены на `/mcp/analytics` — новой ментальной модели не появляется.

Плюс несколько «горячих» ярлыков для частых сценариев, чтобы не платить тремя вызовами
за одно действие: `crm-client-card`, `crm-add-comment`, `crm-create-task`, `crm-plan-progress`.
Ярлыки — тонкие обёртки над теми же операциями реестра.

Читающие тулы помечаются `#[IsReadOnly]`, пишущие — нет: клиент MCP должен понимать разницу.

**Роут** в `routes/ai.php` рядом с существующим:

```php
Mcp::web('/mcp/crm', CrmServer::class)
    ->middleware([AuthenticateCrmAgent::class, 'throttle:60,1']);
```

**Аудит.** Каждая операция записи логируется в отдельный канал (по образцу канала `bi`):
кто (имя токена + `user_id`), какая операция, аргументы, результат или ошибка. Плюс поле
`source` (`web` | `agent`) в записях, создаваемых через гейт — в комментариях, задачах и письмах
должно быть видно, что их сделал агент, а не человек: иначе разбор «кто это написал клиенту»
упрётся в тупик.

**Ограничения записи:**
- отправка писем через агента — под тем же флагом `MAIL_FEATURE_CRM_OUTBOUND`;
- удаление (`delete`) через агента запрещено на уровне реестра, даже если у менеджера есть право:
  ошибочный вызов агента не должен приводить к безвозвратной потере. Мягко удалять свои
  комментарии — можно.

## Границы

- Локальный (stdio) транспорт не заводим: пишущий доступ имеет смысл только с машины менеджера.
- Расширение `/mcp/analytics` не трогаем.
- UI выдачи токенов — карточка `crm-13`.

## Что сделано

**Сервер** `App\Mcp\Servers\CrmServer` на `/mcp/crm` с инструментами `crm-catalog`,
`crm-describe`, `crm-call` и четырьмя ярлыками (`crm-client-card`, `crm-plan-progress`,
`crm-add-comment`, `crm-create-task`). Читающие помечены `#[IsReadOnly]`, пишущие — нет.
Своей логики у инструментов нет: все они идут через `OperationRunner`, тот же, что и REST.

**Токен превращается в сотрудника.** `AuthenticateCrmAgent` вызывает `Auth::setUser()`,
после чего работают уже существующие права, политики и `User::visibleInCrm()`. Второй копии
правил доступа не появилось — значит, ей не с чем разойтись.

**Источник записи** проставляется не вызовом, а контекстом: middleware поднимает
`CrmSource::agent($tokenName)`, трейт `RecordsCrmSource` на четырёх моделях пишет `source`
при создании. Тащить параметр через сигнатуры сервисов означало бы, что достаточно одного
забытого места — и в ленте клиента появится запись неизвестного происхождения. Поле не входит
в `fillable`: иначе агент мог бы представиться человеком.

**Запрет удаления виден, а не спрятан.** `task.delete` есть в каталоге с
`allowed: false` и объяснением. Молчать было бы хуже: агент раз за разом сообщал бы менеджеру
«не нашёл, как удалить», вместо честного «удаление закрыто, удалите руками». Маршрута REST
такая операция не получает вовсе. Мягкое удаление своего комментария оставлено — запись
восстановима.

**Отступление — кодировка ответов.** Штатный `Response::json()` из `laravel/mcp` кодирует
без `JSON_UNESCAPED_UNICODE`, и весь русский текст уезжает агенту как `Заказ`.
Клиент это разберёт, но заплатит втрое больше токенов за те же слова, а человек, читающий лог
обмена, не разберёт вовсе. Payload у нас русский почти целиком, поэтому инструменты кодируют
JSON сами (`InteractsWithCrmOperations::payload()`).

**Аудит** — канал `crm-agent` (`storage/logs/crm-agent.log`, 180 дней). Пишутся только
операции записи, включая неудавшиеся: «агент попробовал и не смог» — такая же часть разбора,
как удавшаяся запись. Чтение не логируется — в этом шуме потерялось бы то, ради чего журнал
и заводится.
