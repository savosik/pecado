# US-21 Разнесение платежа за пределы реализаций (протокол v15.16.0)

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-08-08
**Основание:** сверка спецификации 15.15.0 разработчиком 1С, вопрос 1
**Ответ отправлен:** `docs/erp-answers-2026-08-08.txt`

## Описание

Строка расшифровки платежа (`allocations[]`) в контракте умеет указывать **только
на реализацию**: `shipment_uuid` обязателен, `target_type` знает единственное
значение `shipment`. В 1С расшифровка устроена шире.

Замер 1С на боевой базе за 2026 год:

| На что указывает строка | Строк | Доля |
|---|---|---|
| Реализация | 4 366 | 58% |
| Заказ клиента (предоплата) | 2 033 | 27% |
| Первичный документ | 880 | 12% |
| Отчёт комиссионера | 146 | 2% |
| Прочее | 111 | 1% |

В деньгах хуже: из 156 754 061,98 руб. разнесения на реализации ложится
44 881 268,77 руб., **не помещается 111 872 793,21 руб. — 71,4%**. Не лезут
крупные предоплаты по заказам: чем больше платёж, тем вероятнее, что реализации
ещё нет.

При запуске канала как есть 111,9 млн исчезли бы **молча** — контракт обещает
строку с неизвестным `target_type` пропустить с предупреждением в лог
(`PaymentAllocationService::sync`). Ни ошибки у 1С, ни видимого сбоя на сайте:
клиент увидел бы платёж, у которого разнесено меньше трети суммы.

**Блокирует запуск канала платежей целиком.**

Вариант «1С сама развернёт заказ в реализации» отвергнут обеими сторонами:
на момент платежа реализации может не быть, а при её появлении пришлось бы
досылать обновления по всем ранее отправленным платежам заказа.

## Решение по контракту

```
allocations[].shipment_uuid  — снять required, сделать nullable
allocations[].target_type    — enum: shipment | order | other | null
                               null == shipment (обратная совместимость)
allocations[].order_uuid     — есть; для target_type=order обязателен по смыслу
allocations[].target_uuid    — НОВОЕ, nullable. UUID документа для target_type=other
allocations[].target_name    — НОВОЕ, nullable. Представление документа строкой,
                               только для показа
```

Правило валидности строки:

| `target_type` | Обязательно |
|---|---|
| `shipment` / `null` | `shipment_uuid` |
| `order` | `order_uuid` |
| `other` | только `amount`; `target_uuid` / `target_name` желательны |

Строка вне правила по-прежнему пропускается с предупреждением — но становится
исключением, а не системой.

## Что важно не сломать

- **Пересчёт оплаты реализаций (`paid_amount`, `payment_status`) считается только
  по строкам `target_type = shipment`.** Предоплата по заказу не гасит накладную,
  пока не появится реализация и 1С не переразнесёт платёж.
- Правило v15.11.0 не меняется: `allocations` присылается **целиком** и заменяет
  прежнее разнесение. Отсутствие ключа ≠ пустой массив.
- Сумма строк **не обязана** сходиться с `amount` — разница остаётся
  нераспределённым остатком (авансом), это уже описано и реализовано.
- Все пересчёты остаются полной функцией от состояния БД (`SUM ... GROUP BY`),
  никогда инкрементом: повторная доставка не должна удваивать суммы.

## Что сделано

**Контракт (spec-first):**

- JSON Schema `payment.created` / `payment.updated`: `required` строки сведён
  к одному `amount`, `shipment_uuid` стал nullable, `target_type` расширен
  до `shipment | order | other | null`, добавлены `target_uuid` и `target_name`.
- AsyncAPI: схема `PaymentAllocation` переписана — таблица «тип → обязательное
  поле → что делает сайт», явная запись про то, что накладную закрывают только
  строки `shipment`.
- MkDocs `rules/payments.md`: новый раздел «Типы документов расшифровки» с замером
  1С в строках и в деньгах, правилами валидности и объяснением, что увидит клиент
  по строке `other`. Плюс 6 новых критериев приёмки и changelog.

**Данные.** `payment_allocations.shipment_uuid` перестал быть NOT NULL; добавлены
`target_type` (default `shipment`), `target_uuid`, `target_name` и индекс
`(target_type, order_uuid)`. Существующие строки размечены как `shipment`:
другого типа контракт до v15.16.0 не допускал.

`order_id` намеренно не заводили: связь с заказом остаётся мягкой, по `order_uuid`, —
ровно как связь с реализацией живёт по `shipment_uuid`. Заказ может не приехать
на сайт вовсе, и FK превратил бы это в ошибку вместо ожидаемого состояния.

**Логика.** Разбор строки вынесен в `PaymentAllocationService::parseRow()`:
тип определяет, какое поле обязательно, и строка без него пропускается с записью
в лог — но теперь это исключение, а не 71,4% денег.

Три вещи, которые важно не сломать при доработках:

1. **`paid_amount` реализаций считается только по строкам `shipment`.** Предоплата
   по заказу накладную не гасит. Есть отдельный тест: строка `order`, у которой
   1С справочно указала и `shipment_uuid`, оплату реализации не двигает.
2. **`orders.prepaid_amount` пишет только `PaymentAllocationService`** — колонка вне
   `$fillable`, обновление идёт через `Order::withoutEvents()` + `saveQuietly()`.
   Иначе служебный пересчёт опубликовал бы заказ обратно в 1С.
3. **Пересчёт остаётся полной функцией от БД** (`SUM ... GROUP BY`), никогда
   инкрементом: повторная доставка того же сообщения не задваивает суммы.

**Доклейка при позднем приезде заказа.** Трейт `LinksPrepaymentToOrder` вызывается
из обоих обработчиков заказов — аналог `LinksPaymentAllocationsToShipment`.
Для предоплат порядок «платёж раньше заказа» не редкость, а норма: предоплата
обычно и возникает до того, как документ доедет до сайта.

**Интерфейсы.** ЛК: таблица расшифровки платежа переименована в «Расшифровка
платежа» и показывает три типа документов со ссылками на реализацию или заказ,
для `other` — `target_name` из 1С; в карточке заказа — бейдж «Предоплата»
и строка остатка к оплате. CRM: строки расшифровки в карточке платежа,
связанные документы теперь включают заказы, бейдж предоплаты в шапке заказа.
Админка платежей: тип строки, `document_label`, ссылка на заказ.

## Тесты

`PaymentAllocationTargetsTest` — 14 кейсов:

| Кейс | Что проверяет |
|---|---|
| Предоплата по заказу | Строка сохраняется, `prepaid_amount` заполняется |
| Предоплата ≠ оплата накладной | `paid_amount` реализации того же заказа не двигается |
| Строка `other` | Сохраняется, показывается по `target_name` |
| Смешанный платёж | 20 000 на реализацию + 30 000 предоплаты + 5 000 прочее, остаток 5 000 авансом |
| Строка без `target_type` | По-прежнему считается реализацией (совместимость с v15.11.0) |
| Строка `order` без `order_uuid` | Пропускается |
| Строка `shipment` без `shipment_uuid` | Пропускается |
| Неизвестный тип | Пропускается |
| Платёж раньше заказа | Предоплата подхватывается при приезде заказа |
| Возврат | Уменьшает предоплату |
| Пустой массив | Очищает предоплату, сумма уходит в аванс |
| Идемпотентность | Тройная доставка не множит строки и не задваивает суммы |
| Удаление платежа | Предоплата обнуляется, восстановление возвращает её |
| Сквозной путь | Смешанное сообщение проходит JSON Schema и обработчик целиком |
