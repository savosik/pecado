# US-23 Признак свежести документа: защита от устаревших сообщений (протокол v15.16.0)

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-08-08
**Основание:** сверка спецификации 15.15.0 разработчиком 1С, вопрос 3
**Ответ отправлен:** `docs/erp-answers-2026-08-08.txt`

## Описание

Сайт не может отличить свежее сообщение от устаревшего. Дыра наша.

Дедупликация идёт по `message_id` (таблица `erp_processed_messages`,
`ErpIncomingJob`). Она защищает ровно от одного сценария — **повторной доставки
того же сообщения** брокером. От применения двух **разных** сообщений в неверном
порядке она не защищает никак: `message_id` генерируется новый на каждую отправку.

Порядок не гарантирован ни между очередями (разные connection-ы, разный
`numprocs` — у цен 12 воркеров), ни внутри очереди при `numprocs > 1`.

Живой пример 1С, заказ 29УТ-012045, две отправки подряд:

```
[4609584] событие 15:41:28  →  1 строка: 5 шт, не отменено      (УСТАРЕВШИЕ данные)
[4609585] событие 15:41:28  →  2 строки: 2 активно + 3 отменено (актуальные)
```

`erp_updated_at` у обоих **совпадает до секунды** — различить нечем. Если
сообщения применятся в обратном порядке, сайт запишет устаревшее состояние
и никак этого не заметит.

1С параллельно чинит у себя причину дублей (при оформлении недобора уходит 3–5
сообщений, содержательно новое одно). Но с `revision` лишние сообщения станут
безвредными, поэтому задача не ждёт их фикса.

## Решение по контракту

```
revision — integer, min 0, необязательное. Монотонно возрастает
           В РАМКАХ ОДНОГО uuid ДОКУМЕНТА.
           Глобальная монотонность не нужна и не проверяется.
```

Поведение сайта:

- на документе хранится `applied_revision`;
- сообщение с `revision <= applied_revision` отбрасывается как устаревшее,
  факт пишется в лог **и в журнал шины** (`erp_bus_messages`) — молча не теряем;
- сообщение **без** `revision` применяется как сейчас, без проверки — чтобы 1С
  могла включать поле по каналам постепенно, а не одним днём.

Каналы первой очереди: заказы, реализации, платежи, возвраты.

Расходные ордера **исключены**: у документа в 1С отключена история данных,
брать ревизию неоткуда (тот же корень, что у необязательных `erp_created_at` /
`erp_updated_at`, см. вопрос 12).

Вариант с `erp_updated_at` в миллисекундах отклонён как основной: снижает
вероятность коллизии, но не устраняет её. Принимается только как запасной.

## Что сделано

**Контракт (spec-first):**

- JSON Schema — `revision` в 11 входящих схемах: `order.created/updated/deleted`,
  `shipment.created/updated/deleted`, `payment.created/updated/deleted`,
  `return.updated/deleted`. Тип `["integer", "null"]`, `minimum: 0`.
- AsyncAPI — то же в 11 payload-схемах.
- MkDocs — новая страница [«Порядок доставки и свежесть»](../../../docs-erp/content/rules/message-ordering.md)
  в разделе бизнес-правил: почему `message_id` и `erp_updated_at` задачу не решают,
  требования к значению, поведение сайта, что это значит для 1С. Changelog `[15.16.0]`.

**Проверка централизована, а не размазана по обработчикам.**

`App\Services\Erp\ErpRevisionGuard` с картой «событие → модель документа»,
вызывается из `ErpIncomingJob`:

- **после** валидации схемы — мусорный payload не должен ходить в БД;
- **до** обработчика — устаревшее сообщение не должно ничего менять.

Обработчики не тронуты вовсе. Справочники (товары, цены, остатки, контрагенты)
в карте отсутствуют: там нет документа с жизненным циклом. Расходные ордера
исключены — у документа в 1С отключена история, ревизии не существует.

**Три решения, которые стоит помнить:**

1. **`applied_revision` пишется запросом, а не через модель.** Сохранение `Order`
   поднимает listener публикации заказа обратно в 1С — служебная отметка вызвала бы
   эхо-сообщение в `erp_out.orders`.
2. **Отметка сдвигается только после успешной обработки.** Иначе упавшее сообщение
   заблокировало бы само себя: повтор из очереди пришёл бы с той же ревизией
   и был бы отброшен как устаревший. Есть тест.
3. **Запрос на обновление отметки содержит `where applied_revision < revision`.**
   Два воркера могли взять сообщения по одному документу одновременно, и более
   старое не должно откатить отметку назад.

**Найдено по ходу:** `erp_bus_messages.status` — не строка, а `enum`
(на SQLite — varchar с CHECK). Первая версия миграции меняла тип через `ALTER`
только для MySQL, и запись со статусом `stale` молча не проходила: `ErpBusLogger`
глушит исключения, чтобы сбой логирования не ронял обработку сообщения. Поймано
тестом на журнал шины. Миграция переписана на `->change()` по образцу той,
что добавляла `recovered` в v15.4.

**Админка:** статус «Устаревшее» (оранжевый, `LuClockAlert`) в журнале сообщений
и в фильтре, счётчик-ссылка «Устаревших сообщений: N» на дашборде «Шина ERP» —
рядом с «Восстановлено сущностей». Растущий счётчик означает лишние отправки
из 1С либо систематически рвущийся порядок доставки.

## Тесты

`ErpRevisionGuardTest` — 10 кейсов, все через полный конвейер `ErpIncomingJob`:

| Кейс | Что проверяет |
|---|---|
| Обратный порядок доставки | Состояние остаётся от более свежего сообщения (данные 4609584 / 4609585) |
| Журнал шины | Отброшенное видно со статусом `stale` и текстом «пришла ревизия 7, уже ревизия 8» |
| Равная ревизия | Отбрасывается |
| Бо́льшая ревизия | Применяется |
| Без `revision` | Применяется всегда, отметка не сбрасывается |
| Первое сообщение по документу | Проходит |
| Упавшая обработка | Отметку не двигает, повтор проходит |
| Soft-delete | Отметка сохраняется, документ оживляется более свежим сообщением |
| Реализации и платежи | Проверка работает и там |
| Справочники | `product.updated`, `price.updated`, `stock.updated`, `goods_issue.updated` не проверяются |

Прогон `--filter=Erp` — 796 зелёных. Pint чист, ESLint чист.
PHPStan: `ErpRevisionGuard` и `ErpIncomingJob` без замечаний.
`db:comments:audit --strict` — зелёный, миграция проверена откатом и повторным
применением.
