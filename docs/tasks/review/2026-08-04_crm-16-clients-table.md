## Описание

`/crm/clients` был витриной: восемь колонок, три сырых `<select>` и единственное действие —
«открыть карточку». Всё, что менеджер делает каждый день (написать, позвонить, поставить
задачу, сменить стадию), требовало перехода в карточку и ещё двух-трёх кликов внутри неё.

Карточка отвечает на вопрос «что известно про клиента». Список должен отвечать на другой —
«кем заняться сейчас», и отвечать в самой строке, а не ссылкой на ответ.

Действия в ячейках: клик по email открывает существующий `EmailComposeDialog`, по стадии —
меню смены статуса (тот же `crm.clients.lifecycle.update`, что и в карточке, — журнал смен
ведётся одинаково), по колонке задач — существующий `TaskDialog`, по телефону — меню звонка
(на этапе 3 заменится журналом звонков).

### Решения, принятые по ходу

**Менеджер остаётся read-only.** `users.personal_manager_id` перезаписывает
`HandlePartnerUpdated` при каждом `partner.updated`, поэтому смену менеджера из CRM
не делаем вовсе — назначает 1С. Всё, что менеджер выставил бы там руками, затёрлось бы
следующим сообщением из шины, молча и без следа.

**Факт продаж — только через `ShipmentAnalyticsService::byPartner()`.** Быстрый
`SUM(shipments.total_amount)` для колонки был бы вторым движком расчёта, и цифра в списке
рано или поздно разошлась бы с `/crm/analytics`. Тест
`plan_fact_column_matches_shipment_analytics` сравнивает колонку с `metrics()` — расхождение
падает сборкой, а не всплывает в разговоре с руководителем.

**Состояние срока считает бэкенд.** `due_state` (`overdue|today|tomorrow|week|later|none`)
приезжает готовым: разбирать даты в JSX означало бы держать часовой пояс сервера в двух местах.

**Поиск по задачам сужен правами.** Без `crm-clients-all.view` учитываются только свои
задачи — иначе клиент всплывал бы в выдаче по тексту чужого поручения, то есть по данным,
которых менеджер не видит. Отдельный тест: `manager_does_not_find_client_by_colleagues_task`.

**Сортировка по проценту выполнения — ручной пагинатор.** Процент не колонка, сортировать
в SQL нечем. Порядок считается по всему скоупу (тот же кэшированный агрегат, что у фильтра
«отстают»), страница догружается по срезу идентификаторов. Клиенты без плана всегда в конце:
это не «ноль процентов», а «цифру никто не ставил».

**LIKE + EXISTS вместо Meilisearch.** Индексировать `User` нельзя: `visibleInCrm` в поисковом
движке не воспроизводится, пришлось бы держать `personal_manager_id` актуальным при каждом
`partner.updated`. Порог пересмотра: ответ `/crm/clients` дольше 500 мс или `crm_comments`
больше ~1 млн строк → `FULLTEXT` + `MATCH … AGAINST` за фича-флагом, SQLite-тесты остаются
на LIKE-ветке.

**Попутно починен `useResourceIndex.handleSearch`.** Он пересобирал параметры только из
`search/per_page/sort_*` и молча сбрасывал все остальные фильтры — на всех admin-страницах,
не только в CRM.
