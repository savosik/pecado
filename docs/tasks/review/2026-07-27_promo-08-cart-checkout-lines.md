# Промо 08 — Промо-позиции в корзине и чекауте

**Приоритет:** высокий
**Создано:** 2026-07-27
**Roadmap:** [docs/promo-constructor-roadmap.md → Волна 2](../../promo-constructor-roadmap.md)
**Зависит от:** [promo-02-engine](2026-07-27_promo-02-engine.md), [promo-07-stock-service](2026-07-27_promo-07-stock-service.md)

## Контекст

Переход из режима «показываем» в режим «выдаём». Промо-позиции появляются в корзине
отдельной секцией, в чекауте — отдельной таблицей, и уходят отдельными заказами
(создание заказов — карточка 09, здесь только UI и подготовка данных).

**Промо-строки не хранятся в `cart_items`** (принцип из roadmap). Они вычисляются движком
и отдаются фронту как виртуальные строки. Хранится только выбор клиента в
`cart_promotion_selections`.

## Бэкенд

### `CartService`

`getCartDetails()` ([строка 661](../../../app/Services/Cart/CartService.php#L661)) —
добавить в ответ ключ `promo_items`: массив виртуальных строк, по форме совместимый с
`defectItemDetails()` ([строка 743](../../../app/Services/Cart/CartService.php#L743)), но с:

- `id` вида `promo:{rule_id}:{reward_index}` — **строковый, не числовой**. Фронт использует
  `item.id` и как React-ключ, и как адрес для сети (`/api/cart/items/{id}`); виртуальные
  строки не должны случайно уехать в эти эндпоинты. Тип ключа — самая надёжная защита.
- `item_type: 'promo'`, `promo_kind: 'accountable' | 'sample'`;
- `promotion` — название акции/правила, ссылка на лендинг, если есть;
- `price` — промо-цена из награды (может быть 0, 0.01, 40);
- `is_optional`, `is_declined`;
- `choices` — список товаров на выбор для `type: choice`;
- `available_quantity` — из `PromoStockService`.

`computeCartAggregates()` ([строка 798](../../../app/Services/Cart/CartService.php#L798)) —
добавить суммы промо **отдельными полями** (`promo_quantity`, `promo_amount`), а не
подмешивать в `total_amount_discounted`. Причина: промо уезжает отдельным заказом, и
смешанный итог введёт клиента в заблуждение. Уценка сейчас в общий итог подмешивается —
это её осознанное поведение, копировать его не нужно.

### Эндпоинты выбора

Рядом с `/api/cart/add-defect` и `/api/cart/set-defect-quantity`
([routes/user.php:102–103](../../../routes/user.php#L102)):

```
POST /api/cart/promo/select    { rule_id, reward_index, product_id }   — выбор из choices
POST /api/cart/promo/decline   { rule_id, reward_index, declined }     — отказ от платной
```

Оба пишут в `cart_promotion_selections` и возвращают пересчитанный блок промо целиком.
Отказ от бесплатной позиции (`price = 0`) отклоняется с 422 — бесплатное не отклоняем.

### Чекаут

В [`CheckoutService::checkout()`](../../../app/Services/Order/CheckoutService.php#L37) —
**авторитетный пересчёт** движком внутри транзакции, до сборки заказов. Результат клиентского
пересчёта не принимается на веру ни в каком виде: между открытием чекаута и нажатием кнопки
корзина могла измениться, а остаток склада — уехать.

Если промо-позиция, которую клиент видел, к моменту оформления недоступна — заказ
оформляется **без неё**, молча, и в ответ добавляется мягкое уведомление
(«Промо-позиция “…” больше недоступна и не вошла в заказ»). Ронять чекаут из-за
исчезнувшего подарка нельзя.

## Фронтенд — корзина

Образец для всего — уценка.

- Новые компоненты `CartPromoTableRow.jsx` и `CartPromoMobileCard.jsx` по образцу
  [CartDefectTableRow.jsx](../../../resources/js/Pages/User/Cart/CartDefectTableRow.jsx) (119 строк)
  и [CartDefectMobileCard.jsx](../../../resources/js/Pages/User/Cart/CartDefectMobileCard.jsx).
  Визуально строка идентична товарной, отличие — бейдж: **«Акция»** для подотчётных,
  **«Рекламный образец»** для пробников (цвета выбрать отличными от лилового «Уценка», чтобы
  три вида строк не сливались).
- **Количество не редактируется.** Вместо `QuantityControl` — статичное число. Кнопки
  удаления нет: у отклоняемых позиций вместо неё «Отказаться» / «Вернуть», у неотклоняемых —
  ничего.
- Для `type: choice` — селектор товара прямо в строке («Выберите подарок»), до выбора
  строка показывается с подсказкой и не считается в итог.
- Цена: при 0 — «Бесплатно», иначе обычная сумма. Не писать «0 ₽» — «Бесплатно» читается
  мгновенно.
- Плашка над секцией: «Промо-позиции добавлены автоматически по акции. Они оформляются
  **отдельным заказом**» — клиент должен узнать про отдельный заказ до чекаута, а не после.

### Проводка через существующую структуру

[Cart/Index.jsx](../../../resources/js/Pages/User/Cart/Index.jsx) уже разделяет строки по
`item_type` (строки 33–34) и прокидывает уценку отдельными пропсами, потому что она «не
живёт в store-агрегации». Промо — точно так же:

- `promoItems` фильтруется из `allItems` / приходит отдельным ключом;
- `promoTotals` считается `useMemo` и прокидывается в
  [`CartTable`](../../../resources/js/Pages/User/Cart/CartTable.jsx#L149) и
  [`CartSummary`](../../../resources/js/Pages/User/Cart/CartSummary.jsx#L13) —
  оба уже принимают `defectTotals` тем же способом;
- в `CartSummary` промо показывается **отдельной строкой** «Промо-позиции (отдельный
  заказ)», а не внутри общей суммы.

Промо-строки **исключить** из поиска по корзине, из массового выделения, из «Переместить в
корзину» ([MoveToCartDialog](../../../resources/js/Pages/User/Cart/MoveToCartDialog.jsx)) и
из очистки корзины — они не принадлежат клиенту как обычные позиции. Проверить каждый из
этих сценариев руками.

## Фронтенд — чекаут

[Checkout/Index.jsx](../../../resources/js/Pages/User/Checkout/Index.jsx) уже
параметризован: компонент `ItemTable` ([строка 923](../../../resources/js/Pages/User/Checkout/Index.jsx#L923))
принимает `title`, `icon`, `items`, `totals`, `colorPalette`. Добавляем **две** группы
после уценки (строка 190):

| Группа | Заголовок | Иконка | Палитра |
|---|---|---|---|
| `promoItems` | «Промо-позиции» | `LuGift` | синяя/бирюзовая |
| `sampleItems` | «Рекламные образцы» | `LuSprout` (или подобная) | серая |

Обязательно обновить условие показа общего итога на
[строке 203](../../../resources/js/Pages/User/Checkout/Index.jsx#L203):
`[instockItems, preorderItems, defectItems]` → добавить обе новые группы, иначе при
корзине «товары + подарок» общий итог не покажется.

Под каждой новой таблицей — пометка «Будет оформлено отдельным заказом». Для рекламных
образцов дополнительно: «Не входит в накладную» — это прямое требование учёта, и клиент
должен видеть его до оформления.

## Нюансы

- **Промо-позиции не участвуют в условиях.** Гарантируется движком (карточка 02), но здесь
  нужен интеграционный тест: платная позиция за 40 ₽ не поднимает сумму корзины до
  следующего порога.
- **Дребезг.** Клиент меняет количество → промо появляется → сумма меняется → промо
  исчезает. Пересчёт идёт после debounce количеств (карточка 05); дополнительно проверить,
  что блок не «прыгает» при удержании «−».
- **Несколько корзин.** Выбор в `cart_promotion_selections` привязан к корзине. При
  `moveItems` между корзинами ([CartService::moveItems](../../../app/Services/Cart/CartService.php#L59))
  выбор **не переносится** — промо пересчитается в целевой корзине заново.
- **Пустая корзина из одних промо-позиций невозможна** — они производные; если базовые
  строки удалены, промо исчезает само.
- Chakra — только через `@/components/ui/*`, тексты — только по-русски.

## Критерии готовности

- [x] `getCartDetails()` отдаёт `promo_items` с виртуальными строковыми id; тест, что такой
      id не проходит в `/api/cart/items/{id}` (PATCH и DELETE → 404).
- [x] Итоги промо считаются отдельно (`promo_quantity` / `promo_amount`) и не подмешиваются
      в сумму основной корзины — тест: корзина 300 ₽ + промо 80 ₽ показывает 300 ₽.
- [x] Выбор из `choices` и отказ от платной позиции работают и переживают перезагрузку.
- [x] Отказ от бесплатной позиции возвращает 422.
- [x] Промо-строки исключены из поиска, выделения, перемещения и очистки корзины —
      **структурно**: они приходят отдельным ключом `promo_items`, а все эти сценарии
      работают по `items` / `defectItems`. Фильтровать нечего.
- [ ] ⏳ Чекаут пересчитывает промо авторитетно; исчезнувшая позиция не роняет оформление.
      **Перенесено в promo-09**: пересчёт имеет смысл только вместе с созданием промо-заказов,
      сейчас позиции никуда не записываются и пересчитывать нечего.
- [x] Общий итог в чекауте показывается при комбинации «товары + промо» — условие на
      строке 203 расширено обеими новыми группами.
- [x] Пометки «отдельным заказом» и «не входит в накладную» присутствуют.
- [ ] Проверено вручную: десктоп и мобильные карточки, корзина с одновременным наличием
      наличия, предзаказа, уценки, подотчётной промо-позиции и образца — пять секций
      подряд не должны разваливать вёрстку.

## Отклонения от карточки

**Секция вместо строк в общей таблице.** Карточка предлагала `CartPromoTableRow.jsx` /
`CartPromoMobileCard.jsx` внутри `CartTable`. Сделал отдельный `CartPromoSection.jsx`
со своей таблицей и мобильными карточками: `CartTable` построен на product_id-агрегации
через store со spillover instock/preorder, а промо-строке нужен ровно противоположный
режим — фиксированное количество, никакого store, строковый id. Встраивание потребовало
бы исключений в каждом обработчике таблицы.

**Промо не в `items`, а отдельным ключом.** Это и дало бесплатное исключение из поиска,
выделения, перемещения и очистки — вместо пяти отдельных фильтров.
