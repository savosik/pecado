# res-01 · Топик в Agent Hub: протокол резервов с 1С

**Приоритет:** высокий
**Создано:** 2026-09-02
**Эпик:** [res-00](2026-09-02_res-00-epic.md)
**Зависимости:** нет — стартовая карточка, блокирует весь эпик
**Волна:** 0

## Описание

Без 1С процесса нет: статус «Резерв», приём исходящих сообщений по заказам от сайта,
снятие резерва — всё живёт на стороне 1С:КА2. Протокол согласовываем не устно, а через
Agent Hub — «переговорную комнату» агента сайта и агента 1С (`/api/agent-hub/{token}`,
админка `/admin/agent-topics/{id}`, ход строго по очереди, `proposal` → `resolution`
закрывают топик). Формат обкатан на кругах сверки взаиморасчётов.

### Постановка для топика

Что сайт хочет отправлять:
- признак резерва в `order.created` (заказ создаётся сразу в статусе «Резерв»);
- исходящие `order.updated` (правка состава клиентом) и `order.deleted` /
  `order.cancelled` (отмена клиентом) — сейчас контракт «сайт → 1С» описывает только
  `order.created`.

Что сайт ожидает от 1С:
- статус «Резерв» во входящем `order.updated` (постановка/снятие);
- переход резерва в обычный конвейер после подтверждения клиентом.

Спорные места, которые агенты решают в топике:
- именование события отмены (`order.deleted` vs `order.cancelled`) и его семантика
  (soft-delete? перевод в закрытые?);
- семантика полной замены `items` в направлении сайт → 1С (зеркально
  `HandleOrderUpdated`?), идемпотентность повторной доставки;
- разрешение конфликта «менеджер правит в 1С, клиент правит на сайте» по полю `revision`;
- кто снимает резерв по таймауту — сайт командой или 1С своим таймером — и что делает 1С
  с резервом, если менеджер руками начал сборку.

### Практика работы в комнате (выстрадано на круге 11)

Long-poll `wait=25` не использовать (держит php-fpm воркер) — лента с `wait=0`, ход ждать
вахтой через прод-БД (`SELECT status, turn, last_seq FROM agent_topics`); вахту
перезапускать после каждого своего хода; большие payload забирать с `--compressed`;
ход у себя — законное состояние ожидания.

## Ход работ

- **02.09.2026** — топик **№5** создан на проде (`/admin/agent-topics/5`), постановка
  из этой карточки целиком в `task_body`. Первое сообщение сайта отправлено (seq 1),
  ход передан 1С, статус `in_progress`. Ссылки сторон — на странице топика в админке;
  ссылку `erp_url` нужно передать стороне 1С вручную (их агент читает её сам).

- **02.09.2026, вечер** — агент 1С ответил по всем шести разделам (seq 2). Ключевые
  коррекции протокола:
  - статуса «Резерв» в 1С **нет и не будет**: резерв живёт на строке заказа
    (`ВариантОбеспечения = СоСклада`), статус документа `КОбеспечению`; на сайт резервные
    заказы сейчас приезжают как `ready_for_shipment` — различать по **аддитивным полям
    `reserve`/`reserved_until`** в order.created/updated, новый статус на сайте не заводим;
  - 🔥 наш `order.updated` в 1С реализован, но **молча теряется для проведённых заказов**
    (а заказы с сайта проводятся сразу) — 1С снимет гейт для окна резерва;
  - подтверждение — отдельным событием **`order.confirmed`** (не updated с reserve:false);
  - отмена — `order.deleted`, в 1С = отмена строк + `Закрыт`, без пометки удаления;
  - `revision` — счётчик сообщений, не версия: блокировка по **`items_version`** /
    `base_items_version` (растёт только при изменении строк), конфликт 1С сигналит
    обычным order.updated с полем `conflict`;
  - таймер у сайта + страховочный регламент 1С (`reserved_until` + 6 ч грации);
  - 1С загейтит свою авто-отгрузку по признаку резерва;
  - ⚠️ **бизнес-гейт**: у 1С политика «без резервов», удержание остатка утверждает их
    владелец; протокол доводим сейчас, раскатка — после его подтверждения.
- **02.09.2026, вечер** — сайт принял все три развилки с уточнениями (`message_id` в наших
  исходящих, `items_version` во всех исходящих 1С, conflict тем же updated) — seq 3,
  ход у 1С. Следующий ход сайта — `proposal` с финальной редакцией.

- **03.09.2026** — 1С приняла все уточнения (seq 4). Решение их владельца: **окно 24 часа,
  охват по флагу партнёра**; механика «предел удержания» (наш `reserved_until` — истина в
  пределах их настраиваемого лимита, сверх — удерживают до лимита и возвращают фактический
  срок); два правила рассинхрона флагов; их старый реквизит резерва мёртв (true у всех 710).
  Их замер по августу: 64% заказов отгружаются в сутки, заморозка +353 тыс ₽ при «все, 24 ч».
- **03.09.2026** — ответ на их вопрос об охвате по нашей CRM: из 191 партнёра с профилем
  84 — интернет-магазины; в августе активны 42, дали **96% заказов (1997/2077) и 87%
  оборота (10,11/11,61 млн ₽)**. Реалистичный сценарий — «все заказы, 24 ч».
- **03.09.2026** — отправлен **`proposal`** (seq 5) с финальной редакцией: 4 события
  сайт → 1С (order.created+reserve, order.updated+base_items_version, order.deleted+reason,
  order.confirmed), аддитивные поля 1С → сайт (reserve, фактический reserved_until,
  items_version, conflict{}, partner.reserve_allowed — мастер флага 1С), 8 правил
  (предел удержания, рассинхрон, гейт сборки, конфликты, таймаут+грация 6 ч,
  идемпотентность, раскатка за флагами). Ход у 1С, ждём `resolution`.

- **03.09.2026, 13:41** — **`resolution` получен (seq 6): редакция принята без изменений.**
  Топик №5 `resolved`. Доп. реквизиты заказа (признак резерва, фактический срок, версия
  состава) на стороне 1С уже заведены; канал `partner.*` готов к полю `reserve_allowed`.
  Две ремарки 1С на этап раскатки:
  - **сверка списков участников поимённо**: их флаг «есть интернет-магазин» — у 73 из 1270
    партнёров (29 активных в августе, 74% заказов / 85% оборота), наш профиль CRM — 84
    (42 активных, 96% / 87%); списки пересекаются, но не совпадают, мастер — 1С. Сайт
    присылает свои 84 партнёра по uuid, 1С размечает `reserve_allowed` и возвращает
    фактический состав через `partner.updated` → **учтено в res-05**;
  - расхождение счёта заказов августа (2077 у нас против 2037 у них, ~0,6 млн) — граница
    периода и недоехавшие заказы, отдельного разбора не требуют.
  - 1С ждёт ссылку на обновлённую спецификацию (итог res-02); топик resolved — ссылку
    передать через модератора в админке или новым мини-топиком.
