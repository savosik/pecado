# res-09 · Авто-снятие резерва по таймауту + уведомления

**Приоритет:** высокий
**Создано:** 2026-09-02
**Эпик:** [res-00](2026-09-02_res-00-epic.md)
**Зависимости:** res-05, res-07
**Волна:** 2

## Описание

Дедлайн — главный предохранитель режима: без него интернетчики начнут держать резервы
неделями «на всякий случай».

### Авто-снятие

- Artisan-команда (шедулер, каждые N минут): находит заказы в статусе «Резерв» с истёкшим
  `reserved_until` и снимает резерв — отмена заказа + исходящее сообщение в 1С.
- Кто источник снятия (сайт командой или 1С своим таймером) — по resolution res-01;
  если снимает 1С, команда сайта становится страховкой/сверкой, а не источником.
- Идемпотентность: повторный прогон по уже снятому резерву — no-op; гонка с подтверждением
  клиента в последнюю секунду решается атомарно (снимаем только из статуса «Резерв»).

### Уведомления — через матрицу note-00, без своего движка

Два новых типа уведомлений в `config/mail_occasions.php` + `MailStream::capture()`:

- `orders.reserve_expiring` — «резерв истекает через X часов» (порог — конфиг, слать
  один раз на заказ: ступень в `origin_key` по образцу finance.*);
- `orders.reserve_released` — «резерв снят, товар возвращён в свободный остаток».

Оба `client_visible`; включённость по умолчанию — решить по действующей политике
(клиентские типы выключены умолчанием — но для этих двух есть довод включить, иначе
режим молчит о главном; вынести заказчику). Тестам потока нужен трейт
`EnablesClientNotifications`.

## Ход работ

- **04.09.2026** — реализовано:
  - команда `reserve:release-expired` (шедулер: каждые 5 минут, withoutOverlapping):
    два этапа — предупреждение `orders.reserve_expiring` за `expiring_notice_hours`
    (конфиг, 3 ч) и снятие просроченных: `order.deleted` (reason=reserve_expired) →
    локально closed + soft-delete + история статусов «Резерв истёк — заказ снят
    автоматически»; гонка с подтверждением закрыта `lockForUpdate` + перепроверкой
    состояния;
  - **команда работает независимо от рубильника**: аварийное выключение режима
    не подвешивает висящие резервы (решение из res-05 «доживают штатно»);
  - уведомления через матрицу note-00: `orders.reserve_expiring` и
    `orders.reserve_released` в `config/mail_occasions.php` (client_visible);
    однократность — штатный дедуп MailStream по origin_key (повод + клиент +
    order_number), отдельного состояния не заведено;
  - ⚠️ **default_enabled = false по общей политике клиентских уведомлений** —
    при включении режима владельцем эти два повода нужно включить участникам,
    иначе клиент теряет резерв молча. Вопрос — в чек-лист включения.
  - Тесты: `ReserveAutoReleaseTest` (5 шт: снятие+публикация+история, идемпотентность,
    оба письма, однократность «истекает», работа при выключенном рубильнике);
    смежные Order/Erp/Mail/Console — 546 зелёных, Pint чистый.

## Критерии готовности

- [x] Просроченный резерв снимается автоматически, `order.deleted` уходит в 1С (интеграционный тест).
- [x] Повторный прогон идемпотентен; гонка с подтверждением закрыта lockForUpdate (тест).
- [x] Оба типа уведомлений в каталоге матрицы, письма уходят по настройкам партнёра.
- [x] «Истекает» шлётся ровно один раз на заказ.
- [x] Команда в шедулере каждые 5 минут (лёгкая: два индексных запроса, вне пика не нуждается).
