## Контекст

Заказы создаются **в двух местах с продублированной логикой**:

| | [CheckoutService::checkout()](../../../app/Services/Order/CheckoutService.php#L37) | [ClientApiController::orders()](../../../app/Http/Controllers/Api/ClientApiController.php#L221) |
|---|---|---|
| Сборка `baseOrderData` | строки 50–65 | строки 351–364 |
| Расщепление по типам | `instock` / `preorder` / `defect` | `instock` / `preorder` |
| Создание позиций | `createOrderItems()` (строка 180) | свой `createOrderItems()` (строка 481) |
| Фиксация суммы | `saveQuietly()` | **`$order->update([...])`** |
| События | `OrderCreated::dispatch()` внутри транзакции | `OrderCreated::dispatch()` после коммита |

Если добавлять промо-позиции копипастой в оба места, каналы разойдутся в первый же месяц.
Поэтому общая сборка выносится **до** карточек 08/09/12.

### Попутная находка — расхождение в событиях

`Order` объявляет [`$dispatchesEvents['updated'] => OrderUpdated`](../../../app/Models/Order.php#L99).
`CheckoutService` намеренно фиксирует сумму через `saveQuietly()`, чтобы не выпустить
`OrderUpdated` сразу после создания. `ClientApiController` делает
`$order->update(['total_amount' => $total])` — то есть **выпускает `OrderUpdated` внутри
транзакции**, а `OrderCreated` — только после коммита (строка 420).

`PublishOrderToErp` слушает оба события, а `PublishOrderToErpJob` уходит в очередь
`erp_publish`. Значит для API-заказов в 1С может прийти `order.updated` **раньше**
`order.created`.

**Подтверждено тестом, а не логами.** `ClientApiOrderPublishTest` до фикса падал ровно
так: на один заказ уходило **два** сообщения (`order.updated` + `order.created`),
на расщеплённый — **четыре** вместо двух. Все четыре конфигурации очередей имеют
`after_commit => false`, поэтому задание уходило в Redis прямо из транзакции.
Логи `erp_bus_messages` на dev посмотреть не удалось: SSH закрыт на обоих адресах
(`93.94.150.16:8022` и `93.94.150.74:22` — `Connection refused`), при этом сам стенд
жив (`https://dev.pecado.ru/` отдаёт 200, деплой через self-hosted runner проходит).
То есть дело не в упавшей машине, а в закрытом порте, и ждать его бессмысленно —
проверять надо через админку: **Админка → ERP-шина → Сообщения**, фильтр по
`order.created` / `order.updated` после оформления заказа через клиентское API.

## Задача

`App\Services\Order\OrderAssembler` — единственное место, где создаётся заказ.

```
assemble(OrderDraft $draft): Collection<Order>
```

`OrderDraft` (readonly DTO) несёт: пользователя, компанию, адрес и способ доставки,
комментарии (клиента, менеджера, склада), `cart_id` (nullable — у API его нет), валюту и
курс, и **сгруппированные наборы строк по типу заказа**.

`OrderAssembler` отвечает за:
- создание заказа на каждую непустую группу с корректным `OrderType`;
- создание позиций;
- подсчёт и фиксацию `total_amount` **без** выпуска `OrderUpdated`;
- единый порядок событий: `OrderCreated` **после коммита транзакции** для всех заказов
  (через `DB::afterCommit`), одинаково для чекаута и API;
- расширяемость: добавление типа `promo` / `promo_sample` в карточке 09 не должно трогать
  ни чекаут, ни контроллер API.

## Что остаётся снаружи

`OrderAssembler` **не** занимается:
- проверкой остатков — она разная (чекаут кидает `InsufficientStockException`, API
  «дружелюбно» урезает количество и складывает недостачу в `not_accepted` / `partial`);
- расчётом промо — это `PromotionEngine`, вызывается до сборки;
- листом отбора в `warehouse_comment` — форматтеры остаются отдельными сервисами.

Это принципиально: сборщик должен быть тупым и предсказуемым, вся вариативность — в
подготовке `OrderDraft`.

## Нюансы

- **Никакого изменения внешнего поведения.** Задача чисто структурная: те же заказы, те же
  суммы, те же события (кроме сознательного исправления порядка для API). Формат ответа
  клиентского API не меняется ни на байт — на нём сидят боевые интеграции (Гевея, sex-opt,
  см. `project_geveya_exports`).
- **Цены.** Чекаут берёт цену через `PriceService::getPriceResult()` и пишет в позицию
  `base_price` / `discount_percent` / `final_price`; уценка (`createDefectOrderItems`,
  строка 212) — фиксированную цену из строки корзины без скидок. Обе стратегии должны
  сохраниться, для этого в `OrderDraft` строка несёт уже посчитанную цену либо признак
  «посчитать по прайсу».
- **Снапшоты.** Не потерять `defect_description` (снапшот описания дефекта, строка 224).
  Про `brand_name_snapshot` в карточке была ошибка: поле есть в `$fillable` у `OrderItem`,
  но ни один из двух путей его не заполнял — снапшот бренда живёт в `ShipmentItem`.
  Поведение не менял: заполнять его при сборке заказа — отдельное решение.
- **Транзакция.** Чекаут работает внутри `DB::transaction` целиком, включая проверку
  остатков. Сохранить это свойство: параллельный чекаут той же партии брака уже
  обсуждается в комментарии на [строке 149](../../../app/Services/Order/CheckoutService.php#L149)
  и его поведение менять нельзя.
- **`OrderChangeLogger`.** API логирует недостачу через `logApiShortfall` уже после
  сборки — порядок вызовов сохранить.
