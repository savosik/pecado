# fin-08 · CRM: /crm/finance на регистре + акт сверки

**Приоритет:** высокий
**Создано:** 2026-08-09
**Эпик:** [fin-00](2026-08-09_fin-00-epic.md)
**Зависимости:** `fin-07`
**Волна:** 3

## Описание

Существующие экраны `/crm/finance` меняют источник, но не вид: пульт, план поступлений,
просрочка и балансы остаются как есть. Добавляется то, чего в CRM никогда не было и о чём
просил заказчик — **акт сверки**.

Шесть вопросов отдела продаж и где на них теперь отвечают:

| Вопрос | Экран |
|---|---|
| Какой у клиента баланс | Балансы + карточка клиента |
| Сколько оплатил и когда | **Акт сверки** (новое) + журнал платежей |
| Какая текущая просрочка | Просрочка |
| Сколько заплатит в будущем | План поступлений |
| Какой поток по дням | Пульт платежей |
| Кому звонить | Просрочка → топ-должники |

## Что делаем

### Существующие экраны — смена источника

`app/Http/Controllers/Crm/FinanceController.php` и
`resources/js/Crm/Pages/Finance/{Index,Plan,Overdue,Balances}.jsx`.

Контроллер уже работает через `PaymentForecastService`, поэтому правок в нём минимум — источник
подменён в `fin-07`. Проверить: изоляция `User::visibleInCrm($actor)`, разрез по менеджерам
через `crm-clients-all.view`, пагинация `PER_PAGE=50`, XLSX.

Новая KPI-плитка на пульте: **фактический баланс** рядом с «Долг клиентов по 1С». Два числа
разные по смыслу, и до сих пор их путали.

### Новый экран — акт сверки

`GET /crm/finance/reconciliation` (право `crm-finance.view`), страница
`resources/js/Crm/Pages/Finance/Reconciliation.jsx`, пункт в
`resources/js/Crm/config/menuConfig.ts`.

Форма: клиент + организация + период, соглашение — необязательный фильтр. Таблица — как акт сверки из 1С:

```
Дата | Документ | Тип операции | Дебет | Кредит | Сальдо нарастающим
```

Шапка: сальдо на начало периода. Подвал: обороты дебет/кредит и сальдо на конец.
Внизу — расшифровка формулы словами, чтобы менеджер мог объяснить её клиенту:
«Начальное сальдо + Оплаты + Возвраты товара − Реализации − Возврат денег».

Экспорт в XLSX — четвёртым листом к существующему экспорту либо отдельной кнопкой.

**Баннер расхождения.** Если `SUM(регистр)` не сходится с `contractor_organization_balances.current_balance`
больше чем на 0,01 ₽ — заметное предупреждение над таблицей: цифры расходятся с 1С, обратитесь
к администратору. Молча показывать неверный акт нельзя — его отправят клиенту.

### UI

Chakra UI v3, импорт **только** из `@/components/ui/*`. Layout-примитивы (`Box`, `HStack`,
`Table`) — из `@chakra-ui/react` можно. Весь интерфейс на русском, включая пагинацию,
пустые состояния и ошибки валидации.

## Edge-кейсы

- **У клиента несколько наших юрлиц** → выбор организации обязателен, «все» показывает
  сумму, но акт формируется по одной: сводный акт по разным юрлицам юридически бессмыслен.
- **Движения без соглашения** → в фильтре по соглашению отдельный пункт «Без соглашения».
- **Период до 01.01.2026** → пусто + пояснение, что регистр ведётся с этой даты. Не «нет данных».
- **Мультивалютный контрагент** → акт в валюте движений, рублёвый эквивалент справочно.
- **Сальдо на начало = сальдо на конец при наличии оборотов** → легитимно (оплатил ровно
  столько, сколько отгрузили).
- **Клиент вне скоупа менеджера** → 403 через `User::visibleInCrm()`, как на остальных экранах.

## Что сделано (2026-08-11)

`ReconciliationService` + метод контроллера + `Reconciliation.jsx`, вкладка в разделе
и пункт меню.

**Клиент выбирается явно**, а не берётся из фильтров раздела: акт — документ по одному
контрагенту, «акт по всем клиентам менеджера» не имеет смысла. Чужой клиент даёт 404
через `visibleInCrm`, а не показывает деньги другого менеджера.

**Баннер расхождения красный и с прямым текстом** «акт отправлять нельзя». Мягкое
предупреждение здесь не годится: документ уходит клиенту, и цифра, не сходящаяся
с учётной системой, вернётся к нам вопросом от его бухгалтерии.

**Период раньше 01.01.2026 помечается отдельно** от пустого акта. Разница не косметическая:
пустой акт менеджер отправит клиенту как «расчётов не было», хотя история просто
не заливалась.

**Плитка «Фактический баланс» показывается только на регистре.** Старое ядро отдаёт
`balance_fact = null`, и плитка скрывается: подменять её нулём нельзя — ноль на пульте
читается как «клиент ничего не должен».

**Потолок 2000 строк** с явной пометкой усечения: без неё сальдо на конец было бы
неверным, а выглядело бы правдоподобно.

### Чего нет и почему

**XLSX-экспорт акта не сделан.** Он требует решения, которое лучше принимать на живых
данных: отдельная кнопка или четвёртый лист общей выгрузки — зависит от того, как
менеджеры реально отправляют акт клиенту. Заводить кнопку вслепую значит гадать.
Вынесено в `fin-10` или отдельную карточку после первой заливки.

**Визуальная проверка на dev не проводилась** — регистр пуст, экран покажет форму
и пустое состояние. Смотреть его имеет смысл после `fin-05`.

Тесты: `tests/Feature/Crm/FinanceReconciliationTest.php` — 12 кейсов.
