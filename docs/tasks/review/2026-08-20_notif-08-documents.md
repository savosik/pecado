## Описание

Второй кейс заказчика: «акты сверки по контрагенту Серову приходят на одни емейлы,
а реализации (сканы) — на другие».

Данные уже есть: раздел «Документы» работает на проде с 2026-08-14, 6,5 тыс. печатных форм.
Раздел подписок `documents` заведён в `config/subscriptions.php` заранее и выключен — **и ни
одного триггера у него нет вовсе**. Карточка закрывает этот пробел уже на движке пульта.

Enum `App\Enums\PrintedDocumentType` даёт готовые русские метки и `options()` для конструктора
условий — заводить справочник не нужно.

## Что делаем

### События

| Ключ | Повод | Поля для условий |
|---|---|---|
| `documents.published` | `PrintedDocument` создан или перевыставлен | `document_type` (enum), `base_document_kind`, `organization_id`, `is_revision`, `number`, `document_date` |
| `documents.deleted` | `HandlePrintedDocumentDeleted` | те же |

Кейс Серова закрывается двумя правилами на область «контрагент Серов»:

- `document_type = reconciliation_act` → контакты роли «бухгалтер»;
- `document_type in [upd, waybill, tax_invoice]` → контакты роли «логист».

### Точка диспатча и две ловушки

Сигнал ставится в `app/Services/Erp/Handlers/HandlePrintedDocumentPublished.php`, но
**не безусловно** — две реальные ловушки:

1. **Документ приходит без `company_id`.** Привязку доклеивает команда `documents:relink`
   каждые 10 минут. Сигнал, поставленный сразу, промахнётся мимо правил по контрагенту —
   а это ровно кейс заказчика. Решение: сигнал только при непустом `company_id`; если пусто —
   отложить до relink (диспатч из `RelinkPrintedDocuments` для тех, что докленись, либо
   отложенный job с проверкой).

2. **Файл ещё не перенесён.** `file_status` проходит `pending → stored`, и письмо со ссылкой
   на неперенесённый файл бесполезно. Сигнал только при `file_status = stored`
   (см. константы `PrintedDocument::FILE_*` и скоуп на `FILE_STORED`).

### Защита от первичной выгрузки

В `doc-00` заказчик уже опасался, что первичная выгрузка истории разошлёт тысячи писем —
именно поэтому раздел подписок `documents` заведён выключенным.

Здесь работают два предохранителя эпика:

- **возрастной ценз** из `notif-03`: документ с `erp_created_at` старше
  `max_signal_age_minutes` не порождает рассылку (`skip_reason = too_old`);
- домен гейтится `PULSE_DOMAIN_DOCUMENTS`, по умолчанию выключен.

Дополнительно перед включением на проде — прогон `notifications:simulate` по выборке
документов за сутки, чтобы увидеть порядок числа писем заранее.

### Письмо

Шаблон `resources/views/mail/pulse/documents/published.blade.php`: тип документа, номер, дата,
контрагент, наше юрлицо, **ссылка на скачивание в кабинете, а не вложение**. Документы приватные,
лежат на закрытом диске, и пересылка файла на произвольный адрес из адресной книги — отдельное
решение по безопасности, которого заказчик не просил. Вложения появляются только в `notif-10`
и только для счёта к сроку оплаты.

### Системное правило

`sys.documents.published.client` — `client_user`, приоритет 500, создаётся **выключенным**:
сегодня клиенты писем о документах не получают, и включение должно быть осознанным решением,
а не побочным эффектом деплоя.

## Критерии готовности

- [ ] События `documents.published` / `documents.deleted` в реестре; поля из `PrintedDocumentType::options()`
- [ ] Сигнал ставится только при `file_status = stored` И непустом `company_id`
- [ ] Документы, у которых `company_id` доклеился позже, порождают сигнал после `documents:relink`
- [ ] Возрастной ценз отсекает историческую выгрузку — тест на документе с давним `erp_created_at`
- [ ] Флаг `PULSE_DOMAIN_DOCUMENTS`, по умолчанию выключен
- [ ] Шаблон письма со ссылкой на кабинет; файл не вкладывается
- [ ] Системное правило `sys.documents.published.client` создаётся выключенным
