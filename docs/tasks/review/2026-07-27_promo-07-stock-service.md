# Промо 07 — Фонд промо-позиций (`PromoStockService`)

**Приоритет:** высокий
**Создано:** 2026-07-27
**Roadmap:** [docs/promo-constructor-roadmap.md → Волна 2](../../promo-constructor-roadmap.md)
**Зависит от:** [promo-01-foundation](2026-07-27_promo-01-foundation.md)

## Контекст

Решение заказчика: **отдельного учёта фонда нет**. Сколько промо-позиций можно раздать —
определяется остатком склада-источника, который 1С передаёт по шине
(`stock.updated` → [HandleStockUpdated](../../../app/Services/Erp/Handlers/HandleStockUpdated.php)
→ pivot `product_warehouse.quantity`).

Второе решение: **нет остатка — промо-позицию не добавляем**, молча, без сообщений клиенту.

## ⚠️ Отклонение от карточки: резерв считается по товару, а не по складу

Карточка задавала `available(товар, склад)` и резерв «по заказам с этого склада».
**Схема так не умеет**: ни `orders`, ни `order_items` не хранят склад — `warehouse_uuids`
вычисляется в момент публикации из типа заказа и региона пользователя
([PublishOrderToErp::resolveWarehouseUuids()](../../../app/Listeners/PublishOrderToErp.php#L124)).
Привязать резерв существующего заказа к складу нечем.

Сделано иначе: сигнатура повторяет `StockService::getStock(Product, ?User)` — остаток берётся
по primary-складам региона клиента, резерв считается по товару целиком. Это консервативнее
(промо-заказ в другом регионе уменьшит доступность здесь), и ошибка уходит в безопасную
сторону — карточка сама требует «нет остатка → не выдаём молча», а значит недодать лучше,
чем пообещать и не выдать. Если склад у награды задан явно (`reward.warehouse_id`), остаток
берётся с него напрямую, минуя регион.

## Побочный результат: кейсы `promo` / `promo_sample` пришлось объявить сразу

Планировалось, что типы заказов принесёт promo-09 вместе с контрактом 1С. Не вышло:
первый же тест на удаление промо-заказа упал с `ValueError: "promo" is not a valid backing
value for enum OrderType` — каст `Order::$casts['type']` роняет **любой** Eloquent-путь,
включая листенер публикации в ERP. Без кейсов промо-заказ не живёт вообще.

Кейсы добавлены, но помечены как невыпущенные (`OrderType::UNRELEASED`): `options()`
их не отдаёт, поэтому в фильтрах админки и кабинета они не появятся до promo-09/10 —
иначе пользователь получил бы выбор, который ничего не находит. Контракт с 1С не тронут:
заказов этих типов пока никто не создаёт.

## Задача

`App\Services\Promotion\PromoStockService` — точная копия идеологии
[DefectStockService](../../../app/Services/Defect/DefectStockService.php), включая ключевой
принцип из его док-блока: «резерв — производная величина, а не поле… так удаление заказа
само возвращает партию в продажу, и нет риска рассинхрона денормализованного счётчика».

```
доступно(товар, склад) = product_warehouse.quantity
                       − резерв по order_items незакрытых заказов типов promo / promo_sample
                         с этого склада
```

Методы (сигнатуры по образцу `DefectStockServiceInterface`):

- `available(int $productId, int $warehouseId): int`
- `availableMap(array $pairs): array` — **батч**, ключ `productId:warehouseId`
- `reserved(...)` / `reservedMap(...)`

Интерфейс `App\Contracts\Promotion\PromoStockServiceInterface` + биндинг в провайдере, как
сделано для уценки.

## Резерв — какие заказы считать

Резервируют промо-заказы, которые ещё не отгружены. Ориентир — те же правила, по которым
считается резерв уценки: заказ не удалён (`whereNull('deleted_at')`) и не закрыт.
Уточнить перечень статусов при реализации по
[`OrderStatus`](../../../app/Enums/OrderStatus.php) и **зафиксировать его константой**, а не
раскидывать по коду.

## Батч-безопасность — обязательна

`PromotionEngine` вызывает сервис на каждый рендер корзины, а наград у активных правил
могут быть десятки. Количество запросов не должно зависеть от числа проверяемых пар
«товар + склад»: один запрос к `product_warehouse`, один — к `order_items` с группировкой.
Тест фиксирует потолок запросов через `DB::listen`.

## Подключение к движку

В карточке 02 доступность была заглушкой. Здесь:
- движок проверяет каждую награду через `availableMap()` **одним батчем** на весь
  результат вычисления;
- недоступная награда уходит в `blocked` с причиной `out_of_stock`;
- при `multiply: per_threshold` доступный остаток **урезает множитель**: если по условию
  положено 5 штук, а на складе 2 — выдаём 2, а не «ничего» и не «5».

## Нюансы

- **Овербукинг на обычных складах.** Подотчётная промо-позиция лежит на складе региона и
  параллельно продаётся клиентам: витринное наличие про промо-резерв не знает. Принимаем
  тот же компромисс, что уже принят для уценки —
  [«параллельный checkout может дать небольшой овербукинг… окончательный остаток
  подтверждает 1С реализацией»](../../../app/Services/Order/CheckoutService.php#L149).
  Вычитать промо-резерв из `StockService` **не** нужно: это горячий путь всего каталога.
  Зафиксировать решение комментарием в коде, чтобы к нему не возвращались.
- **Склад «Москва реклама» появится в волне 3.** До тех пор награды с `promo_kind: sample`
  всегда возвращают 0 доступных — и это корректное поведение, а не ошибка.
- **Пустой pivot.** Если у товара вообще нет строки в `product_warehouse` для склада —
  это 0, а не исключение. По шине приходят не все склады.
- **Кэш.** Не кэшировать. Остатки меняются по шине постоянно, а цена ошибки — обещанная и
  не выданная промо-позиция.

## Что пришлось поправить в существующих тестах

Три класса (`PromotionEngineTest`, `CartPromotionProgressTest`, `PromotionRuleControllerTest`)
проверяют правила и тексты, а не склад, и их фикстуры складов не заводят. Раньше движок
работал с заглушкой «всегда доступно» через биндинг по умолчанию — теперь заглушка
привязывается в `setUp` этих классов явно. Это честнее: боевое поведение осталось
поведением по умолчанию, и будущий тест поймает регрессию, а не тихо получит `PHP_INT_MAX`.
