# short-02: справочник причин недоборов, чипы и степень удовлетворения

**Приоритет:** высокий
**Создано:** 2026-08-31
**Продолжает:** [short-01](../review/2026-08-20_short-01-cancellation-journal.md)

## Описание

Метка отмены была зашита в код двумя значениями (`склад` / `клиент`). Реальных
причин у отдела продаж девять, и список будет меняться — заводить их должен РОП
в CRM, а не разработчик в enum.

Заказчик просит:

1. Справочник причин недоборов, который ведёт РОП (создать, переименовать,
   отключить, удалить неиспользуемую).
2. Девять заводских причин из коробки.
3. Выбор причины прямо в строке журнала — выпадающим списком.
4. Легенда причин с описанием: менеджер должен понимать, что выбирает.
5. Быстрые фильтры-чипы с количеством и суммой по категориям.
6. Фильтр по периодам.
7. Степень удовлетворения по закрытию заказов в процентах.

## Решения

- **Причина — строка справочника, категория — перечисление в коде.** Причин будет
  много и они будут меняться; категорий шесть, и они держат аналитику: чипы, цвета,
  легенда. Свободные категории превратили бы справочник в движок правил, а сводку —
  в кашу из синонимов.
- **Заводские причины защищены от удаления** (`is_system`), но отключаются как любые:
  на них ссылается разметка прошлых периодов.
- **Используемую причину удалить нельзя** — только отключить (FK `restrictOnDelete`).
- **`order_items.cancel_source` удалён**: две правды о причине отмены не нужны,
  старая разметка перенесена в причины (`склад` → «недостача на складе»,
  `клиент` → «отменил менеджер по просьбе клиента»).
- **Степень удовлетворения считается по заказам периода**, а не по журналу отмен:
  журнал отвечает «что отменилось», удовлетворение — «какая доля заказанного уехала».
  База по умолчанию — отгруженные заказы (`awaiting_payment`, `ready_for_closure`,
  `closed`): пока заказ собирают, склад ещё снимает позиции. Формально финальный
  статус — `closed`, но 1С им не пользуется: на 7,5 тыс. заказов боевой базы их три,
  и считать по нему значило бы показывать пустой экран.

## Сделано

- **БД**: таблица `shortage_reasons` (название, пояснение, категория, порядок,
  `is_active`, `is_system`), `order_items.cancel_reason_id` (FK, `restrictOnDelete`).
  Колонка `cancel_source` удалена, старая разметка перенесена: 37 складских меток
  боевой базы легли в «Отменил склад по причине недостачи».
- **Категории** — перечисление `App\Enums\Shortage\ShortageReasonCategory`:
  остатки и резерв, снабжение, склад, клиент, менеджер, учёт. Цвет, порядок
  и пояснение для легенды живут там же.
- **Права**: ресурс `crm-shortage-reasons` (view/create/edit/delete) в трёх реестрах
  + миграция выдачи. Менеджеру — только view, справочник ведёт РОП.
- **Экран**: выбор причины списком прямо в строке, чипы категорий с количеством
  и суммой, легенда с описанием, пресеты периода, карточка «Степень удовлетворения»
  (по сумме, по строкам, доля заказов без недобора), вкладка «Причины» с CRUD.
- **Сводки** по партнёрам и товарам показывают разбивку по категориям вместо
  прежней пары «склад / клиент».
- **Смежное**: вечерняя сводка, архив и счётчик меню считают неразобранным
  отсутствие причины; ссылка в письме ведёт в отбор `category=none`.

- [x] Причина выбирается из строки журнала, снимается обратно в «не размечено»
