# crm-01 · Сквозные комментарии: клиент, заказ, реализация + лента клиента

**Приоритет:** высокий
**Создано:** 2026-08-02
**Эпик:** [crm-00](2026-08-02_crm-00-epic.md)
**Волна:** 1 (фундамент)
**Зависимости:** нет — стартовая карточка

## Описание

Дать менеджерам возможность оставлять хронологические комментарии на клиенте, заказе
и реализации, с автором и временем. Главное требование: **в карточке клиента видны все его
комментарии, где бы они ни были оставлены** — включая те, что написаны на его заказах
и отгрузках.

Полиморфных комментариев в проекте нет. Существующие `kanban_comments` жёстко привязаны
к задаче канбана и **не имеют автора** — переиспользовать нечего, заводим свою таблицу.

## Ключевое решение 1: общая карта привязываемых сущностей

`App\Support\Crm\CrmEntityMap` — единственное место, где перечислено, к чему в CRM вообще можно
что-то привязать. На каждую сущность: строковый тип для API, класс модели, как получить клиента
и как построить подпись со ссылкой.

| Тип | Модель | Клиент берётся из |
|---|---|---|
| `client` | `User` | сам `id` |
| `order` | `Order` | `orders.user_id` |
| `shipment` | `Shipment` | `shipments.user_id` |
| `task` | `CrmTask` (волна 3) | `crm_tasks.client_user_id` |

Картой пользуются **комментарии, вложения (`crm-02`) и задачи (`crm-09`)** — все три
полиморфны одинаково. Добавление новой привязываемой сущности = одна строка здесь, без правок
в трёх местах по отдельности.

Тип из запроса резолвится **только** через эту карту, никогда через сырое имя класса:
иначе `commentable_type` из запроса превратился бы в произвольный класс приложения.

## Ключевое решение 2: денормализованный `client_user_id`

У комментария есть **и** полиморфная связь с сущностью (`commentable_type/id`), **и** отдельная
колонка `client_user_id`, проставляемая при создании через `CrmEntityMap::resolveClient()`.

Без этой колонки лента клиента означала бы «собрать все заказы клиента, все его отгрузки,
затем выбрать комментарии по двум спискам ID» — три запроса, растущие с историей клиента.
С ней — один индексированный запрос по `(client_user_id, created_at)`.

Если сущность к клиенту не сводится, `client_user_id` остаётся `null` — запись живёт при своей
сущности и просто не попадает ни в чью ленту. Так же ведут себя заказы без `user_id`
(партнёрские из 1С, 32 шт. на проде): комментируются нормально, в ленту не идут.

## Что делаем

**Миграция `crm_comments`** (комментарии к таблице и всем столбцам — правило проекта):

```php
$table->comment('Комментарии менеджеров к клиентам, заказам и реализациям (CRM)');
$table->id()->comment('Первичный ключ');
$table->morphs('commentable');           // + комментарий колонкам отдельным ->change()
$table->foreignId('client_user_id')->nullable()->constrained('users')->nullOnDelete();
$table->foreignId('user_id')->constrained()->cascadeOnDelete();
$table->text('body')->comment('Текст комментария, обычный текст без разметки');
$table->boolean('is_pinned')->default(false)
      ->comment('Закреплён вверху ленты: важное, что не должно утонуть в хронологии');
$table->timestamps();
$table->softDeletes()->comment('Мягкое удаление: лента — рабочая переписка, восстановимость важнее чистоты');
$table->index(['client_user_id', 'created_at'], 'crm_comments_client_created_idx');
```

Комментарий FK-колонкам ставится **отдельным** `Schema::table(...)->change()` — после
`->constrained()` цепочка `->comment()` в БД не доезжает (грабля зафиксирована в миграции
`2026_07_16_130000_create_analytics_tokens_table.php`).

**Модель `App\Models\CrmComment`** — `SoftDeletes`, связи `commentable()` (morphTo),
`author()` (belongsTo User), `client()` (belongsTo User). Скоуп `forClient(int $userId)`.
Резолв `client_user_id` — в наблюдателе или в сервисе создания, но **в одном месте**, чтобы
новая комментируемая сущность не забыла проставить связь.

**Сервис `App\Services\Crm\ClientTimelineService`** — единая лента карточки клиента.
Возвращает пагинированный список DTO с общей формой:

```
['type' => 'comment'|'task'|'email', 'id', 'happened_at', 'author', 'title', 'excerpt',
 'entity' => ['type' => 'order'|'shipment'|'client', 'id', 'label', 'url']]
```

В этой карточке сервис умеет один тип (`comment`); задачи и письма подмешают карточки
`crm-09` и `crm-10` — расширение существующего сервиса, а не второй.

**Политика `CrmCommentPolicy`**:
- `view` — есть `crm-comments.view` **и** клиент комментария попадает в `User::visibleInCrm($actor)`;
- `create` — `crm-comments.create` + та же проверка видимости клиента;
- `update`/`delete` — только автор, либо обладатель `crm-clients-all.view` (РОП).

Проверка видимости клиента обязательна: без неё менеджер, зная ID, читал бы переписку
по чужому клиенту в обход скоупа.

**Роуты** (в `routes/crm.php`, группа `permission:crm-comments.view`):

```
GET    /crm/clients/{client}/timeline      — лента клиента (JSON, пагинация)
POST   /crm/comments                       — создать (entity_type, entity_id, body)
PATCH  /crm/comments/{comment}             — правка своего
DELETE /crm/comments/{comment}             — мягкое удаление
```

`entity_type` резолвится через `CrmEntityMap`, не через сырое имя класса из запроса.

**Фронтенд:**
- `resources/js/Crm/Components/CommentThread.jsx` — лента + форма, автор и относительное время,
  закрепление, правка/удаление своего. Chakra только из `@/components/ui/*`.
- `resources/js/Crm/Components/ClientTimeline.jsx` — сквозная лента с бейджем сущности
  и ссылкой на неё.
- Врезки: карточка клиента `Crm/Pages/Clients/Show.jsx` (вкладки «Лента» и «Комментарии»),
  админские карточки заказа и реализации.

**Права** в `RolesAndPermissionsSeeder`: ресурс `crm-comments` с действиями
`view, create, edit, delete`, метка «CRM: Комментарии». Выдать `sales-manager`,
`sales-manager-crm`, `sales-head`.

## Границы

- Вложения к комментариям — карточка `crm-02`, здесь только текст.
- Ответы-треды (`parent_id`) не делаем: лента продаж линейна, а вложенность из `kanban_comments`
  там уже создаёт `$with = ['replies']` на каждой выборке. Понадобится — добавим отдельно.
- Полноценных карточек заказа и реализации внутри `/crm/` эта задача не создаёт. Роли без
  доступа в админку (`sales-head`, `sales-manager-crm`) видят такие комментарии в ленте клиента
  со ссылкой на сущность; отдельные CRM-страницы документов — вне скоупа эпика.

### Решения, принятые по ходу

**Эндпоинты отдают JSON, а не Inertia-редиректы.** Один и тот же компонент ленты встраивается
в CRM и в две админские страницы; на редиректах пришлось бы поддерживать три разных способа
обновить страницу после отправки комментария.

**Разделение 404 и 403.** Чужой клиент — всегда 404 (403 подтвердил бы существование клиента).
Свой клиент, но чужой комментарий — 403: правило понятное, скрывать нечего.

**Сущность без клиента доступна только РОПу.** Заказ из 1С без `user_id` в скоуп менеджера
не входит вовсе; иначе комментарии стали бы способом работать с партнёрскими документами
в обход `visibleInCrm`.

**Ссылка на заказ/реализацию отдаётся только тем, кто ходит в админку.** `sales-head`
и `sales-manager-crm` в `/admin` не пускают by design, поэтому им сущность показывается
подписью без URL, а не ссылкой в 403.

**Автор считается непустым.** `users` не удаляются мягко, а `user_id` висит на `cascadeOnDelete` —
комментарий физически не переживает своего автора.
