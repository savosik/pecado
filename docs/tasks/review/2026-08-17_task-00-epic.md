## Что уже построено (не изобретать заново)

- **`CrmTask`** — заголовок, описание, автор, **один** исполнитель, приоритет, `due_at`,
  `done_at`, полиморфная привязка + денормализованный `client_user_id`, softDeletes;
  комментарии, вложения, голосовые заметки. Инварианты держит модель (хук `saving`).
- **`CrmTaskService`** — единая точка на все пути создания (раздел, врезки, звонки,
  недоборы, агентское API `TaskOperations`, MCP `crm-create-task`). Любое новое поле
  проходит через `payload()` и сервис — иначе один из шести путей его потеряет.
- **Закрытие с отчётом**: `POST /crm/tasks/{task}/close`, одна транзакция —
  статус + комментарий + follow-up (`follow_up_of_id`). Диалог `TaskCloseDialog.jsx`.
- **Автоповторы**: `crm_task_recurrences` + идемпотентные `crm_task_occurrences`,
  крон `crm:tasks-recur` (05:40).
- **Напоминания почтой**: `crm:tasks-remind` (08:30), `TaskAssignedNotification`,
  `TaskDueSoonNotification` — всё за флагом `MAIL_FEATURE_CRM_TASKS` (на проде выкл).
- **Скоуп «мои/отдел»**: `ScopeToggle` + `visibleTo()`, права `crm-tasks.*`,
  `crm-department.view/edit`, отдельная способность `reassign`.
- **Календарные гриды в проекте есть** — `PaymentCalendarGrid` (платежи CRM и кабинета):
  образец сетки месяца, не тащить стороннюю календарную библиотеку без нужды.
- **Polling-образец есть** — `PresenceController` + `CRM_PRESENCE_POLL` (45 с):
  вебсокетов в проекте нет вовсе (`BROADCAST_CONNECTION=log`, Reverb/Echo не установлены),
  и эпик их **не вводит** — все «живые» механики строятся на polling.
- **Service worker уже зарегистрирован** (`public/sw.js`, PWA-заглушка 8 строк) —
  web push дописывает обработчики, а не заводит новый SW.

## Ключевые решения дизайна

1. **`assignee_id` остаётся ответственным.** Соисполнители — pivot поверх, а не замена:
   на `assignee_id` завязаны индексы, каунтеры, покрытие клиентов и просрочка. У задачи
   всегда ровно один ответственный за срок; соисполнители видят задачу в «Мне» и могут
   работать с чек-листом, но закрывает — ответственный (или автор/РОП).
2. **Перенос — не закрытие.** Исход «перенести» сдвигает `due_at` и копит счётчик
   переносов; задача остаётся открытой. «Успешно» и «с проблемой» — терминальные,
   оба со статусом `done` и полем `outcome`. Статистика «закрыто вовремя / с опозданием /
   с N переносов» становится честной и ложится в отчёт task-10.
3. **Один reminder-контур на все каналы.** Лог отправленных напоминаний
   (задача × пользователь × канал) общий для тостов, писем и push — иначе три механизма
   будут спамить об одном и том же и их невозможно будет отлаживать.
4. **Личный контроль — это подписка-наблюдение**, а не второй исполнитель: контролёр
   получает уведомления о закрытии/переносе/просрочке и видит пресет «На контроле»,
   но в статистику исполнения не попадает.
5. **Никаких модальных «встречалок» при входе.** Пункт «при входе показывать» решается
   блоком на дашборде + постоянным счётчиком в меню + тостами: модальное окно на входе
   в CRM по опыту раздражает и его закрывают не глядя.
6. **Экспорт в календари — подписной ICS-фид** (одна ссылка, календарь сам обновляется),
   а не разовые .ics-файлы: Google и Яндекс одинаково умеют «добавить по URL».
7. **Метрики отчёта — только из фактов модели** (`done_at`, `outcome`, счётчик переносов,
   `due_at`): никаких параллельных таблиц статистики, отчёт пересчитывается из сырых данных.

## Сквозные требования (каждая карточка)

- Миграции — только новые, с комментариями к таблицам и столбцам; `db:comments:audit --strict` чист.
- После миграций с новыми таблицами — `bi:sync-grants`.
- Новые поля задач доводятся до **всех** путей: `CrmTaskService::payload()`, агентское API
  (`TaskOperations`), MCP (`crm-create-task`), врезка `TaskPanel`, лента клиента.
- Select-фильтры — только через обёртки `@/components/ui/*` с collection; ключи фильтров
  возвращаются в снимке `filters` (round-trip-тест) — классы багов фильтров известны.
- UI полностью на русском; Pint/PHPStan/ESLint чистые; feature-тесты; браузерная проверка на dev.

## Порядок и зависимости

`task-01` ∥ `task-02` ∥ `task-03` → `task-04` → `task-05` ∥ (`task-06` → `task-07`) ∥ (`task-08` → `task-09`) → `task-10`

- Волна 0 — три независимые карточки модели; можно параллелить.
- `task-04` (раздел v2) показывает всё из волны 0 — идёт после неё.
- `task-08` (тосты) требует механики переноса из `task-03`.
- `task-09` (push) переиспользует reminder-контур `task-08`.
- `task-10` (отчёт) требует исходов из `task-03`; лучше запускать последним — отчёт
  красив, когда в нём видны исходы, переносы и трудоёмкость.
