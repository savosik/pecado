# Промо 12 — Расчёт акций в клиентском API

**Приоритет:** средний
**Создано:** 2026-07-27
**Roadmap:** [docs/promo-constructor-roadmap.md → Волна 4](../../promo-constructor-roadmap.md)
**Зависит от:** [promo-06-order-assembler](2026-07-27_promo-06-order-assembler.md), [promo-08-cart-checkout-lines](2026-07-27_promo-08-cart-checkout-lines.md)

## Контекст

`POST /api/client-api/{token}/orders`
([ClientApiController::orders()](../../../app/Http/Controllers/Api/ClientApiController.php#L221))
создаёт заказы напрямую из массива `products`, **без корзины**. На этом эндпоинте сидят
боевые интеграции клиентов (см. `project_geveya_exports`), поэтому обратная совместимость —
жёсткое требование.

Заказчик: расчёт промо в API — **опциональный**.

## Контракт

Новый необязательный параметр запроса:

```
apply_promotions: boolean   (default: false)
```

**По умолчанию `false`** — поведение существующих интеграций не меняется ни на байт: те же
заказы, тот же формат ответа, те же поля. Это не «на всякий случай»: клиент, который не
просил подарков, не должен внезапно получить лишний заказ и лишние строки в ответе.

При `apply_promotions: true`:

1. Из принятых к отгрузке позиций собирается `PromoContext::fromLines(..., channel: 'api')`.
2. `PromotionEngine::evaluate()` отрабатывает по правилам, у которых канал `api` разрешён
   (`audience.channels`) — правило может быть настроено «только сайт».
3. Промо-позиции добавляются в `OrderDraft` и уезжают отдельными заказами `promo` /
   `promo_sample` — той же сборкой, что и на сайте.
4. В ответ добавляются два блока:

```json
{
  "promotions": {
    "applied": [
      {
        "rule_id": 3,
        "promotion": "Lovense: Lush 4 в подарок",
        "product_id": 789,
        "name": "Lovense Lush 4",
        "quantity": 1,
        "price": 0,
        "promo_kind": "accountable",
        "order_id": 10245
      }
    ],
    "near_miss": [
      {
        "rule_id": 5,
        "promotion": "Собери серию",
        "missing": { "type": "amount", "value": 11600, "currency": "RUB" },
        "reward": "Товар X за 10 ₽"
      }
    ]
  }
}
```

Блок `promotions` присутствует **только** при `apply_promotions: true`.

## Важные решения

- **`near_miss` отдаём.** Партнёр может показать «доберите на 11 600 ₽» в своей системе —
  это прямая польза от интеграции. Отдаётся даже когда ничего не начислено.
- **Причины блокировки не отдаём.** `blocked` (нет остатка, лимит) наружу не уходит — то же
  правило, что для сайта. Если промо-позиции нет, её просто нет в `applied`.
- **Награды с выбором (`type: choice`).** Корзины у API нет, значит и
  `cart_promotion_selections` нет. Два варианта: либо принимать выбор в запросе
  (`promo_choices: [{rule_id, reward_index, product_id}]`), либо такие награды в API не
  выдавать. **Рекомендация — второе для первой версии**: молча пропускать `choice`-награды
  и указывать их в `near_miss` с пояснением «выбор промо-позиции доступен только на сайте».
  Приём выбора добавить позже, если понадобится.
- **Отклоняемые платные позиции.** У API нет интерактивного отказа. Считаем, что при
  `apply_promotions: true` клиент согласен на все начисления, **включая платные**. Это надо
  прямо и заметно написать в документации: «промо-позиции с ненулевой ценой создают
  отдельный заказ, который подлежит оплате». Альтернатива на будущее — параметр
  `max_promo_price`, отсекающий платные позиции.
- **Частичное выполнение.** Контроллер «дружелюбно» урезает количества: часть позиций
  попадает в `not_accepted` / `partial`. Промо считается **по фактически принятым**
  позициям, а не по запрошенным — иначе подарок будет выдан за товар, который не отгрузили.
  Это неочевидно и обязательно должно быть в тесте.

## Документация

- Scramble (`/docs/api` и `/docs/api.json`) подхватывает аннотации автоматически, но
  параметр, блок ответа и предупреждение про платные позиции нужно описать явно в
  док-блоке метода — этот JSON читает ИИ-агент.
- Если по клиентскому API есть отдельная страница в `docs-erp/` или `docs/` — обновить и её.

## Нюансы

- **Идемпотентность.** Повторный запрос создаст новые заказы — как и сейчас. Промо ничего
  тут не меняет, но в документации стоит упомянуть, что повторная отправка задваивает и
  промо-заказы.
- **Токен и пользователь.** Индивидуальные цены и аудитория правил резолвятся по
  `ApiToken->user`. Проверить, что правило с ограничением по конкретным клиентам корректно
  срабатывает и в API.
- **Ответ не должен разбухнуть.** При `apply_promotions: false` в JSON не появляется даже
  пустой ключ `promotions` — некоторые клиентские парсеры строгие.

## Критерии готовности

- [x] Без параметра ответ **байт в байт** совпадает с текущим — тест проверяет и состав
      ключей (`['orders', 'total_orders', 'fully_fulfilled']`), и отсутствие промо-заказов.
- [x] С `apply_promotions: true` создаются промо-заказы и возвращается блок `promotions`
      с `order_id` каждой начисленной позиции.
- [x] Тест: промо считается по принятым позициям, а не по запрошенным (частичное
      выполнение) — порог 5, на складе 3, подарка нет.
- [x] Тест: правило с каналом «только сайт» в API не срабатывает.
- [x] Тест: `choice`-награда не выдаётся и попадает в `near_miss` с пояснением
      «Выбор промо-позиции доступен только на сайте».
- [x] Тест: причины блокировки наружу не утекают — в блоке ровно два ключа,
      `applied` и `near_miss`.
- [x] Индивидуальные цены клиента используются при расчёте порога (тест: 8 × 500 ₽ порог
      6000 ₽ не берут, 12 × 500 ₽ — берут).
- [x] Документация в Scramble обновлена, предупреждение про платные промо-позиции на месте —
      док-блок `ClientApiController::orders()`.

## Как сделано

- `App\Services\Promotion\ClientApiPromotions` + DTO `ClientApiPromoResult` — вся логика
  канала вынесена из контроллера. Контроллер только читает флаг, отдаёт принятые позиции
  и подмешивает блок в ответ.
- Строки уезжают тем же `OrderAssembler`, что и чекаут: сборка заказа одна на оба канала.
- Промо-заказ из API получает **лист отбора** в `warehouse_comment` — как и в чекауте
  (карточка promo-11). Кладовщика канал оформления не касается.
- `near_miss` отдаётся всегда, включая случай «ничего не начислено», и несёт `message`
  человеческим языком — партнёр показывает его у себя.

## Отложено осознанно

- **`promo_choices` в запросе** — приём выбора варианта награды. Первая версия такие
  награды просто не выдаёт (решение из контракта выше). Добавить, если попросят.
- **`max_promo_price`** — отсечка платных промо-позиций. Пока действует правило
  «`apply_promotions: true` = согласие на все начисления», прямо написанное в документации.
