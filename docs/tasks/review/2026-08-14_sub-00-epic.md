**Приоритет:** высокий
**Создано:** 2026-08-14
**Карточки:** `sub-01` … `sub-09`
**Флаг:** `SHORTAGE_OFFERS_ENABLED` (на проде выключен до конца волны 1)

| Волна | Карточки | Что даёт |
|---|---|---|
| 0 — фундамент | `sub-01`, `sub-02` | Сущности, детект недобора, алерт по рассинхрону каталога. Недобор перестаёт быть невидимым |
| 1 — ручной MVP | `sub-03`, `sub-04`, `sub-05` | CRM-очередь + карточка, клиентская страница, постинг замены, письма. Кандидатов менеджер добавляет руками |

## Суть в одном абзаце

Недобор рождается на столе упаковщика: заказ уже прошёл сайт → 1С → расходник → сборку,
и при контрольной проверке товар оказался не тем / порванным / бракованным. 1С отменяет
строки и шлёт `order.updated`; сайт уже помечает их `order_items.cancelled = 1` и
показывает клиенту зачёркнутыми — **на этом сегодня всё заканчивается**. Клиент (оптовик,
интернет-магазин) узнаёт о недоборе из коробки, а его собственный покупатель уже внёс
предоплату. Эпик достраивает цепочку: отмена строк → оффер с кандидатами на замену →
письмо-извинение от персонального менеджера → **одна страница по URL**, где клиент без
единого поля ввода выбирает замены и жмёт «Согласовать» → на сайте создаётся **новый**
заказ (реквизиты и доставка наследуются от исходного) → уходит в 1С обычным
`order.created`. Исходный заказ не редактируется — протокол обмена в волнах 0–2 не
меняется вообще.

## Принципы

**1. Исходный заказ неприкосновенен.** Замена = новый заказ со ссылкой на исходный.
Редактирования заказа клиентом в протоколе нет и не появится.

**2. Цена — ограничение, не критерий ранжирования.** Клиент уже продал товар своему
покупателю по своей цене. Коридор асимметричный: вниз до −25 %, вверх до +10 %.
Все цены — индивидуальные для клиента (`PriceService`), не базовые.

**3. Паспортные атрибуты не ранжируют.** Проверено на живом товаре: подбор по числу
совпавших атрибутов ставит «Ошейник TOYFA Theatre за 1550 ₽» (9/10 атрибутов) выше
«Стропы Anonymo за 600 ₽» (5/10) при исходной стропе за 600 ₽ — потому что топ
заполненности это «Страна происхождения», «Изготовитель», «Импортёр», «Фабрика»:
они совпадают у всей серии и не говорят, что это за предмет. Функция товара живёт
в головном слове названия и категории; различающие атрибуты (материал, цвет, объём,
питание) — вторичный сигнал внутри слоя.

**4. Каждый кандидат обязан иметь причину.** Текст «та же линейка, следующее
поколение» менеджер пересылает клиенту, а клиент — своему покупателю.
Замена без объяснения не продаётся.

**5. Уценка того же товара — сильнее любой замены.** Недобор на столе упаковщика
часто и есть момент рождения партии брака: та же единица через WMS станет
`product_defects`. «Идентичный товар, вмята коробка, −30 %» — не замена вовсе.

**6. Выбор людей — обучающая выборка.** Ручное добавление кандидата менеджером и
согласованная клиентом замена пишутся в справочник (`manual` / `learned`);
справочник растёт по реальному спросу, а не разметкой 9 000 карточек вслепую.

**7. Менеджер проверяет, а не делает.** Система готовит оффер, кандидатов, черновик
письма и задачи дожима; человек нужен там, где кандидатов нет (6 из 25) и где
отношения (VIP, повторный недобор, крупная сумма).

## Слои автоподбора (sub-06)

Сквозные условия всех слоёв: `hidden = 0`, остаток ≥ недостающего количества,
индивидуальная цена клиента в коридоре [−25 %; +10 %].

| Слой | Источник | Причина для клиента |
|---|---|---|
| 0 | Тот же товар: остаток появился или внешний остаток поставщика (`external_quantity`) | «Будет N-го, зарезервируем» |
| 0.5 | Тот же `product_id` в `product_defects`: `is_published`, `price ≠ NULL`, не закрыта, `DefectStockService::available()` ≥ qty | «Идентичный, уценка: ‹defect_description›» |
| 1 | Подтверждённая связь `product_substitutions` | Текст из связи |
| 2 | Варианты модели (`model_id`), **исключая generic-группы > 10 товаров** (слипание Neutral/CHERRY) | «Тот же товар, другой цвет/размер» |
| 3 | Линейка бренда: общий префикс названия + бренд + категория (Lush 3 → Lush 4/Mini/2) | «Та же линейка, соседнее поколение» |
| 4 | Функциональный тип: листовая категория + нормализованное головное слово названия; ранжирование различающими атрибутами | «Стропа вместо стропы, другой бренд» |
| 5 | Листовая категория + ценовой коридор, ранжирование по продажам | «Ближайший аналог по назначению и цене» |
| 6 | Семантика Meilisearch (`HybridSearchOptions`) в пределах родительской категории | Последний фолбэк для пустых категорий |

`SimilarProductsService` не переиспользуется как основа (витринный: не знает цену,
количество, причину) — из него берётся только слой 6.

## Границы скоупа

Что **сознательно не входит**:

| Выпилено | Причина |
|---|---|
| ~~Редактирование исходного заказа клиентом~~ | Нет в протоколе; замена — новый заказ |
| ~~Автоотправка офферов без менеджера~~ | Фаза 3 после эпика: сначала фаза «менеджер отправляет всё» должна показать, что автоподбор не предлагает «ошейник вместо стропы» под именем живого человека |
| ~~Увеличение количества сверх отменённого~~ | Докупка — обычный заказ; кап сохраняет смысл связи `replaces_order_item_id` для аналитики |
| ~~Согласование по голой ссылке из письма без входа~~ | Кнопка создаёт финансовый документ с индивидуальными ценами; пересланное письмо не должно давать право постить заказы. Просмотр — по signed URL, подтверждение — под авторизацией владельца |
| ~~Массовая ИИ-разметка всех товаров~~ | ИИ — только: нормализация функционального типа, тексты-обоснования, предразметка дефицитного ядра (десятки позиций) |
| ~~Изменение протокола в волнах 0–2~~ | Пометка о замене — текстом в `manager_comment`. Поле `replaces_order_uuid` — волна 3 (`sub-09`), spec-first |

## Рабочий цикл менеджера (закреплено обсуждением)

- **Триггеры**: `CrmTask` с дедлайном (до конца дня; сумма > порога → +2 часа),
  бейдж «Недоборы» в меню CRM, письмо/пуш со ссылкой в карточку. Ходить проверять не нужно.
- **Карточка** — всё решение на одном экране: строки недобора, контекст клиента
  (оборот, история недоборов), кандидаты по слоям с причинами, прогноз прихода,
  черновик письма. Четыре исхода одной кнопкой: отправить / предложить подождать /
  позвонить / закрыть без замены.
- Снятая менеджером галочка с кандидата — негативный сигнал для пары товаров.
- Ручной кандидат через поиск не уходя с карточки → связь `manual`.
- **Дожим автоматом**: 24 ч без открытия → напоминание клиенту; 48 ч без согласования →
  задача «позвонить»; 7 дней → оффер `expired`, финальная задача менеджеру.
- **Еженедельно (~15 мин)**: очередь подтверждений `learned`/`ai`-связей; новый товар
  в дефицитной категории попадает в неё автоматически.
- Отчёт «повторные недоборы» уходит закупщику сам, менеджер его не собирает.

## Путь клиента (закреплено обсуждением)

Письмо от **персонального менеджера** (не noreply) + баннер в заказе в кабинете →
один URL (signed, 7 дней, просмотр без входа) → страница только про этот заказ:
отменённые строки, под каждой радио-варианты с причинами и **его** ценами, уценка
выделена с описанием дефекта, «подождать прихода», «без замены»; количество
предзаполнено отменённым, уменьшить можно, увеличить нельзя → «Согласовать» (вход,
если не залогинен, с сохранением выбора) → «Создан заказ 29УТ-…, связан с 29УТ-…» →
в старом заказе плашка «замена согласована → заказ №…».
