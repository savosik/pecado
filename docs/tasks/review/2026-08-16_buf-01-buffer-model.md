# buf-01: расчётная модель страхового буфера

**Приоритет:** высокий
**Эпик:** [buf-00](2026-08-16_buf-00-epic.md)
**Создано:** 2026-08-16

## Описание

Фундамент эпика: таблица буферов, сервис с батч-картой и ночной пересчёт по
сигналам. На этом этапе буфер нигде не применяется — только считается и лежит.

### Таблица `product_stock_buffers`

Новая миграция (старые не трогаем), комментарии БД на русском по правилу проекта:

- `product_id` — товар (products.id), unique;
- `buffer_qty` — рассчитанный размер буфера в штуках;
- `manual_qty` — ручной override со склада (nullable; задан → побеждает расчёт);
- `reasons` — JSON с раскладкой сигналов (`{"cancellations": 5, "defect_batches": 2, "shelf_life": true}`) — для объяснения в WMS-консоли;
- `computed_at` — когда пересчитан.

После выкатки на прод — `bi:sync-grants`, иначе ИИ-агент менеджеров таблицу не увидит.

### Сервис `App\Services\Stock\StockBufferService`

- `bufferMap(iterable $productIds): array<int,int>` — батч-карта, один запрос,
  по образцу `PromoStockService::availableMap()`;
- `max(manual_qty ?? buffer_qty, 0)`;
- потребители появятся в `buf-04`/`buf-05`; здесь — только сервис и тесты.

### Команда `stock:buffers:recompute`

В расписании ночью. Сигналы и формула (пороги — в `config/stock_buffer.php`,
не хардкод):

1. **Отмены строк**: `order_items.cancelled = 1` за скользящие 90 дней,
   GROUP BY `product_id` (датой считать `COALESCE(orders.erp_created_at, orders.created_at)` —
   как в `ShortageAnalyticsService`). ≥ 2 событий → сигнал.
2. **Партии брака**: `product_defects` по товару — открытые всегда, закрытые
   за 180 дней. ≥ 1 партии → сигнал.
3. **Срок годности**: `Product::shelfLifeValue` (`product_attribute_values.datetime_value`
   атрибута `srok-godnosti-goden-do`) ближе порога (старт — 6 месяцев) → сигнал.
4. **Ручные пометки** (`manual_qty`) командой не трогаются никогда.

Размер: `buffer_qty = clamp(база_по_сигналам, 0, min(2, ceil(0.1 × остаток_региона)))`.
Товары, потерявшие все сигналы, обнуляются (кроме ручных). Агрегаты с GROUP BY
обязательно проверить на локальной MySQL, не только в SQLite-тестах
(`only_full_group_by`).

Команда обязана фиксировать **дифф**: список SKU, у которых итоговый буфер
реально изменился (в лог и в возвращаемое значение). Это фундамент условной
инвалидации кешей в buf-05 — «ничего не изменилось» не должно трогать ни один кеш.

### Прогон по копии прода

По образцу отчёта в sub-06: запустить пересчёт на локальной копии боевой базы,
таблицей в карточку — сколько SKU получили буфер, суммарно скрытых штук и их
доля от остатка склада, топ-20 SKU с раскладкой сигналов. Ожидание по срезу
2026-08-16: ~100–150 SKU, ~1–2 % единиц.

## Решения по ходу реализации (2026-08-16)

- **Остаток ниже `min_stock` (3 шт) → буфер всегда 0**, без формулы. Карточка задавала
  `ceil(0.1 × остаток)`, что при остатке 1–2 давало бы буфер 1 — прямое противоречие
  принципу эпика «для SKU с 1–2 шт буфер честно даёт ноль». Порог вынесен в конфиг
  (`STOCK_BUFFER_MIN_STOCK`).
- **Сигнал «срок годности» учитывается только при живом остатке**: на копии прода
  943 из 957 товаров с датой ближе порога распроданы в ноль — это шум, а не рисковая
  полка. Отмены и брак остаются сигналами и при нулевом остатке (объясняют историю SKU
  в будущей WMS-консоли; при возврате товара на полку ночной пересчёт поднимет буфер).
- **База формулы** = сумма весов сработавших сигналов (веса в конфиге, по 1):
  один сигнал → 1 шт, два и больше → 2 шт (до clamp по остатку).
- **`computed_at` обновляется только при реальном изменении строки** — иначе «пустой»
  пересчёт писал бы все строки каждую ночь и ломал условную инвалидацию кешей buf-05.
- **Записи с сигналами, но буфером 0 хранятся** (раскладка для WMS-консоли);
  записи, потерявшие все сигналы, удаляются (отсутствие записи = 0), кроме ручных.
