# fin-03 · Таблицы и модели регистра взаиморасчётов

**Приоритет:** высокий
**Создано:** 2026-08-09
**Эпик:** [fin-00](2026-08-09_fin-00-epic.md)
**Зависимости:** `fin-02`
**Волна:** 1 — аддитивно, ничего не ломает

## Описание

Три новые таблицы и три модели. Ни одна существующая таблица не меняется, ни одно существующее
чтение не затрагивается — старый денежный путь продолжает работать без изменений.

Миграции только новые: на dev и prod реальные данные.

## Что делаем

### `agreements` — соглашения с клиентами

> Было `contracts`. Заменено по ответу 1С: договоров в базе 75 и 97,8 % реализаций без них,
> соглашений — 5 102 при 100 % покрытии.

```php
$table->comment('Соглашения с клиентами (из 1С). Условия продаж, группировка взаиморасчётов');
$table->id()->comment('Первичный ключ');
$table->uuid('uuid')->unique()->comment('UUID соглашения в 1С — ключ идемпотентности');
$table->foreignId('user_id')->comment('Партнёр (users.id)');
$table->foreignId('company_id')->comment('Контрагент клиента (companies.id)');
$table->foreignId('organization_id')->nullable()->comment('Наше юрлицо (organizations.id)');
$table->string('number')->nullable()->comment('Номер соглашения');
$table->date('date')->nullable()->comment('Дата соглашения');
$table->string('name')->nullable()->comment('Наименование соглашения как в 1С');
$table->string('currency_code', 3)->nullable()->comment('Валюта расчётов');
$table->string('settlement_procedure')->nullable()->comment('Порядок расчётов из соглашения (перечень значений уточняется у 1С)');
$table->decimal('credit_limit', 20, 2)->nullable()->comment('Кредитный лимит');
$table->unsignedSmallInteger('deferral_days')->nullable()->comment('Дней отсрочки платежа');
// status, revision, erp_created_at, erp_updated_at
```

Индексы: `unique(uuid)`, `(company_id, organization_id)`, `(user_id, status)`.

⚠️ **Соглашение — не измерение регистра.** 1С берёт его из документа-регистратора; при
изменении задним числом группировка исторических движений разъедется. Поэтому соглашение
используется как **фильтр и группировка**, а осью акта сверки служит контрагент × организация
× валюта. Записать это в докблок модели, иначе кто-нибудь построит на нём сальдо.

**Договор отдельной таблицей не заводим** — 75 записей. Хранится полями `contract_uuid` /
`contract_name` прямо в движении.

### `settlement_entries`

Полный состав — в [эпике](2026-08-09_fin-00-epic.md#схема-данных). Места, где легко ошибиться:

- **`amount` знаковый**, `decimal(20,2)`. Комментарий обязан объяснять знак:
  `"Сумма движения со знаком: '+' — в пользу клиента (оплата, возврат товара), '−' — в нашу пользу (реализация, возврат денег)"`.
- **`debit` / `credit` — generated-колонки.** Комментарий им **не задаётся** (правило проекта):
  ```php
  $table->decimal('debit', 20, 2)->storedAs('GREATEST(-amount, 0)');
  $table->decimal('credit', 20, 2)->storedAs('GREATEST(amount, 0)');
  ```
  ⚠️ Проверить на SQLite: `phpunit.xml` использует `:memory:`. Если `storedAs` там не заведётся —
  делать колонки обычными и заполнять в модели, но `SUM(amount)` остаётся основным путём.
- **`nature` и `type`** — строки, не enum БД: новый тип движения не должен требовать миграции.
  Валидацию держит JSON Schema и константы модели.
- **`settled_amount`** осмыслен только при `nature='plan'`; для `fact` всегда `0`.
  Источник — `РегистрНакопления.РасчетыСКлиентамиПоСрокам` (ресурсы `Долг`, `Предоплата`).
  Сайт его **не вычисляет**.
- **`amount_rub`** приходит из 1С как `СуммаРегл` — рублёвый эквивалент, зафиксированный
  учётом на дату операции. Колонки `exchange_rate` нет: курс при необходимости получается
  делением, а хранить два источника истины для одной величины незачем.
- **`settlement_object_kind` / `_uuid` / `_name`** — `ОбъектРасчетов`, измерение регистра.
  Не то же самое, что документ-регистратор: регистратор — кто породил движение, объект
  расчётов — по чему ведётся расчёт. Значения: `order`, `commission_report`,
  `commission_contract`, `shipment`, `other`. Незнакомый вид сохраняем как `other` с `_name`,
  **не отбрасываем**.
- **`agreement_id`** nullable + `agreement_uuid`/`agreement_name` строками; `contract_uuid` /
  `contract_name` — просто поля, без FK.
- **Полиморф** `document_type` / `document_id` **nullable**: движение может приехать раньше
  документа или указывать на документ, которого на сайте нет вовсе.
- **`document_kind` / `document_number` / `document_date`** — дублируют реквизиты из 1С, чтобы
  строка читалась без документа.

Индексы: `unique(uuid)`, `(company_id, organization_id, date)`, `(agreement_id, date)`,
`(settlement_object_kind, settlement_object_uuid)`, `(nature, date)`,
`(document_type, document_id)`, `(user_id, nature, date)`, `(organization_id, nature, date)`.
⚠️ Имена индексов задавать явно: автоимена длиннее 64 символов MySQL не примет — уже наступали
на это в `create_contractor_organization_balances_table`.

### `settlement_checkpoints` — сверенные контрольные точки

> Было `contract_balances` (четвёртый уровень балансов). **Отменено:** ось сверки —
> контрагент × организация, а этот разрез уже существует с v15.8.0
> (`contractor_organization_balances`). Вместо него нужна другая таблица — точки закрытия периода.

`company_id`, `organization_id`, `currency_code`, `as_of_date`, `amount`, `is_verified`,
`erp_updated_at`. Уникальность — `(company_id, organization_id, currency_code, as_of_date)`.

Назначение: сальдо на 01.07.2026, сверенное 1С (дата запрета изменения — 30.06.2026).
Используется **только** командой `settlements:verify` для проверки инварианта
«сальдо 01.01 + движения первого полугодия = checkpoint 01.07». Комментарий таблицы обязан
сказать, что это контрольная сумма, а не источник для расчётов.

### Модели

`app/Models/{Agreement,SettlementEntry,SettlementCheckpoint}.php` по образцу
[`ContractorBalance`](../../../app/Models/ContractorBalance.php) и
[`Payment`](../../../app/Models/Payment.php).

`SettlementEntry`:
- константы `NATURE_FACT`/`NATURE_PLAN`, `TYPE_*` (семь), `TYPE_LABELS` (русские подписи),
  `EPSILON = 0.01` — как в `ShipmentPaymentSchedule`;
- скоупы `scopeFacts()`, `scopePlans()`, `scopeOutstanding()` (непогашенный план),
  `scopeOverdue()`, `scopeUpTo($date)`;
- ⚠️ `scopeOutstanding()` — константу подставлять **в SQL, а не биндингом**: у выражения
  `amount - settled_amount` нет аффинности типа, и SQLite сравнил бы число со строкой. Ровно
  та же грабля описана в `ShipmentPaymentSchedule::scopeOutstanding()`;
- аксессоры `unsettled_amount`, `is_overdue`, `type_label`, `direction_label`;
- связи: `user()`, `company()`, `organization()`, `agreement()`, `document()` (morphTo);
- **статус строки не хранить** — «ожидается / частично / закрыта» и просрочка суть функции от
  `settled_amount` и текущей даты. Прецедент и обоснование — в `ShipmentPaymentSchedule`.

## Edge-кейсы

- `agreement_id = NULL` — движение без соглашения. В акте сверки попадает в группу
  «Без соглашения»; заглушку в `agreements` **не** создаём. На сальдо не влияет: ось
  сверки — контрагент × организация.
- Валюта соглашения и валюта движения различаются → приоритет у валюты движения, `amount_rub`
  считается по ней.
- `settled_amount > amount` — переплата по строке графика, легитимно. `unsettled_amount`
  клампится в ноль, отрицательным не бывает.
- Документ soft-deleted → движения остаются: регистр отражает историю, а не текущее состояние
  документов.

## Что сделано (2026-08-11)

**Миграции** — `2026_08_11_100000_create_agreements_table`,
`…_100100_create_settlement_entries_table`, `…_100200_create_settlement_checkpoints_table`.
Все столбцы с русскими комментариями, generated-колонкам комментарии не задаются.

**Generated-колонки заведены в обоих движках.** `GREATEST` — функция MySQL, в SQLite её нет;
выражение выбирается по драйверу (`MAX` для SQLite), поэтому `debit`/`credit` работают
и в тестах. Обычными колонками их делать не пришлось.

**Отклонения от карточки — два, оба намеренные:**

1. **`user_id` / `company_id` в `agreements` — nullable.** В карточке они были обязательными,
   но соглашение может приехать раньше контрагента: порядок доставки между очередями
   не гарантирован. Обязательный FK отправлял бы такие соглашения в DLQ. Рядом лежат сырые
   `partner_uuid` / `contractor_uuid` / `tax_id` для доклейки — тот же приём, что у платежей.
2. **`settlement_checkpoints.organization_uuid` — `NOT NULL DEFAULT ''`, а не nullable.**
   Уникальный индекс в MySQL считает NULL-ы различными, и точка на уровне контрагента
   задваивалась бы при повторной доставке. Задвоенная контрольная сумма хуже отсутствующей:
   сверка покажет расхождение там, где его нет.

**Добавлено сверх карточки:**

- `is_settled_derived` + `document_settled_amount` — требование круга 6. По заказам
  построчного остатка в 1С нет, есть только сумма по документу; разнесение по этапам
  делается для календаря и обязано быть помечено производным, иначе оно просочится
  в баланс и сверку.
- `meta` (JSON) — `percent`, `term_days`, `basis`, `stage` из строки графика. Шесть колонок
  ради показа календаря того не стоят.
- `movement_kind` — диагностическое поле «Приход/Расход» из 1С. В арифметике не участвует,
  но без него инверсию знака пришлось бы искать вслепую.

**Тесты** — `tests/Unit/Models/SettlementEntryTest.php` (13 кейсов) и `AgreementTest.php` (8).
Проверяется числовой пример акта сверки из контракта (−55 000 ₽ одним `SUM`), клампинг
переплаты, отбор непогашенных строк на SQLite (константа в SQL, а не биндингом) и защита
контрольной точки от задвоения. 21/21 зелёные, Pint и PHPStan по новым файлам чистые.
