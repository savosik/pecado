# debt-02: состояние долга — ночной расчёт ступени и shadow

**Приоритет:** высокий

**Создано:** 2026-08-27

## Описание

`app/Services/Debt/DebtStateService`: для каждой пары партнёр × контрагент —
просрочка (`PaymentForecast::overdueOnly()`, без `document_kind = 'order'`),
возраст старейшей непогашенной строки, доля просрочки во всём долге партнёра.
Ступень по таблице эпика; пороги из `config/debt.php` (`min_overdue`,
`grace_bank_days`, `no_preorders_days` 14, `no_orders_days` 30, `hold_days` 60,
`hold_share` 0.9, `stale_after_days`). Ступень партнёра = худшая по контрагентам.

Таблица `debt_states`: `user_id`, `company_id`, `level`, `since`, `overdue_amount`,
`oldest_due_date`, `reason` (одна строка «почему»), `computed_at`, `dry_run`.
Переходы пишутся в неё же историей (без отдельного журнала): строка на каждую
смену ступени.

Команда `debt:recalculate` — ночью после `mail:finance-scan`; понижение не больше
чем на одну ступень за запуск. `debt:explain {user}` — ступень и «почему» по
каждому контрагенту. Shadow: `DEBT_CONTROL_MODE=shadow` → `dry_run = 1`, действий
нет; отчёт «сколько клиентов на какой ступени и сколько писем ушло бы» — показать
заказчику до включения.

## Критерии готовности

- [ ] Миграция с русскими комментариями, `bi:sync-grants`
- [ ] Юнит-тесты: отсечка, grace, три возрастных порога, доля 90 %, худший контрагент, одна ступень за раз, гейт свежести (агрегаты — на локальной MySQL)
- [ ] Активная разблокировка (debt-05) держит ступень — тест
- [ ] `debt:explain` отвечает одной строкой + детализация по контрагентам
- [ ] Shadow на проде две недели; сводка ступеней и объёма писем показана заказчику
