# Промо 02 — Движок расчёта акций (`PromotionEngine`)

**Приоритет:** высокий
**Создано:** 2026-07-27
**Roadmap:** [docs/promo-constructor-roadmap.md → Волна 1](../../promo-constructor-roadmap.md)
**Зависит от:** [promo-01-foundation](2026-07-27_promo-01-foundation.md)

## Контекст

Движок должен обслуживать три канала: корзину на сайте, чекаут и клиентское API. Заказ по
API создаётся **без корзины вообще** —
[ClientApiController::orders()](../../../app/Http/Controllers/Api/ClientApiController.php#L221)
собирает `Order` напрямую из массива `products`. Поэтому движок принимает не `Cart`, а
снапшот позиций.

## Контракт

```
App\Services\Promotion\PromotionEngine::evaluate(PromoContext $context): PromotionEvaluation
```

### `PromoContext` (readonly DTO)

- `lines: PromoContextLine[]` — `product_id`, `quantity`, `unit_price` (финальная цена
  клиента в рублях), `is_promo` (строка сама является промо-позицией), `item_type`;
- `user: ?User`;
- `channel: string` — `site` | `api`;
- `selections: array` — выбор клиента из `cart_promotion_selections`
  (ключ `rule_id:reward_index` → `product_id` / `declined`);
- `mode: string` — какие правила брать: `info`, `issue` или оба.

Статические конструкторы: `PromoContext::fromCart(Cart, User)` и
`PromoContext::fromLines(array, ?User, string $channel)`. Оба — тонкие адаптеры, вся логика
в самом движке.

### `PromotionEvaluation` (readonly DTO)

- `applied: AppliedReward[]` — правило, индекс награды, товар, количество, цена,
  `promo_kind`, склад-источник, `optional`, `declined`;
- `nearMiss: NearMiss[]` — правило, чего не хватает (`amount` / `quantity`), сколько
  осталось до порога, что будет выдано;
- `blocked: BlockedReward[]` — правило сработало, но награда не выдана; причина:
  `out_of_stock`, `client_limit`, `total_limit`, `not_active_yet`, `wrong_channel`.
  **Клиенту `blocked` не показываем** — это диагностика для админки (карточка 03).

## Алгоритм

1. Загрузить активные правила: `PromotionRule::active()` + фильтр по `mode` + по каналу
   (`audience.channels`) + по аудитории (регион пользователя, `user_ids`, `manager_ids`).
   Кэшировать список активных правил в Redis на короткий TTL (60 с) с инвалидацией по
   обсерверу — движок вызывается на каждый рендер корзины.
2. Отфильтровать строки контекста: **исключить `is_promo`** — промо-позиции не участвуют
   в расчёте условий (иначе платная позиция за 40 ₽ попадёт в сумму и потянет следующее
   правило).
3. Для каждого правила посчитать агрегаты по селекторам. Матчинг товара к селектору —
   через материализованный `promotion_rule_product` (role = `condition`), а не разбором
   JSON на каждый товар.
4. Проверить условия с учётом `mode: all | any`.
5. Для сработавших правил посчитать множитель:
   - `once` → 1;
   - `per_threshold` → `min(floor(значение_агрегата / per_value), max_multiplier)`.
6. Проверить доступность награды (карточка 07, `PromoStockService`). До волны 2 —
   заглушка-интерфейс, всегда «доступно», чтобы движок можно было закончить и
   протестировать независимо.
7. Применить лимиты: `per_client_total`, `total`.
8. Разрешить конфликты: правила с `stackable: false` не сочетаются с другими; при
   конфликте выигрывает большее `priority`, при равенстве — меньший `id`
   (детерминированность обязательна, иначе набор промо-позиций будет прыгать между
   запросами при неизменной корзине).
9. Учесть `selections`: выбор товара для `type: choice` и отказ по `optional`.
10. Собрать `nearMiss` по несработавшим правилам, у которых заполнен хотя бы один селектор
    в корзине (не показываем «доберите на 150 000 ₽», если клиент вообще не трогал
    акционные товары — рекомендуемый порог показа задать константой, обсудить на ревью).

## Цены

Сумма считается по **финальной цене клиента** — по индивидуальным ценам со скидкой.
Использовать
[`PriceServiceInterface::getPriceMapForProducts()`](../../../app/Contracts/Pricing/PriceServiceInterface.php#L39)
— батч уже существует. Построчных `getUserPrice()` в движке быть не должно: индивидуальные
цены живут в **отдельной БД** через
[IndividualPriceProxy](../../../app/Services/Pricing/IndividualPriceProxy.php), и корзина на
200 позиций даст 200 кросс-БД запросов.

Порог в правиле хранится в рублях. Если у пользователя другая валюта, движок конвертирует
сумму корзины в рубли перед сравнением, а не наоборот (иначе порог поплывёт вместе с курсом).

## Производительность

Движок вызывается на каждый рендер корзины, а корзины у оптовиков большие.

- Не более **трёх** запросов к БД на вызов независимо от размера корзины: активные правила
  (из кэша), `promotion_rule_product` по нужным правилам, батч цен.
- Тест с корзиной на 200 позиций и 20 активными правилами: фиксируем количество запросов
  через `DB::listen` и держим потолок.

## Точки вызова (в этой карточке — только чтение)

- `CartService::getCartDetails()` и `computeCartAggregates()` — карточка 05 и 08;
- чекаут — карточка 08;
- API — карточка 12.

В этой карточке движок не подключается никуда, кроме админского предпросмотра (карточка 03)
и тестов. Это сознательно: сначала доказываем корректность, потом включаем в горячий путь.

## Нюансы

- **Детерминированность.** Один и тот же контекст обязан давать один и тот же результат.
  Никакого `rand`, никакой зависимости от порядка выборки без явного `orderBy`.
- **Гость.** `user = null` — индивидуальных цен нет, берём базовую цену. Правила с
  аудиторией по `user_ids`/`manager_ids` для гостя не срабатывают. Витрина гейтит цены по
  `is_staff`, так что для гостя `nearMiss` с суммами лучше не показывать вовсе — решить на
  ревью карточки 05.
- **Бесплатная позиция не отклоняется.** При `price = 0` флаг `optional` игнорируется, а
  запись `is_declined` в `cart_promotion_selections` не создаётся.
- **Пустая корзина** — быстрый выход, без загрузки правил.

## Критерии готовности

- [x] `evaluate()` покрыт unit-тестами на каждый пункт алгоритма: порог по количеству,
      порог по сумме, `all`/`any`, `once`/`per_threshold` с потолком, `choice` с выбором и
      без, `optional` с отказом, конфликт `stackable: false`, приоритеты, лимиты.
- [x] Тест: промо-строки исключены из агрегатов (платная позиция за 40 ₽ не тянет
      следующее правило).
- [x] Тест: сумма считается по индивидуальной цене клиента, а не по базовой.
- [x] Тест: порог в рублях корректно сравнивается с корзиной в другой валюте.
- [x] Тест детерминированности: 10 вызовов на одном контексте дают идентичный результат.
- [x] Тест производительности: корзина 200 позиций × 20 правил укладывается в лимит запросов.
- [x] `PromoContext::fromCart()` и `fromLines()` дают одинаковый результат на одинаковом
      наборе позиций — гарантия, что сайт и API не разойдутся.
- [x] `composer lint` и `composer analyse` чистые.

### Решения, принятые по ходу

- **Кэшируются правила по флагу `is_active`, а период проверяется в PHP.** Если класть в
  кэш результат `active()`, правило, стартующее в середине окна TTL, включалось бы с
  опозданием до минуты.
- **Цены строк из корзины не переносятся в контекст** (кроме уценки, где цена
  зафиксирована в партии): движок сам считает финальную цену клиента батчем. Иначе
  корзина считалась бы по устаревшему `cart_items.price`, а API — по актуальному, и
  `fromCart` с `fromLines` разошлись бы.
- **`unitPrice` в строке — в валюте контекста, цены из батча — всегда в рублях.**
  `PromoContext::$currency` конвертирует только то, что передал вызывающий.
- **Кратность `per_threshold` считается по первому условию правила.** Награда не
  объявляет, к какому из условий относится «на каждые N», а выбор «первое» —
  единственный детерминированный.
- **`mode: info` не мешает вернуть награду.** `AppliedReward::$ruleMode` показывает режим,
  `isIssuable()` отвечает, надо ли класть позицию в корзину. Иначе волне 1 нечего было бы
  показывать. Причина `not_active_yet` выдаётся, когда вызывающий явно просит
  `PromotionRuleMode::ISSUE`, а правило ещё в режиме показа.
- **Проигравшее по приоритету `stackable: false` правило просто не применяется** и в
  `blocked` не попадает: список причин в карточке закрытый, выдумывать шестую не стал.
- **Порог показа `nearMiss` — `PromotionEngine::NEAR_MISS_MIN_PROGRESS = 0.25`**
  (набрано ≥ 25 % порога). Значение обсуждаемое — вынести в настройку недолго.

### Про лимит запросов

Бюджет карточки (три запроса) выполняется для правил с **одним** условием: правила из
кэша (0), `promotion_rule_product` одним запросом (1), товары + индивидуальные цены
батчем (2). Для гостя — два запроса.

Каждое **второе и последующее** условие правила стоит ещё один запрос: pivot не хранит,
из какого условия пришёл товар, поэтому такие селекторы раскрываются отдельно (запрос
ограничен товарами корзины). Стоимость зависит от числа условий, а не от размера корзины —
именно это и проверяет тест: 200 позиций × 20 правил (половина с двумя условиями) дают
столько же запросов, сколько 5 позиций × те же 20 правил, всего 12.

Если это окажется дорого, лечится добавлением номера условия в `promotion_rule_product` —
но менять схему из карточки 01 ради гипотетической нагрузки не стал.

### Не подключено

Движок нигде не вызывается, кроме тестов, — как и требует карточка. Точки вызова:
корзина и чекаут (05, 08), админский предпросмотр (03), API (12).
