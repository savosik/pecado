# ERP — приём обмера грузовых мест расходного ордера (v16.14.0)

**Приоритет:** высокий
**Создано:** 2026-10-01
**Источник:** Agent Hub, топик №13 «Весогабаритные характеристики грузовых мест» (seq 3–7)
**Ветка:** `feature/erp-goods-issue-measurement` (поверх `feature/erp-order-cancel-reason`)

## Контекст

Клиент будет сам отдавать собранный заказ транспортной компании. Тариф у любого перевозчика
считается по весу и габаритам **мест**, а из карточек товара их не вывести. Упаковщик меряет
коробку в РМУ 1С при закрытии; 1С присылает данные в `goods_issue.created/updated`.

Контракт v16.14.0 опубликован проектом 30.09.2026 (ad56753d), 1С приняла его без замечаний
(seq 6). Эта задача — код приёма. Он должен оказаться на проде **раньше**, чем 1С включит
`revision` + `measurement` + `packages[].uuid` (одним выпуском).

## Решения

- `mixed` расчёт **не блокирует**: ордер едет целиком, считаем по всем местам (Трипуть, 28.09.2026).
- `shipping_mode = null` и расхождение «самовывоз ↔ доставка» с заказами сайта — оговорка в журнале шины.
- **Расчёт кладовщику в WMS не блокируется** (Трипуть, 01.10.2026): «сайт пока и так ничего не считает;
  нужно только обеспечить поток информации по габаритам из 1С, в блоке логистики они будут учтены».
  Запрет оставлен выключателем `APISHIP_MEASUREMENT_GATE` (умолчание `false`).
- `done` принимается только из сообщения с `revision`; иначе хранится `pending`, факт в журнале.
- После первой применённой ревизии сообщение без `revision` по ордеру отбрасывается (у прочих документов — применяется).
- `barcode` — строка как пришла: длина переменная, без ведущих нулей, нулями не дополняется.
- `volume` в расчёте не участвует: объём = Д×Ш×В / 1 000 000.
