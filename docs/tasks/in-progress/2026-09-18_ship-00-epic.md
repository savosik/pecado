# ЭПИК: Совместная отгрузка резервов — одна реализация и один расходный ордер (ship-00)

**Приоритет:** высокий
**Создано:** 2026-09-18
**Статус (18.09.2026):** протокол v16.11.0 согласован с 1С в топике №7 Agent Hub (resolution 13:21),
спека и код сайта в ветке `feature/ship-together` (слита с `origin/dev` 19.09.2026, полный прогон зелёный) за рубильником `ORDER_SHIP_TOGETHER_ENABLED`.
Сторона 1С — накопитель групп, предконтроль, транзакционная обвязка — в работе у владельца 1С,
сроки не названы. Включение — по отдельному решению владельцев после совместных испытаний (тест-план Р-7).

## Идея

Интернет-магазины держат по нескольку резервов и отправляют их в отгрузку сразу, одним курьером.
Клиент просит один документ реализации на выбранные резервы, склад — один расходный ордер.
Слить заказы средствами сайта нельзя (правка резерва только на уменьшение, «новый заказ + отмена
резервов» даёт гонку за остаток). Решение: **объединяется отгрузка, а не заказы** — заказы остаются
отдельными документами, 1С оформляет по группе минимальный комплект реализаций и ордеров.

## Контракт (аддитивно)

- `order.confirmed` → 1С: `ship_together_key` (UUID группы) + `ship_together_order_uuids` (манифест,
  минимум 2, одинаков во всех сообщениях группы). Только вместе.
- `order.updated` ← 1С: `ship_together_key`, `ship_together_status` (`confirmed` | `conflict`),
  `ship_together_conflict {reason, message, order_uuid}`; коды `timeout`, `manifest_mismatch`,
  `not_reserved`, `incompatible`, `merge_forbidden`, `shortage`, `processing_error`.
- Правила: `docs-erp/content/rules/order-reserves.md#совместная-отгрузка-резервов-v16110`,
  тест-план `docs-erp/content/tests/reserves.md` (Р-7), changelog 16.11.0.

## Сделано на сайте (ветка)

- Проверки группы до публикации (`ShipTogetherService`): один партнёр, контрагент, валюта, **ровно один склад**
  (`OrderWarehouseResolver` — тот же, что даёт `warehouse_uuids` в `order.created`), способ и адрес доставки,
  все заказы в резерве и не в ожидании. Сообщения группы — одной транзакцией, одинаковый ключ и манифест.
- Резерв локально **не снимается**: `orders.ship_together_status = pending`, правки/отмена/повторная отправка
  закрыты (409 `ship_together_pending`). Итог применяет `HandleOrderUpdated`: успех → резерв снят, отказ →
  заказ снова в резерве с причиной; `reserve:false` без полей группы (старая 1С) снимает ожидание как одиночное.
- Письмо `orders.ship_together_rejected` — одно на группу (origin_key по ключу группы), включено умолчанием
  как остальные резервные поводы.
- Страховка: `reserve:ship-together-timeout` каждые 5 минут — группа без итога дольше
  `ORDER_SHIP_TOGETHER_PENDING_TIMEOUT_MINUTES` (60) возвращается в резерв с локальной причиной `no_response`.
- Кабинет `/cabinet/reserves`: галочки на карточках, «В отгрузку вместе (N)», бейдж «ждём склад», причина отказа;
  карточка заказа — плашка ожидания вместо кнопок. Клиентский API v1 / MCP: операция `reserves.confirm_group`,
  поле `ship_together` в `reserves.list` и карточке заказа.
- Тесты: `tests/Feature/Order/ShipTogetherConfirmTest.php`, `tests/Feature/Erp/ShipTogetherOutcomeTest.php`,
  `tests/Feature/Api/Client/ClientApiShipTogetherTest.php`.

## Осталось до включения

1. Сторона 1С по resolution топика №7 (накопитель, предконтроль, один групповой вызов движков, откат).
2. Совместные испытания на dev по Р-7 (успех, тайм-аут, недобор, разные склады, повтор сообщений).
3. Решение владельцев о включении: `ORDER_SHIP_TOGETHER_ENABLED=true` + `config:cache` + `queue:restart`.
4. Дописать в буклет клиентам (docs/pickup) абзац про «отправить вместе»; legacy client-api (`/api/client-api/{token}`)
   групповой операции не получает намеренно.
5. Решение заказчика: «минимальный комплект» реализаций принято агентом сайта; если нужна жёсткая «ровно одна»,
   переигрывать новым топиком.
