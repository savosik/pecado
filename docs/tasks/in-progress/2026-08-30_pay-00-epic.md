# ЭПИК: зарплата менеджеров в CRM — «Моя зарплата» и настройки РОПа (pay-00)

**Приоритет:** высокий
**Создано:** 2026-08-30
**Статус:** волны 1–3 реализованы 30.08.2026 (ветка `feature/payroll` → `dev`); ждёт визуальной проверки на dev и включения РОПом компонента «Новые клиенты» новой версией схемы
**Вне эпика:** ERP-протокол не затрагивается — расчёт читает уже принятые из 1С данные
(реализации, регистр взаиморасчётов, планы). Журнал смен менеджера у клиента. Лиды как
показатель KPI (только через конверсию в нового клиента).

## Идея

РОП считает зарплату отдела руками в Excel по выгрузке 1С (`tmp/salary/`): вручную размечает
просроченные оплаты, подставляет константы, менеджер узнаёт цифру раз в месяц постфактум.
Раздел CRM **«Моя зарплата»** показывает менеджеру, сколько он заработал на эту минуту, прогноз
на конец месяца и что именно можно поднять, — с пояснением каждого показателя. У РОПа —
настройка констант на менеджера × месяц, утверждение расчёта, сводка по отделу.

Модель гибкая по конструкции: **новая «морковка» = новый компонент-класс, изменение
констант = данные** (без деплоя). Формулу никто не редактирует руками — редактора формул
и движка правил нет намеренно (урок почты note-00: «умерли от необъяснимости»).

## Решения (заказчик, 30.08.2026)

1. **Формула.** `Доход = Оклад + KPI-премия + Доп. доход (+ бонус за новых клиентов)
   (+ ручная корректировка РОПа)`. KPI-премия = `база × min(200 %, F)`,
   `F = множитель_активных × (реализации − штраф_дисциплины) / план_выручки`.
2. **План — по реализациям**, не по деньгам. Неоплаченные накладные входят в факт полностью,
   за них не штрафуют.
3. **Штраф — за финансовую дисциплину**: по накладным, **закрывающий платёж** которых пришёл
   в этом месяце с задержкой от срока оплаты: 3–7 рабочих дней → −1,5 × сумма накладной,
   8+ → −3 ×, до 2 дней — ничего. Штраф на всю накладную, ложится в месяц закрывающего платежа.
4. **Активные клиенты.** План = число партнёров менеджера, на которых назначен план на месяц
   (`crm_sales_plans`, `target_type=client`); факт = любой из плановых, у кого есть отгрузка
   в месяце. **Клиент = партнёр (`users`), не контрагент** — партнёр с несколькими ИП/ООО
   считается одним. Множитель: <80 % → 0,8; 80–90 → 0,9; 90–110 → 1,0; 110–125 → 1,05;
   ≥125 → 1,1.
5. **Новые клиенты и лиды.** Новый клиент — партнёр с первой в истории отгрузкой в месяце;
   бонус за голову с порогом суммы первой отгрузки, половина сразу / половина при повторе
   в N дней, потолок на месяц, «возвращённый» (спящий вернулся) с весом. Лиды в KPI не входят.
6. **Закрытие месяца — РОП утверждает вручную.** Утверждённый снимок неизменяем; поздние
   оплаты/отгрузки задним числом на него не влияют; «переоткрыть» = новая версия черновика.
7. **Таблицы `payroll_*` не выдаются BI-агенту** (`bi:sync-grants` исключает по префиксу).
8. **Golden-пример** (тест до копейки): план 5 000 000, факт 4 900 000, клиентов 25/35,
   просрочка 12 000 (3–7 дн) + 400 000 (8+) → E = 3 682 000, F = 0,8 × 0,7364 = 0,58912,
   KPI = 50 075,20; итого 70 000 + 50 075,20 + 5 000 = **125 075,20**.

### Умолчания, принятые без отдельного вопроса

- Срок оплаты накладной при многострочном графике = последняя дата плановых строк регистра.
- Накладная без восстановленной даты закрытия (≈18 % истории: авансы по заказу, взаимозачёт,
  платёж без номера) — штрафа нет, попадает в очередь `needs_review`; РОП может проставить
  дату вручную с комментарием (как сейчас размечает в Excel).
- Премия не бывает отрицательной: штраф может обнулить KPI, но не залезть в оклад.
- Смена менеджера у клиента: атрибуция по текущему `personal_manager_id`; утверждённый снимок
  замораживает состав.
- Возвраты товара выручку не уменьшают — как на `/crm/plans` (цифры обязаны совпадать).
- Менеджер видит утверждённые прошлые месяцы и черновик текущего; параметры утверждённого
  месяца меняются только через «переоткрыть».

## Архитектура

Четыре раздельные вещи:

| Что | Где | Меняется |
|---|---|---|
| **Компоненты** (оклад, KPI с факторами, доп. доход, корректировка, новые клиенты) | `app/Services/Payroll/Components/*`, каталог `config/payroll.php` | кодом, редко |
| **Схема** — набор компонентов и умолчания | `payroll_schemes` (версии), v1 из конфига | несколько раз в год |
| **Параметры** — константы менеджер × месяц | `payroll_param_overrides` — только отклонения (схема → постоянные менеджера → месяц) | каждый месяц, без деплоя |
| **Снимок расчёта** | `payroll_calculations` (params_effective, inputs, breakdown, forecast; draft → approved → paid) | раз в месяц |

- Выручку считает **только** `ShipmentAnalyticsService` (через `PlanProgressService` /
  `ClientPlanFactService`) — второго движка не заводим.
- Мост «накладная → срок → дата закрытия → задержка в рабочих днях» —
  `payroll_invoice_settlements`: платежи `settlement_entries` type=`payment_in` сопоставляются
  с реализацией по номеру из `settlement_object_name` (на проде 4 830 из 5 885), рабочие дни —
  `TimesheetService::isWorkingDay()` + `config/production_calendar.php`.
- «Реалтайм» = пересчёт черновика джобом с дебаунсом по событиям (`PartnerSettlementsChanged`,
  отгрузки, планы, параметры) + страховочное расписание + polling во фронте раз в минуту.
- Прогноз и советы — тот же калькулятор с гипотетическими входами (what-if), никакой второй
  формулы.
