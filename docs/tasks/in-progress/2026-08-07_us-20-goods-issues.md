# US-20 Расходные ордера на товары из 1С (протокол v15.15.0)

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-08-07

## Описание

Сайт получал из 1С реализации (`shipment.*`), но реализация отражает **уже свершившийся**
факт отгрузки. Документ, по которому склад физически собирает, проверяет, упаковывает и
грузит товар — «Расходный ордер на товары» — на сайте отсутствовал полностью: ни одного
упоминания в коде, схемах и документации.

Из-за этого кладовщики и начальник склада работали в толстом клиенте 1С: в кабинете склада
не видно ни что сейчас в отборе, ни что зависло на этапе, ни сколько мест собрано,
ни по каким заказам идёт ордер.

Ордера приезжают **новыми событиями** `goods_issue.created` / `.updated` / `.deleted`
в **новую очередь** `erp_in.warehouse` (routing key `goods_issue.*`) со своим воркером.
Отдельно от `erp_in.documents` намеренно: у очереди реализаций один воркер, и первоначальная
выгрузка ордеров за всю историю заблокировала бы приём реализаций, платежей и балансов —
ровно та причина, по которой платежам в US-17 завели собственную очередь.

Обратный поток (сайт → 1С) в задачу не входит: журнал read-only, статусами управляет 1С.

## Что сделано

**Контракт (spec-first):**

- JSON Schema — `goods_issue.created.json`, `goods_issue.updated.json`,
  `goods_issue.deleted.json`. Обязательны `event`, `uuid`, `number`, `status`, `items`.
- AsyncAPI `15.14.0` → **`15.15.0`**: канал `erpInWarehouse`, три операции
  `receiveGoodsIssue*`, сообщения `GoodsIssue*`, схемы `GoodsIssueStatus`,
  `GoodsIssueItem`, `GoodsIssuePackage`, три payload-схемы.
- MkDocs: `rules/goods-issues.md`, задание разработчику 1С
  `guides/goods-issues-for-1c.md`, тест-кейсы `1.22 A–E` в `tests/phase-1-inbound.md`,
  changelog `[15.15.0]` с блоком «Требуется от 1С», очередь и routing keys
  в `infrastructure.md`, nav в `mkdocs.yml`.

**Ключевые решения контракта:**

- **`status` — строгий enum** машинных кодов (`prepared`, `to_pick`, `to_check`, `checked`,
  `to_ship`, `shipped`), а не свободная строка как у `shipment.status`. Статус здесь —
  главное, ради чего журнал склада существует: молча принять неизвестный код означало бы
  показать кладовщику состояние, которого нет в его рабочем процессе. Неизвестное значение
  отбивается в `erp_dlq.warehouse`.
- **`operation` — наоборот, свободная строка.** Операций у ордера больше, чем отгрузка
  клиенту (перемещения между складами), и enum отбил бы их в DLQ на ровном месте.
- **`recipient_name` хранится всегда.** Получателем бывает контрагент, которого в справочниках
  сайта нет вовсе — на исходном скриншоте это «Интернет Решения ООО» (Ozon). Без строки-имени
  такой ордер в журнале был бы безымянным.
- **Заказ живёт в строке (`items[].order_uuid`), а не в шапке** — один ордер собирается
  сразу по нескольким заказам. Та же модель, что у `shipment_items.order_uuid`.
- **`packages`: отсутствие ключа и `[]` означают разное** — не трогать сохранённое против
  очистить. Семантика скопирована у `payment_schedule` (v15.12.0).
- Серии номенклатуры и штрихкоды маркировки не принимаем: данных много, задач на них нет.

**Данные:** `goods_issues` (шапка + денормализация `items_count` / `total_quantity` /
`packages_count` / `unresolved_items_count`), `goods_issue_items`, `goods_issue_packages`,
`goods_issue_status_histories`.

Денормализация не преждевременная: журнал по этим полям сортируется и фильтруется на каждой
странице. `unresolved_items_count` — рабочий сигнал рассинхрона каталога, по нему в журнале
отдельный фильтр.

**Логика:**

- `GoodsIssuePayloadMapper` — общий разбор для `created` и `updated` (1С шлёт документ
  целиком в обоих случаях, различать на уровне записи нечем). Handler-ы тонкие.
  Переиспользованы `ResolvesContractorParty` и `ResolvesDocumentOrganization`.
- **Журнал статусов ведёт сайт**: 1С присылает только текущий. Строка пишется **только при
  фактической смене** — 1С досылает документ целиком при любом изменении, и без этой
  проверки журнал забился бы повторами одного статуса.
- `goods_issue.deleted` пишет в журнал псевдостатус `cancelled` («Отменён в 1С»), но
  **собственный статус ордера не трогает**: после восстановления документа должно быть видно,
  на каком этапе его застала отмена.
- `updated` по неизвестному ордеру его **создаёт**: потерянное или пришедшее не по порядку
  `created` иначе навсегда оставило бы склад без ордера.
- Неизвестный товар/заказ обработку не роняют — строка сохраняется со снимком имени и номера
  из 1С.
- Регистрация в трёх точках: `ErpIncomingJob::EVENT_HANDLERS`,
  `ErpMessageValidator::SCHEMA_MAP`, `SetupRabbitMQTopology::INCOMING_QUEUES`.
- Воркер `erp-warehouse-consumer`, `numprocs=1` обязателен: журнал статусов —
  read-modify-write, два воркера на одном документе дадут дубли переходов.

**Доступ:** новый ресурс `wms-goods-issues` с правами `view` и `export` — и только ими:
документ принадлежит 1С, менять на сайте нечего. Обе складские роли (`warehouse-head`,
`storekeeper`) получают полный набор: расходный ордер — их общий рабочий документ.

**Интерфейс:** журнал `/wms/goods-issues` — плитки-счётчики по статусам (они же
переключатели фильтра), мультивыбор статусов/складов/ответственных, фильтры по приоритету,
способу доставки, периодам даты документа и даты отгрузки, «зависшие дольше 24 ч»,
«с позициями без товара в каталоге», поиск по номеру ордера, номеру заказа, получателю
и товару, сортировка, выгрузка XLSX (два листа: «Ордера» и «Позиции», текущая выборка
с фильтрами). Карточка: шапка, позиции **сгруппированные по заказам**, упаковочные листы,
лента истории статусов. Плитка «Расходные ордера» на дашборде WMS.

Админка: очереди `erp_in.warehouse` / `erp_dlq.warehouse` в «Шине ERP» и `rabbitmq:status`.
Фильтр событий в логе шины строится динамически — правки не потребовал.

## Замечено попутно (не чинил — за рамками задачи)

Валидатор схем проверяет `format: uuid` — сообщение с невалидным UUID отбивается целиком.
В задании для 1С это отражено требованием присылать GUID-ы теми же, что в `price.updated`
и `stock.updated`, но в changelog отдельным пунктом не вынесено: правило общее для всего
протокола, а не для расходных ордеров.
