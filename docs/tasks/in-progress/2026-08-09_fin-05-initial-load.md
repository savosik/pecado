# fin-05 · Первичная выгрузка регистра из 1С

**Приоритет:** высокий
**Создано:** 2026-08-09
**Эпик:** [fin-00](2026-08-09_fin-00-epic.md)
**Зависимости:** `fin-04` (приём готов), готовность стороны 1С
**Волна:** 2 — сначала dev, прод только после сверки

## Описание

Наполнение регистра историческими данными. Карточка **совместная** — основную работу делает
сторона 1С, сайт наблюдает, считает и ловит проблемы.

**Две даты, а не одна.** 1С сообщила, что 01.01.2026 не сверена: даты запрета изменения стоят
на 31.03, 30.04 и 30.06.2026. Поэтому берём обе точки:

- **01.01.2026** — начало ленты движений, сальдо помечено несверенным;
- **01.07.2026** — сверенное сальдо, приходит как `settlement.checkpoint`.

Инвариант, который это даёт: «сальдо 01.01 + движения первого полугодия» обязано сойтись
с checkpoint на 01.07. Сойдётся — история H1 достоверна. Нет — расхождение известно точной
величиной, и решение «показывать ли первое полугодие» принимается осознанно, а не по умолчанию.

## Порядок выгрузки (нарушать нельзя)

| Шаг | Что | Объём | Почему такой порядок |
|---|---|---|---|
| 1 | `agreement.created` по всем соглашениям | **5 102** | Движения на них ссылаются |
| 2 | `settlement.opening_balance` на 01.01.2026 | по контрагентам | Точка отсчёта. Без неё баланс занижен на всю историю до 2026 |
| 3 | `settlement.posted` по документам с 01.01.2026 | **224 632 строки / 17 607 документов** | Основной объём |
| 4 | `payment_schedule.updated` по незакрытым документам | — | Прогноз. Только где остаток > 0 |
| 5 | `settlement.checkpoint` на 01.07.2026 | по контрагентам | Сверенная точка для инварианта |
| 6 | `balance.updated` по всем контрагентам | — | Контрольная сумма для `fin-06` |

Шаги 3–4 — пачками с паузой, не одним залпом. Очередь `erp_in.settlements` отдельная, поэтому
прод-обмен по заказам и остаткам не встаёт. 224 тысячи строк — объём умеренный, `numprocs=2`
достаточно.

⚠️ **38 % объёма — движения `ЗаказКлиента`** (85 249 строк). Их трактовка (факт или план)
зависит от ответа 1С на вопрос Б в [`fin-01`](../todo/2026-08-09_fin-01-1c-prompt.md).
Заливку не начинать, пока ответа нет: перезаливать 85 тысяч строк с другой трактовкой дороже,
чем подождать.

## Что делает сайт

- Мониторинг заливки: глубина очереди, скорость, DLQ. `docker exec pecado-app php artisan horizon`
  и RabbitMQ management.
- `ERP_BUS_LOGGING_ENABLED=true` на время заливки — потом **обязательно выключить**: журнал
  `erp_bus_messages` уже был замечен как основной источник мусора в БД (96 % прод-базы вместе
  с Pulse).
- Промежуточные счётчики: сколько движений принято, сколько с `NULL` в связях, сколько в DLQ.
- Команда `php artisan settlements:stats` — сводка по типам, датам, соглашениям без движений и
  движениям без соглашения.

## Edge-кейсы

- **Соглашения у документа нет.** Редкий случай (покрытие 100 % по замерам 1С). Движения приезжают с пустым
  `agreement_uuid`, сводятся в группу «Без соглашения». Посчитать долю — если она велика,
  разбивка по соглашениям теряет смысл; на сальдо это не влияет (ось — контрагент × организация).
- **Сальдо на 01.01.2026 не по всем контрагентам.** Контрагент без сальдо считается открытым с нуля.
  Отдельным счётчиком: сколько контрагентов без `opening_balance`.
- **Документ за 2026 год, которого нет на сайте** (сайт импортировал историю в мае 2026 —
  см. `project_analytics_business_date`). Движение сохраняется без связи, читается по
  реквизитам. Это нормально и **не** повод дозагружать документы.
- **Заливка прервалась.** Повторный запуск безопасен: идемпотентность по `uuid`. Проверить
  тестом до боевого прогона, а не после.
- **DLQ наполняется.** Остановить заливку, разобрать причину. Типовое: неизвестный `type` или
  знак не по соглашению.
- **Тепловой лимит машины.** Локально ничего тяжёлого не гоняем; заливка идёт на dev-сервере.
