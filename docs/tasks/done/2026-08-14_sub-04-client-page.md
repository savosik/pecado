# sub-04: клиентская страница подборки и постинг заказа-замены

**Приоритет:** высокий
**Эпик:** [sub-00](2026-08-14_sub-00-epic.md)
**Зависит от:** sub-02 (наполнение — sub-03 руками или sub-06 автоматом)
**Создано:** 2026-08-14

## Описание

Страница «Замена по заказу N» — единственное место, куда идёт клиент.
Никаких полей ввода: компания, адрес, способ доставки наследуются от исходного заказа.

### Доступ

- URL по `substitution_offers.uuid`, подписанный (`URL::temporarySignedRoute`,
  живёт до `expires_at`): **просмотр** из письма без входа.
- **Согласование — только под авторизацией владельца заказа** (user или его
  компания): кнопка создаёт финансовый документ с индивидуальными ценами,
  пересланное письмо не должно давать право постить заказы. Неавторизованный
  жмёт «Согласовать» → вход → возврат на страницу с **сохранённым выбором**.
- Открытие страницы: `status pending → viewed`, `viewed_at`.
- Просроченный/закрытый оффер → честная заглушка «подборка неактуальна,
  свяжитесь с менеджером ‹имя, контакты›».

### Содержимое

По каждой отменённой строке — радио-группа:
- кандидаты с ценой клиента (пересчитанной на момент рендера, не snapshot),
  остатком и причиной; **уценка выделена** и показывает `defect_description`;
- «Подождать прихода ~‹дата›» — если слой 0 дал прогноз;
- «Без замены» (по умолчанию, если клиент ничего не выбрал).

Количество: предзаполнено `suggested_quantity`, уменьшать можно, увеличивать
нельзя. Кандидат с остатком меньше нужного показывает «доступно k из n».
Внизу — «Итого замена: X ₽ (вместо Y ₽)».

### Постинг («Согласовать замену»)

1. Собрать **программную корзину** из выбранного: обычные кандидаты →
   `item_type` по остатку, уценка → `item_type = defect` + `product_defect_id`.
2. Вызвать `CheckoutService::checkout(cart, company исходного заказа,
   delivery_address исходного, deliveryMethod исходного)` — он сам расщепит на
   заказ(ы) по типам (обычный + `defect`), проверит остатки и посчитает цены.
3. На созданных заказах: `replacement_for_order_id` = исходный;
   на строках — `replaces_order_item_id`; в `manager_comment` — текст
   «Замена недоборов по заказу ‹номер›» (**протокол не меняется**, 1С видит
   обычный `order.created`).
4. Оффер → `confirmed`, `result_order_ids`, выбор зафиксирован в
   `chosen`/`chosen_quantity` + события `client_chosen`/`client_skipped`.
5. `InsufficientStockException` (товар кончился, пока клиент думал) →
   не 500, а возврат на страницу: «‹Название› закончился, вот обновлённые
   варианты» + пересбор кандидатов по этой строке.
6. Двойной сабмит (два таба) → второй получает «уже согласовано, заказ №…».

### Кабинет

- В исходном заказе над зачёркнутыми строками — баннер «По k позициям подобрана
  замена → посмотреть» (пока оффер жив) или плашка «замена согласована →
  заказ №…» (после).
- Экран подтверждения: «Создан заказ 29УТ-…, связан с 29УТ-…» + ссылка.

## Критерии готовности

- [ ] Просмотр по signed URL без входа; согласование требует авторизации владельца; выбор переживает редирект на вход
- [ ] Постинг через `CheckoutService`: смешанный выбор (обычный + уценка) создаёт два связанных заказа
- [ ] Связи `replacement_for_order_id` / `replaces_order_item_id` проставлены; пометка в `manager_comment`
- [ ] Кап количества; частичная доступность показана честно
- [ ] `InsufficientStockException` обработан человеческим сообщением; двойной сабмит идемпотентен
- [ ] Цены на странице = ценам созданного заказа (индивидуальные, `PriceService`)
- [ ] Статусная машина оффера: viewed/confirmed/expired покрыта тестами
- [ ] Интеграционный тест: согласование → в `erp_out.orders` уходит валидный по JSON Schema `order.created` (обычный и defect)
- [ ] UI на русском; браузерная проверка на dev, включая мобильную ширину (клиент откроет письмо с телефона)
