# org-08 · Организация возврата — справочно, с реализаций

**Приоритет:** средний
**Создано:** 2026-08-01
**Закрыта:** 2026-08-11 — разработка завершена, приёмка не проводилась по решению заказчика
**Скоуп сужен:** 2026-08-01 — организация справочная, в 1С **не отправляется**
**Эпик:** [org-00](../backlog/2026-08-01_org-00-epic.md)
**Зависимости:** `org-04` (организация берётся с реализации)

## Описание

С v12.13.0 возврат формируется **на основании реализаций** — каждая позиция несёт
`shipment_uuid`. После `org-04` у реализации есть организация, значит организация
возврата **выводима**: сайт может показать её клиенту и менеджеру, не спрашивая 1С.

Отправлять её в `return.created.to_erp` **не нужно**: 1С выводит организацию из тех же
реализаций-оснований. Дублирование в контракте создало бы второй источник истины
на ровном месте.

## Что делаем

**Миграция:** `returns` + `organization_id` (nullable FK) с комментарием
`'Организация реализаций-оснований (organizations.id). Справочно: 1С определяет её сама'`.

**Заполнение при создании возврата:** организация берётся с реализаций, на которые
опираются позиции. Если основания принадлежат разным организациям — `NULL`
(см. edge-кейс 1), а не «первая попавшаяся».

**Приём `return.updated`** + `organization` — если 1С прислала, сохраняем: её значение
авторитетнее выведенного.

**UI:** организация в карточке возврата и в списке возвратов — ЛК, админка, CRM.
Колонка и фильтр в списках. Под флагом `ORGANIZATIONS_ENABLED`.

**Исходящий payload не меняется.**

## Edge-кейсы

1. **Позиции из реализаций разных организаций** → `organization_id = NULL`, в UI
   «несколько организаций». Разбивать возврат **не нужно**: 1С разложит документы сама
   по основаниям. Клиента не ограничиваем.
2. **Legacy-реализация без организации** → `NULL`, строка в UI скрыта.
3. **Смешение legacy-реализации и реализации с организацией** → `NULL`. Не «протаскиваем»
   организацию на позиции, к которым она не относится.
4. **Организация реализации — stub** → показываем как есть, клиент увидит UUID. Stub-записи
   должны быть заметны в админке, чтобы менеджер дозаполнил имя.
5. **Частичный возврат** — организация от реализации, **не** от заказа: они могут
   разойтись (`org-04`, edge-кейс 4).
6. **Реализация удалена** после создания возврата → `organization_id` сохранён снапшотом,
   не пересчитываем.
7. **Возврат уценки** — партия брака; проверить, что списание/восстановление остатка
   не задето.
8. **Существующие возвраты** на момент релиза → `organization_id = NULL`. Бэкфилл по
   реализациям возможен и безопасен (организация выводится однозначно), но делать его
   только там, где все основания одной организации.

## Не входит

Отдельно найденный при проектировании дефект — возврат может смешивать позиции
реализаций **разных контрагентов клиента** — вынесен в самостоятельную карточку
[returns-mixed-contractors](../backlog/2026-08-01_returns-mixed-contractors.md). К организациям
он отношения не имеет и чинится независимо.
