## Описание

Сегодня баланс ведётся по паре (пользователь, контрагент клиента):
`contractor_balances` + `contractor_balance_overdue_details`. Нужен третий уровень —
**наша организация**: клиент должен видеть, кому именно он должен, потому что платит он
на разные расчётные счета.

Структура становится: `партнёр → контрагент клиента → наша организация → сумма`.

## Что делаем

**Миграция `contractor_organization_balances`:**

```php
$table->comment('Взаиморасчёты клиента в разрезе его контрагента и нашей организации');
$table->foreignId('user_id')->comment('Партнёр (users.id)');
$table->foreignId('company_id')->comment('Контрагент клиента (companies.id)');
$table->foreignId('organization_id')->comment('Наша организация (organizations.id)');
$table->decimal('current_balance', 15, 2)->default(0)
      ->comment('Текущий баланс: отрицательное значение — долг клиента');
$table->decimal('overdue_debt', 15, 2)->default(0)->comment('Просроченная задолженность');
$table->timestamp('balance_erp_updated_at')->nullable()->comment('Момент актуальности данных в 1С');
$table->unique(['company_id', 'organization_id']);
```

`contractor_balance_overdue_details` + `organization_id` (nullable FK).

**`contractor_balances` остаётся агрегатом** — детализация добавляется рядом, а не внутрь
(принцип 4 эпика). Существующие
чтения (`CabinetController`, `ShipmentController`, админка `ContractorBalanceController`)
не меняются.

**`HandleBalanceUpdated` — две ветки:**

| Пришло | Поведение |
|---|---|
| `contractors[].organizations[]` есть | пишем детализацию; `contractor_balances` = сумма по организациям |
| детализации нет | legacy: пишем `contractor_balances` напрямую, как сейчас |

**Приоритет при расхождении.** Если 1С прислала и contractor-уровень, и детализацию,
и `SUM(organizations) ≠ contractor.current_balance` — **источник истины contractor-уровень**
(его клиент видит как итог), расхождение пишем `Log::warning` с обеими суммами.
Детализация показывается как «в том числе». Причина выбора: расхождение почти наверняка
означает, что часть расчётов в 1С не разнесена по организациям, и обнулять итог из-за
этого нельзя.

**Просрочка.** `overdue_details[].organization_uuid` — если не пришёл, выводим организацию
из реализации по `shipment_uuid` (после `org-04` она там есть). Не вывелась — `null`.

**ЛК клиента.** Блок баланса: итог по контрагенту + раскрытие по организациям с
реквизитами для оплаты (из `organizations.bank_*`) — это главная польза для клиента.
Формулировка на русском: «Задолженность перед ООО «Пекадо» — 120 000 ₽, из них
просрочено 15 000 ₽».

**Админка/CRM.** Разрез по организациям в карточке контрагента, фильтр «есть просрочка
перед организацией X».

## Edge-кейсы

1. **Детализация ещё ни разу не приходила** → блок разреза в ЛК **не показывать вовсе**
   (не показывать «одна организация: не указана» — это выглядит как поломка).
2. **`SUM(organizations) ≠ contractor.current_balance`** → приоритет у contractor-уровня,
   warning в лог. Метрика: количество таких сообщений — индикатор готовности 1С.
3. **Организация исчезла из массива** между сообщениями — значит расчётов с ней больше нет.
   Строку **не удаляем**, обнуляем (иначе история пропадёт из отчётов). Строки, отсутствующие
   в свежем сообщении, обнуляются в рамках той же транзакции.
4. **Переплата одной организации не гасит долг перед другой.** Взаимозачёт между нашими
   юрлицами — компетенция 1С. В ЛК не суммировать плюс и минус разных организаций
   «в одно число» без пояснения, иначе клиент решит, что долга нет.
5. **Контрагент клиента работает только с одной нашей организацией** — обычный случай,
   разрез из одной строки. Показывать без раскрытия, чтобы не плодить интерфейс.
6. **Организация в балансе не заведена в справочнике** → stub (клиент увидит UUID). Здесь
   это заметнее, чем в заказах: stub-организации в балансе стоит алертить менеджеру.
7. **Просрочка есть, а реализации на сайте нет** (не доехала или удалена) →
   `organization_id = null` в детали просрочки, сумма всё равно учитывается.
8. **Валюта.** Балансы приходят без указания валюты; при разрезе по организациям
   это может стать важно (расчёты в разных валютах). Зафиксировать вопрос стороне 1С,
   в схему поле **не** добавлять до ответа.
9. **Гонка сообщений** — `balance.updated` по одному партнёру приходит часто; вся
   перезапись строго в одной транзакции с `balance_erp_updated_at`-проверкой:
   сообщение старше сохранённой метки игнорируется.

### Решения, принятые по ходу

**Пустой `organizations: []` трактуется как «разреза нет», а не «обнули всё».** Расчётов
«ни с одной организацией» при непустом балансе не бывает, а молчаливое обнуление истории
необратимо.

**Разрез не пишется, если контрагент не найден на сайте.** Ключ таблицы — пара
(контрагент, организация), писать некуда. Пишем warning.

**В ЛК показываются только ненулевые строки и только не-заглушки.** Обнулённые строки
клиенту не нужны (долг погашен), а у заглушки вместо названия UUID. В админке, наоборот,
нули видны: менеджеру полезно знать, что расчёты с юрлицом были и закрыты.

**Суммы разных организаций нигде не складываются в одно число** — ни в кабинете,
ни в админке. Переплата одному юрлицу не гасит долг другому, а «ноль» на экране убедил бы
клиента, что платить нечего.

⚠️ Автоимена индексов новой таблицы вышли длиннее 64 символов — MySQL их не принимает.
Заданы явно: `cob_company_organization_unique`, `cob_user_organization_index`.
