# org-07 · Сужение складов в исходящем заказе до одного

**Приоритет:** низкий
**Создано:** 2026-08-01
**Закрыта:** 2026-08-11 — **решено не делать**
**Статус:** ⏸ отложено 2026-08-01 — временно склады продолжают уходить перечислением
UUID-ов, как сейчас. Заказ по складам региона не разбивается
**Эпик:** [org-00](2026-08-01_org-00-epic.md) — карточка вне волн, ничего не блокирует

## Закрытие (2026-08-11)

**Не делаем.** Решение от 01.08 подтверждено: склады региона взаимозаменяемы и уходят
перечислением, исходящий контракт эпик не менял вовсе. Сужать заказ до одного склада
пришлось бы ради стройности схемы, а не ради потребности.

## Решение (2026-08-01)

Пока склады, объединённые в один регион, считаются взаимозаменяемыми: сайт отправляет
`warehouse_uuids[]` перечислением, 1С выбирает склад сама. Разбиение заказа по складам
**не делаем**.

Исходящий контракт в эпике организаций **не меняется вообще** — это позволило убрать
из скоупа всю работу по исходящей стороне.

## Что здесь останется, если решение изменится

Карточка сохранена, чтобы не проектировать заново. Триггер к возврату: требование, чтобы
один заказ соответствовал одному складу.

**Первый шаг — выяснить, есть ли вообще работа.** Проверить на проде состав
`region_warehouse`:

```sql
SELECT type, region_id, COUNT(*) FROM region_warehouse GROUP BY region_id, type
HAVING COUNT(*) > 1;
```

- у каждого региона один склад наличия → замена списка на единственный элемент, разбиение
  не нужно;
- складов несколько → нужен выбор склада по наличию и разбиение заказа по складам.

Локальная БД пуста, проверять только на проде.

**Объём работ:**
- в `order.created.to_erp` добавляется `warehouse_uuid`; `warehouse_uuids[]` остаётся
  на переходный период, чтобы 1С не релизилась одновременно;
- выбор склада: покрывающий максимум позиций, при равенстве — по порядку в регионе;
- разбиение по складам, если позиции лежат на разных: по документу на склад. В чекауте
  это надо показать, как уже сделано для типов заказов (`promo-08`);
- особые типы (`defect`, `promo_sample`, `preorder`) не трогаются — у них склад
  определён однозначно, существующие гейты публикации сохраняются.

**Edge-кейсы:**
1. Позиция лежит на двух складах региона → дробление строки между документами; клиенту
   показать до подтверждения.
2. Регион у клиента не задан → сейчас уходит пустой `warehouse_uuids`; поведение сохранить.
3. ⚠️ **Костыль подмены UUID склада предзаказа** (`project_preorder_warehouse_hack`, на
   проде с 2026-06-26, «Тюмень Основной» → `3d0a3eb9…`) живёт внутри
   [resolveWarehouseUuids](../../../app/Listeners/PublishOrderToErp.php#L141). Любая
   переработка этого метода обязана его сохранить вместе с флагом
   `PREORDER_WAREHOUSE_UUID_OVERRIDE_ENABLED`. Пока карточка отложена — метод не трогаем,
   и это ещё одна причина её не начинать без нужды.
4. Остатки протухли между показом корзины и оформлением → склад определять в момент
   оформления.
5. 1С провела заказ на другой склад → принимаем её значение (`org-03`), расхождение в лог.
6. Клиентское API и заказы менеджера в CRM идут тем же путём.

## Критерии готовности

*Не применимо — карточка отложена.*

- [ ] Появилось требование «один заказ = один склад»
- [ ] Состав `region_warehouse` на проде проверен, объём работ определён
