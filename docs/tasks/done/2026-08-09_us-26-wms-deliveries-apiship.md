# US-26 Отправки в транспортные компании через ApiShip

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-08-09

## Описание

Логистического слоя в системе не было вообще. Доставка описывалась только атрибутивно —
`orders.delivery_method` плюс `delivery_address` строкой и `goods_issues.delivery_type`
из 1С. Трек-номеров не существовало ни одного (grep по `track_number|tracking` в `app/`
давал ноль), таблицы перевозчиков не было.

Из-за этого склад собирал груз, а дальше оформлял заявку вручную на сайтах перевозчиков:
стоимость доставки нигде не учитывалась, состояние отправки нигде не было видно, а на
вопрос «где посылка» менеджер шёл в чужой личный кабинет.

Раздел `/wms/deliveries`: начальник склада выбирает несколько реализаций, система считает
вес по товарам, кладовщик задаёт места и габариты, выбирает перевозчика по расчёту
стоимости, передаёт заявку и дальше видит статус доставки без ручных проверок.

Интеграция — через агрегатор [ApiShip](https://docs.apiship.ru/docs/api/): один договор
вместо отдельных подключений к каждой ТК.

**По шине RabbitMQ ничего не публикуется.** Отправка — документ сайта, 1С про неё не знает.
`docs/asyncapi/` и `docs-erp/` задача не затрагивает; правило об интеграционных тестах
шины здесь неприменимо, но HTTP-интеграция покрыта полностью.

## Что сделано

**Данные (5 таблиц, все миграции новые, с русскими комментариями):**

- `delivery_shipments` — отправка: состав, тариф, трек, статусы, снапшоты адресов
  в формате ApiShip. Номер `DS-000123` присваивается после вставки из `id` — расчёт
  «максимум + 1» ловил бы гонку при двух кладовщиках сразу.
- `delivery_shipment_documents` — какие реализации вошли в груз, со снапшотами веса и суммы.
- `delivery_shipment_places` — грузовые места: вес в **граммах**, габариты в **сантиметрах**.
- `delivery_shipment_status_histories` — журнал смен статуса с источником.
- `apiship_requests` — журнал HTTP-вызовов по образцу `supplier_preorder_requests`.

**Ключевые решения:**

- **Запрет «реализация в двух отправках» — в сервисе, не индексом.** Уникальным индексом
  это не выразить: после отмены заявки груз собирают заново, и та же реализация обязана
  попасть в новую отправку. Отменённые и провалившиеся отправки документы отпускают
  (`DeliveryShipmentStatus::holdsDocuments()`).
- **Два енума вместо одного.** До передачи заявки статуса у перевозчика ещё нет, а складу
  уже надо отличать черновик от посчитанного груза. `ApiShipStatus` (19 ключей ТК) →
  `DeliveryShipmentStatus` (8 внутренних) через `toShipmentStatus()`.
- **Возвраты и утеря — это `in_transit`, не `delivered`/`cancelled`.** Груз ещё в работе
  у перевозчика, и отправка должна оставаться на радаре склада.
- **Незнакомый ключ статуса не ломает приём** — сохраняется как есть, внутренний статус
  не меняется. Новый статус у ТК не должен ронять вебхуки.
- **`POST /orders` без автоматических повторов** (`tries = 1`, `retry()` только на GET):
  метод неидемпотентен, ретрай после таймаута завёл бы вторую заявку на тот же груз.
  Та же логика, что у `SendPreorderToSupplierJob`.
- **Вес товаров без `weight_gross` берётся из конфига, а не ноль.** Ошибки API не будет,
  но перевозчик посчитает тариф по объёмному весу и выставит другой счёт. Позиции без веса
  подсвечиваются в мастере.
- **Мастер разложен на две страницы.** Состав, места и адрес — в `Create`, расчёт и передача
  заявки — в карточке: они опираются на сохранённые вес и адрес, и считать их по
  несохранённой форме означало бы держать половину состояния в браузере.
- **Отмена заявки — только `warehouse-head`.** Может стоить денег и разъезжается с уже
  напечатанными этикетками.

**Статусы — вебхук плюс сверка:**

- `POST /api/delivery/apiship/webhook/{secret}` — основной канал. Подписи ApiShip не даёт,
  поэтому защита трёхслойная: мастер-флаг, секрет в URL через `hash_equals`, allowlist IP.
  На всё, кроме проблем доступа, отвечаем `200`: ApiShip считает неудачей HTTP ≥ 500 и
  ретраит трижды.
- `apiship:sync-statuses` каждые 30 минут — страховка. Один запрос
  `GET /orders/statuses/interval` вместо поштучного опроса; курсор с нахлёстом 5 минут.
  Нужна ровно на случай, когда сайт лежал дольше трёх попыток доставки вебхука.

**Адрес получателя — три источника** (`DeliveryAddressResolver`): строка из
`orders.delivery_address`, `delivery_addresses.address_data` клиента, ручной ввод.
Первые два — свободный текст, поэтому разбираются через уже существующий `DaDataClient`;
ручной ввод использует готовый компонент `AddressSuggest`.

**Фронтенд:** `Wms/Pages/Deliveries/{Index,Create,Show}.jsx`, пункт «Отправки в ТК» в меню.
Соблюдён двойной рендер домена WMS — таблица на десктопе, карточки на телефоне.

**Тесты:** `tests/Feature/Wms/Delivery/` — 5 файлов, 43 теста на `Http::fake`.
Покрыты: права обеих ролей и отсутствие доступа в `/admin`, расчёт веса и фолбэк,
запрет двойного включения реализации, разбор ответа калькулятора, передача заявки,
ошибка валидации от ТК, не-JSON ответ, выключенная интеграция (`assertNothingSent`),
кэш токена, этикетка, ПВЗ, курьер, отмена, вебхук (секрет / allowlist / повтор /
незнакомый статус / чужой номер), команда сверки с `--dry-run`.

**Документация:** `docs/APISHIP.md` — поток, таблица соответствия статусов, раздел
про ретраи и идемпотентность, переменные окружения, инструкция по тестовой среде ApiShip.

## Что осталось

- Показ отправок клиенту в личном кабинете — следующая итерация. Модель данных уже
  клиенто-ориентированная (`user_id`, снапшоты адресов, публичный `tracking_url`),
  кабинетных страниц нет намеренно.
- Боевые креды ApiShip: `APISHIP_ENABLED=false` до получения договора. Проверка
  идёт на тестовой среде `http://api.dev.apiship.ru/v1` (логин/пароль `test`).
- Подписку на вебхук нужно зарегистрировать вручную после деплоя:
  `php artisan apiship:register-webhook`.
