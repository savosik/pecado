# sub-02: детект недобора — офферы рождаются сами

**Приоритет:** высокий
**Эпик:** [sub-00](2026-08-14_sub-00-epic.md)
**Зависит от:** sub-01
**Создано:** 2026-08-14

## Описание

Точка рождения оффера — `OrderItemsSynchronizer::sync()`: он единственный, кто
переводит строки в `cancelled = 1` (и `order.created`, и `order.updated` проходят
через него). После коммита транзакции обработчика — доменное событие
`OrderItemsCancelled(order, стало-отменённых-строк)`.

Слушатель (за флагом `SHORTAGE_OFFERS_ENABLED`):

1. **Нет открытого оффера** по заказу → создать `pending`-оффер: адресат из заказа,
   `manager_user_id` = `user.personal_manager_id`, `expires_at` +7 дней.
2. **Есть `pending`/`viewed`** → дополнить новыми строками (1С проверяет сборку
   в несколько заходов — вторая волна отмен по тому же заказу реальна).
   Идемпотентность: уникальный ключ из sub-01, повторная доставка сообщения из
   RabbitMQ не плодит дубли.
3. **Есть `confirmed`** → создать новый оффер (первый уже отработал).
4. Поставить менеджеру `CrmTask`: «Недобор по заказу N — ‹клиент›, ‹сумма› ₽,
   ‹k› позиций», дедлайн — сегодня 18:00; если сумма отменённого > порога
   (env `SHORTAGE_URGENT_AMOUNT`, старт 10 000 ₽) — дедлайн +2 часа.
   Ссылка задачи ведёт в карточку недобора.
5. Фолбэк адресации (правило «по данным, не по ролям»): у пользователя нет
   `personal_manager_id` → задача руководителю отдела / получателям из
   `MAIL_ORDER_FALLBACK_RECIPIENTS`. Недобор не должен зависнуть ничьим.

Кандидатов подбора здесь **нет** — оффер рождается пустым, наполнение: волна 1
руками (sub-03), волна 2 автоматом (sub-06).

### Отдельный канал: рассинхрон каталога

Позиция с `product_id IS NULL` (товар в payload есть, на сайте не нашли по UUID) —
**не недобор**, замена не нужна. Нужен алерт: лог-уровень warning + счётчик в
админ-дашборд ErpBus. 87 случаев за историю — молча копятся и сейчас.

### Чистка данных (разово, при выкатке)

У 10 заказов с недобором персональный менеджер — «Контент-менеджер», у 2 — никого.
Разобраться с назначением и починить фолбэком выше.

## Критерии готовности

- [ ] Событие диспатчится только по **новым** отменам (строка уже была cancelled → не диспатчится), после коммита
- [ ] Оффер: создание / дополнение / новый-после-confirmed — три сценария покрыты
- [ ] Повторная доставка того же `order.updated` не создаёт дублей строк оффера
- [ ] CrmTask с дедлайном и порогом срочности; фолбэк без персонального менеджера
- [ ] Флаг `SHORTAGE_OFFERS_ENABLED` выключен → поведение системы не меняется вовсе
- [ ] Алерт по `product_id IS NULL` в ErpBus-дашборде
- [ ] Интеграционные тесты (правило integration-tests: путь начинается с сообщения шины): `order.updated` с отменой → оффер + задача; вторая волна отмен → дополнение; roundtrip `order.created` сайтового заказа без отмен → офферов нет
