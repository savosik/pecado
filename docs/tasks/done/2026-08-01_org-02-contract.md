# org-02 · Контракт: опциональные поля организации во входящих сообщениях

**Приоритет:** высокий
**Создано:** 2026-08-01
**Закрыта:** 2026-08-11 — разработка завершена, приёмка не проводилась по решению заказчика
**Уточнено:** 2026-08-01 — исходящий контракт **не меняется вовсе**, справочник в шину не едет
**Эпик:** [org-00](../backlog/2026-08-01_org-00-epic.md)
**Зависимости:** `org-01`

## Описание

Spec-first-шаг: расширить контракт **до** любого кода волны 1. После этой карточки 1С
может начать слать организацию в любой момент — сайт примет без ошибок валидации,
а после волны 1 ещё и сохранит.

Изменения **только во входящих** сообщениях. Сайт в 1С ничего нового не отправляет.

Порядок по правилу проекта: **JSON Schema → AsyncAPI → MkDocs → changelog → сборка**.

## Что делаем

**JSON Schema** (`app/Services/Erp/Schemas/`) — все поля **опциональные**, ни одного
в `required`:

| Файл | Добавляется |
|---|---|
| `order.created.json`, `order.updated.json` | `organization` `{uuid, name?, tax_id?}`, `warehouse_uuid` |
| `shipment.created.json`, `shipment.updated.json` | то же |
| `return.updated.json` | `organization` `{uuid, name?}` — справочно |
| `balance.updated.json` | `contractors[].organizations[]`: `{uuid, current_balance, overdue_debt, overdue_details[]}` |

**Чего в контракте не появляется** — фиксируется в документации явно, чтобы не всплыло
позже как «а давайте»:

| Не появляется | Почему |
|---|---|
| Справочник организаций в шине (`organization.*`, очередь `erp_in.organizations`) | 1С его не отправляет; организации заводятся в админке руками, 1С указывает только UUID (`org-01`) |
| `organization_uuid` в `stock.updated` | Остатки приходят агрегатом по складу — подтверждено 1С |
| `organization_uuid` в `price.updated` | Приходит агрегированная лучшая цена, без разреза — подтверждено 1С |
| Организация в `order.created.to_erp` | Сайт её не определяет |
| `warehouse_uuid` (единственный) в `order.created.to_erp` | Склады уходят перечислением `warehouse_uuids[]`, как сейчас. Сужение до одного склада отложено — см. [org-07](../backlog/2026-08-01_org-07-orders-outbound.md) |
| Организация в `return.created.to_erp` | 1С выводит её из реализаций-оснований |
| Ставка НДС | Вне скоупа — [отдельная карточка](../backlog/2026-08-01_vat-rates-on-products.md) |

**AsyncAPI** `docs/asyncapi/pecado-erp-integration.yaml` — расширение message-ей четырёх
входящих событий. Новых каналов и operation-ов **нет**. Версия спеки → **15.8.0**: все
изменения обратно совместимы, ломающего ничего нет, поэтому минорная.

**MkDocs** `docs-erp/content/`:
- новая страница `rules/organizations.md` — что такое организация, в каких документах
  приходит, почему её нет в остатках, ценах, справочнике и исходящих сообщениях;
- ⚠️ в `rules/stock.md` — **закрепить действующее поведение** как требование: остатки
  присылаются агрегатом по складу (подтверждено 1С 2026-08-01), раздельные сообщения по
  организациям на один склад недопустимы. Причина: `HandleStockUpdated` пишет остаток
  перезаписью по ключу (товар, склад), и переход на раздельные сообщения молча занизил бы
  наличие — победило бы последнее;
- ⚠️ в `rules/prices.md` — то же для цен: приходит агрегированная лучшая цена;
- правки в `rules/orders.md`, `rules/shipments.md`, `rules/returns.md`, `rules/balance.md`;
- в `rules/orders.md` пункт v15.7.1 «организация определяется 1С по `type`» **остаётся
  в силе** — промо-хардкод не отменяется, уточняется лишь, что теперь 1С возвращает
  выбранную организацию обратно;
- `changelog.md` — запись 15.8.0 с явным «все поля опциональны, обратная совместимость
  полная, исходящие сообщения не изменились».

**Задание для 1С** `docs/erp-1c-organizations-prompt.md` по образцу
`docs/erp-1c-promo-integration-prompt.md`. Проговорить:
- 1С **обязана** возвращать организацию и склад в `order.*` и `shipment.*`;
- баланс присылается с разрезом по организациям и суммами по каждой;
- достаточно **UUID** организации; название и ИНН — необязательный бонус, справочник
  ведётся на сайте вручную;
- остатки и цены — **строго агрегатом**, как сейчас;
- сайт организацию не присылает и присылать не будет;
- склады в заказе от сайта продолжают уходить перечислением UUID-ов.

**Сборка:** `docker exec pecado-node npm run asyncapi:build` + `mkdocs build`.

## Edge-кейсы

- **1С шлёт `organization`, сайт ещё не умеет читать** (промежуток до волны 1) — валидатор
  обязан пропускать. Проверить, что ни в одной схеме нет `additionalProperties: false`.
- **Пришёл только UUID, без названия** — основной ожидаемый случай. Схема не должна
  требовать `name`.
- **`organization.uuid` и `organization.tax_id` указывают на разные записи** → приоритет
  у UUID, как для `contractor` в v13.2.
