# sub-09: протокол — необязательное поле `replaces_order_uuid` в order.created

**Приоритет:** низкий (нужно только если 1С захочет видеть связь полем)
**Эпик:** [sub-00](2026-08-14_sub-00-epic.md)
**Зависит от:** sub-04 (сама связь уже работает через `manager_comment`)
**Создано:** 2026-08-14

## Описание

Волны 0–2 живут без изменения протокола: заказ-замена уходит в 1С обычным
`order.created` с текстовой пометкой в `manager_comment`. Если стороне 1С
понадобится машинная связь (например, чтобы в 1С показывать «замена по
документу №…» или строить свою аналитику недоборов) — добавляется
**необязательное** поле:

```json
"replaces_order_uuid": {
  "type": ["string", "null"],
  "format": "uuid",
  "description": "UUID заказа, недоборы которого закрывает этот заказ-замена"
}
```

Необязательность делает изменение обратно-совместимым: 1С, не знающая поле,
просто игнорирует его.

**Порядок строго spec-first** (правило erp-exchange-protocol):

1. JSON Schema исходящего заказа (`app/Services/Erp/Schemas/*.to_erp.json`)
2. AsyncAPI `docs/asyncapi/pecado-erp-integration.yaml` (минорная версия)
3. Бизнес-правила `docs-erp/content/rules/orders.md` — раздел «Заказ-замена»:
   откуда берётся, что 1С может с ним делать, что поле опциональное
4. Changelog `docs-erp/content/changelog.md`
5. Сборка: `docker exec pecado-node npm run asyncapi:build` + mkdocs
6. Только потом код: прокинуть `orders.replacement_for_order_id → uuid` в payload
   `PublishOrderToErpJob`
7. Письмо/вопрос стороне 1С — надо ли им это поле и роняет ли их валидация
   незнакомые поля (проверить ДО выкатки)

## Критерии готовности

- [ ] Спека, схема, MkDocs, changelog — до кода
- [ ] Поле в payload только когда связь есть; обычные заказы не изменились байт-в-байт
- [ ] Интеграционные тесты: заказ-замена → payload валиден по новой схеме и содержит uuid исходного; обычный заказ — поля нет
- [ ] Подтверждение от 1С, что незнакомое/новое поле не ломает их приёмник
