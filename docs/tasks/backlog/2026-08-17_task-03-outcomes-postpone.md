# task-03: три исхода — успешно, с проблемой, перенести

**Приоритет:** высокий
**Эпик:** [task-00](2026-08-17_task-00-epic.md)
**Зависит от:** —
**Создано:** 2026-08-17

## Описание

Сейчас закрытие бинарно: `done` или `canceled`. Нужно различать «сделал»,
«сделал, но что-то пошло не так» и «не успел — двигаю срок». Это фундамент
отчёта task-10 и честной статистики дисциплины.

### Модель

- `crm_tasks.outcome` — `string(20) nullable`,
  комментарий: `"Исход закрытия: 'success' — успешно, 'problem' — с проблемой; null — не закрыта или отменена"`.
  Enum `App\Enums\Crm\TaskOutcome` с русскими метками и цветами (green/orange).
- `crm_tasks.postponed_count` — `unsignedSmallInteger default 0`,
  комментарий «Сколько раз переносился срок».
- **Перенос — не закрытие**: задача остаётся в своём статусе, `due_at` сдвигается,
  `postponed_count++`, в комментарии задачи автоматически пишется системная запись
  «Перенесена с 18.08 на 20.08: причина» (причина опциональна). Отдельной таблицы
  истории не заводим — лента комментариев уже хронологична и видна в карточке.
- `canceled` остаётся для «неактуально» — это не исход, а отмена.

### Диалог закрытия v2 (`TaskCloseDialog`)

Вместо одной кнопки — три действия:

| Действие | Что происходит | Комментарий | Follow-up |
|---|---|---|---|
| **Завершить успешно** | `status=done`, `outcome=success`, `done_at` | опционален | предлагается, можно скипнуть (как сейчас) |
| **Завершить с проблемой** | `status=done`, `outcome=problem`, `done_at` | **обязателен** — «с проблемой» без описания проблемы бессмысленно | предлагается с **включённым** чекбоксом (проблема почти всегда требует следующего шага), можно снять |
| **Перенести** | статус не меняется, `due_at` → новая дата, `postponed_count++` | опционален (причина) | не предлагается — задача жива |

Для переноса — пресеты даты: «завтра», «+3 дня», «следующий понедельник» + произвольная.
Всё, как и сейчас, одной транзакцией в `CrmTaskService` (`close()` расширяется,
перенос — новый метод `postpone()`).

### Эндпоинты

- `POST /crm/tasks/{task}/close` — принимает `outcome`, валидация «problem ⇒ comment required».
- `POST /crm/tasks/{task}/postpone` — `{ due_at, reason? }`; право — как у закрытия
  (участник задачи); контролёры (task-01) уведомляются.

Механика переноса переиспользуется тостами (task-08: «перенести из тоста»)
и календарём (task-06: drag-n-drop) — поэтому отдельный эндпоинт, а не вариант PATCH.

### Отображение

- В списке и карточке закрытой задачи — бейдж исхода («Успешно» / «С проблемой»).
- `postponed_count > 0` — серый бейдж «переносилась ×N» (сигнал РОПу).
- Фильтр по исходу в разделе задач; в ленте клиента запись закрытия показывает исход.
- Существующие закрытые задачи остаются с `outcome=null` — в отчётах считаются
  «закрыто (без исхода)», задним числом ничего не красим.

## Доводка

`CrmTaskService::payload()`, агентское API `TaskOperations::close` (+`postpone`),
MCP, `TaskFeedEntry`, `ClientTimelineService`.

## Критерии готовности

- [ ] Миграция с комментариями; `db:comments:audit --strict` чист
- [ ] «С проблемой» без комментария отклоняется, задача не закрывается
- [ ] Перенос сдвигает срок, копит счётчик, пишет системный комментарий, не меняет статус
- [ ] Follow-up: скипается на «успешно», предложен включённым на «проблеме», отсутствует на переносе

- [ ] Бейджи исхода и «переносилась ×N» в списке; фильтр по исходу round-trip-ится в снимке filters
- [ ] Контролёры уведомляются о закрытии с исходом и о переносе
- [ ] Агентское API/MCP умеют исходы и перенос
