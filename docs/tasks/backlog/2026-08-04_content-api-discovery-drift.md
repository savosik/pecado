# `/api/content/me`: discovery, собранный из роутера, а не из строк в контроллере

**Приоритет:** средний
**Создано:** 2026-08-04
**Зависимости:** нет — карточка самостоятельна

## Постановка

`GET /api/content/me` рассказывает ИИ-агенту контент-менеджера, что он умеет. Список
эндпоинтов в ответе **захардкожен плоскими строками** в
[`MeController`](../../../app/Http/Controllers/Api/Content/MeController.php) и уже разошёлся
с маршрутами: в группе `api/content/*` зарегистрировано 69 адресов, в ответе — 16 названий
без методов и параметров.

Отсутствуют в ответе целиком:

```
regions
products/search, products/facets, products/price-intervals
promotions/{promotion}/products
product-selections/{productSelection}/products
stories/{story}/slides, .../slides/reorder, .../slides/{slide}
products/{product}/media/{media}   (удаление)
```

Плюс `products/{product}/media` подаётся одной строкой, хотя это три разных метода.

**Почему это стоит чинить.** Агент строит вызов по этому ответу. Расхождение здесь —
не косметика документации, а тихая поломка: агент не знает про поиск товаров и фасеты,
не знает про слайды сторис и не может вывести, каким методом дёргать медиа. Ошибки в логах
при этом нет — он просто не делает того, что мог бы, и сообщает менеджеру «такого не умею».

## Ключевое решение: источник — роутер

Дописать недостающие строки — починить сегодняшний список и получить тот же разъезд через
месяц. Ответ должен собираться обходом зарегистрированных маршрутов:

```php
collect(Route::getRoutes())
    ->filter(fn (Route $r) => str_starts_with((string) $r->getName(), 'api.content.'))
    ->map(fn (Route $r) => [
        'name' => Str::after($r->getName(), 'api.content.'),
        'method' => collect($r->methods())->first(fn ($m) => $m !== 'HEAD'),
        'uri' => '/'.$r->uri(),
        'parameters' => $r->parameterNames(),
    ])
```

Группировка по разделам (контент / каталог / медиа / прочее) выводится из первого сегмента
адреса, а не задаётся вторым списком: иначе появился бы новый справочник, который разъедется
ровно так же, как разъехался нынешний.

**Полноценный реестр операций, как `App\Services\Crm\Api\OperationRegistry`, сюда не нужен.**
У CRM-API один контроллер на все операции, и без реестра у него не было бы ни маршрутов,
ни схем. У content-API обычные ресурсные контроллеры: Scramble вытягивает из них схемы сам,
недостаёт только честного discovery. Заводить ради этого второй реестр — дороже задачи.

## Границы

- Формат ответа менять целиком не нужно: `data.user` и `data.token` остаются как есть,
  переписывается только `data.endpoints`.
- Права и абилити токена в разрезе эндпоинтов не считаем: в отличие от CRM, у content-API
  один агент с полным набором, флаг `allowed` там нечему различать.
- `/docs/api` и `/docs/api.json` (Scramble) не трогаем — они собираются из контроллеров
  и не разошлись.

## Критерии готовности

- [ ] `data.endpoints` собирается из роутера; второго списка эндпоинтов в коде нет
- [ ] Каждый эндпоинт несёт метод, адрес и параметры пути
- [ ] В ответе присутствуют `regions`, `products/search`, `products/facets`,
      `products/price-intervals`, слайды сторис и удаление медиа
- [ ] Feature-тест сверяет число эндпоинтов в ответе с числом маршрутов группы `api.content.*`
      — страж, который поймает следующий разъезд, а не только нынешний
- [ ] Ответ и описания — на русском
