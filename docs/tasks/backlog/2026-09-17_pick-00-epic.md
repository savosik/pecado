# ЭПИК: Самовывоз 9–21 — статусы сборки, пропуск курьеру, выдача на складе (pick-00)

**Приоритет:** высокий
**Создано:** 2026-09-17
**Статус (17.09.2026):** постановка. Ветка `feature/pick-pickup` (worktree `.claude/worktrees/pickup`).
**Вне эпика:** слоты записи на самовывоз и расчёт доставки (`dlv-00`, карточка dlv-04 —
идентификацию курьера этот эпик у неё забирает, слоты остаются там); изменения контракта
с 1С (выдача живёт только на сайте, по шине не ходит); выдача заказов, уезжающих
транспортной компанией (их ведёт раздел «Отправки» ApiShip).

## Идея

Склад переходит на график **пн–сб, 9:00–21:00**. Интернет-магазины (96 % заказов) получают
розничные заказы вечером и в выходные, и теперь могут закрывать их без нас: поставили заказ
в резерв → подтвердили у своего покупателя → нажали «В отгрузку» (или отменили) → отправили
курьера на склад. Менеджеры работают пн–пт 9–18 и в этом цикле не участвуют. Это наш ответ
на доставку маркетплейсов «за 4 часа»: магазин остаётся конкурентным, потому что товар
у него на руках через час после звонка покупателю.

Резервы уже в бою (res-00, 84 участника). Не хватает второй половины цикла:

1. **Клиент слеп после кнопки «В отгрузку».** Он не видит, собран ли заказ, ждёт ли выдачи,
   забрал ли его курьер, за какими заказами можно посылать.
2. **Склад слеп на выдаче.** Нет списка «к самовыдаче», нет способа проверить курьера, нет
   отметки «выдан» — в 1С такого статуса нет и не будет.
3. **Курьеров может быть несколько.** Один забирает часть заказов, остальное ждёт другого.
4. **Нет материалов.** Без буклета и инструкций новый график станет снегом на голову для
   клиентов, склада и отдела продаж.

Процесс выдачи строим по образцу ПВЗ маркетплейса: у клиента в кабинете **пропуск** (QR и
шестизначный код), кладовщик сканирует его телефоном, видит, что отдать, и отмечает выдачу.

## Решения (заказчик, 17.09.2026)

1. **График склада:** пн–сб 9:00–21:00. **SLA сборки 30–40 минут.**
2. **«Час до закрытия» = приём к сборке до 20:00.** Заказ, отправленный в отгрузку до 20:00,
   собирается и выдаётся сегодня до 21:00; позже — сборка со следующего рабочего дня склада
   с 9:00. Клиент видит это обещание в момент отправки. Смысл правила — курьер не звонит
   кладовщику с просьбой задержаться.
3. **Верификация курьера — код выдачи из кабинета** (QR + 6 цифр). Клиент пересылает курьеру
   пропуск только на те заказы, которые надо забрать.
4. **Скан расходного листа не обязателен.** Пропуск отвечает на вопрос «что и кому отдать»;
   скан листа — необязательная проверка «та ли коробка». Запуск не зависит от того, как 1С
   формирует штрихкод.
5. **Менеджеров вне их рабочего дня не дёргаем** (кроме форс-мажора). Единственный стоп
   на пути заказа к складу — задолженность (`DebtGate`, уже работает).
6. **Порядок работ:** эпик и карточки → три PDF → код по волнам.

**Умолчания, принятые без отдельного вопроса:**

- Единица выдачи — **расходный ордер (РО)**: это физические коробки. Клиент мыслит заказами,
  поэтому в кабинете заказы сгруппированы по РО, чекбокс стоит на группе. РО нельзя поделить
  между двумя курьерами — об этом прямо сказано в интерфейсе и в буклете.
- Пропуск двух видов: **«на всё готовое»** (умолчание, состав считается в момент скана) и
  **«на выбранное»**. Срок жизни — до конца третьего рабочего дня склада, клиент может отозвать.
- Всё за рубильником `PICKUP_ENABLED` (`config/pickup.php`), включение — по команде заказчика.
- История до запуска в список «Ждут выдачи» не попадает (`pickup.handover_since`).

## Факты из живых данных (1500 РО с 08.08.2026, проверено 17.09.2026)

| Факт | Следствие |
|---|---|
| Все 290 самовывозных РО проходят `to_ship → shipped` за 0–5 минут, **до приезда курьера** | «Собран, ждёт выдачи» = `shipped` без записи выдачи. `prepared…to_ship` = «собирается» |
| `shipped` обратим: откаты в `to_pick` (38), `prepared` (26), отмена (18) | Стадию считаем на лету, не храним. Откат уже выданного РО → пометка `needs_review` |
| `goods_issues.delivery_type` пуст во всех строках | Самовывоз берём с заказа: `orders.delivery_method = pickup` через `goods_issue_items.order_uuid` |
| `goods_issues.user_id` пуст у 40 %, `goods_issue_items.order_id` пуст у 24 % строк | Клиента определяем от заказа и только по `order_uuid` (как `GoodsIssue::relatedOrders()`) |
| 228 РО покрывают несколько заказов (до 30); у 46 заказов по два РО; 12 РО смешанные; у 132 РО заказов нет | Стадия заказа = минимум по его РО; смешанный РО считаем самовывозом с пометкой; РО без заказа — только ручной поиск |
| `checking` и `checked` в данных не встречаются | На экранах не выделяем |
| У 199 клиентов несколько юрлиц | Пропуск принадлежит пользователю, юрлицо — группировка на экране |

**Штрихкод печатной формы типовой 1С** (подсистема «Штрихкодирование печатных форм», УТ 11 /
КА 2): Code128, число = GUID документа без дефисов, переведённый из шестнадцатеричной системы
в десятичную; контрольного символа сверх штатного Code128 нет. Обратно: десятичное → hex →
дополнить нулями слева до 32 знаков → разбить 8-4-4-4-12. GUID расходных ордеров, реализаций
и заказов у сайта есть. Гипотеза подтверждается на пяти реальных листах (pick-08).

## Стадии заказа глазами клиента

| Стадия | Когда | Подпись |
|---|---|---|
| `reserved` | `orders.reserve = true` | В резерве |
| `sent_to_warehouse` | резерв снят, РО ещё нет | Передан на склад (+ обещание «соберём к ~14:40» или «начнём в пн в 9:00») |
| `picking` | есть РО в `prepared…to_ship` | Собирается |
| `ready` | самовывоз, все РО `shipped`, выдачи нет | Собран, ждёт выдачи |
| `handed_over` | есть запись выдачи по всем РО | Выдан курьеру (кем, когда) |
| `shipped` | доставка, все РО `shipped` | Отгружен |

Промежуточные состояния («собран частично», «выдан частично») получаются сами: стадия заказа —
минимальная по его РО, а счётчик «2 из 3 мест» показывается рядом.

## Критерии готовности эпика

- [ ] Клиент в кабинете и через API видит по каждому заказу: собирается, собран и ждёт выдачи, выдан.
- [ ] При отправке в отгрузку клиент видит честное обещание времени с учётом графика и отсечки 20:00.
- [ ] Кладовщик на телефоне видит список к выдаче, сканирует пропуск, выдаёт часть или всё, видит просрочку SLA.
- [ ] Двойная выдача невозможна, ошибочная отменяется с причиной, всё с автором и временем.
- [ ] Клиент может отдать разным курьерам разные заказы.
- [ ] Менеджер утром видит, что произошло вечером и в субботу, без звонков.
- [ ] Буклет и две инструкции в PDF разосланы до включения рубильника.
- [ ] История до запуска не всплыла в списке «Ждут выдачи».
- [ ] Контракт ERP не тронут; `PermissionNamingTest`, `db:comments:audit --strict`, `make verify` зелёные.

## Открытые вопросы перед стартом

**Требуют решения заказчика или владельца 1С:**

1. **Кто создаёт расходный ордер вечером и в субботу.** В описании статусов: «подготовлен —
   менеджер создал РО». Если РО не создаётся автоматически, заказ после 18:00 до склада не
   дойдёт, и весь график не заработает. Вопрос владельцу 1С — до рассылки буклета.
2. **Недобор при сборке вне рабочего дня менеджера.** Сейчас `orders.shortfall` адресован
   менеджеру. Кто и как сообщает клиенту вечером, что позиции нет?
3. **Попросить 1С заполнять `delivery_type` в РО.** Поле в контракте уже есть, контракт не
   меняется; снимет зависимость от связи РО с заказом.
4. **Включать ли `orders.ready_for_pickup` умолчанием.** Предлагаем да, как резервы: иначе
   клиент узнает о готовности, только открыв кабинет.
5. **Что курьер подписывает при получении** (УПД, доверенность, печать) — формулировка для буклета.
6. **Пять реальных расходных листов** (фото) — подтвердить формат штрихкода.

**Закрываем сами при реализации:**

- Один график на все склады; адрес выдачи — из конфига (у 528 РО `warehouse_id` пуст).
- Смешанный РО (самовывоз и доставка) показываем в выдаче с пометкой.
- Откат `shipped` после уведомления «собран»: повторное письмо только после нового `shipped`.
