# fin-06 · Сверка регистра: команда `settlements:verify`

**Приоритет:** высокий
**Создано:** 2026-08-09
**Эпик:** [fin-00](2026-08-09_fin-00-epic.md)
**Зависимости:** `fin-05`
**Волна:** 2 — **приёмочный гейт волны 3**

## Описание

Пока эта команда не показывает ноль расхождений, чтение на регистр **не переключается**.
Это единственный объективный критерий, что новая модель лучше старой, а не просто другая.

Смысл в трёх источниках, которые обязаны сойтись:

| Источник | Что это |
|---|---|
| **Регистр** — `SUM(settlement_entries.amount) WHERE nature='fact'` | Новая модель |
| **Контрольная сумма** — `contractor_organization_balances` из `balance.updated` + `settlement_checkpoints` на 01.07.2026 | Мнение 1С |
| **Старая модель** — `shipments.total_amount - paid_amount` + `payment_allocations` | Что показывает сайт сегодня |

Ожидание: первые два сходятся до копейки, третий расходится — и расхождение объясняется
авансами, зачётами и корректировками. Если расходятся первые два — виновата интеграция, а не
старая модель.

## Что делаем

`app/Console/Commands/VerifySettlements.php` → `php artisan settlements:verify`.

Опции: `--client=` (один партнёр), `--agreement=`, `--threshold=1.00` (порог в рублях),
`--format=table|csv`, `--only-mismatch`.

Вывод — таблица по контрагентам и организациям:

```
Клиент | Организация | Регистр | 1С (balance) | Δ | Старая модель | Δ старой
```

Плюс итоговая сводка: сколько сущностей сошлось, сколько нет, суммарное расхождение,
топ-10 худших.

Отдельные проверки-инварианты:

- [ ] `SUM(organizations) == contractor` — уровни агрегации сходятся (как в v15.8.0)
- [ ] **сальдо 01.01 + движения первого полугодия == `settlement_checkpoint` на 01.07.2026**
- [ ] нет движений с `nature='fact'` и ненулевым `settled_amount`
- [ ] нет плановых строк с `date` раньше даты документа-основания
- [ ] нет движений с датой раньше 01.01.2026 (кроме `opening_balance`)
- [ ] у каждого контрагента есть `opening_balance` — или он в списке исключений
- [ ] знак по каждому `type` соответствует соглашению (`shipment` не бывает положительной и т.д.)

Последний пункт — самый ценный: перепутанный знак на стороне 1С **не ловится валидацией схемы**,
только здесь.

## Как разбирать расхождения

Порядок диагностики, чтобы не гадать:

1. **Регистр ≠ 1С** — интеграция. Смотреть DLQ, `erp_bus_messages`, движения без соглашения.
2. **Регистр = 1С, старая модель мимо** — ожидаемо, это и есть причина эпика. Задокументировать
   пару характерных примеров в changelog: они будут лучшим обоснованием мажора.
3. **Все три сошлись** — подозрительно. Проверить, что регистр вообще наполнен, а не пуст.

## Edge-кейсы

- **Клиент без движений** — не расхождение, если и баланс нулевой. Не показывать в отчёте.
- **Расхождение ровно на сумму движений без соглашения** — соглашение не заполнено в 1С, не ошибка
  интеграции. Считать отдельной строкой сводки.
- **Мультивалютный контрагент** — сверять **в валюте движения**, не в рублях: рублёвое
  расхождение может быть курсовым, а не учётным.
- **Расхождение меньше порога** — не шум: копейки по тысяче контрагентов дают заметную сумму.
  Показывать в сводке отдельной строкой «в пределах порога».
- **Команда на проде** — только чтение, никаких записей. `--format=csv` для разбора вне консоли.
