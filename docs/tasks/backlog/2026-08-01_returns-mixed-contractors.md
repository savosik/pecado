# Возврат может смешивать реализации разных контрагентов клиента

**Приоритет:** средний — существующий дефект, не связан с организациями
**Создано:** 2026-08-01
**Найдено при:** проектировании эпика [организаций](2026-08-01_org-00-epic.md)

## Суть

`product_returns` не хранит контрагента вообще, а
[ReturnController](../../../app/Http/Controllers/User/ReturnController.php#L320) валидирует
только существование позиции реализации:

```php
'items.*.shipment_item_id' => 'required|integer|exists:shipment_items,id',
```

У пользователя может быть несколько своих юрлиц (`Company`), и реализации у них разные.
Ничто не мешает собрать один возврат из позиций реализаций **разных контрагентов** —
валидации нет, поля для контрагента нет.

## Почему это плохо

Возврат — основание для документа в 1С, а документ выписывается на конкретного
контрагента. Возврат, смешавший двух, либо разложится в 1С непредсказуемо, либо упрётся
в ручной разбор менеджером. Взаиморасчёты ведутся по контрагенту (`contractor_balances`),
поэтому и сумма возврата должна относиться к одному.

## Что сделать

1. Проверить на проде, есть ли такие возвраты:

```sql
SELECT ri.return_id, COUNT(DISTINCT s.company_id) c
FROM return_items ri JOIN shipments s ON s.id = ri.shipment_id
GROUP BY ri.return_id HAVING c > 1;
```

2. Миграция: `product_returns` + `company_id` (nullable FK) с комментарием
   `'Контрагент клиента, по реализациям которого оформлен возврат (companies.id)'`.
3. Валидация в `ReturnController`: все позиции должны опираться на реализации одного
   контрагента. Сообщение на русском — «Позиции из реализаций разных контрагентов
   нельзя вернуть одним документом. Оформите отдельный возврат по каждому.»
4. Пикер реализаций группирует по контрагенту; при попытке смешать — понятная подсказка,
   а не сухая ошибка после отправки формы.
5. Бэкфилл `company_id` у существующих возвратов, где контрагент однозначен.

## Edge-кейсы

- **Найденные смешанные возвраты** (если есть) — разобрать вручную с менеджером, не
  «чинить» скриптом: за ними могут стоять уже проведённые в 1С документы.
- **Реализация без `company_id`** (legacy) → возврат остаётся с `NULL`, валидация
  пропускает: ужесточать на исторических данных нельзя.
- **Черновики возвратов** на момент релиза — валидация только для новых.
- **Пользователь с одним контрагентом** (основная масса) — поведение не меняется.

## Связь с эпиком организаций

Карточка [org-08](2026-08-01_org-08-returns-by-organization.md) добавляет к возврату
**нашу** организацию (справочно, с реализаций). Здесь речь про **контрагента клиента** —
другая сторона сделки, другая причина, чинится независимо. Делать можно в любом порядке.

## Критерии готовности

- [ ] Проверено, есть ли смешанные возвраты на проде; найденные разобраны
- [ ] Миграция с комментарием, `db:comments:audit` чист, `bi:sync-grants` выполнен
- [ ] Валидация «один контрагент на возврат» с сообщением на русском
- [ ] Пикер реализаций группирует по контрагенту и предупреждает заранее
- [ ] Бэкфилл выполнен там, где контрагент однозначен
- [ ] Тест: позиции из реализаций разных контрагентов отклоняются
- [ ] Тест: возврат по одному контрагенту создаётся как раньше
