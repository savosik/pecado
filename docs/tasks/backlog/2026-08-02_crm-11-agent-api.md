# crm-11 · REST `/api/crm/*`: реестр операций, документация и discovery

**Приоритет:** высокий
**Создано:** 2026-08-02
**Эпик:** [crm-00](2026-08-02_crm-00-epic.md)
**Волна:** 5 (гейт для ИИ-агентов)
**Зависимости:** волны 1–4 в том объёме, который выносится в API

## Описание

Открыть возможности CRM машинным потребителям: REST-API с документацией и методом, который
сам рассказывает агенту, что он умеет — по аналогии с `/api/content/*` для контент-менеджера.
Это фундамент под `crm-12` (MCP-сервер), который будет вызывать те же операции.

## Ключевое решение: реестр операций как единственный источник

`App\Services\Crm\Api\OperationRegistry` описывает каждую операцию:

```php
new Operation(
    id: 'client.comment.create',
    method: 'POST',
    uri: 'api/crm/comments',
    permission: 'crm-comments.create',
    summary: 'Оставить комментарий по клиенту, заказу или реализации',
    schema: [...],   // JSON Schema аргументов
);
```

Из реестра растут три вещи: маршрутизация REST, ответ discovery-метода и (в `crm-12`)
каталог MCP-инструментов. Так документация не может разойтись с реальностью.

**Почему не как в `/api/content/me`:** там список эндпоинтов **захардкожен** в контроллере
плоскими строками без методов и параметров — и уже разошёлся с роутами (`regions`,
`products/search`, `products/facets`, `products/price-intervals` в ответе отсутствуют).
Для агента, который строит вызов по этому ответу, такое расхождение — тихая поломка.

## Что делаем

**Группа роутов** в `routes/api.php`:

```php
Route::prefix('crm')->name('api.crm.')
    ->middleware([AuthenticateCrmAgent::class, 'throttle:crm-api'])
    ->group(...);
```

Middleware `AuthenticateCrmAgent` — карточка `crm-12` (там же таблица токенов). В этой карточке
API может временно ходить под `auth:sanctum`; порядок мерджа: `crm-11` кладёт контроллеры
и реестр, `crm-12` подставляет свою аутентификацию.

**Состав операций** (по мере готовности волн):

| Раздел | Операции |
|---|---|
| Клиенты | список с фильтрами, карточка, сводка по продажам |
| Профиль | чтение, обновление полей и заметок, интересы |
| Статусы | смена жизненного статуса с причиной, история |
| Комментарии | лента клиента, создание, правка, удаление своего |
| Задачи | список, создание, смена статуса, закрытие |
| Планы | планы периода, постановка (в рамках прав актора) |
| Выполнение | прогресс, burndown, разрез по менеджерам |
| Возможности | ранжированный список по пресету |
| Письма | черновик, отправка, журнал |
| Вложения | загрузка и удаление |

**Все операции работают через те же сервисы, что и веб-интерфейс** (`ClientProfileService`,
`ClientLifecycleService`, `SalesPlanService`, `OpportunityService`, `ClientTimelineService`).
Второй реализации бизнес-правил не появляется — иначе агент и человек начнут получать разные
результаты на одинаковых действиях.

**Скоуп данных.** Ни один контроллер не принимает «id менеджера» из запроса: набор клиентов
всегда `User::visibleInCrm($actor)`, где актор — аутентифицированный пользователь. Чужой клиент
даёт **404**, а не 403 — как в существующем `ClientController::show()`, чтобы не подтверждать
существование записи.

**Discovery `GET /api/crm/me`** — ответ строится **из реестра**:

```json
{
  "data": {
    "actor": { "id": 12, "name": "…", "email": "…", "is_head": false },
    "permissions": ["crm-clients.view", "crm-comments.create", "…"],
    "scope": { "clients_visible": 409, "manager_profile": "Сухов" },
    "operations": [
      { "id": "client.comment.create", "method": "POST", "uri": "api/crm/comments",
        "summary": "…", "permission": "crm-comments.create", "allowed": true,
        "schema": { "…" } }
    ],
    "docs": { "ui": "/docs/crm-api", "openapi": "/docs/crm-api.json" }
  }
}
```

`allowed` считается по правам актора — агент сразу видит, что ему доступно, и не тратит вызовы
на заведомые 403.

**Документация — отдельный документ Scramble** рядом с `content` и `kanban`
в `AppServiceProvider`:

```php
Scramble::registerApi('crm', ['api_path' => 'api/crm', 'info' => [...]])
    ->afterOpenApiGenerated(fn (OpenApi $o) => $o->secure(SecurityScheme::http('bearer', 'bearer')));
Scramble::registerUiRoute(path: 'docs/crm-api', api: 'crm');
Scramble::registerJsonSpecificationRoute(path: 'docs/crm-api.json', api: 'crm');
```

В `info.description` — краткие бизнес-правила для агента (клиент = пользователь с
`personal_manager_id`; факт продаж = отгрузки по `erp_created_at`; лояльностью владеет 1С),
по образцу описания kanban-документа.

Контроллеры аннотируются PHPDoc-тегами Scramble (`@tags`, `@bodyParam`, `@queryParam`), как
в `Api\Content\NewsController`.

**Rate limiter `crm-api`** в `AppServiceProvider` — по образцу `content-api`, но по владельцу
токена, а не по IP.

## Границы

- Аутентификация, токены и аудит — карточка `crm-12`.
- MCP-сервер — карточка `crm-12`.
- Публичный доступ к документации уже обеспечен гейтом `viewApiDocs` — трогать не нужно.

## Критерии готовности

- [ ] `OperationRegistry` — единственный источник; список эндпоинтов нигде не продублирован строками
- [ ] `GET /api/crm/me` отдаёт актора, права, скоуп и полный каталог операций с флагом `allowed`
- [ ] `/docs/crm-api` и `/docs/crm-api.json` открываются на dev и prod
- [ ] Операции вызывают те же сервисы, что и веб-интерфейс
- [ ] Обращение к чужому клиенту даёт 404 во **всех** операциях
- [ ] Право проверяется на каждой операции; отсутствие права → 403
- [ ] Ответы и сообщения об ошибках — на русском
- [ ] Feature-тесты `tests/Feature/Api/Crm/`: discovery, изоляция скоупа по каждому разделу,
      гейты прав, совпадение результата с веб-контроллером
