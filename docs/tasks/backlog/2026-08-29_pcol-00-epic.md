# ЭПИК: персональные подборки в кабинете (pcol-00)

**Приоритет:** средний
**Создано:** 2026-08-29
**Статус:** постановка зафиксирована, код не начат
**Вне эпика:** ERP-протокол не затрагивается — подборки только читают уже принятые из 1С данные

## Идея

Раздел кабинета со списком подборок, построенных на данных **самого клиента** (реализации,
заказы, индивидуальные цены, просмотры). Отличие от контентных подборок
(`product_selections`, `/collections/{slug}`): состав у каждого клиента свой и считается
из его истории, а не задаётся руками.

## Решения (заказчик, 29.08.2026)

1. **Своя страница с плитками** — список подборок. В плитке: **название**, **краткое
   описание** («что это значит», одна фраза), **число товаров**. Клик по плитке — каталог
   подборки.
2. **Каталог подборки = обычный каталог**: `ProductController::renderCatalog` с
   `initialFilters`, как у контентных подборок и избранного. Новый фильтр
   `personal_collection={slug}` → множество `product_id` из кеша; все фильтры, сортировки,
   вид и пагинация каталога наследуются бесплатно.
3. **Подборка скрывается, если товаров меньше одной страницы каталога** (сейчас
   `DEFAULT_PER_PAGE = 20`). Полупустая персональная подборка выглядит хуже, чем её
   отсутствие. Порог — константа, привязанная к per_page каталога, не отдельная настройка.
4. **Кеш для сложных выборок.** Состав (список `product_id` + служебные числа вроде
   старой/новой цены) считается фоновым джобом и кладётся в кеш; витрина читает только
   кеш и никогда не считает тяжёлую выборку в запросе. Причина: реализации и
   индивидуальные цены лежат в разных БД (`mysql` и `prices`), SQL-join невозможен, а
   `individual_prices` — десятки миллионов строк. Простые выборки (просмотры, избранное)
   можно считать на лету. Пересчёт — ночью + по событиям, которые меняют состав
   (приём файла индивидуальных цен, `stock.updated`, новая реализация) с дебаунсом.
5. Раздел виден только клиентам (пользователь с `erp_id`, то есть с индивидуальными
   ценами); гостям и лидам плитки не показываем.

## «Стало дешевле» — правила, проверенные на проде 29.08.2026

Проверка на 20 клиентах (6 675 пар клиент × товар): **у 19 из 20 подборка непустая**,
4–88 товаров; на пороге ≥3 % — 2–42. См. память `project_personal_collections.md`.

- Сравнивать с **фактически оплаченной** ценой последней реализации
  (`shipment_items.total / quantity`, со скидками) за 180 дней. Обратное сравнение
  («стало дороже») на 93 % — артефакт разовых скидок, поэтому в эту сторону подборки нет.
- Текущая цена — `individual_prices` по правилу сайта (мин. `warehouse_id`; по факту цена
  одинакова на всех складах).
- **Порог значимости ≥ 3 %** — без него в подборку лезет шум 1–2 %.
- **Только товары в наличии** на наших складах (без «Тюмень Основной»): из 352
  подешевевших 91 нет нигде, 26 — только у конкурента.
- Крупные падения (50–87 %) — настоящие глобальные снижения каталога (JO Premium:
  base 455 ₽ при прошлых продажах по 1 400+; насадки Diva 392 ₽ вместо 2 915 ₽), то есть
  подборка подхватывает и распродажи, и персональные улучшения цены — это фича.

## «Недавно просмотрено» — концепция (добавлено 29.08.2026)

Самая простая подборка по смыслу, но **единственная без готовых данных**: истории
просмотров в проекте нет — ни таблицы, ни счётчика на товаре, ни localStorage.

- **Предпосылка — журнал просмотров** `product_views` (`user_id`, `product_id`, `viewed_at`,
  `source`: `page` — страница товара, `quickview` — модалка; QuickView перехватывает клики
  по `/products/{slug}` и тоже считается просмотром). Пишется асинхронно через очередь,
  не в запросе. Дедуп: один товар не чаще раза в час на пользователя. Ретенция ~180 дней.
  Гостей не пишем — раздел только для клиентов. Комментарии в БД по правилу проекта.
- **Определение**: товары, открытые клиентом за последние 30 дней, по одному разу каждый,
  **порядок — по времени последнего просмотра** (свежее выше). Это единственная подборка,
  где сортировка по умолчанию — не каталожная, а своя; `renderCatalog` должен уметь
  принимать порядок «как в списке id». Товары из реализаций **не исключаются** — клиент
  мог смотреть, чтобы дозаказать.
- **Без кеша**: выборка дешёвая (индекс `user_id, viewed_at`), считается на лету.
- Товары не в наличии **показываем** (в отличие от «Стало дешевле») — клиент их сам
  открывал, скрывать нечестно; каталожный фильтр наличия остаётся ему доступен.
- Общее правило «меньше страницы — скрыть» действует и здесь: у редко заходящих клиентов
  плитка будет появляться только после 20 открытых карточек. Осознанно: это
  вспомогательная подборка, а не «хлебные крошки».
- `viewed_not_bought` («Смотрели, но не купили») — производная того же журнала: ≥ 2
  просмотров за 90 дней и ни одной строки в реализациях/заказах; кандидат в «горячие».

## Точки входа в раздел (решение заказчика 29.08.2026)

**Канонический адрес:** `/cabinet/collections` — страница плиток; каталог подборки —
`/cabinet/collections/{slug}` (та же страница каталога, что у `/products/favorites`).
Раздел кабинетный, потому что доступен только клиентам и живёт на их данных.

Точки входа, по убыванию важности:

1. **Меню кабинета** (`CabinetLayout`), группа «Обзор» — пункт «Подборки для вас» между
   «Дашборд» и «Аналитика», иконка `LuSparkles`. Пункт виден клиенту всегда; если ни одна
   подборка не прошла порог — страница показывает пустое состояние («подборки собираются
   из ваших заказов и просмотров»), а не прячет раздел.
2. **Мега-меню каталога**, вкладка «Подборки» (`CatalogPanel`) — для залогиненного клиента
   сверху секция «Для вас» с персональными подборками (название + число), ниже —
   контентные как сейчас. Это главная «покупательская» точка: клиент собирает заказ именно
   из каталога. Секция появляется только при ≥ 1 непустой подборке.
3. **Главная** (волна 2) — для клиента карусель «Для вас» над «Новинками» по образцу
   `ProductSelectionTabs`, вкладки = непустые персональные подборки.

Не добавляем: карточку-превью на дашборд кабинета (отклонено заказчиком 29.08 —
дашборд остаётся про деньги, заказы и менеджера), пункт в шапку рядом с «Избранное»
(шапка и так плотная) и в мобильную нижнюю навигацию (пять позиций заняты). На мобильном вход — через «Кабинет» и через
вкладку «Подборки» каталога.

Числа на плитках и в меню берутся из того же кеша, что и составы (кеш хранит
`product_ids` + `count`), отдельных запросов навигация не делает.

## Открытые вопросы перед стартом (ревизия 29.08.2026)

Проверка по коду показала: из шести подборок волны 1 полностью определена только
«Стало дешевле». Остальное — либо решение заказчика, либо предпосылка, которую закрываем
сами. Для каждого вопроса — предлагаемое умолчание; если заказчик не возражает, делаем так.

### Требуют решения заказчика

1. **«Пора пополнить» — движка нет.** `OpportunityService` ранжирует клиентов для CRM,
   а циклы пополнения (`up-05`) и закупочный лист (`up-06`) не реализованы.
   *Умолчание:* простая статистика внутри эпика — товар куплен ≥ 3 раз за 365 дней,
   средний интервал между реализациями T, с последней прошло ≥ T. Позже `up-05`
   переиспользует этот расчёт. Альтернатива — перенести в волну 2 до `up-05`.
2. **«Вы это покупали» — окно.** *Умолчание:* все товары из реализаций за 365 дней,
   сортировка по числу реализаций (чаще — выше), без порога по количеству.
3. **«Снова в наличии» — определение.** *Умолчание:* товар из реализаций клиента за
   365 дней (позже — и из просмотров), у которого есть событие `in_stock` за последние
   30 дней после `out_of_stock`. Журнал событий ведётся только с 12.08.2026 — первые
   недели подборка будет тонкой, это нормально.
4. **«Есть только у нас» — обязательное сужение.** Весь каталог «есть у нас, нет в
   Тюмени» — тысячи товаров и не персонально. *Умолчание:* пересечение с ассортиментом
   клиента (реализации за 365 дней). Показываем всем клиентам, а не только «двойным».
5. **Старая цена на карточке в «Стало дешевле».** Без «вы брали по 1 428 ₽» подборка
   теряет половину смысла, но это правка карточки товара в каталоге.
   *Умолчание:* бейдж со старой ценой и процентом только внутри этой подборки.
6. **Сортировки по умолчанию.** *Умолчание:* «Стало дешевле» — по выгоде (%),
   «Пора пополнить» — по просрочке цикла, «Вы это покупали» — по частоте,
   «Недавно просмотрено» — по времени; остальные — каталожная. Пользователь может
   переключить на любую каталожную. Каталогу нужен режим «порядок как в списке id».

### Закрываем сами при реализации (решений не требуют)

- Флаг выкатки `cabinet_personal_collections_enabled` по образцу `contracts`/`documents`
  (`CabinetLayout.features`), включаем на dev, на прод — после визуальной проверки.
- Хранилище кеша — таблица `personal_collection_items` (`user_id`, `collection`,
  `product_id`, `payload` json, `position`, `computed_at`), не Redis: переживает рестарт,
  доступна аналитике (`bi:sync-grants`), комментарии по правилу проекта. Счётчики для
  меню — из неё же одним `GROUP BY`.
- Фильтр `personal_collection` — в `ProductFilterRequest` + `CatalogQueryBuilder`
  рядом с `in_favourites`; гость/чужой slug → пусто.
- Журнал просмотров не пишет сотрудников (`is_staff`) и гостей.
- Тесты: prices DB в тестах — реальная (см. `tests/TestCase.php`, чистится в tearDown),
  фикстуры «попал / не попал» для каждой подборки; правило порога; чтение только из кеша.
- «Тюмень Основной» — по `config('erp.external_remains.tyumen_warehouse_uuid')`, не по имени.

### Гипотезы не проверены на проде

Цифры есть только по «Стало дешевле». Остальные пять подборок волны 1 не прогонялись;
перед стартом стоит так же оценить, у скольких клиентов они переваливают порог 20 —
особенно «Снова в наличии» (короткий журнал) и «Пора пополнить».
