## Суть в одном абзаце

На проде (21.08.2026) долг клиентов 11,34 млн ₽, из них просрочено 2,60 млн на
54 контрагентах; 59 % просрочки — один клиент. Сегодня взыскание держится на памяти
двух менеджеров. Эпик строит **машину уровней**: каждый клиент находится в одном из
четырёх состояний — `чисто → напоминания → только предоплата → стоп` — и переходы
между ними порождают действия автоматически: касания через пульт уведомлений,
ограничения через гейт чекаута, задачи менеджеру через CrmTask. Вниз (ужесточение)
система движется медленно и планово, вверх (смягчение) — мгновенно по событию оплаты
из 1С, без участия людей. Клиент гасит долг самообслуживанием: готовая платёжка
(PDF + файл для клиент-банка + QR), сценарии «погасить просрочку / весь долг /
предоплата», отправка бухгалтеру в два клика.

## Анти-боинг: принципы управляемости (зафиксировано обсуждением)

Риск «панели боинга» — главный проектный риск. Защита:

1. **Ручки — в конфиг, не в UI.** Пороги/grace/гистерезис живут в `config/debt.php`
   и меняются релизом. РОП в интерфейсе работает со списком клиентов, а не с настройками.
2. **Одна ручка на клиента.** Никаких индивидуальных порогов. Три профиля
   (`regular` / `marketplace` / `legal`) + единственный оверрайд «пауза до даты
   с причиной» (менеджер ≤ 7 дней, РОП ≤ 30; бессрочной нет ни у кого).
3. **Четыре состояния, не больше.** Всё, что хочется сделать пятым уровнем, —
   это действие внутри существующего (блок предзаказов = действие позднего жёлтого).
4. **Конституция в коде** (невыключаемые инварианты):
   - автоматика никогда не ограничивает без предшествующего письма-предупреждения;
   - никакой эскалации по данным старше `debt.stale_after_days` (`balance_erp_updated_at`);
   - любое ограничение снимается оплатой автоматически;
   - профили `marketplace`/`legal` в автоматику не входят;
   - у каждого перехода и касания есть однострочный ответ «почему» (explain).
5. **Shadow-режим до боевого**: минимум 2 недели система пишет журнал «я бы сделала X»,
   ничего не делая; включение — поштучно по ступеням.

## Решения, принятые при постановке (21.08.2026)

| Вопрос | Решение |
|---|---|
| Верхняя ступень | «Финансовый арест»: вход и раздел оплат открыты, покупки закрыты. `UserStatus::BLOCKED` (логаут-блок) остаётся ручным инструментом админа вне лестницы |
| Кредитный лимит | Мастер — `agreements` из 1С; фолбэк — 50 % среднемесячного оборота за 90 дней; ручная правка РОП поверх. **Клиенту лимит не показывается** — знание лимита стимулирует выбирать его до дна |
| Отсечка значимости | Просрочка < 5 000 ₽ не влияет на уровень («проблема копейки»: 18 из 53 просрочек < 1000 ₽) |
| Grace | 5 банковских дней после срока платежа |
| Подача в кабинете | «Норма невидима»: у чистого клиента никакой шкалы нет; статус появляется только при значимой просрочке. Следующую ступень и даты переходов не показываем |
| Отправитель писем | Мягкие — от персонального менеджера; предупреждения об ограничениях и арест — от компании |
| Предзаказы | Закрываются на позднем жёлтом (`reminder` дольше N дней) — раньше обычных заказов |
| «Только предоплата» | Чекаут работает: заказ создаётся с пометкой «отгрузка после оплаты» + сразу платёжка на сумму заказа. Протокол 1С не меняется |
| Авторазморозка | Просрочка упала ниже отсечки → ограничения сняты мгновенно по событию из 1С |
| Обещания | Фиксируют менеджер и клиент; у клиента — одно активное, ≤ 14 дней, после нарушения — только через менеджера |
| Диспут | Спорная сумма сразу исключается из скоринга; менеджеру задача с SLA 2 рабочих дня |
| Претензия | Авторасчёт процентов по ст. 395 ГК (менеджер может править); отправка всегда ручная |

## Данные, на которых стоит дизайн (prod, срез 2026-08-21)

| Факт | Число | Следствие |
|---|---|---|
| Долг / просрочка | 11,34 / 2,60 млн ₽ (86 / 54 контрагента) | Масштаб оправдывает автоматику |
| Просрочки < 1000 ₽ | 18 из 53 контрагентов | Абсолютная отсечка обязательна |
| Гевея: просрочка к обороту | 1,54 млн = 157 % месячного оборота | Критерий «доля от оборота» разделяет лучше абсолютных сумм |
| Железняк: то же | 85 тыс = 9 % оборота | Крупный долг ≠ проблемный клиент |
| «Полные» неплательщики | 5 клиентов, оборот за 90 дней = 0 | Профиль `legal`: лестница не для них, сразу претензия |
| Хроничность | 15 клиентов с 6+ просроченными строками | Сигнал «хроник» в скоринге |
| Балансы маркетплейсов | WB/ЯМ не обновлялись 17 дней | Гейт свежести данных обязателен |

## Что уже построено (не изобретать заново)

- **Пульт уведомлений**: домен `finance` с событиями `payment_due_soon` /
  `overdue_started` / `overdue_grew` / `overdue_cleared`, `FinanceScanner`
  (ежедневно 07:00), пресет «Бухгалтерия», роль `accountant` в `client_contacts`,
  DeliveryGuard/suppressions, отправка на произвольный email, режим shadow.
- **Математика**: интерфейс `PaymentForecast` (`aging()`, `overdueOnly()`,
  `topDebtors()`, `noScheduleQuery()`), `contractor_balance_overdue_details`
  (просрочка по документам), `contractor_organization_balances` (разрез по нашим юрлицам).
- **Реквизиты**: `organizations` (наши юрлица: ИНН/КПП/БИК/счета, отсекать `is_stub`),
  `company_bank_accounts` (счета плательщика).
- **Акты сверки**: `ReconciliationService` + кабинет + XLSX + печатная форма
  `RECONCILIATION_ACT` из 1С — готово целиком.
- **Блок аккаунта**: `UserStatus::BLOCKED` + `EnsureUserIsNotBlocked` (остаётся вне лестницы).
- **Задачи**: `CrmTaskService::create()`, образец идемпотентности — `CrmTaskRecurrenceService`.
- **Точка врезки гейта**: `CheckoutService::checkout()` — единственный вход всех путей заказа.

## Порядок и зависимости

`debt-01` → `debt-02` → (`debt-03` ∥ `debt-04`) → (`debt-05` ∥ `debt-06`) → `debt-07` →
(`debt-08` ∥ `debt-09`) → (`debt-10` ∥ `debt-11`)

Инвариант «блок только после письма» делает `debt-03` блокером `debt-06`.
`debt-07` (разморозка) обязана выйти в один релиз с `debt-06` (ограничениями) —
ограничивать без мгновенной авторазморозки запрещено.
