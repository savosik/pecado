# ЭПИК: прокачка CRM — рабочее место отдела продаж и гейт для ИИ-агентов

**Приоритет:** высокий
**Создано:** 2026-08-02
**Скоуп зафиксирован:** 2026-08-02
**Роадмап:** [docs/crm-boost-roadmap.md](../../crm-boost-roadmap.md)
**Карточки:** `crm-01` … `crm-13`

## Суть в одном абзаце

`/crm/` сегодня — **read-only витрина** над `users` и `shipments`: список клиентов, карточка,
команда, отчёт продаж. Ничего из того, что менеджер делает руками, в системе не живёт — заметки
о клиенте в головах, задачи в мессенджерах, переписка в почте, планы в Excel. Эпик превращает
витрину в рабочее место и накрывает его гейтом, через который те же операции выполняет ИИ-агент
менеджера, не открывая интерфейс.

Симптом текущего состояния: право `crm-clients.edit` объявлено в `RolesAndPermissionsSeeder`
и **нигде не проверяется** — редактировать в CRM попросту нечего.

## Что входит

| № | Требование | Карточка |
|---|---|---|
| 1 | Профиль клиента в свободной форме: заметки, интересы, настроение, ЛПР, платёжное поведение | `crm-03` |
| 2 | Статус лояльности (из 1С) + управляемый жизненный статус (лид / активен / закрылся) | `crm-04` |
| 3 | Месячные планы продаж по клиентам и менеджерам + дашборд выполнения с burndown | `crm-05`, `crm-06` |
| 4 | Подсветка возможностей: кому продать, кто не брал, кто просел | `crm-07` |
| 5 | «Грядки» — визуальный пульт плана с провалом в аналитику клиента | `crm-08` |
| 6 | Хронологические комментарии к клиенту, заказу и реализации; сквозная лента в карточке клиента | `crm-01` |
| 7 | Задачи себе и коллегам: дедлайны, отметка выполнения, полиморфная привязка к любой сущности, отдельный полный список | `crm-09` |
| 8 | Вложения к задачам, комментариям, карточке клиента, заказам, реализациям | `crm-02` |
| 9 | Отправка HTML-писем из CRM с вложениями + журнал отправок | `crm-10` |
| 10 | REST `/api/crm/*` с документацией и discovery-методом | `crm-11` |
| 11 | MCP `/mcp/crm` с записью от имени менеджера + выдача токенов | `crm-12`, `crm-13` |

## Зафиксированные решения

| Вопрос | Решение | Почему |
|---|---|---|
| Профиль клиента | Гибрид: структурированные поля + свободный Markdown | Поля нужны для фильтров и для ИИ, свободный текст — для того, что в поля не влезает |
| Факт продаж | Отгрузки в ₽ по `erp_created_at` | Так считает текущий `/crm/analytics`; расхождение цифр между экранами недопустимо |
| Статус лояльности | Владелец — 1С, в CRM read-only | `HandlePartnerUpdated` перезаписывает `client_status_id` при каждом `partner.updated` — правка из CRM была бы затёрта |
| Жизненный статус | Новое поле сайта в `crm_client_profiles` | 1С о нём не знает и знать не должна |
| Лиды | Видимость `visibleInCrm` не трогаем | На проде лидов ~10 (0,2 % спроса); «лид» — стадия клиента, у которого уже есть менеджер |
| Комментарии | Видны всему отделу, без флага приватности | Помогает передавать клиента и подменять коллегу; видимость клиента и так ограничена скоупом |
| Почта | SMTP сайта, `From` = ящик отдела, `Reply-To` = менеджер | Не требует хранить пароли личных ящиков, работает на текущем SMTP сразу |
| Гейт для ИИ | Новый `/mcp/crm` **поверх** REST `/api/crm/*` | Общий слой операций; смешивать запись с read-only BI-доступом `/mcp/analytics` (bi_agent, только SELECT) нельзя |

## Что сознательно не входит

| Выпилено | Причина |
|---|---|
| Отправка статуса лояльности в 1С | Требует spec-first правок AsyncAPI и работ на стороне 1С. Отдельная карточка, когда будет договорённость |
| Раздел «Лиды» и назначение менеджера из CRM | Лидов на проде ~10, механизм не окупается сейчас |
| Личные SMTP-ящики менеджеров | Хранение чужих кредов и обработка сбоев по каждому ящику — отдельная задача с своей ценой |
| Канал telegram для уведомлений | Поле в `entity_subscriptions` есть, кода нет — вне этого эпика |
| Воронка сделок (deals/pipeline) | Продажи здесь идут повторными отгрузками, а не сделками; воронка добавила бы сущность без потребителя |

## Границы: чего эпик НЕ ломает

- **Шина данных не затрагивается.** Ни одного нового события AsyncAPI/RabbitMQ. Правило
  обязательных ERP-интеграционных тестов к этому эпику не применяется.
- **`users` остаётся зоной 1С.** Все CRM-поля — в отдельных таблицах `crm_*`. Проверено, что
  `PublishUserToErp` шлёт партнёра в шину только при первом заполнении `name`, то есть новые
  колонки в `users` не вызвали бы утечки — но границу владения держим явной.
- **Движок аналитики не форкается.** Планы, «грядки» и «возможности» считают факт через
  существующий `ShipmentAnalyticsService` + `AnalyticsContext::forScope()`.
- **Каркас панели общий.** Новые страницы — обычные `Crm/Pages/*` с `CrmLayout`, пункты меню
  в `Crm/config/menuConfig.ts` с указанием права.

## Порядок волн

```
Волна 1 (01, 02) ──┬── Волна 2 (03, 04) ──┐
                   └── Волна 3 (09, 10) ──┼── Волна 5 (11 → 12 → 13)
Волна 4 (05 → 06 → 07 → 08) ──────────────┘
```

Волна 4 не зависит от волн 1–3 и может идти параллельно. Волна 5 закрывает то, что готово
к моменту её старта.

## Критерии готовности эпика

- [ ] Менеджер ведёт профиль клиента и меняет его жизненный статус; лояльность видна как «из 1С»
- [ ] Комментарий, оставленный на заказе или реализации, виден в ленте клиента
- [ ] Задачи ставятся себе и коллегам, с дедлайном, вложениями и привязкой к любой сущности
      (или вовсе без неё), при этом полный список задач доступен отдельным разделом
- [ ] Планы на месяц заданы, `/crm/plans` показывает факт, совпадающий с `/crm/analytics`
- [ ] `/crm/beds` показывает грядки и открывает аналитику по клиенту
- [ ] Письмо уходит из CRM и попадает в журнал
- [ ] ИИ-агент менеджера через `/mcp/crm` выполняет всё вышеперечисленное и не может выйти
      за пределы клиентов своего менеджера
