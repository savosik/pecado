## Описание

Правило проекта: **всё, что идёт через RabbitMQ и отражено в AsyncAPI, покрывается интеграционными
тестами** (`feedback_integration_tests`, `project_integration_test_setup`). Контракт тонкой модели меньше
прежнего, но меняет остатки по складам сайта и строку заказа.

Покрыть:

- **снимок предложений**: приём, повтор того же `revision`, устаревший `revision`, пустой `offers[]`,
  неизвестные `organization_uuid` / `warehouse_uuid`, снимок без склада предзаказа;
- **инвариант суммы**: после снимка сумма строк по складу = `product_warehouse`; `stock.updated` по складу
  вне снимка работает как прежде;
- **`order.created`**: строка с `offer_key` и без него; покупка у двух продавцов → два сообщения с общим
  признаком; идемпотентность;
- **`order.updated`**: отмена строки с `no_stock_seller` / `no_stock_vat` и с неизвестным кодом → `other`;
  письмо клиенту о недоборе по новой причине (`EnablesClientNotifications`), для закрытых и старых заказов —
  тишина (инцидент 25.09);
- **обратная совместимость**: прежние сообщения без новых полей валидны и ведут себя предсказуемо;
- журнал шины (`erp_bus_messages`) содержит новые события.

Помнить: тесты идут на SQLite, а он скрывает `only_full_group_by` — агрегаты по складу проверять
дополнительно на MySQL (`feedback_sqlite_hides_group_by_errors`).

## Критерии готовности

- [ ] Тесты приёма снимка зелёные, включая краевые случаи и инвариант суммы
- [ ] Тесты публикации `order.created` с ключом и без, многопродавцовой покупки
- [ ] Тесты приёма отмены строки с новыми кодами и письма клиенту
- [ ] Тест обратной совместимости со старым форматом
- [ ] Полный прогон (`make test`) зелёный — запускает оркестратор в очереди выкатки
