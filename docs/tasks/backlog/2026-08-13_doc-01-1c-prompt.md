## Описание

Контракт печатных форм пишется в обычном порядке проекта — **spec-first**: JSON Schema →
AsyncAPI → бизнес-правила → промт → код. Отступление, как в `fin-01`, здесь не нужно:
события аддитивные, ничего существующего не ломается, и цена ошибки в схеме — правка одного
поля, а не переделка модели денег.

Артефакт для 1С — `docs-erp/content/guides/printed-documents-for-1c.md`, самодостаточный
промт по образцу [`cost-price-for-1c.md`](../../../docs-erp/content/guides/cost-price-for-1c.md)
и [`settlements-for-1c.md`](../../../docs-erp/content/guides/settlements-for-1c.md).

## Контракт

| Событие | Очередь | Routing key | Что означает |
|---|---|---|---|
| `printed_document.published` | `erp_in.printed_documents` | `printed_document.published` | Печатная форма сформирована и выложена в бакет |
| `printed_document.deleted` | `erp_in.printed_documents` | `printed_document.deleted` | Форма отозвана: документ помечен на удаление или отменён |

Очередь новая, а не существующая `erp_in.documents` (там `shipment.*` с одним воркером):
первичная выгрузка форм за год заблокировала бы приём реализаций.

`required` у `published`: `event`, `message_id`, `uuid`, `type_code`, `file_url`, `date`.
`contractor_uuid` обязателен **бизнес-правилом, но не схемой** — иначе документ без него ушёл бы
в DLQ, а требование эпика прямо противоположное: файл не теряется ни при каких условиях.

## Самое опасное место — идентификатор печатной формы

В КА2 печатная форма не является объектом и собственного UUID не имеет. Значит 1С обязана
завести регистр сведений «ПечатныеФормыДляСайта» с измерениями (Документ-основание, ВидФормы)
и реквизитами (UUID, ИмяФайла, Хеш, Ревизия) — либо вычислять `uuid` детерминированно из пары
(UUID документа, код вида).

`uuid` обязан быть **стабильным между перевыставлениями**. Нестабильный `uuid` валидацией
схемы не ловится: сообщение пройдёт, а клиент получит второй счёт вместо обновлённого первого.
Это первый и самый подробный раздел промта.

## Три случая перевыставления — проговорить отдельно

| Случай | Что делает 1С | Что делает сайт |
|---|---|---|
| Переформировали ту же форму (исправили реквизиты, номер тот же) | Тот же `uuid`, `revision + 1`, новый файл | Перезаписывает документ и файл. У клиента остаётся одна актуальная форма |
| Корректировочный счёт-фактура, УКД | Это **другой документ 1С**: новый `uuid`, свой `type_code`, ссылка на основание тем же `shipment_uuid` | Создаёт вторую форму. Старую не трогает — обе нужны учёту |
| Документ отменён или помечен на удаление | `printed_document.deleted` с тем же `uuid` | Мягкое удаление, файл остаётся на диске |

Путаница между первым и вторым случаем — вторая по вероятности ошибка внедрения после `uuid`.

## Что делаем

### 1. Схемы

- `app/Services/Erp/Schemas/printed_document.published.json`
- `app/Services/Erp/Schemas/printed_document.deleted.json`

По образцу `individual_prices.ready.json`: `event` как `const`, `additionalProperties: true`.

### 2. AsyncAPI

`docs/asyncapi/pecado-erp-integration.yaml` — `info.version` 16.0.0 → 16.1.0, канал
`erpInPrintedDocuments`, две операции `receive*`, два message, payload-схемы.
Затем `npm run asyncapi:build`, сгенерированное закоммитить.

### 3. Бизнес-правила

`docs-erp/content/rules/printed-documents.md` по шаблону `rules/payments.md`.

### 4. Промт

`docs-erp/content/guides/printed-documents-for-1c.md`. Обязательные разделы:

| Раздел | Содержание |
|---|---|
| Роль и задача | Разработчик 1С:КА2, дорабатывающий обмен с `pecado.ru` через RabbitMQ |
| Зачем это бизнесу | Клиент запрашивает документы письмом менеджеру; раздел снимает поток с отдела продаж |
| Что уже сделано на стороне сайта | Очередь, бакет, доступ на запись, таблица, раздел ЛК, DLQ |
| Актуальная документация | Ссылки на AsyncAPI, JSON Schema, бизнес-правила, changelog |
| **⚠️ Идентификатор печатной формы** | Регистр «ПечатныеФормыДляСайта», стабильный `uuid`, почему схема этого не ловит |
| Формат сообщения | JSON-пример каждого события целиком + таблица «поле → реквизит КА2» |
| **Что именно класть в S3** | Только PDF, один файл = одна форма, ≤ 50 МБ, ключ `<ГГГГ>/<ММ>/<uuid>.pdf`, выкладывать до отправки сообщения, ничего не удалять и не перезаписывать |
| Коды видов форм | Таблица латинский код ↔ русское имя ↔ печатная форма КА2, правило для формы вне таблицы |
| Когда слать | При сохранении формы в регистр, а не при каждом открытии печати менеджером |
| **Перевыставленный документ** | Три случая выше, каждый со своим правилом |
| Ревизия и порядок доставки | Почему `revision` обязателен |
| Идемпотентность | `message_id` на сообщение, `uuid` на документ |
| Привязка к сторонам | `contractor_uuid` обязателен по бизнес-правилу; сайт документ не потеряет и доклеит позже |
| Порядок первичной выгрузки | Одна форма каждого вида → пачка на одном контрагенте → история с ограничением темпа |
| Критерии приёмки | Чек-лист |
| Если что-то не сходится | DLQ, типовые ошибки |
