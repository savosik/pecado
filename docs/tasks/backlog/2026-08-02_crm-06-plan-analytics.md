# crm-06 · Выполнение планов: дашборд, прогноз и burndown

**Приоритет:** высокий
**Создано:** 2026-08-02
**Эпик:** [crm-00](2026-08-02_crm-00-epic.md)
**Волна:** 4 (планы и аналитика)
**Зависимости:** `crm-05` (планы)

## Описание

Показать выполнение планов: общее по отделу, по каждому менеджеру и по клиентам, с прогнозом
на конец месяца и **burndown** — графиком «сколько осталось добрать» против идеальной линии,
как в скраме.

## Ключевое требование: факт считает существующий движок

Факт продаж берётся **только** через `ShipmentAnalyticsService` с контекстом
`AnalyticsContext::forScope($clientIds, AnalyticsContext::DATE_ERP, null)` — отгрузки в рублях
по бизнес-дате 1С. Ровно то же, что показывает `/crm/analytics`.

Свой SQL по `shipments` в этой карточке писать **нельзя**: расхождение цифр между
`/crm/plans` и `/crm/analytics` — баг по определению, а два независимых расчёта рано или поздно
разъедутся на фильтрах, мягком удалении или курсах валют.

Напоминание про даты: по `created_at` вся историческая база выглядит купленной в мае 2026
(при запуске прода историю 1С затянули одним импортом). Бизнес-дата — `erp_created_at`.

## Что делаем

**Расширение `App\Services\Crm\SalesPlanService`:**

```php
public function progress(CarbonInterface $month, PlanScope $scope): array
// => ['plan', 'fact', 'percent', 'remaining', 'forecast', 'needed_per_day',
//     'days_passed', 'days_total', 'pace']  // pace: 'ahead' | 'on_track' | 'behind'

public function burndown(CarbonInterface $month, PlanScope $scope): array
// => [['date', 'ideal_remaining', 'actual_remaining'], ...]  по дням месяца

public function byManager(CarbonInterface $month, User $actor): array
// строки: менеджер, план, факт, %, прогноз, число активных клиентов
```

**Прогноз** — линейная экстраполяция текущего темпа на конец месяца (`fact / days_passed *
days_total`). Простая модель названа простой: подписываем «прогноз при текущем темпе», а не
«прогноз» — чтобы никто не принял её за предсказание с учётом сезонности.

**Burndown**: идеальная линия — равномерное списание плана по дням месяца; фактическая —
остаток `план − накопленный факт` на каждый день. Дни после сегодняшнего не рисуем.

Накопленный факт по дням берётся из `ShipmentAnalyticsService::timeSeries()` (уже умеет
группировку по дню с каркасом пустых бакетов) — вручную не считаем.

**Скоуп.** РОП видит отдел, разрез по менеджерам и планы клиентов; менеджер — свой план
и планы своих клиентов. Гейт разреза по менеджерам — `crm-clients-all.view`, как в
существующем `AnalyticsController`. Набор клиентов менеджера — `User::visibleInCrm()`,
разрез менеджера — через `shipments.user_id → users.personal_manager_id`
(метод `byManager()` в `ShipmentAnalyticsService` уже это делает).

**Сверка «сумма планов клиентов против плана менеджера»** — показывается как расхождение
с суммой и знаком, не как ошибка.

**Роуты** в `routes/crm.php` под `permission:crm-plans.view`:

```
GET /crm/plans/progress        — сводка выполнения (план, факт, прогноз, темп)
GET /crm/plans/burndown        — точки графика
GET /crm/plans/by-manager      — разрез по менеджерам (гейт crm-clients-all.view)
GET /crm/plans/export          — XLSX через App\Services\SimpleXlsxExporter::stream()
```

**Фронтенд** — вкладка «Выполнение» на `Crm/Pages/Plans/Index.jsx`:
- KPI-плитки: план, факт, %, остаток, «нужно в день», прогноз при текущем темпе;
- burndown на `recharts` (две линии: идеальная пунктиром, фактическая сплошной);
- таблица по менеджерам с прогресс-барами (для РОПа);
- таблица по клиентам с сортировкой по «отставанию».

Палитра и правила читаемости графиков — по скиллу `dataviz`; светлая и тёмная темы обе.
Никаких эффектов сверх этого (правило о минимализме UI-эффектов в проекте).

**Кэш.** Сводка за закрытые месяцы не меняется — кэшируем на сутки по ключу
`crm:plan-progress:{период}:{скоуп}`. Текущий месяц — на 5 минут: `ShipmentAnalyticsService`
делает несколько тяжёлых агрегатов, а дашборд открывают часто.

## Границы

- Планы по брендам/категориям/товарам — вне скоупа (см. `crm-05`).
- Мотивация и расчёт бонусов не делаем — это про зарплату, а не про CRM.
- Прогноз с сезонностью не делаем: для этого нужен ряд по годам, а на проде история с ноября 2025.

## Критерии готовности

- [ ] Факт считается **через `ShipmentAnalyticsService`**, свой SQL по `shipments` отсутствует
- [ ] Цифра факта за период совпадает с `/crm/analytics` за тот же период — проверено на dev
- [ ] Burndown строится: идеальная и фактическая линии, будущие дни не дорисованы
- [ ] Разрез по менеджерам доступен только с `crm-clients-all.view`
- [ ] Менеджер видит только свой план и своих клиентов
- [ ] Прогноз подписан как «при текущем темпе»
- [ ] XLSX выгружается
- [ ] Feature-тест `tests/Feature/Crm/PlanProgressTest.php`: совпадение факта с движком аналитики,
      изоляция скоупа, гейты прав, корректность burndown на фикстуре
