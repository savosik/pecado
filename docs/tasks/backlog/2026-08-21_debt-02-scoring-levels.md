# debt-02: скоринг и машина уровней (светофор долга)

**Приоритет:** высокий
**Эпик:** [debt-00](2026-08-21_debt-00-epic.md)
**Зависит от:** debt-01
**Создано:** 2026-08-21

## Описание

Домен `app/Services/Debt/`. Уровни — enum `DebtLevel`:
`clean` (чисто) → `reminder` (жёлтый, напоминания) → `prepay_only` (только
предоплата) → `hold` (стоп: покупки закрыты, вход и оплаты открыты).

### Сигналы скоринга (все — через `PaymentForecast` и `contractor_balance_overdue_details`, без новых запросов)

| Сигнал | Источник | Правило |
|---|---|---|
| Значимая просрочка | `contractor_balances.overdue_debt` | Участвует, только если > 5 000 ₽ **и** старше 5 банковских дней (иначе клиент `clean`) |
| Доля от оборота | просрочка / среднемесячный оборот за 90 дней (`shipments.total_amount` по `erp_created_at`) | Кусочная формула: при обороте ниже порога — оценка по абсолютной сумме и возрасту долга |
| Возраст | старейшая просроченная строка графика | Корзины 7/30/90 дней |
| Хроничность | эпизоды просрочки за 12 мес | Хронику (6+ эпизодов) — сокращённый grace |
| Нарушенное обещание | `payment_promises` (debt-08) | Сильнейший сигнал: немедленно уровень выше |

**Гистерезис обязателен**: порог входа на уровень выше порога выхода
(пример: вход в `prepay_only` при доле ≥ 15 %, выход при ≤ 10 %) — клиент на границе
не мигает. Все пороги — в `config/debt.php`, в UI их нет (анти-боинг).

### Профили

`users.debt_profile`: `regular` (лестница целиком) / `marketplace` (вне автоматики,
только строка в отчёте РОП) / `legal` («мёртвые» без оборота — короткая ветка:
письмо → претензия, без тостов и блокировок). Назначение профиля — вручную в CRM;
стартовая разметка: WB, Яндекс.Маркет, Ozon → `marketplace`; 5 неплательщиков
с нулевым оборотом → `legal`.

### Таблицы

- `debt_statuses` — текущий уровень клиента: `user_id` (unique), `level`, `since`,
  `reason` (однострочный «почему»), `computed_at`;
- `debt_level_transitions` — журнал переходов: откуда/куда, причина, `dry_run`
  (shadow), кто/что инициировал;
- поле `users.debt_profile`.

### Пересчёт и режимы

- Плановый пересчёт — командой рядом с `FinanceScanner` (та же частота);
  событийный (мгновенный, только вверх) — в debt-07.
- **Shadow-режим**: `DEBT_CONTROL_MODE=shadow` — уровни считаются, переходы пишутся
  с `dry_run=1`, никаких действий. Минимум 2 недели, затем поштучное включение
  ступеней через `DEBT_CONTROL_LIVE_ACTIONS` (паттерн `live_events` пульта).
- `debt:explain {user}` — консольный разбор: сигналы, уровень, ближайший переход
  (паттерн `notifications:explain`).

### Инварианты (зашиты в код, тестами)

- эскалация запрещена: по данным старше `stale_after_days`; для `marketplace`;
  при активной паузе (debt-09) или активном обещании (debt-08);
- понижение уровня (ужесточение) — не больше чем на одну ступень за пересчёт;
- каждый переход обязан иметь непустой `reason`.

## Критерии готовности

- [ ] Миграции с русскими комментариями, `bi:sync-grants` после наката
- [ ] `DebtScoringService` + `DebtLevelResolver`: юнит-тесты на отсечку, grace, гистерезис, кусочную формулу оборота, хронику (агрегаты проверить на локальной MySQL)
- [ ] Инварианты покрыты тестами (staleness, marketplace, одна ступень за раз)
- [ ] Shadow: две недели журнал пишется на проде, действия не выполняются
- [ ] `debt:explain` отвечает на «почему у клиента X такой уровень» одной строкой + детализация
