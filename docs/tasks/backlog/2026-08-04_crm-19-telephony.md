# crm-19 · Телефония: звонки из CRM, запись, расшифровка и резюме

**Приоритет:** низкий — идея зафиксирована, к работе не приступаем
**Создано:** 2026-08-04
**Эпик:** [crm-00](2026-08-02_crm-00-epic.md)
**Волна:** 6 (рабочее место менеджера), продолжение [crm-18](../review/2026-08-04_crm-18-calls.md)
**Зависимости:** `crm-18` (журнал звонков — схема и лента уже готовы)

## Описание

`crm-18` научил CRM хранить звонки, но набирает менеджер сам и результат записывает руками.
Ручной ввод люди саботируют — не со зла, а потому что после разговора есть дела важнее.
Значит, звонок должен попадать в CRM сам.

Целевой поток: менеджер жмёт «Позвонить» в карточке или таблице → АТС соединяет → после
разговора запись скачивается в MinIO → Yandex SpeechKit расшифровывает с разделением
говорящих → OpenRouter делает резюме в три строки и предлагает следующий шаг → всё это
появляется в ленте клиента. **Входящие обрабатываются так же**: определяется клиент по номеру,
создаётся запись, менеджер видит карточку ещё до того, как поднял трубку.

## Главная развилка: сейчас звонят с обычных мобильников

Это определяет всю интеграцию. Обычный мобильный не даёт ни записи разговора, ни события
о звонке — прикрутить к нему API нечего. Вариантов три:

| Вариант | Суть | Цена вопроса |
|---|---|---|
| **FMC** (Fixed Mobile Convergence) | Корпоративные SIM оператора-партнёра АТС; все звонки с мобильного идут через АТС и записываются | Смена SIM у менеджеров, привязка к оператору; зато привычный телефон и мобильная связь вне офиса |
| **Софтфон** | Приложение АТС на телефоне или в браузере, звонки через интернет | Ничего не менять у оператора, но качество зависит от сети и людей надо переучивать |
| **Гибрид** | Входящие на облачный номер с записью, исходящие остаются мобильными | Половина звонков мимо CRM — то есть половина смысла |

Гибрид как постоянное решение не годится, но годится как первый шаг: входящие приносят
пользу сразу и не требуют трогать телефоны менеджеров.

## Выбор провайдера

Критериев ровно три, остальное — маркетинг: **REST API инициации звонка**, **вебхуки событий**
(начался / ответили / завершился) и **доступ к файлу записи**. Готовые интеграции с amoCRM
и красивый кабинет нам бесполезны — CRM своя.

Кандидаты: **Sipuni** (простой API, дёшево — лучший старт для самописной интеграции),
**Манго Телеком** (самый широкий API в РФ, дороже), **Zadarma** (дёшево, есть бесплатная АТС),
**UIS/Comagic** (сильная аналитика, избыточен). Тарифы и лимиты проверять актуальные —
они меняются чаще документации.

## Что уже готово, а что добавить

`crm_calls` спроектирована под это заранее — половина работы сделана.

| Готово | Добавить |

| Резолв `client_user_id` в модели, лента, права `crm-calls.*`, политика | Контроллер вебхука вне `auth` + проверка подписи провайдера |

| `CallDialog`, `CallFeedEntry`, режим «Звонок» в ленте | Плеер записи в ленте, спойлер с расшифровкой |

## Расшифровка: SpeechKit, а не Whisper через OpenRouter

Ловушка именно этого проекта: OpenRouter с прода ходит **только через outbound-proxy**
(SSH-туннель до VPS, см. `project_openrouter_outbound_proxy`). Текстовые запросы через него
идут нормально, но десятки аудиофайлов по 5–20 МБ в день — хрупко: туннель отвалится, и это
обнаружится по молча копящейся очереди.

**Yandex SpeechKit** доступен с прода напрямую, оплата в рублях, асинхронное распознавание
длинных записей — ровно наш случай. Главное: **диаризация** — разделение говорящих. Без неё
расшифровка разговора читается как поток сознания. Альтернатива того же класса — SaluteSpeech.
Локальный `faster-whisper` — только при наличии GPU; на CPU расшифровка десятиминутного
разговора займёт больше самого разговора.

**Запись обязательно скачивать себе** в MinIO через `MediaService`. Провайдеры хранят файлы
ограниченное время, а `recording_url` часто ещё и с истекающей подписью — через год «послушать,
что обещали» превратится в 404.

## Резюме через OpenRouter — где реальная польза

Сама расшифровка это стена текста, её никто не читает. Ценность на втором проходе (текст
лёгкий, туннель справляется):

- **резюме в три строки** — оно идёт в ленту, полная расшифровка прячется под спойлер;
- **извлечённые договорённости** → предзаполненная follow-up задача с датой; `follow_up_task_id`
  и создание задачи одной транзакцией уже есть, ИИ подставляет заголовок и срок;
- **сигналы для карточки**: упомянутые бренды и товары, возражения, тональность
  (`crm_client_profiles.sentiment` сейчас заполняется руками).

Задачу ИИ **предлагает**, а не создаёт молча: автоматически созданная из галлюцинации задача
с чужим сроком подорвёт доверие ко всему разделу быстрее, чем принесёт пользы.

## Правовая сторона — не формальность

Запись разговоров без уведомления собеседника — 152-ФЗ и ст. 138 УК. Нужны: голосовое
предупреждение о записи в начале звонка (настраивается у провайдера), пункт в политике
обработки персданных, согласие сотрудников на запись рабочих разговоров. Расшифровка через
внешний сервис — передача персданных обработчику, это тоже должно быть отражено. Дешевле
сделать сразу, чем объясняться потом.

## Порядок работ (три этапа, каждый полезен сам по себе)

1. **Входящие + вебхук.** Звонок сам ложится в журнал, клиент определяется по номеру.
   Не требует трогать телефоны менеджеров — самый дешёвый вход.
2. **Исходящие (click-to-call) + запись.** Скачивание в MinIO, плеер в ленте. Здесь же
   решается развилка FMC / софтфон.
3. **Расшифровка и резюме.** За фича-флагом, как все внешние интеграции проекта: одна
   переменная в `.env` выключает, если качество распознавания разочарует.

## Открытые вопросы

- Какой вариант заводки мобильных выбираем — FMC, софтфон или гибрид?
- Есть ли статические IP для белого списка провайдера (у части API это обязательное условие)?
- Кто платит за минуты распознавания и в каком объёме — нужна оценка по числу звонков в день.
