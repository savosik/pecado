# fin-07 · Прогноз поступлений и презентер на регистре

**Приоритет:** высокий
**Создано:** 2026-08-09
**Эпик:** [fin-00](2026-08-09_fin-00-epic.md)
**Зависимости:** `fin-06` зелёный
**Волна:** 3 — за флагом `SETTLEMENTS_LEDGER_ENABLED`

## Описание

Счётное ядро переезжает на `settlement_entries`. Ключевое — сервис **сильно упрощается**:
исчезает половина причин, по которым он был сложным.

| Что уходит | Почему |
|---|---|
| `noScheduleQuery()` (~50 строк) | Долг без графика — обычная строка регистра, а не отдельная ветка |
| `amount - paid_amount - prepaid_amount` | Одна колонка `settled_amount` от 1С |
| Сведение валют по текущему курсу | `amount_rub` посчитан на дату операции при приёме |
| Джойн `shipment_payment_schedules × shipments × users × organizations` | Разрезы лежат в самой строке регистра |

Что **сохраняется** как есть — оно рабочее: `FinanceFilters`, `AGING_BUCKETS`,
`applyDefaultOrder()`, структура `row()`, XLSX-экспорт, изоляция через `User::visibleInCrm()`.

## Что делаем

### `app/Services/Crm/Finance/PaymentForecastService.php`

Переписать запросы на `settlement_entries`. Соответствие методов:

| Метод | Было | Стало |
|---|---|---|
| `plannedQuery()` | `shipment_payment_schedules` + 4 джойна | `nature='plan'`, `unsettled > EPSILON` |
| `noScheduleQuery()` | Отдельная ветка | **Удалить** |
| `factsByDay()` | `payments.date`, `CASE direction` | `nature='fact' AND type IN (payment_in, payment_out)` — знак уже в `amount` |
| `aging()` | По `due_date` графика | По `date` плановых строк |
| `balances()` | `ContractorBalance` | `SUM(amount) WHERE nature='fact'`, ось контрагент × организация |
| `summary()` | 10+ подсчётов из трёх источников | Те же KPI, один источник |
| `topDebtors()` | Как есть | Источник другой |
| `toRub()` | Текущий курс из `Currency` | `amount_rub` из строки |

Новое в `summary()`: **фактический баланс** (акт сверки) рядом с текущей задолженностью —
раньше эти два числа не различались, что и было источником путаницы.

⚠️ Сохранить приём из текущего кода: в `sumByDay()`/`sumRub()` использовать `select()`,
а не `selectRaw()` — иначе `only_full_group_by` уронит запрос на MySQL. SQLite это молча
проглатывает, тестами не ловится.

### `app/Support/Payments/PaymentSchedulePresenter.php`

Переписать на плановые строки регистра. Заодно чинится существующий дефект: агрегат блока
считает `unpaid = total - paid` без `prepaid_amount`, тогда как построчный `unpaid_amount`
его вычитает — итог не сходится с суммой строк при наличии авансов.

### Флаг

`config/settlements.php` → `SETTLEMENTS_LEDGER_ENABLED` (по умолчанию `false`).
Ветвление — в одной точке, а не по всему сервису: фабрика, отдающая старую или новую
реализацию за общим интерфейсом. Иначе `if` расползётся по двадцати методам и волна 4
станет невыполнимой.

## Edge-кейсы

- **Флаг выключен** → поведение байт в байт прежнее. Тестом.
- **Регистр пуст, флаг включён** → отчёт пустой, а не «нулевой долг у всех». Показывать
  явное предупреждение, а не молчать.
- **Движение без договора** → попадает в отчёт в группу «Без договора», не теряется.
- **Валюта без курса на дату** → `amount_rub = NULL`, строка видна в детализации с исходной
  суммой, но не участвует в рублёвых итогах. Счётчик таких строк — в сводке.
- **Клиент с переплатой** → положительный баланс, в просрочку и в «кому звонить» не попадает.
