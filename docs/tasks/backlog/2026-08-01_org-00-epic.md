## Суть в одном абзаце

У компании несколько организаций (наших юрлиц). **Сайт про них не решает — сайт про них
знает.** Организацию определяет 1С и присылает в заказах, реализациях и взаиморасчётах;
сайт сохраняет и показывает её клиенту, менеджеру, админу и в отчётах. Ни цены, ни
остатки, ни выбор организации при оформлении сайт не трогает.

## Границы скоупа

Что **входит**:

| № | Требование |
|---|---|
| 1 | Цены и остатки на сайте остаются как сейчас: цены по клиентам, остатки по складам. Сайт принимает **агрегат** — лучшую цену и суммарный остаток по складу |
| 2 | Сайт отправляет заказ **без организации**. Склады уходят перечислением `warehouse_uuids[]`, как сейчас: склады региона взаимозаменяемы, заказ по ним не разбивается |
| 3 | Особые виды заказов (уценка, промо, тестеры) 1С по-прежнему различает по `type` и флагам — как сейчас, ничего не меняем |
| 4 | 1С присылает в заказах конкретные **организацию и склад** |
| 5 | 1С присылает в реализациях конкретные **организацию и склад** |
| 6 | 1С присылает баланс с указанием, **какой организации и сколько** должен клиент |
| 7 | Организацию возврата сайт выводит из реализаций-оснований — **справочно**; 1С определяет её сама |
| 8 | Организация видна везде: ЛК клиента, админка, CRM, аналитика, отчёты, табличные выгрузки |

Что **сознательно не входит** (и почему):

| Выпилено | Причина |
|---|---|
| ~~Остатки в разрезе организаций~~ (была `org-05`) | 1С шлёт агрегат по складу — подтверждено. Остатки по организациям на сайте не нужны |
| ~~Цены в разрезе организаций~~ | 1С шлёт агрегированную лучшую цену — подтверждено |
| ~~Справочник организаций через шину~~ | 1С его не отправляет. Организации заводятся в админке руками с UUID, как склады; 1С указывает только UUID |
| ~~Выбор организации при оформлении~~ | Организацию определяет 1С. Разбиения корзины по юрлицам не будет |
| ~~Сужение складов в исходящем заказе до одного~~ (`org-07`) | Отложено: склады региона взаимозаменяемы, уходят перечислением. **Исходящий контракт не меняется вовсе** |
| ~~Промо-организации из справочника сайта~~ | Хардкод 1С по `type` (`promo` → ООО Пекадо, `promo_sample` → Реклама) **остаётся** и работает |
| ~~Отправка организации в возврате~~ | 1С выводит её из реализаций сама; дублировать незачем |
| ~~НДС~~ | Вынесен из эпика в отдельную карточку [ставки НДС на товарах](2026-08-01_vat-rates-on-products.md) |

**Следствие:** эпик стал целиком **входящим** — сайт принимает, сохраняет и показывает.
Ни одна схема `*.to_erp.json` не меняется.

✅ **Подтверждено 1С 2026-08-01:** `stock.updated` и `price.updated` приходят
**агрегированными** — остаток по складу, лучшая цена, без разреза на организации.
Расхождения с текущей реализацией нет, `HandleStockUpdated` и `HandlePriceUpdated`
остаются как есть.

Требование всё же закрепляется в `rules/stock.md` и `rules/prices.md` (`org-02`):
`HandleStockUpdated` пишет остаток **перезаписью** по ключу (товар, склад), поэтому
переход 1С на раздельные сообщения по организациям молча занизил бы наличие — победило бы
последнее сообщение. Записываем в контракт, чтобы это не изменили ненароком.

## Принципы

**1. Все поля организации опциональны в обе стороны.**
`additionalProperties: true` уже стоит во всех схемах, поэтому 1С может начать слать
организацию в любой момент без релиза сайта. Ни одно поле не становится `required`
до `org-11`.

**2. `NULL` = «организация не указана», а не «неизвестная организация».**
Историю не бэкфиллим догадками. В UI и отчётах — явная группа «не указана», которая
остаётся навсегда как честное отражение истории.

**3. Справочник ведётся руками, неизвестный UUID даёт заглушку.**
1С справочник организаций не присылает — юрлица заводятся в админке разово с UUID,
как склады. Документ с UUID, которого в справочнике нет, создаёт заглушку
(`is_stub = true`); админ дозаполняет название, и все ранее принятые документы сразу
отображаются правильно, без бэкфилла. Заглушки обязаны быть **заметны в админке** —
это единственный сигнал, что 1С работает с незаведённым юрлицом.

**4. Детализация рядом с агрегатом.**
Касается только взаиморасчётов: `contractor_organization_balances` дополняет
`contractor_balances`, который остаётся агрегатом-проекцией. Существующие чтения
не меняются.

**5. Флаг `ORGANIZATIONS_ENABLED` гейтит только UI.**
Приём и сохранение работают всегда — иначе данные, присланные 1С раньше срока,
потеряются безвозвратно.

**6. Источник истины по организации — всегда 1С.** Сайт её не выводит и не угадывает
(кроме возврата, где она справочно берётся с реализации-основания).

## Схема данных

```
organizations                        ← заводится в админке вручную, как склады
  id, external_id (UUID 1С, nullable unique), name, legal_name, tax_id, tax_code,
  bank_* (реквизиты для оплаты — нужны клиенту, чтобы погасить долг),
  is_active, is_stub, sort_order, timestamps, deleted_at

orders            + organization_id (null), + warehouse_id (null)
shipments         + organization_id (null), + warehouse_id (null)
returns           + organization_id (null)   ← выводится с реализаций, справочно
                                              (таблица называется `returns`, модель ProductReturn)

contractor_organization_balances
  user_id, company_id, organization_id, current_balance, overdue_debt,
  balance_erp_updated_at              unique(company_id, organization_id)
contractor_balance_overdue_details  + organization_id (null)
```

Таблиц остатков и цен эпик **не касается**.

## Изменения контракта

Входящие (1С → Сайт) — всё опционально, версия спеки **15.8.0** (обратно совместимая):

| Событие | Что добавляется |
|---|---|
| `order.created`, `order.updated` | `organization` `{uuid, name?, tax_id?}`, `warehouse_uuid` |
| `shipment.created`, `shipment.updated` | то же |
| `return.updated` | `organization` (справочно) |
| `balance.updated` | `contractors[].organizations[]` с суммами и просрочкой |

Достаточно одного `uuid` — название и ИНН необязательны, справочник ведётся на сайте.

Исходящие (Сайт → 1С): **изменений нет.** Ни одна схема `*.to_erp.json` не трогается,
новых каналов и очередей не появляется.

## Edge-кейсы

**Документы**
1. Организация не пришла (legacy или 1С ещё не научилась) → `NULL`, в UI строка скрыта, не «—»
2. Организация пришла впервые для существующего документа → нормальный сценарий переходного периода
3. Организация сменилась в `order.updated` → перезапись + запись в `OrderChangeLog`
4. У заказа одна организация, у его реализации другая → легитимно (1С могла переоформить), не «чиним», подсвечиваем
5. 1С прислала склад, которого нет на сайте → `warehouse_id = NULL` + лог; склад автоматически **не** заводим
6. UUID организации не заведён в админке → заглушка; админ дозаполняет название, документы подтягиваются сами
7. Админ опечатался в UUID → рядом появится заглушка с правильным; два похожих юрлица в списке — сигнал об опечатке

**Взаиморасчёты**
8. `SUM(organizations) ≠ contractor.current_balance` → приоритет у contractor-уровня, warning в лог
9. Организация исчезла из массива → строку обнуляем, не удаляем
10. Переплата одной организации **не гасит** долг перед другой; взаимозачёт — компетенция 1С
11. Детализация ещё ни разу не приходила → блок разреза в ЛК не показывать вовсе

**Инфраструктура**
12. Удаление организации с историей → только soft delete
13. Новые таблицы → комментарии в БД + `bi:sync-grants`, иначе аналитический MCP их не увидит
14. `resolveWarehouseUuids` в `PublishOrderToErp` эпик **не трогает** — значит костыль подмены UUID склада предзаказа (`project_preorder_warehouse_hack`) в безопасности
