# up-02: сущности домена допродаж и ночной расчёт циклов

**Приоритет:** высокий
**Эпик:** [up-00](2026-08-14_up-00-epic.md)
**Зависит от:** up-01 (решение orders vs shipments)
**Создано:** 2026-08-14

## Описание

### `purchase_cycles` — материализованные циклы «клиент × товар»

| Поле | Комментарий |
|---|---|
| `user_id`, `product_id` | уникальная пара |
| `purchases_count` | число закупок в окне расчёта (учитываются только `cancelled = 0`) |
| `median_interval_days` | медиана фактических интервалов — не среднее (одна пауза-отпуск не должна ломать цикл) |
| `interval_stability` | коэффициент вариации интервалов; нестабильные пары не сигналят |
| `typical_quantity`, `typical_amount` | медианные количество и сумма закупки — предзаполнение листа |
| `last_purchased_at` | бизнес-дата: `erp_created_at` (решение up-01) |
| `next_due_at` | `last + median_interval`; просрочка = `now > last + median × 1.3` |
| `calculated_at` | расчёт ночной командой `upsell:recalculate-cycles` |

Порог входа: ≥3 закупок, интервал 7–90 дней, стабильность выше порога (конфиг).
Сегодняшний масштаб: 3 596 пар, из них 1 534 просрочены (53 клиента, ~6,1 млн ₽).

### `product_complements` — направленный справочник сопутствия

Зеркало `product_substitutions` из sub-01, та же механика:
`from_product_id → to_product_id` (к игрушке смазка, не наоборот; допустимо
`from_category_id → to_product_id` для правил уровня категории), `kind`
(`consumable` — расходник, `care` — уход, `accessory` — аксессуар, `power` —
питание/батарейки), `source` (`manual` / `learned` / `ai` / `stats` —
co-occurrence), `score`, `note`, `confirmed_at`, `rejected_at`, `created_by`.

### `upsell_signals` — показанный сигнал и его судьба (замыкание цикла)

| Поле | Комментарий |
|---|---|
| `user_id`, `product_id` | кому и что |
| `layer` | слой: `replenish` / `complement` / `gap` / `novelty` / `back_in_stock` / `liquidation` |
| `surface` | где показано: `cart` / `post_order` / `shortage_page` / `digest` / `cabinet` / `crm` |
| `reason` | текст причины, как её видел клиент |
| `digest_id` | nullable FK — если сигнал ушёл в составе дайджеста |
| `status` | `shown` → `clicked` → `added_to_cart` → `ordered` / `dismissed` |
| `order_id`, `order_item_id` | nullable — какой заказ/строка закрыли сигнал |

Идемпотентность показа: не дублировать живой сигнал по той же паре
(user, product, layer) — паттерн `CrmBackInStockOffer` («факт предложения
переживает всё»).

### `upsell_digests` — выпуск закупочного листа

`uuid` (для URL), `user_id`, `manager_user_id`, `status`
(`draft` → `sent` → `viewed` → `converted` / `expired`), `scheduled_for`
(предсказанная дата закупки), `sent_at`, `viewed_at`. Содержимое — сигналы
по `digest_id`.

### Метка источника на заказе

`orders.upsell_source` (nullable string) — проставляется, когда заказ рождён
из корзины, в которую добавляли по сигналам; строки, добавленные сигналом,
связываются через `upsell_signals.order_item_id`. Протокол 1С не трогается.

## Критерии готовности

- [ ] Миграции с русскими комментариями (db-comments), только новые; `bi:sync-grants` после наката
- [ ] Модели + фабрики; связи в `User`, `Product`, `Order`
- [ ] `upsell:recalculate-cycles`: расчёт ночью по расписанию, идемпотентный, медиана и стабильность покрыты юнит-тестами (агрегаты проверить на локальной MySQL)
- [ ] `upsell:preview {user_id}` — отладочная команда: показать циклы/просрочки/сигналы клиента до всякого UI
- [ ] Пороги (закупок ≥3, интервал 7–90, просрочка ×1.3, стабильность) — в конфиге
