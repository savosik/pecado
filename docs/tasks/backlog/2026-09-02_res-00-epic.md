# ЭПИК: Заказы в резерве — самообслуживание отказов интернет-магазинов (res-00)

**Приоритет:** высокий
**Создано:** 2026-09-02
**Статус (04.09.2026):** волны 0–2 полностью готовы — res-01…res-09 в review, всё за
рубильником `ORDER_RESERVE_ENABLED=false`. Протокол v16.9.0 на проде, спека у 1С.
Раскатка идёт в **топике №6** Agent Hub (сверка 84 uuid отправлена, ход у 1С).
Осталось: волна 3 (res-10 API, res-11 метрики), совместные испытания Р-1…Р-6,
включение по решению владельцев.

**Чек-лист включения режима** (после испытаний): 1) `ORDER_RESERVE_ENABLED=true` на
проде; 2) 1С включает свои обработчики и гейт авто-отгрузки; 3) включить участникам
уведомления `orders.reserve_expiring` / `orders.reserve_released` (умолчание false
по политике — иначе клиент теряет резерв молча); 4) `bi:sync-grants` на проде
(таблица `order_reserve_overrides`); 5) проверить приход `partner.updated` с
разметкой `reserve_allowed`; 6) мобильная визуальная проверка чекаута и раздела.

Ключевые параметры от владельцев: окно **24 часа** (предел удержания — настройка 1С), охват —
флаг `reserve_allowed` в `partner.*` (мастер — 1С, сайт сужает), подтверждение отдельным
`order.confirmed`, конфликты по `items_version`, отмена `order.deleted` с `reason`.
**Вне эпика:** оплата резервов, платное удержание резерва, изменение ценообразования, синхронизация с удалённой доской kanban-api

## Идея

Владельцы интернет-магазинов (десятки клиентов) оформляют у нас заказ сразу при получении
розничного заказа на своём сайте — чтобы застолбить товар. Затем обзванивают своих
покупателей, и каждый отказ или правка превращается в звонок нашему менеджеру: «удалите
заказ», «уберите две позиции». Трудоёмкость чужих отказов ложится на наш отдел продаж.

Легализуем паттерн: заказ сразу уходит в 1С и ставится в статус «Резерв» (товар
заблокирован — главная потребность интернетчика закрыта), а окно между «зарезервировал»
и «подтвердил» клиент обслуживает сам — в кабинете или через клиентский API. Менеджер
исчезает из цепочки. Не подтвердил вовремя — резерв снимается автоматически.

## Решения (заказчик, 02.09.2026)

1. **Чекаут**: вместо текущей галочки подтверждения — radio из двух вариантов:
   «Подтверждаю — можно отгружать» (умолчание) / «Поставьте в резерв» (с показом срока
   жизни резерва).
2. **Кабинет**: отдельный пункт меню «Заказы в резерве» с таймером обратного отсчёта на
   каждом заказе. После успешного оформления резервного заказа — редирект в этот раздел;
   если заказ один — сразу в детали заказа (там тоже таймер).
3. **Три кнопки** у резервного заказа: «Отправить в отгрузку» (подтверждение),
   «Редактировать» (состав), «Отменить».
4. **Клиентский API**: те же операции в `/api/client-api/{token}/*` — магазин может
   автоматизировать отказы со своей стороны без людей вообще.
5. **Опция отключаемая, но клиентам включена по умолчанию**: доступна всем сразу;
   отключение — точечное по партнёру (рычаг РОПа против злоупотреблений) плюс глобальный
   рубильник для тихой выкатки и аварийного гашения.
6. **UX идеален на десктопе и мобильном**: основной сценарий интернетчика — правка резерва
   с телефона сразу после звонка своему покупателю.
7. **Без 1С процесса нет**: статус «Резерв», приём исходящих `order.updated`/`order.deleted`
   от сайта — всё живёт в 1С. Протокол взаимодействия решают наши ИИ-агенты через Agent Hub
   (протокол топиков, `proposal` → `resolution`); resolution топика — вход в spec-first.

### Умолчания, принятые без отдельного вопроса

- Хранение включённости — по проектному принципу «только отклонения от умолчания»
  (как `notification_preferences`): умолчание в конфиге, в таблице живут лишь отключения.
- Уведомления о резервах — через матрицу note-00, новые типы уведомлений
  `orders.reserve_expiring` и `orders.reserve_released`; никакого отдельного движка.
- Резервный заказ — не долг («заказ — это план», круг 12 сверки взаиморасчётов).
- Конфликты одновременной правки (менеджер в 1С vs клиент на сайте) — по полю `revision`,
  оно уже есть во входящем `order.updated`.

## Критерии готовности эпика

- [ ] Топик Agent Hub закрыт resolution, протокол зафиксирован в AsyncAPI и MkDocs.
- [ ] Клиент сам отменяет неподтверждённый заказ из кабинета — без звонка менеджеру.
- [ ] Резервный заказ виден в 1С в статусе «Резерв» и не двигается в отгрузку до подтверждения.
- [ ] Просроченный резерв снимается автоматически, клиент получает письмо.
- [ ] Все операции доступны через клиентский API и задокументированы в Scramble.
- [ ] Опция отключается точечно у партнёра и глобально флагом; при отключении чекаут выглядит как раньше.
- [ ] Чекаут и раздел резервов безупречны на мобильном (проверка на реальном экране).
- [ ] Интеграционные тесты покрывают все новые сообщения шины.

## Открытые вопросы перед стартом

**Требуют решения заказчика:**

1. Срок резерва: единый или индивидуальный по партнёру? Стартовое значение
   (предлагаем 48 ч конфигом).
2. Участвует ли резервный заказ в лимитах дебиторки (предлагаем — нет, «заказ — это план»).

**Закрываем сами при реализации:**

3. Редактирование в v1 — только уменьшение/удаление строк; добавление позиций (рост суммы
   резерва, риск по остаткам) — отдельным решением после обкатки.
4. Именование события отмены (`order.deleted` vs `order.cancelled`), семантика полной
   замены `items`, идемпотентность — решается в топике res-01.
5. Кто снимает резерв по таймауту — сайт командой или 1С своим таймером — решается в топике res-01.
