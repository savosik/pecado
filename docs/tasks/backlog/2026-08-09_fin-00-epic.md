**Приоритет:** высокий
**Создано:** 2026-08-09
**Скоуп зафиксирован:** 2026-08-09 — см. «Границы»
**Статус:** волна 0 закрыта — контракт согласован и опубликован (спека 16.0.0).

**Карточки:** `fin-01` … `fin-11`

## Суть в одном абзаце

Сайт перестаёт **считать** деньги и начинает их **показывать**. Сегодня долг клиента выводится
на сайте из графа документов (реализации × платежи × расшифровки × график оплат), и этот граф
систематически расходится с 1С, потому что 1С гасит долг ещё авансами по заказам, зачётами и
корректировками, которых сайт не видит. Вместо графа — **плоский полиморфный реестр движений**,
который присылает 1С, и из которого любой ответ получается суммированием.

## Почему это не очередной патч

Каждая предыдущая итерация усложняла счётную машину и не закрывала корень:

| Версия | Что сделали | Чем кончилось |
|---|---|---|
| v15.11.0 | Платежи + расшифровка на реализации | Вместило **28,6 %** денег |
| v15.16.0 | Расшифровка расширена на заказы и «прочее» | Не помещалось **111 872 793,21 ₽ (71,4 %)** |
| 2026-08-09 | Зачёт авансов заказа в график (FIFO на сайте) | У клиента **5,53 млн ₽** просрочки против **478 тыс ₽** по 1С |
| 2026-08-09 | Деньги в ЛК скрыты флагом `CABINET_FINANCE_ENABLED=false` | «Показывать клиенту завышенный долг хуже, чем не показывать никакого» |

Плюс в MCP/CRM API пришлось навесить `meta.notes`: «это НЕ долг клиента, отвечайте по
`payment.balances`». Когда документация к API просит агента не верить самому API — модель
кончилась.

**Корень:** сайт не может знать то, что знает только 1С. Дальше усложнять бессмысленно.

## Границы скоупа

Что **входит**:

| № | Требование |
|---|---|
| 1 | 1С шлёт **движения регистра взаиморасчётов** — источник истины по деньгам |
| 2 | 1С шлёт **остаток по каждой плановой строке**; сайт не раскладывает платежи FIFO |
| 3 | История: сальдо на **01.01.2026** + движения после + сверенный checkpoint на **01.07.2026** |
| 4 | **Соглашения** появляются как сущность (договоров в базе фактически нет — 2,2 %) |
| 5 | Клиент видит: сколько должен сейчас, дошёл ли платёж, акт сверки |
| 6 | CRM видит: баланс, оплаты, просрочка, будущий поток по дням, кому звонить |
| 7 | `balance.updated` остаётся **контрольной суммой** для верификации регистра |
| 8 | Мажорная версия спеки **16.0.0** + промт для ИИ-агента на стороне 1С |

Что **сознательно не входит** (и почему):

| Выпилено | Причина |
|---|---|
| ~~Автоблокировка должников на сайте~~ | Данные (`credit_limit`, просрочка) появятся, механизм — отдельной задачей. Блокировка продаж — решение бизнеса, не побочный эффект рефакторинга |
| ~~«Обещанный платёж» от менеджера~~ | Заказчик поправил термин: 1С шлёт **график оплат**. Это рассрочка, которую даём мы, а не обещание клиента. CRM-сущности «обещание» не заводим |
| ~~Разнесение платежа на документы~~ | Заказчик прямо указал: таскать, на какие заказы/реализации разнесён платёж, **не стоит — это путает**. Разнесение выражается движениями регистра |
| ~~Взаимозачёты как отдельная механика~~ | Приезжают обычным движением `adjustment`. Сайт про них не решает |
| ~~Онлайн-эквайринг~~ | Отдельная сущность, по этой шине не ходит (как и сейчас) |
| ~~Сайт публикует что-либо денежное в 1С~~ | Эпик целиком **входящий**. Ни одна схема `*.to_erp.json` не меняется |

## Принципы

**1. Источник истины по деньгам — 1С, всегда.** Сайт не выводит, не досчитывает и не
«исправляет» присланное. Расхождение регистра с `balance.updated` — повод написать в лог и
показать баннер, а не повод посчитать по-своему.

**2. Строка регистра самодостаточна.** Реквизиты документа (`document_number`, `document_date`,
`document_kind`) дублируются прямо в строке рядом с полиморфной связью. Строка обязана читаться,
даже если документа на сайте ещё нет. Это снимает весь класс багов «приехало раньше документа»,
на которые сейчас навешаны четыре трейта-доклейщика.

**3. `SUM(amount)` = баланс, без единого `CASE`.** `amount` знаковый, дебет/кредит — generated.
Иначе каждый SQL-запрос ИИ-агента на MCP превращается в упражнение по бухучёту.

**4. Знак — как в 1С.** «`+`» увеличивает баланс в пользу клиента, «`−`» — в нашу. Совпадает с
действующим `contractor_balances.current_balance` («отрицательный = долг»), поэтому существующие
экраны и инструкции MCP не переворачиваются.

**5. Курс валюты фиксируется на дату операции.** Сейчас `PaymentForecastService` сводит валюты по
*текущему* курсу — акт сверки от этого меняется задним числом.

**6. Волны 1–2 аддитивны.** Новые таблицы и приём ничего не ломают, старый путь продолжает
работать. Переключатель чтения один — `SETTLEMENTS_LEDGER_ENABLED`. Удаление старого — только
волна 4, после чистой сверки на проде.

**7. Промт для 1С уходит до фиксации контракта.** Мажорную спеку дорого переделывать, если 1С
чего-то не сможет. Поэтому `fin-01` идёт раньше `fin-02`.

## Схема данных

> **Уточнено 2026-08-09 по ответу 1С.** Договоров в базе фактически нет (75 штук, 97,8 %
> реализаций без договора) — их место занимают **соглашения** (5 102, покрытие 100 %).
> Ось акта сверки — **контрагент × организация × валюта**, а не договор. Подробности —
> в разделе «Уточнения по ответу 1С».

```
agreements                            ← НОВОЕ: соглашения с клиентами (было: contracts)
  id, uuid (1С, unique), user_id, company_id, organization_id,
  number, date, name, currency_code, settlement_procedure,
  credit_limit, deferral_days, status,
  revision, erp_created_at, erp_updated_at, timestamps

settlement_entries                    ← НОВОЕ: регистр взаиморасчётов
  id, uuid (1С, unique), revision, source (erp|crm),
  nature (fact|plan), type,
  date, valid_until,
  user_id, company_id, organization_id, agreement_id,
  partner_uuid, contractor_uuid, organization_uuid, agreement_uuid, agreement_name,
  contract_uuid, contract_name,       ← договор: поля, не сущность (2,2 % покрытия)
  settlement_object_kind, settlement_object_uuid, settlement_object_name,
                                      ← ОбъектРасчетов: измерение регистра
  amount (signed), currency_code, amount_rub,   ← amount_rub = СуммаРегл из 1С
  settled_amount,                     ← только для nature=plan, приходит из 1С
  debit  GENERATED AS (GREATEST(-amount, 0)),
  credit GENERATED AS (GREATEST( amount, 0)),
  document_type, document_id,         ← полиморф
  document_uuid, document_kind, document_number, document_date,
  comment, erp_created_at, erp_updated_at, timestamps

settlement_checkpoints                ← НОВОЕ: сверенные контрольные точки сальдо
  company_id, organization_id, currency_code, as_of_date, amount, is_verified
```

~~`contract_balances`~~ **не нужна**: ось сверки — контрагент × организация, а этот разрез
уже существует с v15.8.0 (`contractor_organization_balances`). Четвёртый уровень не появляется.

Типы движений:

| `type` | `nature` | Знак | Что это |
|---|---|---|---|
| `opening_balance` | fact | ± | Начальное сальдо на 01.01.2026 |
| `shipment` | fact | − | Реализация клиенту |
| `payment_in` | fact | + | Поступление средств от клиента |
| `payment_out` | fact | − | Физический возврат денег клиенту |
| `goods_return` | fact | + | Возврат товара по накладной (зачёт брака) |
| `commission_sale` | fact | − | Отчёт комиссионера. **Отбор их не снимает**: после фильтра остаются 29 документов на 66 034 282,63 — полноценный тип, не «на случай» |
| `adjustment` | fact | ± | Взаимозачёт, корректировка задолженности, корректировка реализации |
| `payment_due` | plan | − | Плановый платёж по графику оплат |

**Движений заказа в регистре нет** (круг 2): `ЗаказКлиента` двигает `КОплате` и `КОтгрузке`,
но `Сумма` = 0,00 за весь год. Правило контракта: в `settlement.posted` попадают только движения
с ненулевым `Сумма` — заказы отпадают сами, объём ленты падает с 224 632 до ~139 000 строк.

Формула акта сверки заказчика ложится ровно на `nature='fact'`:
`Начальное сальдо + Оплаты + Возвраты товара − Реализации − Возврат денег` = `SUM(amount)`.

## Edge-кейсы

**Движения**
1. Движение приехало раньше документа → сохраняется, читается по `document_number`/`document_kind`
2. Документ перепроведён в 1С → `settlement.posted` с полным набором строк заменяет прежние
3. Проведение отменено → `settlement.reverted`, вклад документа гасится
4. Повторная доставка того же `uuid` → не задваивает (идемпотентность по `uuid`)
5. Устаревшая ревизия обогнала свежую → отбрасывается `ErpRevisionGuard`
6. Движение без соглашения → `agreement_id = NULL`, группа «Без соглашения». Не теряем
   и не выдумываем. На баланс не влияет: ось сверки — контрагент × организация

**Валюты**
7. Рублёвый эквивалент приходит из 1С (`СуммаРегл`), а не считается курсом на сайте
8. `amount_rub` не пришёл для валютного движения → строка видна в исходной валюте,
   в рублёвые итоги не входит, счётчик таких строк в сводке

**Сверка**
9. `SUM(fact) ≠ contractor_organization_balances` → приоритет у 1С, warning + баннер в CRM
10. Сальдо 01.01 + движения H1 ≠ `settlement.checkpoint` на 01.07 → первое полугодие
    недостоверно; величина расхождения известна, решение по показу H1 принимается явно
11. Регистр пуст, а старая модель показывает долг → чтение **не переключаем**, `fin-06` красный

**Инфраструктура**
12. Новые таблицы → комментарии в БД + `bi:sync-grants`, иначе аналитический MCP их не увидит
13. Первичная заливка 224 632 движений → пачками с паузой, отдельная очередь
14. Знак перепутан на стороне 1С → `settlements:verify` ловит первым же прогоном

## Уточнения по ответу 1С (2026-08-09)

Сторона 1С ответила замерами боевой базы. Ответ подтвердил замысел и поменял четыре места.

**Подтверждено:**

- движения выгружаются по документу-регистратору — выполнимо;
- **`settled_amount` есть в 1С готовым** — `РегистрНакопления.РасчетыСКлиентамиПоСрокам`,
  ресурсы `Долг` и `Предоплата`. Самодельный FIFO не нужен, ключевой риск эпика снят;
- взаимозачёты и корректировки идут отдельными движениями;
- объём за 2026 — **224 632 строки по 17 607 документам**.

**Главная находка — диагноз подтверждён цифрой.** `ЗаказКлиента` даёт **85 249 строк, 38 %
всех движений**, и его не было ни в нашем списке, ни в старой модели. Это ровно те предоплаты
по заказам, которые не помещались в 111,9 млн ₽.

**Изменено:**

| Было | Стало | Причина |
|---|---|---|
| Договоры как сущность | **Соглашения** (`agreements`) | 75 договоров против 5 102 соглашений; 97,8 % реализаций без договора |
| Акт сверки по договору | По **контрагент × организация × валюта** | Соглашение — не измерение регистра, точность сальдо не гарантирована |
| `contract_balances` (4-й уровень) | **Не нужна** | Ось сверки уже покрыта `contractor_organization_balances` |
| `settlement_kind` в договоре | `settlement_procedure` в соглашении | Порядок расчётов задаётся соглашением |
| — | `settlement_object_*` | `ОбъектРасчетов` — измерение регистра, не учли |
| `exchange_rate` в движении | `amount_rub` из `СуммаРегл` | Уже посчитано учётом, не разъедется с отчётами 1С |
| Отсечка 01.01.2026 | 01.01.2026 **+ checkpoint 01.07.2026** | Даты запрета — 31.03/30.04/30.06; 01.01 не сверена |
| Список документов | Переписан | Нет `КорректировкаДолга`, `СписаниеЗадолженности`, `ОтчетКомиссионераОПродажах`; кассовых ордеров в 2026 — ноль |

**Решение по точке отсчёта.** Берём оба сальдо: несверенное на 01.01.2026 как начало ленты
и сверенное на 01.07.2026 как контрольную точку. Сумма «01.01 + движения H1» обязана сойтись
с checkpoint — расхождение становится измеримым вместо скрытого. Это тот же принцип, что
и во всём эпике: расхождение — сигнал, а не повод считать по-своему.

**Решение по оси сверки.** Соглашение 1С честно пометила как не-измерение: при изменении
задним числом группировка разъедется. Поэтому соглашение — фильтр и группировка внутри акта,
а ось — регистровый срез контрагент × организация × валюта. Договор принимаем полями
(`contract_uuid`, `contract_name`), справочник на 75 записей не заводим.

## Результаты круга 2 (2026-08-10)

1С ответила и **исправила собственную ошибку из круга 1**: движения `ЗаказКлиента` не «те самые
предоплаты», а нулевые по `Сумма`. Решение «не начинать заливку до ответа Б» окупилось —
трактовка была бы противоположной верной.

Закрыто:

| Вопрос | Ответ |
|---|---|
| **А.** Ресурс баланса | `Сумма`. Остальные четыре — плановые |
| **Б.** Движения заказа | **План.** `Сумма` = 0,00 за весь год. В ленту не отдаются |
| **В.** Регл или Упр | Совпадают до копейки (406 550 169,26), валютных договоров нет. Берём `СуммаРегл` |
| Порядок расчётов | `orders` (3 972), `advance_orders_debt_invoices` (962), пусто (167), `settlement_documents` (1). Значения «по договору» нет вовсе |
| Аналитика в шапке | **Нельзя.** 33 % документов имеют несколько объектов расчётов → переносим в строку |
| `settlement.checkpoint` | Пришлют, и при каждом закрытии периода |
| Отмена задним числом | `reverted` / `posted` с полным составом; дата запрета не мешает |
| Полнота документов | **Одиннадцать видов**, а не шесть. «Корректировка задолженности», а не «долга» |
| Сроки | 3–4 недели остаются в силе |

**Найдено при сверке их цифр с нашими — новый блокер.** По документам числа сходятся, по деньгам
поступления расходятся вдвое: 1С 156 965 966,64 против сайта 84 956 456,35 при 2 845 и 2 689
документах. Реализации сходятся (1,06), списание совпадает до копейки (1,00), поступления —
**1,85**. Похоже, `Сумма` в их замерах суммируется по модулю, без учёта `ВидДвижения`: платёж
даёт и приход, и расход одной суммы. Если так, знак движения обязан приезжать явно, иначе баланс
будет неверным у всей базы, и валидация схемы этого не поймает.

**Гипотеза «отчёты комиссионера = наши 111,9 млн» снята.** Комиссионеры — это маркетплейсы
(Wildberries, Ozon и подобные), и на сайт они не выгружаются вообще: ни контрагенты, ни
документы. Сайт — B2B-кабинет оптовых клиентов. Значит 111 674 523,87 по отчётам комиссионера
к нам отношения не имеют, а совпадение величин случайно. Наши 111 872 793,21 — вообще цифра
из замера самой 1С, на сайте этих денег никогда не было.

**Следствие для контракта, важнее перечня типов документов:** отбор движений должен идти
**по контрагенту**, тем же правилом, что уже применяется к реализациям, заказам и платежам.
Тогда комиссионные документы отпадут сами, отбор останется согласованным с `balance.updated`,
и новый клиент подхватится автоматически. Перечислять виды документов как фильтр — тупик.

Расхождение по поступлениям (1,85) объяснилось **отсутствием отбора в замере**, а не двойным
счётом: 1С прислала движения одного платежа — одна строка `Расход`, пары приход/расход нет.
После отбора реализации сходятся до документа (7 360 против наших 7 358).

## Результаты круга 3 (2026-08-10)

| Вопрос | Ответ |
|---|---|
| **Г.** Двойной счёт | Нет. Одна строка `Расход` на платёж |
| **Д.** Знак | **В 1С обратный нашему**: их `Приход` = долг вырос = наш минус. Знак применяет 1С по нашей таблице типов; `ВидДвижения` отдаётся дополнительным полем для разбора |
| **Ж.** Отчёт комитенту | Расчёты с поставщиком, отбор снимает полностью. Код не заводим |
| **З.** Отбор | Список `КонтрагентыИсключения` (РВБ, Яндекс.Маркет, Маркетплейс, Яндекс.Лавка) + признак «Собственный» у партнёра + контурные фильтры |
| **Е.** Обороты со знаком и отбором | Итого −4 726 058,58 по 1С = **+4,73 млн в нашем знаке** |
| Ключ аналитики в строку | Согласны, и `partner_uuid` тоже. Правило: **всё из ключа аналитики живёт в строке** |

**Отбор НЕ убирает комиссионеров:** после него остаются 29 документов на 66 034 282,63 —
это не «редкие клиенты на комиссии», а сопоставимая с реализациями величина.

**Найдено при разборе — рассогласование отборов.** У 67 контрагентов есть баланс на сайте
и **ни одного документа**, суммарно −3 303 630,96. Среди них РВБ ООО (−3 060 928) и
ЯНДЕКС МАРКЕТ ООО (−83 660) — оба в списке `КонтрагентыИсключения` самой 1С. То есть
`balance.updated` их присылает, а документы отбор не пропускает.

Сегодня это терпимо — баланс просто число. После перехода на регистр акт сверки обязан
объяснять баланс, и 3,3 млн станут красными в первом же прогоне `settlements:verify`.
Требование: **один отбор на движения, баланс и сальдо.** Приезжает баланс — обязаны приезжать
движения; исключён контрагент — исключён везде.

**Решение по комиссионерам:** берём всё, что проходит отбор по контрагенту. Резать по типу
документа нельзя — если клиент вдобавок торгует по комиссии, его акт сверки перестанет
сходиться с его же балансом.

## Результаты круга 4 (2026-08-10)

**Комиссионеры опознаны.** Из 29 документов на 66 034 282,63: «ИНТЕРНЕТ РЕШЕНИЯ ООО» — это
**Ozon**, 17 документов на 64,6 млн (98 %); «Екатеринбург Яблоко» — розничная сеть, 1,3 млн;
и только «Мультимедийный мир» (101 249,50) — живой клиент на комиссии. Наши 7 строк на 77 тыс
по нему же — порядок совпал. 1С вносит Ozon и Золотое Яблоко в исключения.

**67 осиротевших балансов — наш артефакт, не дефект 1С.** При внедрении сначала залили клиентов
и балансы, потом стали заливать остальное и отфильтровали контрагентов постфактум. Код отбора
у 1С в порядке. Чистится разово по списку исключённых контрагентов, который запросили у 1С:
свой критерий («баланс есть, документов нет») ошибочен — документы могут отсутствовать из-за
контурных фильтров у нормального клиента.

`balance.deleted` понижено до необязательного: событие пригодится, когда клиента будут выводить
из обмена штатно, но схемы не блокирует.

**Яндекс.Лавка — живой клиент, даркстор, покупает оптом.** Её надо **убрать** из
`КонтрагентыИсключения`, а не добавлять филиалы. 17 реализаций и 17 заказов — законные.

**🐛 Найдена причина, которую 1С не смогла объяснить.** У партнёра «Яндекс.Лавка ООО, г. Москва»
**три записи контрагента с одним ИНН 9718101499** и разными UUID: документы (17 реализаций)
едут на id=477, а баланс приходит на id=487, где документов нет вовсе. Матчинг у нас идёт
по `uuid` в приоритете (правило v13.2), поэтому разные UUID дают разные Company.

Масштаб проверен: пар «партнёр + ИНН» с несколькими контрагентами — девять, реально разъехались
документы и баланс — только у Лавки. Системной проблемы нет, но **для v16 это критично**:
движения лягут на одну запись, `settlement.checkpoint` на другую, и `settlements:verify`
покажет красное по живому клиенту.

**Исключать маркетплейсы по партнёру, а не по контрагенту** — остаётся в силе как упрощение:
у Ozon 4 юрлица, у Золотого Яблока 2, внесение одного головного оставит филиалы.

## Результаты кругов 5–6 (2026-08-10) — контракт закрыт

**Все вопросы закрыты, блокеров нет.** Итог шести кругов:

| Тема | Решение |
|---|---|

| Оплата по заказу | Новое поле шапки `document_settled_amount` — авторитетная сумма по заказу целиком |
| Контрагенты Лавки | Дубли. Схлопываем на `48cb2c6c-4e44-11ef-8e63-ce9830629797` (17 реализаций) |

| Ozon | Исключаем **по трём ИНН `7704217370`**, не по партнёру |
| Золотое Яблоко | По партнёру можно — состав проверен, посторонних нет |

**🐛 Партнёр 1С ≠ пользователь кабинета.** У партнёра «Интернет Решения ООО» одиннадцать
контрагентов, из них Ozon только три. Среди остальных — **«ИП Ракович Владимир Сергеевич»:
223 реализации, 163 заказа, баланс 56 089, активен**. Исключение по партнёру убило бы живого
клиента. У нас он отдельный аккаунт с двумя контрагентами.

Правило в контракт: **отбор по партнёру применяется только там, где состав контрагентов
проверен обеими сторонами.** По умолчанию отбор идёт по контрагенту.

### Правило разнесения оплаты заказа — записать в код и в правила

> Оплаченная сумма заказа берётся из `document_settled_amount` и **никогда не вычисляется**.
> Разнесение по этапам графика — только для отображения календаря, помечается производной
> величиной, **в баланс и сверку не входит**.

Это не возврат к прежнему FIFO: тот раскладывал платежи **между документами** и накапливал
ошибку (5,53 млн вместо 478 тыс). Здесь авторитетное число делится **внутри одного заказа**
по одному-двум этапам; итог по заказу верен по построению, неточной может быть только дата.
