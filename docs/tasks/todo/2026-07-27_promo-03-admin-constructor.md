# Промо 03 — Конструктор правил в админке

**Приоритет:** высокий
**Создано:** 2026-07-27
**Roadmap:** [docs/promo-constructor-roadmap.md → Волна 1](../../promo-constructor-roadmap.md)
**Зависит от:** [promo-01-foundation](2026-07-27_promo-01-foundation.md), [promo-02-engine](2026-07-27_promo-02-engine.md)

## Контекст

Существующий редактор акции —
[resources/js/Admin/Pages/Promotions/Edit.jsx](../../../resources/js/Admin/Pages/Promotions/Edit.jsx)
(222 строки): одна форма на `useForm`, отправка через `FormData` + `router.post` с
`_method: PUT`, потому что там загрузка картинок (list-item, detail-desktop, detail-mobile,
галерея). Вкручивать в эту же форму редактор JSON-правил не нужно — форма станет
неуправляемой, а любая ошибка валидации правила будет ронять сохранение картинок.

**Решение:** правила — отдельный раздел `/admin/promotion-rules` со своими CRUD-страницами.
Со страницы акции — блок «Правила акции» со списком связанных правил и кнопкой «Добавить
правило» (уходит в отдельный раздел с предзаполненным `promotion_id`).

## Маршруты

В [routes/admin.php](../../../routes/admin.php) рядом с блоком `promotions.*` (строки 565–580),
тем же стилем — группы по правам:

```
/admin/promotion-rules                    index    promotion-rules.view
/admin/promotion-rules/create             create   promotion-rules.create
/admin/promotion-rules                    store    promotion-rules.create
/admin/promotion-rules/{rule}/edit        edit     promotion-rules.edit
/admin/promotion-rules/{rule}             update   promotion-rules.edit
/admin/promotion-rules/{rule}             destroy  promotion-rules.delete
/admin/promotion-rules/{rule}/preview     preview  promotion-rules.view   (POST)
/admin/promotion-rules/{rule}/rebuild     rebuild  promotion-rules.edit   (POST)
```

Пункт меню — в [resources/js/Admin/config/menuConfig.ts](../../../resources/js/Admin/config/menuConfig.ts),
в ту же группу, где «Уценка» и «Справочник дефектов» (строки 100–101), либо в раздел
маркетинга рядом с акциями — выбрать по факту при реализации, но **не создавать новую
группу верхнего уровня** ради одного пункта.

## Страницы

### Список `/admin/promotion-rules`

Через существующий `DataTable` ([Admin/Components/DataTable.jsx](../../../resources/js/Admin/Components/DataTable.jsx)),
как в остальных разделах. Колонки:

| Колонка | Содержимое |
|---|---|
| Название | + ссылка на акцию-лендинг, если привязана |
| Режим | бейдж «Только показ» (серый) / «Выдаёт» (зелёный) |
| Статус | «Активно» / «Выключено» / «Не начата» / «Завершена» — вычисляется по периоду |
| Период | «с 01.08.2026 по 31.08.2026», прочерк если без ограничений |
| Условие | человекочитаемая строка: «Сумма акционных позиций ≥ 150 000 ₽» |
| Награда | «Lovense Lush 4 × 1 за 0 ₽» |
| Выдано | счётчик выданных промо-позиций (волна 2; до неё — прочерк) |

Фильтры: поиск по названию, статус, режим, привязанная акция.

### Форма создания/редактирования

Вкладки (`Tabs` из `@/components/ui/*` — **не** из `@chakra-ui/react` напрямую,
см. `.claude/rules/chakra-ui-components.md`; если сниппета нет, ставить через
`npx @chakra-ui/cli snippet add tabs`):

**1. Основное** — название, привязка к акции (`SelectRelation`), режим (`RadioGroup`:
«Только показывать» / «Выдавать промо-позиции»), активность (`Switch`), период
(два поля даты), приоритет, «можно совмещать с другими акциями» (`Switch`).

Режим «Выдавать» до завершения волны 2 должен быть **задизейблен** с подсказкой
«Выдача промо-позиций появится после подключения складского учёта акций». Это не
косметика: включённый режим `issue` без карточек 07–09 создаст правило, которое ничего не
делает, и маркетолог решит, что всё сломано.

**2. Условия** — конструктор списка условий. Каждое условие — карточка:

- селектор товаров: переиспользовать
  [`ProductSelector`](../../../resources/js/Admin/Components/ProductSelector.jsx) (mode `multi`),
  [`CategoryTreeSelector`](../../../resources/js/Admin/Components/CategoryTreeSelector.jsx),
  [`TagSelector`](../../../resources/js/Admin/Components/TagSelector.jsx),
  `MultiEntitySelector` для брендов, чекбоксы для `ErpPromotion` («Новинки», «Хиты»,
  «Ликвидация») и переключатель «вся корзина»;
- «Считать»: сегментированный выбор «Количество штук» / «Сумму»;
- порог: числовое поле с суффиксом «шт.» или «₽» в зависимости от выбора;
- под условием — живая подсказка «Сейчас под условие подходит N товаров» (запрос к
  материализованному списку).

Переключатель «Выполнить все условия / Достаточно любого» — над списком, только если
условий больше одного.

**3. Награды** — список наград. Поля карточки награды:

- «Что выдаём»: конкретный товар (`ProductSelector` mode `single`) или «Клиент выбирает
  из списка» (mode `multi`, минимум 2 товара);
- количество;
- **цена промо-позиции** — числовое поле, ₽, по умолчанию 0. Подсказка под полем:
  «0 — подарок. Можно указать любую цену: 0,01 ₽, 10 ₽, 40 ₽ — клиент оплатит её в
  отдельном заказе»;
- вид: «Подотчётная (выписывается в накладной)» / «Пробник (не выписывается)» —
  `RadioGroup` с пояснениями прямо в подписи, потому что различие неочевидно;
- склад-источник (`SelectRelation` по складам; для пробников — только склады с флагом
  `is_promo_sample`, до волны 3 список будет пуст, и это надо явно сказать текстом);
- кратность: «Один раз при достижении порога» / «На каждые …» + поле `per_value` + поле
  «но не более … раз» (обязательное, с валидацией);
- «Клиент может отказаться» (`Switch`) — **скрывать** при цене 0.

**4. Аудитория и лимиты** — регионы (`RegionSelector`, уже используется в акциях),
конкретные клиенты, менеджеры, каналы (чекбоксы «Сайт», «API»), лимит на клиента, общий лимит.

**5. Предпросмотр** — см. ниже.

### Предпросмотр — обязательная часть, не украшение

Форма: поле «ID корзины» или «ID заказа» → кнопка «Проверить» → POST на `preview` →
результат прогона `PromotionEngine` по этой корзине.

Показывать:
- **сработало / не сработало** — крупно;
- фактическое значение агрегата против порога: «Сумма акционных позиций: 138 400 ₽ из
  150 000 ₽, не хватает 11 600 ₽»;
- что было бы выдано: товар, количество, цена, склад;
- **причину, по которой награда не выдана** — из `blocked` движка: «нет остатка на складе
  “Москва реклама”», «исчерпан лимит клиента», «правило ещё не началось», «канал не
  разрешён».

Без этого экрана маркетолог не сможет отличить «правило настроено неверно» от «товара нет
на складе», и разбираться будут разработчики. Клиенту причины не показываются никогда
(решение п. 5 в roadmap), поэтому админка — единственное место, где они видны.

### Блок на странице акции

В [Promotions/Edit.jsx](../../../resources/js/Admin/Pages/Promotions/Edit.jsx) и
[Show.jsx](../../../resources/js/Admin/Pages/Promotions/Show.jsx) — карточка «Правила акции»:
список связанных правил (название, режим, статус, условие одной строкой), ссылки на
редактирование, кнопка «Добавить правило». **Внутрь `FormData`-формы ничего не добавляем** —
блок рендерится вне `<form>`, чтобы не задеть загрузку картинок.

## Бэкенд

`App\Http\Controllers\Admin\PromotionRuleController` в стиле соседних контроллеров
(наследует `AdminController`, трейт `RedirectsAfterSave`, Inertia-ответы, пагинация
`min(max($perPage,5),100)`).

Валидация — через `PromotionRuleSchemaValidator` из карточки 01, ошибки возвращаются в
формате Inertia-ошибок и подсвечиваются у конкретных полей формы, а не одним общим тостом.

Человекочитаемое описание условия/награды (для списка и предпросмотра) —
`App\Services\Promotion\PromotionRuleDescriber`, чтобы одна и та же формулировка
использовалась в админке, а позже — в корзине и на лендинге.

## Нюансы

- **Весь интерфейс на русском**, включая ошибки валидации и пустые состояния
  (`.claude/rules/ru.md`).
- Chakra — только через `@/components/ui/*`, кроме layout-примитивов `Box`, `Flex`,
  `Stack`, `Text`, `Heading`, `SimpleGrid`.
- Тосты — через существующий `toaster` (`@/components/ui/toaster`), формулировки в стиле
  соседних страниц: заголовок + короткое описание.
- Кнопка «Пересчитать участников» (вызов `rebuild`) — на форме и в списке; после
  массового изменения категорий материализованный список устаревает, и у админа должен
  быть способ обновить его без ожидания ночной команды.
- Удаление правила — через существующий `ConfirmDialog`, с явным предупреждением, если
  правило уже выдавало промо-позиции.

## Критерии готовности

- [ ] CRUD правил работает, права `promotion-rules.*` проверяются на каждом маршруте.
- [ ] Конструктор условий и наград собирает корректный JSON; ошибки валидации
      показываются у соответствующих полей по-русски.
- [ ] Режим «Выдавать промо-позиции» задизейблен с поясняющей подсказкой.
- [ ] Предпросмотр по ID корзины показывает агрегат, порог, недостачу, выдаваемые позиции
      и причину блокировки.
- [ ] Поле «Клиент может отказаться» скрыто при цене 0.
- [ ] Для пробников список складов пуст и сопровождается пояснением (до волны 3).
- [ ] Блок «Правила акции» на странице акции не ломает сохранение картинок и галереи.
- [ ] Feature-тесты: доступ по правам, создание правила, отказ при невалидном JSON,
      предпросмотр.
- [ ] Проверено вручную на десктопе и на узком экране — таблицы админки не уезжают.
