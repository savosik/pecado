# US-18 График оплат по реализациям (протокол v15.12.0)

**Приоритет:** высокий
**Исполнитель:** savosik
**Создано:** 2026-08-07

## Описание

Продолжение US-17. В прошлом релизе на сайт приехал **факт** оплаты (очередь
`erp_in.payments`, разнесение по реализациям, статус оплаты). Теперь приезжает **план** —
табличная часть «Правила оплаты» реализации из 1С.

Результат для пользователей:

- **клиенту** — «Календарь оплат» в личном кабинете: когда и сколько он должен заплатить;
- **менеджеру** — «Календарь поступления денег» в CRM: план по графику и факт по дням.

Новой очереди нет: график приезжает массивом `payment_schedule` внутри
`shipment.created` / `shipment.updated` (`erp_in.documents`). График — часть документа,
и отдельная очередь создала бы гонку «график приехал раньше реализации».

## Что сделано

**Контракт (spec-first):**

- JSON Schema — `payment_schedule` в `shipment.created.json` и `shipment.updated.json`.
  Обязательны только `due_date` и `amount`; опционально `percent`, `line_number`,
  `term_days`, `basis`/`basis_name`, `stage`/`stage_name`, `order_uuid`.
- AsyncAPI `15.11.0` → **`15.12.0`**, схема `ShipmentPaymentScheduleLine` + пример payload-а.
- MkDocs: раздел «График оплаты» в `rules/shipments.md`, changelog `[15.12.0]`
  с блоком «Требуется от 1С».

**Данные:**

- `shipment_payment_schedules` — строки графика (FK на реализацию, индекс `(due_date, shipment_id)`).
- `shipments.payment_due_date` — ближайшая непогашенная плановая дата (денормализация
  для фильтров CRM, потокового экспорта и MCP-агента).

**Логика:** `PaymentScheduleService` — единственный писатель `paid_amount` строк и
`payment_due_date`. Раскладка FIFO по плановой дате: 1С разносит платёж по реализациям,
а не по строкам графика, поэтому связку строит сайт. Пересчёт — полная функция от
состояния БД, не инкремент. Запускается из обработчиков реализаций и из
`PaymentAllocationService` (изменился факт — переехал план). Страховочная сеть —
`php artisan payments:recalculate`.

**Интерфейсы:** вкладка «Календарь» в `/cabinet/payments` и `/crm/payments`, блок
«График оплаты» в карточке реализации (кабинет, CRM, админка), MCP-операция
`payment.schedule`, правило про план ≠ факт в инструкциях аналитического MCP.

**Тесты:** 324 зелёных в затронутых наборах, из них новые —
`PaymentScheduleServiceTest` (15), `PaymentScheduleIntegrationTest` (5, сквозь `ErpIncomingJob`),
плюс дополнения в `HandleShipmentCreated/UpdatedTest`, `PaymentsCabinetTest`,
`PaymentJournalTest`, `PaymentOperationsTest`.

## Доставка

1. `git push origin dev` → `Deploy to Dev`. Убедиться, что run создался
   (`gh run list --branch dev --limit 3`): потерянный вебхук задним числом не проигрывается.
2. Проверка на dev:
   ```bash
   curl -s https://dev.pecado.ru/docs/erp/spec.yaml | head -5              # version: 15.12.0
   curl -s https://dev.pecado.ru/docs/erp/spec.yaml | grep -c payment_schedule
   ```
   Глазами: `/cabinet/payments` → вкладка «Календарь», `/crm/payments` →
   «Календарь поступлений», `/docs/erp-guide/rules/shipments/`.
3. Релиз: `git push origin dev:main` (approve не настроен — прод уедет автоматически).
4. **Дождаться 200 на pecado.ru**: упавший прод-деплой оставляет сайт под maintenance
   до ручного `artisan up`.

### Что произойдёт автоматически

- `migrate --force` — две миграции: `shipment_payment_schedules`, `shipments.payment_due_date`.
- **Только на prod:** `bi:sync-grants` — доступ `bi_agent` к новой таблице, иначе
  MCP-агент менеджеров её не увидит.
- Новых очередей и воркеров нет — `worker.conf` не менялся.

## Требуется от 1С

- **Отсутствие ключа `payment_schedule` ≠ пустой массив.** Ключа нет — сайт не трогает
  сохранённый график; `[]` — очищает. Та же ловушка, что с `allocations` в 15.11.0.
- График присылать **целиком**, а не досылать изменившиеся строки.
- `due_date` обязателен — строка без даты пропускается.
- `basis` и `stage` присылать **латинскими кодами** дополнительно к русским
  наименованиям: на коды опирается логика, русский текст меняется с настройками учёта.
- **Для исторических документов нужна повторная выгрузка `shipment.updated`** — иначе
  календарь будет пустым до следующего перепроведения реализации в 1С.

## Дальше по теме (отдельной задачей)

- **График оплат по заказам** (предоплата по неотгруженному) — в этой версии не передаётся.
- Уведомления клиенту о приближающейся дате оплаты — на существующем механизме
  подписок (`MAIL_FEATURE_ENTITY_SUBSCRIPTIONS`).
- Не смешивать план с `contractor_balance_overdue_details`: там факт просрочки от 1С,
  здесь план. Расхождение имеет смысл показать менеджеру, но не «чинить» автоматически.
