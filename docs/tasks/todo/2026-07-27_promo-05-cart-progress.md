# Промо 05 — Прогресс акции в корзине («доберите на X»)

**Приоритет:** средний
**Создано:** 2026-07-27
**Roadmap:** [docs/promo-constructor-roadmap.md → Волна 1](../../promo-constructor-roadmap.md)
**Зависит от:** [promo-02-engine](2026-07-27_promo-02-engine.md)

## Контекст

Финал волны 1: движок работает, правила настраиваются, но промо-позиции не выдаются. В
корзине показываем **только информацию** — насколько клиент близок к акции. Это самая
ценная часть волны с точки зрения продаж и одновременно способ обкатать движок на реальных
корзинах, ничем не рискуя.

Устройство корзины, которое надо учитывать:

- [Cart/Index.jsx](../../../resources/js/Pages/User/Cart/Index.jsx) (509 строк) разделяет
  `items` и `defectItems` по `item_type` (строки 33–34), считает `defectTotals` отдельным
  `useMemo` (строка 96) и прокидывает их в `CartTable` и `CartSummary` **отдельными
  пропсами** — потому что уценка «не живёт в store-агрегации»
  ([CartTable.jsx:191](../../../resources/js/Pages/User/Cart/CartTable.jsx#L191),
  [CartSummary.jsx:45](../../../resources/js/Pages/User/Cart/CartSummary.jsx#L45)).
- Количества — оптимистичные, в zustand-сторе
  ([useCartStore.js](../../../resources/js/stores/useCartStore.js)) с debounce перед
  отправкой (строки 272–292 для товаров, 423–433 для уценки).

Из этого следует главное ограничение: **прогресс, посчитанный на сервере, будет отставать
от того, что клиент видит в полях количества.** Нужен явный механизм синхронизации.

## Механика обновления

Новый эндпоинт `GET /api/cart/promotions` (рядом с `/api/cart/summary` в
[routes/user.php:95](../../../routes/user.php#L95)) → `PromotionEngine::evaluate()` по
активной корзине → `applied` (пока пустой, режим `info`) + `nearMiss`.

Вызов из стора — **тем же debounce-механизмом**, что и синхронизация количеств, но с
отдельным общим таймером (не по товару): после того как отработал любой
`set-product-quantity` / `set-defect-quantity` / bulk, дёргаем пересчёт промо один раз.
Не делать отдельный запрос на каждое изменение количества — при long-press на «+» это
десятки запросов.

Пока запрос в полёте — показывать предыдущее значение приглушённым (`opacity`), не
скелетон: мигающий блок над корзиной раздражает сильнее, чем слегка устаревшее число.

## Что показываем

Блок «Акции» над таблицей корзины (или под тулбаром — уточнить на ревью макета), по
карточке на каждое правило из `nearMiss`:

```
🎁  Lovense: Lush 4 в подарок
    Наберите акционных позиций ещё на 11 600 ₽ — и получите Lush 4 в подарок
    [███████████░░░░░░]  138 400 из 150 000 ₽
    Показать акционные товары →
```

- Прогресс-бар (`Progress` из `@/components/ui/*`).
- Формулировка — из `PromotionRuleDescriber` (карточка 03), чтобы текст в админке, корзине
  и на лендинге был один и тот же.
- «Показать акционные товары» ведёт в каталог с фильтром «Участвует в акции» (карточка 04)
  либо на лендинг акции, если правило к ней привязано.
- Когда порог достигнут — карточка меняется на «Условия акции выполнены» с пометкой
  **«промо-позицию добавит менеджер»** (в волне 1 автоматической выдачи нет, и обещать её
  нельзя).

## Нюансы

- **Ничего не показываем, если клиент не трогал акционные товары.** Иначе корзина
  превратится в рекламный щит из десяти акций. Порог показа — движок отдаёт `nearMiss`
  только при ненулевом агрегате (карточка 02, п. 10); фронт дополнительно ограничивает
  число карточек (2–3, остальные — за «ещё N акций»).
- **Про блокировки молчим.** `blocked` (нет остатка, лимит исчерпан) в ответ этого
  эндпоинта не попадает вовсе — это решение зафиксировано в roadmap, и утечка таких
  сообщений клиенту недопустима.
- **Гости.** Корзина доступна авторизованным; если блок будет виден кому-то без цен,
  скрывать суммы и показывать только количественные пороги.
- **Мобильная версия.** Корзина на мобиле рисуется карточками
  ([CartMobileCard.jsx](../../../resources/js/Pages/User/Cart/CartMobileCard.jsx),
  [CartDefectMobileCard.jsx](../../../resources/js/Pages/User/Cart/CartDefectMobileCard.jsx)).
  Блок акций должен быть компактным: одна строка текста + бар, без «Показать товары» в
  отдельной строке.
- **Несколько корзин.** У пользователя их может быть несколько
  (`getOrCreateActiveCart`, переключение через `CartManagerDialog`). Прогресс считается
  **по активной корзине**, и при переключении обязан пересчитаться.
- **Никаких тяжёлых эффектов.** Только прогресс-бар и смена текста; анимации переливания,
  конфетти и подобное не добавлять (см. `feedback_ui_effects_minimal` — пакет «вау-фишек»
  уже отклонялся).
- **Импорт заказа.** После `importOrder` / `importOrderFile` корзина меняется целиком —
  не забыть дёрнуть пересчёт промо (эти действия идут мимо debounce количеств).

## Критерии готовности

- [ ] Эндпоинт `/api/cart/promotions` отдаёт `nearMiss` по активной корзине; feature-тест
      на авторизацию и на чужую корзину.
- [ ] Пересчёт вызывается один раз после серии изменений количества, а не на каждое
      нажатие (тест: 10 быстрых кликов → один запрос).
- [ ] Прогресс обновляется после: изменения количества, удаления строки, очистки корзины,
      импорта заказа, переключения активной корзины.
- [ ] Формулировки берутся из `PromotionRuleDescriber` и совпадают с админкой.
- [ ] При достигнутом пороге текст честно говорит, что позицию добавит менеджер.
- [ ] `blocked`-причины не утекают в ответ эндпоинта (тест).
- [ ] Проверено на мобильной ширине и на корзине из 200 позиций (блок не тормозит ввод).
