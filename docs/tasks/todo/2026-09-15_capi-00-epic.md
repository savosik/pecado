# ЭПИК: клиентский API v1 и MCP для агентов клиентов (capi-00)

**Приоритет:** средний
**Создано:** 2026-09-15
**Статус:** план утверждён 16.09.2026, карточки capi-01…capi-16 в `backlog/`; ветка `feature/capi-client-api`
**Вне эпика:** ERP-протокол (слой потребляет уже принятые из 1С данные, заказ уходит в 1С прежним
путём через `PublishOrderToErpJob`); контент-разделы кабинета (FAQ, новости, подборки, статьи);
пресеты поиска; конструктор выгрузок; аналитика кабинета (`/analytics`, ABC/XYZ — решение
заказчика 15.09.2026); трек-номер и статус доставки (решение 16.09.2026 — эпик доставки).

## Идея

Клиент подключает своего ИИ-агента (Claude Desktop, Claude Code, Cursor, собственный бот) и
решает **рутину без менеджера и без веб-интерфейса**: смотрит цены и остатки, собирает корзину и
оформляет заказ, следит за статусом, правит резервы, забирает документы и сверку, видит долг,
формирует платёжку, оформляет возврат, ведёт реквизиты и контакты, задаёт вопрос менеджеру и сам
включает себе уведомления о статусах. Сначала — REST v1 с версионностью и OpenAPI (агенты умеют
работать по OpenAPI уже сейчас), затем MCP-сервер как тонкая витрина над тем же слоем.

Образец — домен CRM: реестр операций `app/Services/Crm/Api/*` → `CrmApiController` → `CrmApiDocument`
→ `CrmServer`. Один реестр порождает маршруты REST, discovery, OpenAPI и каталог инструментов MCP;
второго перечня нет намеренно (урок `/api/content/me`, карточка `content-api-discovery-drift`).

## Решения заказчика (15–16.09.2026)

1. **Сначала REST v1, потом MCP** над тем же слоем операций.
2. **Legacy `/api/client-api/{token}/*` поддерживается бессрочно.** Его внутренности переводятся на
   общие сервисы (создание заказа, реализации, резервы) **при неизменных ответах и нетронутых
   тестах** `tests/Feature/Api/ClientApi*Test.php` — шесть файлов служат контрактом неизменности.
3. **Токен один и полный.** Режимов/скоупов нет; таблица `api_tokens` та же, клиенту ничего заново
   заводить не нужно. В v1 токен идёт в заголовке `Authorization: Bearer`, не в пути.
4. **Аналитика кабинета в API не нужна.**
5. **Документация — только OpenAPI (Scramble):** отдельный документ `client` на `/docs/client-api`
   (UI) и `/docs/client-api.json` (агентам), собирается из реестра. Ручной документации v1 в кабинете
   нет: `/api-tokens` даёт ключи, URL, ссылку и короткий «быстрый старт». Рукописный блок legacy в
   `resources/js/Pages/User/Cabinet/ApiTokens/Index.jsx` остаётся, сворачивается в раздел «Legacy API»
   и дальше не растёт.
6. **`Idempotency-Key` обязателен** на `orders.create` и `checkout.submit` (без ключа — 422),
   необязателен на остальных пишущих операциях.
7. **Трекинг доставки** — не в этом эпике; в API зарезервировано место под блок `delivery`.

## Принципы

1. **Один реестр операций — все витрины.** `App\Services\Client\Api\OperationRegistry`: операция =
   id, секция, метод, uri, параметры, гейт, идемпотентность, контекст юрлица, исполнитель. Из реестра
   растут маршруты `/api/client/v1/*`, `GET /me`, OpenAPI, каталог инструментов MCP. Тест на дрейф
   реестр ↔ маршруты ↔ OpenAPI обязателен.
2. **Слой транспортно-независимый.** Операции вызывают сервисы (`CartService`, `CheckoutService`,
   `OrderAssembler`, `ClientOrderActions`, `ReturnService`, `PaymentOrderService`,
   `CabinetSettlementFinance`, `ReconciliationService`, `PriceService`, `StockService`, …). Логика,
   которая сейчас живёт в контроллерах кабинета (~1000 строк по 12 контроллерам), выносится в сервисы,
   и **кабинетный контроллер переводится на них в той же карточке** — иначе появится третья копия.
3. **Из `Crm\Api` переиспользуются как есть** `Param`, `OperationInput`, `OperationDenied` (переезд в
   `App\Support\OperationApi\*`). `Operation`, `Registry`, `Runner`, документ и MCP-трейт — свои: у
   клиента нет прав, есть фича-гейты, юрлицо и идемпотентность.
4. **Фича-гейты — один предикат с кабинетом** (`FeatureGate`: documents, finance, contracts, reserve,
   order-cancel, payment-orders). Кабинет прячет раздел 404-м, API отвечает **403 + код**
   (`documents_disabled`, `finance_unavailable`, `reserve_unavailable`, …) и показывает `allowed=false`
   в `/me`: агент должен отличать «выключено» от «не найдено».
5. **Контекст юрлица.** Заказ, документы и долг живут на контрагенте. У создания — `company_id` с
   умолчанием (`is_default` → единственная → 422 `company_required` с перечнем); у списков —
   `company_id` как фильтр без умолчания. Чужая компания → 404.
6. **Идемпотентность через таблицу** `client_api_idempotency_keys` (не кэш: потерянный ключ после
   создания заказа = дубль в 1С). Повтор с тем же ключом и телом → сохранённый ответ; другое тело →
   422; параллельный повтор → 409; TTL 24 ч.
7. **Единый конверт** `{data, meta, errors[{code,message,field?}]}`, курсорная пагинация с тай-брейком
   `id`, `per_page` ≤ 100 (цены/остатки ≤ 500 — это фид синхронизации). Даты ISO 8601, деньги —
   число + `currency_code`.
8. **Лимиты и аудит:** `throttle:client-api` (60/мин по владельцу токена, жёстче менеджерского),
   лог-канал `client-agent` — только пишущие операции, с `token_id`, `user_id`, `company_id`, ключом.
9. **Удалений через API нет** (компании, счета, адреса, контакты — только деактивация/смена умолчания);
   исключение — корзина, она не бизнес-документ.
10. **Файлы — по временной подписанной ссылке** (`documents.link`, `contracts.link`,
    `payment-orders.link`), чтобы агент мог передать документ человеку без Bearer.

## Критерии готовности (эпик)

- [ ] Legacy `/api/client-api/{token}/*` работает без изменений; шесть его тестовых файлов не
      редактировались и зелёные.
- [ ] Каждая операция реестра доступна по REST v1, видна в `/me` и в `/docs/client-api.json`; тест на
      дрейф в обе стороны. Ручных описаний v1 в JSX нет.
- [ ] Повтор `orders.create`/`checkout.submit` с тем же `Idempotency-Key` не создаёт второй заказ и не
      публикует в шину дважды; без ключа — 422.
- [ ] Операции на чужую компанию / заказ / реализацию / документ → 404 без подтверждения существования.
- [ ] Выключенный раздел → 403 с кодом и `allowed=false`; предикат гейта физически один с кабинетом.
- [ ] Кабинет и API оформляют заказ через один слой: паритет-тест «одна корзина двумя путями →
      одинаковые заказы».
- [ ] MCP-сервер `/mcp/client` поднят на dev; сценарий «цены → корзина → заказ → статус» проходит
      реальным MCP-клиентом и закреплён тестом; токен клиента не открывает `/mcp/crm` и наоборот.
- [ ] Весь текст ошибок, документа и инструкций — на русском; `make verify` зелёный.

## Известный долг (не в эпике)

- Токен `api_tokens.token` хранится и показывается открытым текстом (наследие legacy).
- `ClientOrderActions::cancel` читает `request()` — устраняется в capi-06 (`StatusCommentContext`).
