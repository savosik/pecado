# Отправки в транспортные компании (ApiShip)

Раздел `/wms/deliveries` в кабинете склада: сборка груза из реализаций 1С, расчёт
стоимости у перевозчиков, передача заявки и отслеживание доставки.

Интеграция идёт через агрегатор [ApiShip](https://docs.apiship.ru/docs/api/) — один
договор вместо отдельных подключений к СДЭК, ПЭК, Деловым Линиям и другим.

**По шине RabbitMQ отправки не ходят.** 1С про них ничего не знает: реализация
(`shipments`) приезжает из 1С, а решение «эти пять реализаций едут одной машиной
такой-то ТК» принимает склад на сайте. `docs/asyncapi/` и `docs-erp/` эта задача
не затрагивает.

## Поток

```
Реализации из 1С (shipments)
        │
        ▼  кладовщик выбирает, задаёт места и адрес
delivery_shipments (черновик)     ← вес считается по products.weight_gross
        │
        ▼  POST /calculator
Список тарифов всех перевозчиков → кладовщик выбирает
        │
        ▼  POST /orders  (асинхронно: в ответе только orderId)
Заявка у перевозчика
        │
        ├─◄─ вебхук ORDER_STATUS      (основной канал, приходит сразу)
        └─◄─ apiship:sync-statuses    (страховка, каждые 30 минут)
        │
        ▼
Трек-номер, история статусов, «Доставлен»
```

## Особенности API, которые легко нарушить

| Что | Как правильно |
|---|---|
| Единицы | Вес — **граммы**, габариты — **сантиметры**. Ошибка не даёт ошибки API: перевозчик молча считает тариф по другому объёмному весу и выставляет другой счёт |
| Авторизация | Заголовок `Authorization: <токен>` **без** `Bearer`. Токен берётся готовым из кабинета (`APISHIP_TOKEN`) либо выменивается на `POST /login` по паре логин/пароль |
| Перевозчики | Расчёт вернёт пустой список, пока в кабинете ApiShip не подключена ни одна служба доставки. Проверяется через `GET /connections` — при `total: 0` тарифов не будет ни по одному запросу |
| Создание заявки | Асинхронное. В ответе только `{orderId, created}` — трек-номера там нет, он приезжает вебхуком либо через `GET /orders/{id}` |
| Отмена | `GET /orders/{orderId}/cancel` — именно GET, не POST |
| Идемпотентность | Ключ — `order.clientNumber`, у нас это номер отправки `DS-000123`. По нему же приходят вебхуки |
| Доставка до ПВЗ | `order.deliveryType = 2` **и** `order.pointOutId` с идентификатором из `GET /lists/points` |
| Калькулятор | Каждый вызов ApiShip считает тарифицируемой транзакцией — ответы кэшируются на `APISHIP_CALCULATOR_CACHE_TTL` |

## Статусы

Внутренний жизненный цикл (`App\Enums\Delivery\DeliveryShipmentStatus`) отделён от
статусов перевозчика: до передачи заявки никакого статуса у ApiShip ещё нет.

| Внутренний | Когда |
|---|---|
| `draft` | Черновик: груз собран, тариф не выбран |
| `calculated` | Тариф выбран, можно передавать заявку |
| `submitting` | Заявка уходит в ТК |
| `submitted` | Заявка принята ApiShip |
| `in_transit` | Груз в работе у перевозчика |
| `delivered` | Доставлено |
| `cancelled` | Отменено |
| `failed` | Передать заявку не удалось (причина — в `last_error` и в журнале вызовов) |

Соответствие статусов ApiShip внутренним — в `ApiShipStatus::toShipmentStatus()`:

| Ключ ApiShip | Русское название | Внутренний статус |
|---|---|---|
| `uploading`, `uploaded` | Передаётся / принят перевозчиком | `submitted` |
| `uploadingError` | Ошибка передачи перевозчику | `failed` |
| `onPointIn`, `onWay`, `onPointOut`, `delivering`, `readyForRecipient` | Движение груза | `in_transit` |
| `returning`, `returned`, `returnedFromDelivery`, `returnReady`, `partialReturn`, `lost`, `problem` | Возвраты и проблемы | `in_transit` — груз ещё в работе, и отправка должна оставаться на радаре склада |
| `delivered` | Доставлен получателю | `delivered` |
| `deliveryCanceled` | Доставка отменена | `cancelled` |

**Незнакомый ключ не ломает приём.** Он сохраняется в `apiship_status_key` как есть,
внутренний статус остаётся прежним, в лог пишется `info`. Новый статус у перевозчика
не должен ронять обработку вебхуков.

## Ретраи и идемпотентность

- **`POST /orders` — без автоматических повторов.** Метод неидемпотентен: ретрай после
  таймаута заведёт у перевозчика вторую заявку на тот же груз. Отсюда `tries = 1`
  в `SubmitDeliveryShipmentJob` и `retry()` только на GET-запросах в `ApiShipClient`.
  Повтор — кнопкой из карточки.
- **GET-запросы** повторяются дважды с паузой 500 мс.
- **Токен**: `APISHIP_TOKEN` используется как есть; при авторизации по логину и паролю
  токен кэшируется на сутки, а ответ 401 сбрасывает кэш и повторяет запрос один раз.
- **Вебхук + сверка дублируют друг друга по построению.** Запись в
  `delivery_shipment_status_histories` появляется только при фактической смене ключа
  статуса, иначе журнал забился бы повторами «В пути» каждые полчаса.

## Вебхук ORDER_STATUS

Эндпоинт: `POST /api/delivery/apiship/webhook/{secret}`.

**Подписи запроса ApiShip не даёт**, поэтому защита сложена из трёх слоёв
(`App\Http\Middleware\ApiShipWebhookEnabled`):

1. мастер-флаг `APISHIP_WEBHOOK_ENABLED`;
2. секретный сегмент URL, сравнение через `hash_equals`; пустой секрет в конфиге
   закрывает эндпоинт целиком (503);
3. необязательный allowlist IP (`APISHIP_WEBHOOK_ALLOWED_IPS`).

ApiShip считает доставку неудачной при HTTP ≥ 500 или ответе дольше 30 секунд и
повторяет её до трёх раз. Поэтому на всё, кроме проблем доступа, эндпоинт отвечает
`200`: неизвестный `clientNumber` и мусорный payload — наша забота, а не повод
заставлять ApiShip ретраить.

Регистрация подписки — разовая операция на среду:

```bash
docker exec pecado-app php artisan apiship:register-webhook          # подписаться
docker exec pecado-app php artisan apiship:register-webhook --list   # посмотреть подписки
docker exec pecado-app php artisan apiship:register-webhook --delete=<uuid>
```

Автоматической регистрации при старте нет намеренно: молчаливая перерегистрация
плодила бы дубли подписок, и каждый статус приходил бы по несколько раз.

## Сверка статусов

```bash
docker exec pecado-app php artisan apiship:sync-statuses            # обычный прогон
docker exec pecado-app php artisan apiship:sync-statuses --dry-run  # показать, ничего не сохраняя
docker exec pecado-app php artisan apiship:sync-statuses --since="2026-08-01 00:00:00"
```

В расписании — каждые 30 минут с `withoutOverlapping()`. Один запрос
`GET /orders/statuses/interval` отдаёт изменения по всем заявкам сразу; поштучный
опрос был бы на два порядка дороже. Интервал берётся от курсора прошлой успешной
сверки минус 5 минут нахлёста — событие могло произойти ровно в момент прошлого
прогона и не попасть в её окно.

Команда нужна ровно на один случай: сайт лежал дольше трёх попыток доставки вебхука.
Тогда событие теряется навсегда, и восстановить его больше нечем.

## Разделы кабинета склада

| Раздел | Что там |
|---|---|
| «Реализации к доставке» (`/wms/delivery-candidates`) | Рабочий стол: фильтры, группировки (клиент / адрес / дата / способ), скрытие лишнего, вкладки «К отправке» и «Самовывоз». Отсюда выбранное уходит в мастер |
| «Отправки» (`/wms/deliveries`) | Журнал отправок, карточка с расчётом тарифов, треком, историей статусов и документами |
| «Настройки ApiShip» (`/wms/delivery-settings`) | Токен, отправитель, значения по умолчанию. Только начальнику склада |

Мастер создания (`/wms/deliveries/create`) намеренно компактный: состав правится
поиском с мультивыбором, а весь разбор живёт в отдельном разделе.

## Ручные отправки

Не всё едет через ApiShip: часть перевозчиков к агрегатору не подключена, заявку
делают на сайте ТК или по телефону, а к моменту внедрения склад уже что-то отправил.

Кнопка **«Уже отправлено»** в разделе «Реализации к доставке» создаёт отправку
с флагом `is_manual`: перевозчик и трек вписываются руками, состояние выбирается
из трёх (`submitted` / `in_transit` / `delivered`), дата — только не в будущем.

Такая отправка ведёт себя как обычная: занимает реализации (они уходят из списка
кандидатов), попадает в журнал с пометкой «вручную», её стоимость учитывается
в сводке за месяц. Недоступны только то, чего без заявки в ApiShip не существует:
расчёт тарифов, этикетка и вызов курьера.

## Настройки через интерфейс

Токен и адрес отправителя ведёт начальник склада на `/wms/delivery-settings`.
Значения из формы **перекрывают `.env`** — договор с перевозчиком перевыпускают
без участия разработчика, и требовать ради этого деплой бессмысленно.

- Токен, пароль и секрет вебхука хранятся в `settings` **зашифрованными**
  (`Crypt::encryptString`): таблица читается BI-агентом и попадает в дампы.
- Секреты не отдаются на фронт — только признак «задано». Пустое поле означает
  «не менять», стирание — отдельным чекбоксом.
- Кнопка «Проверить связь» дёргает `GET /webhooks` и справочник ПВЗ.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APISHIP_ENABLED` | `false` | Мастер-выключатель. Пока `false`, наружу не уходит ни один запрос |
| `APISHIP_BASE_URL` | `https://api.apiship.ru/v1` | Боевая среда. Тестовая — `http://api.dev.apiship.ru/v1` (**http**, TLS там нет) |
| `APISHIP_TOKEN` | — | Готовый токен из кабинета. Задан — `POST /login` не вызывается вовсе. **Значение из формы настроек перекрывает эту переменную** |
| `APISHIP_LOGIN` / `APISHIP_PASSWORD` | — | Альтернатива токену. В тестовой среде — `test` / `test` |
| `APISHIP_TIMEOUT` | `30` | Таймаут запроса, секунды |
| `APISHIP_TOKEN_TTL` | `86400` | Сколько держать токен в кэше |
| `APISHIP_CALCULATOR_CACHE_TTL` | `600` | Кэш расчёта: вызовы калькулятора тарифицируются |
| `APISHIP_WEBHOOK_ENABLED` | `false` | Приём вебхуков |
| `APISHIP_WEBHOOK_SECRET` | — | Секретный сегмент URL. Генерировать длинным: `Str::random(48)` |
| `APISHIP_WEBHOOK_ALLOWED_IPS` | пусто | Allowlist через запятую; пусто — проверка выключена |
| `APISHIP_SENDER_*` | — | Отправитель: `COMPANY`, `CONTACT`, `PHONE`, `EMAIL`, `COUNTRY`, `REGION`, `CITY`, `STREET`, `HOUSE`, `INDEX` |
| `APISHIP_DEFAULT_WEIGHT_GRAMS` | `500` | Вес позиции, если у товара не заполнены `weight_gross`/`weight_net` |
| `APISHIP_DEFAULT_PLACE_LENGTH/WIDTH/HEIGHT` | `40` / `30` / `20` | Габариты типовой коробки, см |

## Схема данных

| Таблица | Что хранит |
|---|---|
| `delivery_shipments` | Отправка: состав, выбранный тариф, трек, статусы, снапшоты адресов, флаг `is_manual` |
| `delivery_shipment_documents` | Какие реализации вошли в груз (+ снапшоты веса и суммы) |
| `delivery_shipment_places` | Грузовые места: вес в граммах, габариты в сантиметрах |
| `delivery_shipment_status_histories` | Журнал смен статуса с источником (`webhook` / `poll` / `manual`) |
| `apiship_requests` | Журнал HTTP-вызовов: запрос без токена, ответ, код, длительность, ошибка |
| `delivery_hidden_shipments` | Реализации, убранные складом из списка кандидатов |
| `settings` (группа `apiship`) | Настройки из интерфейса; секреты зашифрованы |

Журнал вызовов — не роскошь: ApiShip возвращает причины отказа перевозчика отдельным
массивом `errors`, и увидеть их постфактум больше негде. В карточке отправки он
доступен только начальнику склада.

## Права

Ресурс `wms-deliveries` с действиями `view`, `create`, `edit`, `submit`, `cancel`.

| Роль | Права |
|---|---|
| `warehouse-head` | все пять + `wms-delivery-settings.{view,edit}` |
| `storekeeper` | `view`, `create`, `edit`, `submit` |

Настройки интеграции — только начальнику склада: там токен боевого API и адрес
отправителя, от которого считаются все тарифы.

Отмена оставлена за начальником склада: она может стоить денег и разъезжается с уже
напечатанными этикетками.

⚠️ Префикс `wms-` обязателен для любого нового права раздела. `User::hasAdminAccess()`
считает непанельным любое право без `wms-`/`crm-`, и право с другим именем молча
открыло бы складским ролям `/admin`. Это ловит тест
`tests/Feature/Crm/PermissionNamingTest.php::warehouse_roles_are_wms_only`.

## Проверка на тестовой среде

```env
APISHIP_ENABLED=true
APISHIP_BASE_URL=http://api.dev.apiship.ru/v1
APISHIP_LOGIN=test
APISHIP_PASSWORD=test
```

Личный кабинет тестовой среды — `http://a.dev.apiship.ru/` (логин/пароль `test`).
Базы боевой и тестовой сред разные.

Вебхук на локальную машину не достучится — проверять на dev после деплоя
(`https://dev.pecado.ru`) либо руками:

```bash
curl -X POST https://dev.pecado.ru/api/delivery/apiship/webhook/<secret> \
  -H 'Content-Type: application/json' \
  -d '{"orderInfo":{"clientNumber":"DS-000001","providerNumber":"CDEK-123"},
       "status":{"key":"onWay","name":"В пути","created":"2026-08-09T12:00:00+03:00"}}'
```
