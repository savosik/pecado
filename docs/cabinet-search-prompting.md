# Плейбук работы с ИИ-агентом по инициативе «Поиск в личном кабинете»

Документ описывает, **как** использовать Claude Code для последовательного закрытия PR из [cabinet-search-roadmap.md](cabinet-search-roadmap.md). Цель — дойти до финиша за конечное число сессий, не теряя контекст и не ломая прод.

## Главный принцип

**Одна сессия = один PR, максимум одна волна.**

Не пытаться «давай реализуй всю инициативу одним прогоном». Контекстное окно даже на Opus 4.7 (1M) не безграничное, плюс каждый PR должен быть отдельно проверяемым и отдельно откатываемым. Закрытый PR → новая сессия → следующий PR.

## Что Claude Code подтягивает сам

При старте сессии в этом проекте автоматически подгружаются:
- `CLAUDE.md` — архитектура, команды Docker, ключевые правила.
- `.claude/rules/*.md` — Docker-only, миграции только новые, UI на русском, Chakra UI v3 из `@/components/ui/*`, ERP spec-first.
- `~/.claude/projects/.../memory/MEMORY.md` — индекс памяти пользователя.

**В промпт это писать не нужно.** Достаточно сослаться на путь к roadmap/карточке — агент сам прочитает и применит правила.

## Что обязательно положить в промпт

1. **Ссылка на roadmap и карточку** (путь от корня проекта).
2. **Идентификатор PR** (например, «PR 2.1») — чтобы скоуп был однозначен.
3. **Этап волны** — `Этап 1 (LIKE-only)` или `Этап 2 (fuzzy)`. Без этого агент может попытаться сделать всё сразу.
4. **Чего НЕ делать** — какие части карточки относятся к другим PR.
5. **Где остановиться** — DoD, описанный явно.

## Cold start: первая сессия по новому PR

Шаблон промпта:

```
Реализуй PR <N.M> из docs/cabinet-search-roadmap.md.
Карточка: docs/tasks/backlog/2026-04-28_cabinet-search-<slug>.md.
Скоуп — только <одной фразой>.
<Что НЕ трогать в этом PR — другие этапы/разделы>.

Перед стартом:
1. Прочитай roadmap (раздел Волны N), карточку и относящиеся к ней сценарии в docs/cabinet-search-scenarios.md.
2. Перемести карточку в docs/tasks/in-progress/.

В конце:
- composer test и composer lint зелёные (Docker: docker exec pecado-app composer …).
- Обнови чек-лист в карточке.
- Сообщи коммит-сообщение и текст PR-описания (не делай commit/push).
```

### Конкретные примеры

#### PR 1.1 — PHP-хелперы фундамента

```
Реализуй PR 1.1 из docs/cabinet-search-roadmap.md.
Карточка: docs/tasks/backlog/2026-04-28_cabinet-search-foundation.md.
Скоуп — только PHP: классы App\Support\Search\DocumentNumber и App\Support\Search\QueryRouter
+ unit-тесты в tests/Unit/Support/Search/.
Frontend (PR 1.2) и подключение хелперов к контроллерам (волны 2-3) НЕ трогай.
В тестах покрой все примеры из § «Сквозные принципы» и сценарии C-1.1, C-1.6, C-1.9.

Перед стартом — mv карточки в in-progress/.
В конце — `docker exec pecado-app composer test` и `composer lint` зелёные, чек-лист PR 1.1 в карточке отмечен.
```

#### PR 2.1 — Orders Этап 1 (LIKE)

```
Реализуй PR 2.1 из docs/cabinet-search-roadmap.md.
Карточка: docs/tasks/backlog/2026-04-28_cabinet-search-orders.md.
Скоуп — ТОЛЬКО Этап 1 (LIKE-only, без Meilisearch). Сценарии C-1.1 … C-1.13.
Этап 2 (fuzzy) НЕ делать — он уйдёт в волну 4.
Используй уже существующие App\Support\Search\DocumentNumber и QueryRouter.

Backend:
- Расширить OrderController::index в соответствии с этапом 1 карточки.
- Покрыть feature-тестом каждый новый источник совпадения (товар, бренд, SKU, штрихкод, контрагент, ИНН, комментарий).

Frontend:
- Подключить useSearchHistory и общий <SelectedFilters /> на Orders/Index.jsx.
- Чипы активных фильтров через общий компонент.

Перед стартом — mv карточки в in-progress/.
DoD — composer test, lint, проверка golden path в браузере на http://localhost:8085/cabinet/orders.
```

#### PR 4.2 — Fuzzy за фича-флагом

```
Реализуй PR 4.2 из docs/cabinet-search-roadmap.md.
Карточки: orders, returns, shipments (Этап 2 в каждой).
Скоуп — подключить fuzzy через Scout/Meilisearch к контроллерам Orders/Returns/Shipments
ЗА флагом config('search-cabinet.fuzzy_documents') (env CABINET_SEARCH_FUZZY_DOCUMENTS, default false).

ВАЖНО:
- Индексация (PR 4.1) уже сделана — модели OrderItem/ReturnItem/ShipmentItem уже Searchable.
- Fuzzy ТОЛЬКО для product_name_snapshot и brand_name_snapshot (контракт из § «Сквозные принципы»).
- SKU/штрихкод/UUID/ИНН — exact, без fuzzy.
- Scope user_id обязательно сохранить — fuzzy не должен пробивать видимость.
- Дедупликация результатов: документ может найтись и по номеру (LIKE), и по составу (fuzzy) — выводим один раз.
- При флаге = false поведение должно быть идентично PR 2.1 — feature-тесты на старое поведение НЕ должны сломаться.

DoD — flag-on/flag-off feature-тесты, lint, проверка на dev.
```

#### PR с миграцией (5.1 — пресеты)

```
Реализуй PR 5.1 из docs/cabinet-search-roadmap.md.
Карточка: docs/tasks/backlog/2026-04-28_cabinet-search-cross-cutting.md (раздел A-2).
Скоуп — пресеты сохранённых поисков:
- Миграция user_search_presets (новая, не редактировать существующие).
- Модель UserSearchPreset.
- Контроллер SearchPresetController с index/store/destroy + policy (доступ только к своим).
- Routes /cabinet/search-presets/{section} — index/store/destroy.
- Frontend <SavedSearches section="..." current={filters} /> — подключить в Orders как smoke.
- Флаг config('search-cabinet.presets') / env CABINET_SEARCH_PRESETS=false по умолчанию.

ВАЖНО:
- Миграция — только новая (правило проекта). Не править существующие.
- Feature-тест: создание/удаление пресета, scope user_id (нельзя получить чужой).

DoD — composer test, lint, проверка golden path в Orders на dev.
```

## Continue: возобновление прерванной сессии

Если сессия закончилась посреди PR (контекст упёрся, ошибка, перерыв):

```
Продолжаю PR <N.M> из docs/cabinet-search-roadmap.md.
Карточка лежит в in-progress/: docs/tasks/in-progress/<filename>.md.
Прочитай карточку, статус отмеченных пунктов в чек-листе, сделай git status и git diff,
скажи что уже сделано и что осталось до DoD. Не пиши код, пока не подтвердим план.
```

После этого ответ агента покажет состояние, и можно дать следующую инструкцию.

## Code review одной сессией

После того как PR готов, перед `git commit`:

```
Сделай review PR <N.M>:
- git diff и git status
- Покрытие feature-тестами всех сценариев из чек-листа карточки
- Соответствие принципам из docs/cabinet-search-roadmap.md (аддитивность, scope user_id, dedup, флаг если применим)
- Pint + PHPStan (`docker exec pecado-app composer lint && composer analyse`)
- Не сломаны существующие тесты (composer test)

Дай вердикт: что не дотянуто и что готово к коммиту.
```

## Чек-лист агента перед коммитом

Каждый PR агент обязан проверить (зашить в промпт или попросить):

- [ ] Команды выполнялись через `docker exec pecado-app/pecado-node/pecado-worker`, не на хосте.
- [ ] `composer test` зелёный (включая старые тесты — на ломку обратной совместимости).
- [ ] `composer lint` (Pint) и `composer analyse` (PHPStan) зелёные.
- [ ] Pages/User/* — все надписи на русском (UI на русском — правило проекта).
- [ ] Chakra UI компоненты импортированы из `@/components/ui/*`, не из `@chakra-ui/react`.
- [ ] Если в PR есть миграция — только новая, существующие не тронуты.
- [ ] Если PR за флагом — флаг существует в `config/search-cabinet.php` и `.env.example` обновлён.
- [ ] Карточка backlog обновлена (отмечен этап) или перемещена в `review/`/`done/`.

## Анти-паттерны промптов

❌ **«Сделай всю инициативу поиска в кабинете»** — нереалистичный скоуп, агент будет либо галлюцинировать, либо упрётся в контекст.

❌ **«Расширь OrderController, чтобы клиенту было удобно»** — нет ссылки на сценарии, агент будет фантазировать UX.

❌ **«Добавь fuzzy-поиск везде»** — нет указания на этап, нет ограничений по скоупу (только названия товаров и брендов!), нет указания на флаг.

❌ **«Заодно подправь админку»** — расширение скоупа PR за пределами карточки.

❌ **«Сделай как в карточке»** без указания, какой этап и какой PR — карточки часто содержат несколько этапов.

✅ **«PR 2.1 — Orders Этап 1, только LIKE, не трогай fuzzy и не подключай <MatchBadge>, скоуп — карточка cabinet-search-orders.md, сценарии C-1.1 … C-1.13»** — однозначно.

## Когда задавать вопросы пользователю, а когда действовать

Агент должен **спрашивать** если:
- Карточка содержит TBD или открытый вопрос (например, owner-scope медиатеки в C-8.4).
- Нужно решение по схеме БД (новая колонка с уникальным ограничением и неочевидным значением по умолчанию).
- Фича-флаг затрагивает поведение, которое уже видят пользователи на prod.
- Тесты на старое поведение начали падать после изменений — это сигнал, что аддитивность нарушена.

Агент должен **действовать без вопросов** если:
- Скоуп описан в карточке однозначно.
- Изменения чисто аддитивны (новые поля поиска, новые опциональные query-параметры).
- Это unit-тест/feature-тест на новый сценарий.
- Это рефакторинг внутри одного PR без смены публичных API.

## Параллельные сессии

Если хочется параллелизировать (один разработчик ведёт две ветки) — допустимо в волнах **без зависимостей**:

| Волна | Можно параллельно с |
|---|---|
| 2 (документы) | 3 (корзинно-избранное), 6 (низкоприоритетные) — ветки разные, файлы не пересекаются |
| 4 (fuzzy) | — должна идти после волн 2 и 3 |
| 5 (UX) | 6 — обычно изолированно |

В одной волне параллелить разные PR — рискованно: они могут затронуть общий компонент `<SelectedFilters />` или `useSearchHistory`. Лучше последовательно.

## Сессионный бюджет (грубая оценка)

| Волна | Кол-во PR | ~Сессий |
|---|---|---|
| 1 — Фундамент | 2 | 1 |
| 2 — Документы (LIKE) | 5 | 3-4 |
| 3 — Корзинно-избранное | 2 | 1-2 |
| 4 — Fuzzy | 4 | 3-4 |
| 5 — UX | 4 | 3-4 |
| 6 — Низкоприоритетные | 3 | 2-3 |
| **Итого** | **20** | **13-18** |

Каждая «сессия» — это один заход в Claude Code от cold start до закоммиченного и пуш­нутого PR. Часть PR закрывается за 30 минут (PR 1.1 — pure helpers), часть — за пару часов (PR 4.2 — fuzzy с тестами на оба состояния флага).
