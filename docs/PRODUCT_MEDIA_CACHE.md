# Персистентное кэширование медиа товаров (Spatie MediaLibrary)

## Описание проблемы
При удалении товара через Eloquent (`$product->delete()`), Spatie MediaLibrary автоматически удалял все физические файлы (S3/MinIO), ассоциированные с данным товаром.
Это приводило к проблемам при удалении и повторном создании товаров во время тестирования или сбоев импорта каталога: для восстановления изображений приходилось каждый раз заново скачивать десятки гигабайт медиа-файлов с внешнего API.

## Архитектура решения

Решение основано на концепции **«персистентного хранения в MinIO»**, при котором MinIO выступает в роли кэша:

1. Файлы сохраняются по статичному пути, привязанному не к `id` товара (которое меняется после пересоздания), а к его артикулу `code`.
2. При удалении товара физические файлы в MinIO не удаляются — удаляются только записи о них в БД.
3. При повторном появлении товара с тем же артикулом, база данных легко восстанавливает связь с уже существующими файлами без обращения к внешнему серверу.

### 1. Собственный Path Generator

Для переопределения папок файлов используется класс `App\Media\ProductPathGenerator`, реализующий логику Spatie.
Этот генератор настраивается в:
- `config/media-library.php` (секция `custom_path_generators`)

Вместо классического пути `{model}/{id}/{media_id}/`, для продуктов используется стабильный путь:
`products-media/{code}/{collection}/`

### 2. Предотвращение физического удаления файлов

Spatie MediaLibrary перехватывает событие Eloquent `deleting` благодаря трейту `InteractsWithMedia` и удаляет прикрепленные медиафайлы методом `deleteAllMedia()`.

Чтобы обойти это, в модели `App\Models\Product` переопределён этот метод:

```php
public function deleteAllMedia(): self
{
    // Массовое удаление через SQL-запрос
    // Не триггерит MediaObserver, ответственный за удаление файлов из S3/MinIO
    $this->media()->delete();

    return $this;
}
```

### 3. Как файл узнаёт артикул?

Поскольку метод `getPath()` генератора путей не всегда имеет доступ к `Model` (или эта связь может быть ещё не установлена), артикул передаётся в `custom_properties` медиа файла ещё в момент загрузки.

В ресурсах где происходит загрузка из внешнего каталога (`DownloadProductMediaJob`), это выглядит так:
```php
$product->addMediaFromUrl($url)
        ->withCustomProperties(['product_code' => $data['code']])
        ->toMediaCollection('main');
```

## Artisan-команды

### 1. `php artisan catalog:restore-cached-media`
Восстанавливает связь товаров (у которых отсутствует медиа) с файлами, найденными в кэше MinIO по артикулу товара. Если файлы найдены, команда напрямую создаёт нужные SQL-записи в таблице `media`. **Без сетевого скачивания.**

Опции:
- `--dry-run` — посмотреть, какие товары будут восстановлены, без изменений в БД.
- `--regenerate` — после восстановления записей запустить `media-library:regenerate` **только для созданных id** (`--with-responsive-images --force`), чтобы пересоздать конверсии и адаптивные изображения. Если флаг не передан, в финальном выводе печатается готовая команда регенерации.

### 2. `php artisan catalog:purge-media-cache`
Служит «сборщиком мусора». Команда сканирует директорию `products-media/` в MinIO, и физически удаляет те папки (артикулы), для которых больше не существует записей товара в БД `products`.

Опция: `--dry-run` — вывести список сирот, которых удалит команда.

### 3. `php artisan catalog:reattach-orphaned-media`
Переподвязывает orphaned media-записи к живому `Product` по `custom_properties.product_code`. Используется, когда `Product` пересоздаётся при синхронизации с 1С: media-запись остаётся со старым `model_id`, а файлы в MinIO живут по `products-media/{code}/...`. Команда обновит `model_id` в живой товар.

### 4. `php artisan dev:cleanup` (взаимодействие с кэшем)
Очистка dev-данных **по умолчанию сохраняет оригиналы медиа товаров** в MinIO (`products-media/{code}/...`), чтобы их можно было восстановить через `catalog:restore-cached-media`.

Что именно делает с медиа товаров:
- удаляет записи `media` из БД (массовый SQL-delete мимо Eloquent-обсёрверов);
- удаляет производные файлы — `products-media/{code}/{collection}/conversions/` и `responsive-images/`;
- **не трогает** оригиналы в `products-media/{code}/{collection}/`.

Для брендов, категорий и сертификатов используется `DefaultPathGenerator`, для них и оригиналы, и конверсии удаляются полностью (структура `{model_id}/{uuid}/`).

Опции:
- `--force` — пропустить интерактивное подтверждение.
- `--purge-product-media` — также удалить из MinIO оригиналы файлов товаров. Использовать только когда действительно нужен полный сброс кэша (например, при изменении формата хранения).

После `dev:cleanup` в выводе появляется подсказка с готовой командой восстановления.

## Типичный сценарий: сброс dev-данных и восстановление медиа

```bash
# 1. Снести dev-данные. Оригиналы медиа товаров остаются в MinIO.
docker exec pecado-app php artisan dev:cleanup --force

# 2. Заново загрузить товары (через ERP-синхронизацию или импортёры).

# 3. Подвязать оригиналы из кэша MinIO к новым товарам и пересоздать конверсии.
docker exec pecado-app php artisan catalog:restore-cached-media --regenerate

# 4. (опционально) Для товаров без кэша — догрузить с внешнего API.
docker exec pecado-app php artisan catalog:fetch-missing-media
```

Полный сброс кэша (редкий случай):
```bash
docker exec pecado-app php artisan dev:cleanup --force --purge-product-media
```

## Автотесты
Работоспособность механизма задокументирована Feature-тестами в `tests/Feature/ProductMediaCacheTest.php`:
- Сохраняются ли файлы после `$product->delete()`
- Успешно ли воссоздаются SQL-записи `catalog:restore-cached-media`
- Чистит ли мусор `catalog:purge-media-cache`
