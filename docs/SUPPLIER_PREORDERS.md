# Отправка предзаказов поставщику (Customer API sex-opt.ru)

Предзаказ на сайте — обещание клиенту привезти товар, которого нет на складе.
Чтобы обещание было обеспечено, тот же состав автоматически уходит поставщику
(Andrey Company / sex-opt.ru) с комментарием «поставьте в резерв».

Это **не** обмен с 1С: канал отдельный, HTTP, через RabbitMQ и AsyncAPI не идёт,
контракт `docs/asyncapi/pecado-erp-integration.yaml` не затрагивается.

## Как работает

Резерв ставит **сайт** — и по своим предзаказам, и по заведённым в 1С:
у 1С канала к поставщику нет. Отсюда два входа в одну и ту же отправку.

**Предзаказ с сайта:**

1. Клиент (или менеджер в админке) оформляет заказ типа `preorder`.
2. Событие `OrderCreated` ловит [SendPreorderToSupplier](../app/Listeners/SendPreorderToSupplier.php)
   и ставит в очередь `default` job [SendPreorderToSupplierJob](../app/Jobs/SendPreorderToSupplierJob.php).
   Чекаут чужой API не ждёт.

**Предзаказ, заведённый менеджером в 1С (v15.9):**

1. Из шины приходит `order.created` с `type: "preorder"` — это **единственный**
   признак предзаказа, других у сайта нет.
2. [HandleOrderCreated](../app/Services/Erp/Handlers/HandleOrderCreated.php) после
   коммита транзакции ставит тот же job. Событий там нет по определению
   (`Order::withoutEvents`, иначе заказ улетел бы обратно в 1С), поэтому job
   ставится точечно.
3. Отправляется **только документ, пришедший впервые**: предзаказ с сайта уже ушёл
   поставщику при оформлении и возвращается сюда roundtrip-ом с тем же `uuid`.
   Документ со статусом «Удалён» пропускается.

Дальше путь общий: job вызывает [SupplierPreorderSender](../app/Services/Supplier/SupplierPreorderSender.php),
который собирает позиции, зовёт `send_order` и пишет попытку в
`supplier_preorder_requests` вместе с полным ответом поставщика.

Что **не** отправляется автоматически: изменение состава предзаказа из 1С
(`order.updated`) — резерв у поставщика остаётся прежним, повтор делает менеджер
кнопкой в админке. Сменить тип уже сохранённого заказа на `preorder` через
`order.updated` тоже нельзя — тип фиксируется при первом получении документа.

### Формат запроса

```json
{
  "api_key": "…",
  "method": "send_order",
  "data": {
    "stock": "tmn",
    "comment": "предзаказ ORD-2026-0042 поставьте в резерв.",
    "items": { "УТ-00007466": 3, "0T-00002013": 2 },
    "testmode": false,
    "rollback_on_warnings": false
  }
}
```

- **Склад** — `services.sex_opt.preorder.stock`, по умолчанию `tmn` (Тюмень).
- **Комментарий** — фиксированный шаблон `предзаказ {номер} поставьте в резерв.`
  Для заказа с сайта это `orders.number` (номера 1С на момент отправки ещё нет),
  для заказа из 1С — её номер документа (`29УТ-000123`).
- **Коды товаров** — `products.code` («Код/артикул товара из 1С»), fallback `products.sku`.
  Позиции без кода не отправляются и попадают в `skipped_items` записи лога.
  Одинаковые коды суммируются: ключ у поставщика уникален.

### Как трактуется ответ

`result=success` означает лишь, что запрос составлен верно. Создан ли заказ,
показывает `transaction`:

| Статус в логе | Условие | Смысл |
|---|---|---|
| `success` | `result=success`, `transaction=commit` | заказ создан у поставщика |
| `testmode` | ответ успешный, отправляли с `testmode=true` | проверка прошла, заказ не создан |
| `rollback` | `result=success`, `transaction=rollback` | поставщик откатил транзакцию, заказа нет |
| `failed` | `result=error`, не-JSON, HTTP-ошибка, таймаут | не отправлено |

`warnings.shortage` (нехватка остатка) и `warnings.unknown_items` (коды, которых
поставщик не знает) сохраняются и показываются в админке.

## Ретраи

Автоматических ретраев **нет** (`tries = 1`): у `send_order` нет ключа
идемпотентности, и повтор после таймаута мог бы создать у поставщика второй заказ.
Неудачная попытка видна в админке, повтор — решение менеджера (кнопка
«Отправить повторно»). Повторная отправка заказа, уже созданного у поставщика,
возможна только через эту кнопку (`force`): автоматика такой заказ пропускает.

## Админка

- **Продажи → Предзаказы поставщику** (`/admin/supplier-preorders`) — журнал всех
  попыток: статус, склад, ответ, предупреждения, фильтры по статусу/номеру/датам.
  Карточка попытки показывает запрос и ответ целиком.
- **Карточка предзаказа** (`/admin/orders/{id}`) — блок «Отправка поставщику»
  с историей попыток по этому заказу и кнопкой отправки.

Права: `supplier-preorders.view` (просмотр), `supplier-preorders.send` (отправка).
Выданы `super-admin`, `sales-manager` (обе) и `buyer-manager` (просмотр)
миграцией `2026_08_02_120100_grant_supplier_preorder_permissions`.

## Настройки (.env)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SUPPLIER_PREORDER_ENABLED` | `false` | мастер-выключатель отправки |
| `SUPPLIER_ORDER_API_URL` | `https://api.sex-opt.ru/customer/api/v1` | эндпоинт Customer API |
| `SUPPLIER_ORDER_API_KEY` | — | ключ API поставщика |
| `SUPPLIER_ORDER_API_TIMEOUT` | `30` | таймаут запроса, с |
| `SUPPLIER_PREORDER_STOCK` | `tmn` | склад поставщика (`tmn` / `msk`) |
| `SUPPLIER_PREORDER_TESTMODE` | `true` везде, кроме `production` | тестовый режим: поставщик откатывает транзакцию |
| `SUPPLIER_PREORDER_ROLLBACK_ON_WARNINGS` | `false` | откатывать заказ целиком при нехватке остатка |

### Статус на проде

С 2026-08-06 отправка **временно выключена**: деплой принудительно ставит
`SUPPLIER_PREORDER_ENABLED=false` в `/srv/pecado/.env` (шаг `[0.3/9]` в
[deploy-prod.yml](../.github/workflows/deploy-prod.yml)). Чтобы вернуть отправку,
поменяй `false` на `true` в обеих строках этого шага и выкати релиз — правка
`.env` руками на сервере переживёт до первого деплоя, но не дольше.

Порядок включения на проде: прописать `SUPPLIER_ORDER_API_KEY`, включить
`SUPPLIER_PREORDER_ENABLED=true` при `SUPPLIER_PREORDER_TESTMODE=true`, проверить
в журнале ответы поставщика (коды товаров совпадают, `unknown_items` пуст) и
только затем снять testmode.

Ключ API и документация поставщика лежат локально в `docs/andrey/` — папка в
`.gitignore` и в репозиторий не попадает.

## Требование к стороне 1С

Предзаказ, заведённый менеджером в 1С, должен приходить с `type: "preorder"`.
Без этого поля документ сохранится на сайте как обычный заказ, резерв не уйдёт,
и обновлением это уже не исправить. Зафиксировано в контракте v15.9.0:
[правила заказов](../docs-erp/content/rules/orders.md), [changelog](../docs-erp/content/changelog.md).
