Объединение подтверждённых заказов клиента в одну реализацию и один расходный ордер

# Задача

Клиенты — интернет-магазины — держат у нас по нескольку заказов в резерве (режим «Заказы в резерве», протокол v16.9.x,
в бою с 10.09.2026). Когда их покупатели подтверждают покупки, клиент отправляет в отгрузку сразу несколько резервов
и присылает одного курьера. Клиент просит: **отметить нужные резервы галочками и получить по ним ОДИН документ
реализации**. Склад просит: **по возможности один расходный ордер** на такую группу, а не по ордеру на заказ.

Цель топика — договориться, как сайт сообщает 1С «эти заказы отгружаются вместе» и что 1С с этим делает.
Это топик одной задачи. Он самодостаточен: на другие топики не ссылается.

# Почему это стало срочным

С переходом склада на график пн–сб 9:00–21:00 клиенты оформляют и забирают заказы вечером и в субботу без участия
менеджера (менеджеры работают пн–пт 9:00–18:00). Всё, что сегодня делается в 1С руками, вечером делать некому.

Объединение уже происходит, но непонятно чьими руками. По данным сайта (снимок на 17.09.2026, документы, у которых
в строках указан заказ):

| Документ | Всего | Из них по нескольким заказам |
|---|---|---|
| Расходный ордер | 1310 | 170 (до 30 заказов в одном) |
| Реализация | 8634 | 630 |

# Что есть в протоколе сейчас (v16.10.0)

- Клиент подтверждает резерв — сайт шлёт `order.confirmed` по КАЖДОМУ заказу отдельно. Поля сообщения:
  `event`, `message_id`, `uuid` (заказ), `confirmed_at`, `timestamp`. Признака «вместе с другими» нет.
- 1С снимает признак резерва, заказ уходит под отгрузку; дальше приходят `goods_issue.*` и `shipment.*`,
  где заказ указан в СТРОКЕ (`items[].order_uuid`) — то есть контракт уже умеет выражать «один ордер / одна
  реализация по нескольким заказам». Менять входящие сообщения не требуется.
- Правка состава резерва (`order.updated` сайт → 1С) — только уменьшение. Дописать строки одного заказа в другой
  нельзя, поэтому «слить заказы» средствами сайта невозможно.
- Объединять заказы через «создать новый общий заказ + отменить резервы» сайт НЕ будет: между отменой и созданием
  товар уходит в свободный остаток (может уйти другому покупателю), а при обратном порядке новый заказ получает
  недобор, потому что товар закреплён за резервами.

# Предложение сайта

Объединять не заказы, а **отгрузку**. Заказы остаются отдельными документами, а реализация и расходный ордер
оформляются общими.

1. В кабинете клиент отмечает резервы галочками и жмёт «В отгрузку выбранное».
2. Сайт шлёт по каждому заказу прежний `order.confirmed` с новым НЕОБЯЗАТЕЛЬНЫМ полем, например:
   - `ship_together_key` — UUID группы, одинаковый у всех заказов группы;
   - `ship_together_size` — сколько заказов в группе (чтобы 1С понимала, что группа собрана целиком, и не ждала
     вечно, если одно сообщение потерялось).
3. 1С, получив все сообщения группы, оформляет ОДИН расходный ордер и ОДНУ реализацию по всем заказам группы.
4. Старые клиенты протокола поле не шлют — поведение прежнее. Изменение аддитивное.

Ограничения группы, которые сайт готов проверять сам до отправки: один партнёр, один контрагент (юрлицо), одна
организация-продавец, один склад, один способ доставки, все заказы — действующие резервы.

# Вопросы к стороне 1С

1. Кто и как сейчас объединяет несколько заказов в один расходный ордер и одну реализацию: менеджер вручную,
   кладовщик, штатная обработка, регламентное задание? По какому признаку выбираются заказы?
2. Может ли 1С делать это автоматически по признаку группы из `order.confirmed`, без участия человека —
   в том числе вечером и в субботу?
3. Какие условия объединения обязательны на вашей стороне (контрагент, договор, организация, склад, валюта, НДС,
   способ доставки, вид цены)? Чего из этого нет в списке ограничений выше?
4. Реализация и расходный ордер объединяются одинаково или по-разному? Возможна ли одна реализация при нескольких
   ордерах и наоборот? Что важнее сделать первым, если обе цели сразу недостижимы: клиенту нужен один документ
   реализации, складу — меньше расходных ордеров.
5. Как 1С должна поступить, если группа пришла не целиком (часть сообщений не дошла или один заказ группы отклонён):
   ждать, оформить пришедшее, вернуть конфликт? Нужен ли тайм-аут и какой?
6. Что происходит с группой при недоборе по одному из заказов?
7. Смежный вопрос того же процесса, без ответа на который вечерний график не работает: **кто создаёт расходный
   ордер по обычному заказу «к отгрузке» вечером и в субботу?** На копии боевой базы сайта 24 из 50 последних
   заказов имеют статус «Готов к отгрузке», а расходного ордера по ним нет. Если ордер создаёт менеджер, заказ,
   отправленный в 19:00, до склада не дойдёт до утра. Нужно ли автоматическое создание ордера и возможно ли оно?
8. Есть ли вариант проще предложенного — например, 1С сама объединяет все подтверждённые заказы одного
   контрагента, ожидающие отгрузки, без всякого признака с сайта?

# Порядок работы

- Контракт меняется spec-first: JSON Schema → AsyncAPI → бизнес-правила и тест-план → changelog → код, с
  интеграционными тестами на стороне сайта. До resolution в этом топике сайт код не пишет.
- Итог топика — `proposal` с финальной редакцией поля (имена, типы, правила группы, поведение при неполной группе)
  и ответный `resolution`.
- Действующая спецификация: https://pecado.ru/docs/erp/spec.yaml
- Правила резервов: https://pecado.ru/docs/erp-guide/rules/order-reserves/
- Правила расходных ордеров: https://pecado.ru/docs/erp-guide/rules/goods-issues/

Первый ход — за стороной сайта: сайт откроет диалог этим же предложением и вопросами 1–8.
