# Сценарии поиска «капризного клиента» в личном кабинете

## Введение

Документ описывает требования к поиску и фильтрации в личном кабинете пользователя — что именно должен уметь искать **«капризный и требовательный клиент»**: оптовик, который заказывает регулярно, помнит товары по бренду и ИНН поставщика, иногда вводит запрос с ошибкой и не хочет переключаться между разделами, чтобы вспомнить, в каком заказе был нужный товар.

Документ — **backlog требований**, не план реализации. Каждый сценарий C-N.M пригоден как карточка задачи в `docs/tasks/backlog/`.

### Как читать

- **§ — раздел кабинета.** Внутри раздела указан текущий набор возможностей и пробелы.
- **Сценарий C-N.M** — конкретный пользовательский запрос с примером, ожидаемым результатом и местом срабатывания (UI-поле или endpoint).
- **(есть)** — реализовано сейчас, оставлено для документации поведения.
- **(нет)** — пробел, требующий доработки.

### Кто такой «капризный клиент» в нашем контексте

- **Оптовик** с десятками заказов в месяц, помнит товары не по номеру заказа, а по бренду / артикулу / штрихкоду.
- **Не использует мышь**: ввёл часть строки, ожидает мгновенный список, выбрал первое попавшееся.
- **Делает опечатки** в названиях брендов и товаров (`адидас` / `addidas`), но **никогда** в номерах документов и штрихкодах.
- **Хочет шарить ссылки** на найденные документы и фильтры.
- **Возвращается** к одним и тем же поисковым запросам ежемесячно.
- **Сканирует штрихкод** телефоном/сканером — ожидает, что длинная цифровая строка точно совпадёт с EAN13 и сразу даст товар.

## Сквозные принципы (применимы ко всем разделам)

1. **Регистр и пробелы:** поиск регистронезависим, лишние пробелы по краям и внутри схлопываются. `  Adidas   Sport  ` ≡ `adidas sport`.
2. **Дефисы и спецсимволы в номерах:** `29УТ-003413` ≡ `29УТ003413` ≡ `003413`. Поиск по подстроке + по варианту без дефисов.
3. **Минимум символов:** автокомплит срабатывает с **2 символов**, debounce 250–300 мс. Меньше — показывать историю запросов.
4. **Fuzzy и морфология — только для названий товаров и брендов:** русское/английское написание, словоформы, опечатки до 2 символов (Levenshtein ≤ 2). Для номеров документов, артикулов (`sku`/`code`), штрихкодов (`EAN13`/`EAN8`), ИНН, UUID — **только точное или префиксное** совпадение.
5. **Подсветка совпадения:** в выдаче ясно показано, где сработал поиск — «совпадение в составе заказа: товар X», «совпадение в номере», «совпадение в комментарии». Без этого пользователь не понимает, почему документ нашёлся.
6. **Чипы активных фильтров:** все фильтры (включая поиск) отображаются как удаляемые чипы под формой. Применяется во всех разделах единообразно.
7. **Шаринг URL:** все параметры поиска и фильтра в query string, поддержка перезагрузки страницы и копирования ссылки.
8. **История запросов:** последние 10 запросов в выпадайке поиска (per-user, per-section). Кликом — повтор.
9. **Сохранённые поиски:** возможность дать название набору фильтров и закрепить его в боковой панели раздела.
10. **Scope:** пользователь всегда видит только свои документы (`user_id` или `whereHas('company', ...)`). Поиск по составу не должен «пробивать» этот scope.
11. **Подсчёт «найдено N» с дедупликацией:** если документ нашёлся одновременно по номеру и по составу — он в выдаче один раз.
12. **«Ничего не найдено» с подсказками:** при пустом результате показать «Возможно, вы имели в виду…» (для fuzzy-поиска по товарам/брендам) либо «Попробуйте искать без дефиса / по части номера».

## §1. Заказы (`/cabinet/orders`)

**Текущее:** [OrderController.php:41-47](app/Http/Controllers/User/OrderController.php) — LIKE по `uuid`, `number`, `erp_number`, `id`. Никакого поиска по составу.

### C-1.1. Поиск по части номера 1С (есть, требует доработки дефиса)
**User story:** Как клиент, я хочу ввести только хвост номера из 1С (`003413`), чтобы быстро найти заказ, не вводя префикс `29УТ-`.
**Пример запроса:** `003413`, `29ут003413`, `29УТ-003413`, `29УТ-3413`.
**Ожидаемый результат:** найден заказ с `erp_number = '29УТ-003413'`. Все три варианта дают одинаковый результат.
**Где должно работать:** поле «Поиск по номеру…» на [Orders/Index.jsx:99-105](resources/js/Pages/User/Cabinet/Orders/Index.jsx).
**Замечания:** добавить нормализацию — убрать дефисы и пробелы перед `LIKE`, искать в номерах как по нормализованной форме, так и по оригиналу. Без fuzzy.

### C-1.2. Поиск по UUID или его хвосту (есть)
**User story:** Как клиент, я хочу найти заказ по любому фрагменту UUID (например, последним 6 символам), потому что вижу его в URL прошлого письма.
**Пример запроса:** `7f3a8c`, `7f3a8c12-...`.
**Ожидаемый результат:** заказ, у которого `uuid LIKE '%7f3a8c%'`.
**Где должно работать:** то же поле поиска.
**Замечания:** уже работает. Зафиксировать в тестах.

### C-1.3. Поиск по названию товара в составе (нет)
**User story:** Как клиент, я хочу найти заказы, в которых был товар «Кроссовки Air Max», чтобы повторить покупку, не помня номера.
**Пример запроса:** `Air Max`, `air max`, `аир макс`, `кроссовки эир`, `air maxx` (опечатка).
**Ожидаемый результат:** все заказы пользователя, среди позиций которых есть товар с названием, fuzzy-совпадающим с запросом. В выдаче — пометка «совпадение в составе: Кроссовки Nike Air Max 90, артикул AM90-001».
**Где должно работать:** то же поле поиска (единая строка, разные источники совпадения).
**Замечания:** **fuzzy и морфология — да**. Реализация — индексация `OrderItem.product_name_snapshot` + `product_id` через Meilisearch (или join с `products` через `whereHas` для exact-матча, fuzzy — через Scout). Scope: только заказы текущего пользователя.

### C-1.4. Поиск по бренду в составе (нет)
**User story:** Как клиент Adidas, я хочу видеть все заказы, где был хотя бы один товар Adidas.
**Пример запроса:** `Adidas`, `адидас`, `addidas`, `аdidas`.
**Ожидаемый результат:** все заказы, у которых есть хотя бы одна позиция с товаром `brand.name ILIKE 'adidas%'` (с fuzzy для опечаток).
**Где должно работать:** то же поле поиска **и** отдельный фасет «Бренд» в фильтрах (multi-select).
**Замечания:** fuzzy для бренда — да. Дополнительно: фасет «Бренд» в боковой форме фильтров — список топ-20 брендов из истории заказов пользователя.

### C-1.5. Поиск по артикулу/SKU товара в составе (нет)
**User story:** Как клиент, я знаю свой артикул `AM90-001` и хочу найти все заказы, где он был.
**Пример запроса:** `AM90-001`, `am90`, `AM90` (префикс).
**Ожидаемый результат:** все заказы с позицией `product.sku = 'AM90-001'` (точное) или `sku LIKE 'AM90%'` (префиксное).
**Где должно работать:** то же поле поиска.
**Замечания:** **fuzzy НЕ применяется** — артикул должен совпадать точно или префиксно (предотвращает мусорные совпадения).

### C-1.6. Поиск по штрихкоду EAN13 в составе (нет)
**User story:** Как клиент со сканером, я хочу отсканировать штрихкод и сразу увидеть все мои заказы с этим товаром.
**Пример запроса:** `4607123456789` (длинная цифровая строка).
**Ожидаемый результат:** все заказы с позицией, у которой `product.barcodes.barcode = '4607123456789'`. Точное совпадение, без LIKE-обёртки.
**Где должно работать:** то же поле поиска. Эвристика «строка из 8/12/13/14 цифр» → точный поиск по `product_barcodes.barcode`.
**Замечания:** **fuzzy запрещён**. Если ровно 13 цифр — приоритет EAN13 в выдаче.

### C-1.7. Поиск по коду товара 1С в составе (нет)
**User story:** Как клиент, я работаю с кодами 1С (`code` товара) и хочу искать заказы по ним.
**Пример запроса:** `00012345`.
**Ожидаемый результат:** все заказы с позицией `product.code = '00012345'` (точное).
**Где должно работать:** то же поле поиска.
**Замечания:** fuzzy запрещён.

### C-1.8. Поиск по названию контрагента (нет)
**User story:** Как клиент с несколькими юрлицами, я хочу ввести `ООО Ромашка` и увидеть только заказы этой компании, не открывая dropdown «Контрагент».
**Пример запроса:** `ромашка`, `Ромашка`, `ООО Р`, `OOO Romashka` (если поддерживается транслит — в будущем).
**Ожидаемый результат:** заказы, у которых `company.name ILIKE '%ромашка%'`.
**Где должно работать:** то же поле поиска **и** dropdown «Контрагент» с автокомплитом (вместо текущего фиксированного списка).
**Замечания:** scope обязательно — только компании, принадлежащие пользователю ([OrderController.php:62-64](app/Http/Controllers/User/OrderController.php)). Fuzzy не применяется (имена юрлиц требуют точности).

### C-1.9. Поиск по ИНН контрагента (нет)
**User story:** Как клиент, я хочу найти заказы по ИНН компании.
**Пример запроса:** `7707083893`.
**Ожидаемый результат:** заказы, где `company.tax_id = '7707083893'` (точное) или `LIKE '7707%'` (префикс).
**Где должно работать:** то же поле поиска. Эвристика «10 или 12 цифр подряд» → искать как ИНН.
**Замечания:** fuzzy запрещён.

### C-1.10. Поиск по комментарию к заказу (нет)
**User story:** Как клиент, я оставлял комментарий «Привезти к 17:00 на склад» и хочу найти этот заказ через поиск по тексту.
**Пример запроса:** `17:00`, `привезти на склад`.
**Ожидаемый результат:** заказы, у которых `comment ILIKE '%17:00%'`.
**Где должно работать:** то же поле поиска (с пометкой «совпадение в комментарии»).
**Замечания:** fuzzy не применяется (комментарии — свободный текст, ложные срабатывания дороже пропуска).

### C-1.11. Фильтр «только предзаказы / только обычные / смешанные»
**User story:** Как клиент, я хочу отдельно посмотреть свои предзаказы, а потом — обычные заказы.
**Пример запроса:** клик по чекбоксу «Только предзаказы».
**Ожидаемый результат:** заказы с `type = 'preorder'`. Текущий фильтр `type` есть в [OrderController.php:50-52](app/Http/Controllers/User/OrderController.php), но нужно добавить опцию «смешанные» (заказы, у которых часть позиций — предзаказ, часть — обычные).
**Где должно работать:** select «Тип заказа» в [Orders/Index.jsx:196-213](resources/js/Pages/User/Cabinet/Orders/Index.jsx).

### C-1.12. Фильтр по диапазону количества позиций (нет)
**User story:** Как клиент, я хочу найти крупные заказы — те, где было больше 50 позиций.
**Пример запроса:** «Позиций от 50».
**Ожидаемый результат:** заказы, у которых `items_count >= 50`.
**Где должно работать:** новые поля «Позиций от/до» рядом с «Сумма от/до».

### C-1.13. «Повторить заказ» — найти прошлые заказы с конкретным товаром (нет)
**User story:** Как клиент, я хочу из карточки товара / из избранного нажать «Когда я это покупал?» и увидеть список своих заказов с этим товаром.
**Пример запроса:** клик «Найти в моих заказах» на карточке товара `product_id = 12345`.
**Ожидаемый результат:** редирект на `/cabinet/orders?product_id=12345` со списком заказов, содержащих этот товар (по убыванию даты).
**Где должно работать:** дополнительный query-параметр `product_id` в [OrderController.php](app/Http/Controllers/User/OrderController.php) + кнопка на карточке товара.

### C-1.14. Сохранённые поиски «Все заказы Adidas в этом году» (нет)
**User story:** Как клиент, я каждый месяц проверяю «Все заказы Adidas с начала года» — хочу сохранить набор фильтров и кликом возвращаться к нему.
**Пример запроса:** настроил фильтр {brand_in_items: 'Adidas', date_from: '2026-01-01'} → нажал «Сохранить как…», ввёл имя → пункт появился в боковой панели.
**Ожидаемый результат:** клик по сохранённому поиску — все фильтры применяются за один шаг.
**Где должно работать:** общий механизм сохранённых поисков (см. Приложение А).

## Приложение А. Кросс-разделы — единые механизмы

Эти возможности имеет смысл реализовать **единообразно** во всех листингах кабинета (заказы, возвраты, отгрузки, корзины, избранное, медиатека, выгрузки), а не точечно.

### A-1. История последних запросов
**User story:** Кликаю в пустое поле поиска — вижу 10 последних своих запросов в этом разделе. Кликаю — повтор.
**Ожидаемый результат:** хранится per-user, per-section (например, в `localStorage` `cabinet.search.{section}.history`). Серверная история (как в каталоге через `SearchController::history`) — опционально.
**Замечания:** см. реализацию каталога — [Search.jsx](resources/js/shared/Search.jsx) и [SearchDropdown.jsx](resources/js/components/common/SearchDropdown.jsx) — переиспользовать.

### A-2. Сохранённые поиски (пресеты)
**User story:** Настроил фильтр «Заказы Adidas с начала года» → нажал «Сохранить как…» → пресет появился в боковой панели. Клик — все фильтры применяются.
**Ожидаемый результат:** новая модель `UserSearchPreset` с `user_id`, `section` (orders/returns/...), `name`, `filters` (JSON). UI — кнопка «Сохранить» рядом с «Применить» и список пресетов сбоку.

### A-3. Шаринг URL
**User story:** Скопировал URL текущего поиска и переслал коллеге — он видит ту же выдачу.
**Ожидаемый результат:** все параметры поиска и фильтра в query string, страница восстанавливается из URL.
**Где работает:** уже реализовано в большинстве разделов через `withQueryString()`. Унифицировать.

### A-4. Чипы активных фильтров
**User story:** Ниже формы вижу набор удаляемых чипов — клик по «×» убирает один фильтр.
**Ожидаемый результат:** единый компонент `<SelectedFilters />` (есть в каталоге — [Products/SelectedFilters.jsx](resources/js/Pages/User/Products/SelectedFilters.jsx)) — вынести в общий и использовать на всех страницах кабинета.

### A-5. Подсветка совпадения и пометка источника
**User story:** В выдаче заказа понятно, что я нашёл его не по номеру, а по составу: пометка «совпадение в составе: Кроссовки Nike Air Max». В тексте — выделение жирным фрагмента совпадения.
**Ожидаемый результат:** сервер возвращает поле `match_source` (`number`/`composition`/`comment`/`company`) и `match_snippet`. UI рендерит соответствующий бейдж.

### A-6. Экспорт результата поиска
**User story:** Применил фильтры → нажал «Экспорт CSV/XLSX» → скачал результат с теми же колонками, что в таблице.
**Ожидаемый результат:** на каждой странице кабинета — кнопка «Экспорт» в шапке таблицы. Использует тот же query, что и поиск.

### A-7. Debounce + автосабмит фильтров
**User story:** Я ввожу текст в фильтр «Сумма от» → результат обновляется через 400 мс без нажатия «Применить».
**Ожидаемый результат:** все фильтры — мгновенные с debounce, кнопка «Применить» становится не нужна. Кнопка «Сбросить» остаётся.
**Где работает:** уже сделано в [Cabinet/Media/Index.jsx](resources/js/Pages/User/Cabinet/Media/Index.jsx) (debounce 300мс). Распространить на остальные разделы.

### A-8. «Ничего не найдено» — умный fallback
**User story:** Поиск не дал результатов — вижу подсказку «Возможно, вы имели в виду: <fuzzy-вариант>?» или «Попробуйте без дефиса: 003413».
**Ожидаемый результат:** при пустом результате — генерация подсказки на основе fuzzy-индекса (для названий товаров/брендов) или эвристик (нормализация номера, замена `o` ↔ `о`, удаление дефисов).
