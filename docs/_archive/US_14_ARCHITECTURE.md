# Архитектурное решение: Индивидуальные цены пользователей (US-14)

## 1. Вводные данные и проблематика
В рамках отказа от зеркалирования логики скидок 1С на сайте, было принято решение передавать из 1С **готовые** (рассчитанные) цены для каждого пользователя (партнёра), товара и склада.

**Масштаб данных:**
- Количество товаров: 10 000
- Количество складов: 5
- Количество пользователей: 800
- **Итого:** потенциально до **40 000 000** уникальных цен.

**Проблема больших данных и медленной передачи:**
Передача 40 млн цен по одной через RabbitMQ в реальном времени невозможна. Смена базовой цены или глобального курса валюты в 1С приведёт к каскадному пересчету и генерации миллионов событий. Очередь RabbitMQ переполнится, а потребители на стороне Laravel (workers) не справятся с нагрузкой (вставка по одной записи убьет БД). Также сама 1С зависнет на генерации такого количества AMQP-сообщений.

## 2. Оценка мощностей Dev-сервера
Текущие характеристики сервера (93.94.150.16 / 10.2.2.100):
- **Процессор:** AMD Ryzen 5 4600H (6 ядер, 12 потоков) — *отличный показатель для веб-сервера.*
- **Оперативная память:** 16 ГБ (доступно ~4.4 ГБ свободно, часть в кэше) — *достаточно для MySQL/Redis.*
- **Диск:** NVMe SSD (остаток 23 ГБ) — *очень быстрый диск, критически важно для БД.*
- **Резюме:** Сервер легко справится со хранением 40 млн записей, при условии правильной архитектуры БД (индексы) и пакетной (bulk) вставки. Однако 23 ГБ свободного места на диске требуют осторожности — база не должна пухнуть от логов очередей.

## 3. Где и как хранить цены на сайте

### Вариант А: MySQL (Рекомендуемый для старта)
40 млн записей — это нормальный объем для реляционной базы, если таблица спроектирована узко.
Создаем таблицу `individual_prices`:
- `product_uuid` (UUID/char(36) или `product_id` bigint(unsigned) для ускорения)
- `warehouse_uuid` (UUID/char(36) или `warehouse_id`)
- `partner_uuid` (UUID/char(36) или `partner_id`)
- `price` (DECIMAL(10,2))
**Индексы:** Композитный Primary Key `(partner_id, product_id, warehouse_id)`.
**Объем:** Сама таблица займет около 1.5 - 2.5 ГБ на диске (вместе с индексами). На NVMe диске выборка по первичному ключу займет < 1 мс.

### Вариант Б: Redis (Для максимальной скорости чтения)
Если каталог сложный и требует вывода 100 товаров на странице с учетом цен конкретного юзера, MySQL может создавать нагрузку.
В Redis можно хранить цены как Hash:
Ключ: `price:{partner_uuid}:{warehouse_uuid}`
Поля: `product_uuid` -> `1500.00`
**Объем:** На 800 юзеров это 4000 ключей (по каждому складу), внутри которых до 10к полей. Это займет около 1-2 ГБ оперативной памяти.

**Вывод:** Используем **MySQL** как основное хранилище (учитывая, что у нас всего 4.5ГБ свободной RAM), но данные обновляем **строго через `INSERT ... ON DUPLICATE KEY UPDATE` батчами по 1000-5000 строк**.

## 4. Формат передачи данных (RabbitMQ + MinIO/S3)

Нельзя отправлять цены поштучно. Используем **модель "Файл + Уведомление" (Событие о готовности дампа)**. У нас в Docker уже есть `MinIO`, что идеально подходит для этого.

### Стратегия обмена:
1. 1С генерирует пакет измененных цен (например, в формате JSON Lines или CSV).
2. 1С загружает этот файл в **MinIO** (S3).
3. 1С отправляет в RabbitMQ маленькое сообщение со ссылкой на файл.
4. Laravel скачивает файл из MinIO и загружает в БД через потоковое чтение (или `LOAD DATA INFILE`).

### Формат сообщения в RabbitMQ (erp_in.prices)

Отказываемся от `agreement.created`, вместо него вводим `individual_prices.ready`:

```json
{
  "event": "individual_prices.ready",
  "message_id": "msg-price-dump-a1b2c3d4",
  "upload_type": "delta", // "full" (полная выгрузка) или "delta" (только изменения)
  "file_url": "s3://prices-exchange/2026-03-26/delta_14-05.jsonl",
  "records_count": 150000,
  "timestamp": "2026-03-26T14:05:00+03:00"
}
```

### Формат файла в MinIO (например `delta_14-05.jsonl`)
JSON Lines (каждая строка — валидный JSON). Это позволяет читать файл потоково, не загружая гигабайты в RAM.
```json
{"partner_uuid":"...","warehouse_uuid":"...","product_uuid":"...","price":1250.00}
{"partner_uuid":"...","warehouse_uuid":"...","product_uuid":"...","price":1300.00}
```

## 5. Стратегия выгрузки (Событийно или по времени?)

**Делать по каждому событию в 1С — КАТЕГОРИЧЕСКИ НЕЛЬЗЯ.**
Если менеджер изменит базовую цену группы из 100 товаров, 1С должна будет пересчитать 100 * 5 * 800 = 400 000 цен индивидуально. Запускать этот процесс синхронно при записи товара в 1С приведет к зависанию базы 1С у пользователей.

### Рекомендуемый подход для 1С (Асинхронный/Регламентный):
1. **Отслеживание изменений (Логирование):**
   При изменении цены, скидки, курса валют, или параметров партнера, 1С делает запись во внутренний регистр сведений "К пересчету индивидуальных цен" (указывая товар или партнера).
2. **Фоновое задание (Cron / Регламентное задание в 1С):**
   Раз в 15 или 30 минут запускается фоновое задание. Оно собирает пул измененных товаров/партнеров, рассчитывает для них цены для всех складов.
3. **Батчинг:**
   Задание формирует JSONL файл (delta), кладет в MinIO и пушит RabbitMQ событие. Если изменений не было — ничего не делает.
4. **Ночной пересчет (Full Dump):**
   Раз в сутки (например, в 03:00) 1С выгружает ПОЛНЫЙ ДАМП всех 40 млн цен. Laravel принимает `upload_type: "full"` и полностью заменяет/сверяет таблицу. Это гарантия того, что рассинхрон из-за потерянных событий будет исправлен.

## Итоговое резюме
1. **Хранилище:** MySQL, таблица `individual_prices` с композитным Primary Key. Из-за лимитов ОЗУ Redis лучше пока не использовать как primary source.
2. **Транспорт:** MinIO (S3) для самих данных + RabbitMQ для сигнала-уведомления.
3. **Расписание:** Регламентное задание в 1С каждые 15-30 минут (для дельт) + ночная полная выгрузка.
4. **Формат:** Потоковый JSON Lines (`.jsonl`) файл внутри архива.

## 6. Ответы на архитектурные вопросы

### Нужно ли применять шардирование в MySQL или хранить цены в отдельных таблицах для пользователей?
**Нет, это антипаттерн в данном случае.**
Создание 800 таблиц (по пользователю) усложнит поддержку схемы БД и миграции. Объем в 40 миллионов строк для одной таблицы MySQL (особенно InnoDB) — это совершенно нормальная нагрузка. 
Самое важное — правильный составной первичный ключ: `(partner_uuid, product_uuid, warehouse_uuid)`.
При наличии такого ключа и размещении файлов БД на быстром NVMe-диске (что у нас есть на dev-сервере), поиск цены для списка 50 товаров на странице каталога (через `WHERE partner_uuid = ? AND product_uuid IN (...)`) займёт **менее 1-2 миллисекунд**.
Шардирование или партиционирование (например, `PARTITION BY HASH(partner_id)`) имеет смысл рассматривать только если таблица разрастётся до сотен миллионов строк и возникнут проблемы со скоростью вставки (INSERT/UPDATE), но для 40 млн записей единой таблицы более чем достаточно.

### Нужно ли загружать в Redis цены на товар для пользователя при авторизации?
**Нет, это избыточно и создаст проблемы с синхронизацией.**
Если загружать цены в момент логина:
1. Вы создаете скачок нагрузки: нужно вытащить 50 000 строк (10к товаров * 5 складов) из MySQL и положить в Redis в момент создания сессии. Это сделает вход на сайт заметно медленным для пользователя.
2. 50 000 ключей в Redis займут около 3-5 МБ памяти на одного активного пользователя. 800 юзеров онлайн = до 4 ГБ забитой оперативки (вы упретесь в лимиты dev-сервера).
3. Инвалидация: если 1С пришлёт обновление цены, пока юзер сидит на сайте, придется искать его сессионный кэш в Redis и точечно обновлять его, что усложняет логику.

**Правильный подход:** Запрашивать цены напрямую из MySQL (по индексам) на лету при генерации страницы (или API-ответа). Если же нужен кэш страниц, то логичнее кэшировать целые ответы API/HTML кусочки для конкретной страницы каталога пользователя.

### Как и когда чистить потоковый файл, который хранится в MinIO?
**С помощью Laravel Scheduler (фоновых задач).**
Файлы `.jsonl` в MinIO нужны только как транспортный инструмент. 
- На стороне Laravel нужно создать Artisan-команду (например, `app:clean-price-dumps`).
- Команду прописать в `app/Console/Kernel.php` (или `routes/console.php` в Laravel 11) для ежедневного запуска (`->dailyAt('04:00')`).
- Логика команды должна обходить бакет `prices-exchange` и удалять все файлы (дампы цен), дата изменения которых **старше 3-х или 7-ми дней**.
- Три дня — оптимальный буфер: если в пятницу вечером выгрузка сломалась (например, баг в парсере на Laravel), в понедельник утром у разработчика всё ещё будут исходные JSONL файлы от 1С для дебага. После решения проблемы файлы старше 3 дней спокойно удалятся.

### Стоит ли поднять отдельную базу типа ClickHouse для цен (ведь это легко сделать в Docker)?
**Однозначно нет. Для данной задачи ClickHouse не подходит.**
1. **Тип нагрузки (OLTP vs OLAP):** Вывод цен на сайте (например, показ 50 товаров в каталоге для конкретного юзера) — это типичная OLTP-нагрузка (точечные `SELECT` запросы по индексам). ClickHouse — это колоночная СУБД для OLAP (аналитики). Она блестяще считает сумму или среднее по миллиарду строк, но работает **медленнее**, чем MySQL при точечном поиске (point lookups) конкретной строки по ID. B-Tree индексы MySQL идеальны для быстрого извлечения конкретных цен.
2. **Обновление данных (Mutations):** В MySQL мы можем делать `INSERT ... ON DUPLICATE KEY UPDATE` батчами. В ClickHouse операции `UPDATE/DELETE` (мутации) крайне тяжеловесны и выполняются асинхронно. Это создаст массу проблем при обновлении цен.
3. **Потребление ресурсов:** ClickHouse требует достаточно много оперативной памяти (рекомендуется от 4-8 ГБ просто для старта). На dev-сервере сейчас свободно около 4.5 ГБ RAM. Добавление ClickHouse усложнит инфраструктуру и "съест" ресурсы, при этом не дав никаких преимуществ для нашей задачи, с которой MySQL справится "одной левой".

## 7. Roadmap реализации (План работ)

### Техническое задание для разработчика 1С (Выгрузка индивидуальных цен)

**Цель:** Обеспечить передачу готовых индивидуальных цен (товар + склад + клиент) на сайт без перегрузки очереди RabbitMQ, используя потоковую батч-выгрузку файлов через S3 (MinIO).

#### 1. Структура хранения очереди (Регистр сведений)
**Зачем это нужно:** Чтобы не тормозить работу менеджеров 1С во время проведения документов сложными пересчетами 40 млн цен. Мы лишь "помечаем" измененные объекты, а тяжелый расчет откладываем на фоновое задание.

Создать непериодический независимый регистр сведений `ОчередьВыгрузкиИндивидуальныхЦенPecado`:
- **Измерения:** 
  - `Объект` (Любая ссылка: СправочникСсылка.Номенклатура, СправочникСсылка.Партнеры, СправочникСсылка.Валюты, Документы ценообразования и т.д.)
- **Назначение:** Фиксация "грязных" объектов, изменение которых влияет на итоговую цену на сайте.

#### 2. Регистрация изменений (Подписки на события)
**Зачем это нужно:** 1С должна автоматически «ловить» любые изменения, которые могут повлиять на финальную цену клиента на сайте, чтобы отправить их в очередь на пересчет.

Добавить подписки на события `ПриЗаписи` (или проведение) для:
- **Партнеры** (изменение индивидуального соглашения, смена тарифа).
- **Сегменты партнеров** (при добавлении/удалении партнера из сегмента, к которому привязаны скидки).
- **Номенклатура** (изменение базовой цены, принадлежности к бренду/сегменту).
- **Сегменты номенклатуры** (привязка/отвязка товаров к акциям).
- **Документы ценообразования** (Установка цен номенклатуры, Установка скидок/наценок, Индивидуальные соглашения).
- **Справочник "Валюты"** (изменение курса базовых валют мгновенно пересчитывает цены всего привязанного каталога).
- *Логика подписки:* При записи объекта просто добавлять ссылку на него в регистр `ОчередьВыгрузкиИндивидуальныхЦенPecado`.

#### 3. Алгоритм подготовки цен (Учет кейсов изменения)
**Зачем это нужно:** Это ядро выгрузки (мозг). По ссылке на измененный объект алгоритм должен понять, ЧТО именно нужно пересчитать, чтобы не считать лишнего (все 40 млн), но и не пропустить важного (каскадные изменения).

Создать серверную процедуру для анализа ссылок из очереди:
- **Кейс А: Изменился документ "Установка цен номенклатуры" (или базовая цена)** 
  -> Ищем все товары в документе -> Пересчитываем цены **этих товаров** для **ВСЕХ выгружаемых партнеров** и складов.
- **Кейс Б: Изменился "Партнер" (его соглашение/тариф/сегмент)** 
  -> Пересчитываем цены по **ВСЕМ товарам**, но только для **этого партнера** по всем складам.
- **Кейс В: Изменился "Товар" (Номенклатура попала в новый сегмент)** 
  -> Пересчитываем цену **этого одного товара** для **ВСЕХ партнеров** и складов.
- **Кейс Г: Изменилась "Скидка/Наценка" (общая акция на сегмент)**
  -> Определяем сегмент товаров и сегмент партнеров, на которые действует скидка -> Пересчитываем пересечение: **все товары сегмента** для **всех партнеров сегмента**.
- **Кейс Д: Изменился курс в справочнике "Валюты"** 
  -> Если цены каталога или соглашения жестко зависят от этой валюты, придется инициировать полный пересчет: **ВСЕ зависимые товары** для **ВСЕХ партнеров** (Либо поместить в очередь специальный маркер полной выгрузки).
- **Результат:** Процедура генерирует таблицу: `partner_uuid`, `product_uuid`, `warehouse_uuid`, `price`.

#### 4. Инкрементальная выгрузка дельт (Фоновое задание 1)
**Зачем это нужно:** Регулярная отправка на сайт свежих измененных цен "пачками" (дельт), чтобы клиенты видели актуальный прайс в течение дня без часовых задержек.

- **Расписание:** Каждые 15–30 минут рабочего дня.
- **Шаги выполнения:**
  1. Выбрать записи из регистра `ОчередьВыгрузкиИндивидуальныхЦенPecado`. Если пусто — завершить.
  2. Рассчитать новые индивидуальные цены (по алгоритму из п.3 "Кейсы").
  3. Сформировать текстовый файл в формате **JSON Lines** (`.jsonl`). Каждая строка — самостоятельный JSON-объект без запятых в конце и без массива `[]` вокруг. 
     *Пример строк в файле:*
     `{"partner_uuid":"...","product_uuid":"...","warehouse_uuid":"...","price":1500.00}`
  4. Загрузить файл по S3 API (MinIO) в бакет `prices-exchange` (например: `s3://prices-exchange/2026-03-26/delta_14-30.jsonl`).
  5. Отправить уведомление (Event) в RabbitMQ (в exchange `erp.events` с routing key `individual_prices.ready`), чтобы Laravel поймал ссылку на файл:
     ```json
     {
       "event": "individual_prices.ready",
       "message_id": "<uuid_сообщения>",
       "upload_type": "delta",
       "file_url": "s3://prices-exchange/2026-03-26/delta_14-30.jsonl",
       "records_count": 5000,
       "timestamp": "2026-03-26T14:30:00+03:00"
     }
     ```
  6. Очистить успешно обработанные ссылки из регистра `ОчередьВыгрузкиИндивидуальныхЦенPecado`.

#### 5. Полная ночная выгрузка / Full Dump (Фоновое задание 2)
**Зачем это нужно:** Железобетонная страховка от рассинхронов. Если из-за технического сбоя сеть мигнула, брокер RabbitMQ упал, или кто-то вручную поправил цены напрямую в БД 1С без вызова событий — ночной дамп гарантированно "выровняет" все цены на сайте в состояние 1-в-1 с 1С.

- **Расписание:** Один раз в сутки в период минимальной нагрузки (например, 03:00 ночи).
- **Шаги выполнения:**
  1. Игнорируя регистр изменений, в цикле перебрать **ВСЕ** выгружаемые товары, склады и всех выгружаемых партнеров.
  2. Рассчитать 100% цен (ожидаемый объем — до 40 млн строк). 
  3. Так как объем гигантский, файл необходимо писать **потоково** (порционно записывая строки в файл на диск), чтобы предотвратить падение рабочего процесса 1С по нехватке памяти (Out of Memory). Можно разбивать дамп на несколько файлов (тогда отправлять массив ссылок в `file_urls`).
  4. Загрузить файлы в S3 бакет `prices-exchange`.
  5. Публикация сообщения-уведомления в RabbitMQ аналогична п.4, но с параметром `"upload_type": "full"`:
     ```json
     {
       "event": "individual_prices.ready",
       "message_id": "<uuid_сообщения>",
       "upload_type": "full",
       "file_url": "s3://prices-exchange/2026-03-26/full_03-00.jsonl",
       "records_count": 40000000,
       "timestamp": "2026-03-26T03:00:00+03:00"
     }
     ```

### Со стороны Сайта (Разработчик Laravel)
1. **Подготовка базы данных:** 
   - Создание миграции для таблицы `individual_prices` (поля `partner_uuid`, `product_uuid`, `warehouse_uuid`, `price`).
   - Навешивание композитного первичного ключа `(partner_uuid, product_uuid, warehouse_uuid)`.
2. **Настройка S3 Client:**
