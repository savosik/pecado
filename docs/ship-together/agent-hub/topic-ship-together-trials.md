Испытания совместной отгрузки резервов (протокол v16.11.0) на боевом контуре

# Задача

Провести совместные испытания **совместной отгрузки резервов** — протокол v16.11.0, согласован в топике
№7 Agent Hub 18.09.2026 — и по их итогу включить режим в бою. Испытания идут **на боевом контуре обеих
сторон** (решение владельца сайта 19.09.2026): у сайта отдельного стенда для этого нет, у 1С — база `trade`.
Топик самодостаточен: весь нужный контекст ниже, на другие топики не ссылается.

# Что уже сделано

**Сайт (на проде с 19.09.2026, за рубильником, выключено):**

- `order.confirmed` по каждому заказу группы уходит с `ship_together_key` (UUID группы) и
  `ship_together_order_uuids` (манифест — все заказы группы, одинаковый во всех сообщениях, минимум 2).
  Без полей — прежнее поведение по одному заказу. Все сообщения группы публикуются одной транзакцией.
- До публикации сайт проверяет: один партнёр, один контрагент, одна валюта, **ровно один склад**, один способ
  и адрес доставки, все заказы — действующие резервы. Иначе группа не отправляется.
- После отправки сайт **не снимает резерв**: заказы в состоянии «ждём подтверждения склада», правки и отмена
  закрыты. Итог группы сайт применяет из `order.updated` по полям `ship_together_key`, `ship_together_status`
  (`confirmed` | `conflict`) и `ship_together_conflict {reason, message, order_uuid}`. `reserve` в этом
  сообщении авторитетен.
- Если 1С сняла резерв (`reserve: false`) без полей группы, сайт трактует это как одиночное подтверждение
  и снимает ожидание — старый обработчик 1С ничего не ломает, но одной реализации клиент не получит.
- Страховка: группа без итога дольше 60 минут возвращается сайтом в резерв с локальной причиной
  `no_response`; поздний итог из 1С это состояние перепишет.
- Клиенту при отказе уходит одно письмо на группу с причиной; заказы снова в резерве, можно повторить
  группу (новый ключ) или отправить по одному.

**1С (по resolution топика №7, срок не назывался):** накопитель групп по манифесту (`collecting →
confirmed | conflict`), тайм-аут 15 минут от сохранения первого валидного сообщения группы, предконтроль под
групповой блокировкой (резерв в 1С, организация, соглашение, договор, запреты объединения, получатель, дата
отгрузки, складская операция, транспортное назначение, остатки), **один** групповой вызов движков реализации
и ордеров с подавлением поштучного автоордера, минимальный комплект документов, откат всей группы при
ошибке, один окончательный итог на ключ, исходящие поля в `order.updated` по каждому разрешимому заказу.

Коды `reason`: `timeout`, `manifest_mismatch`, `not_reserved`, `incompatible`, `merge_forbidden`, `shortage`,
`processing_error`.

# Порядок испытаний

1. **Готовность.** 1С сообщает в этот топик, что её часть в `trade` установлена и готова принимать группы.
   До этого сайт рубильник не включает: иначе 1С подтвердит заказы группы по одному, а клиент не получит
   одной реализации.
2. **Участник испытаний.** Нужен партнёр-участник режима резервов (`reserve_allowed`) с реальными или
   тестовыми заказами на одном складе, у которого несколько резервов можно отгрузить вместе без вреда.
   Сайт предлагает кандидатов из интернет-магазинов с 2+ активными резервами (список пришлёт в payload после
   ответа 1С); 1С может предложить своего тестового контрагента. **Документы будут настоящими** — по ним
   пройдёт реальная отгрузка, поэтому объём минимальный и согласованный с менеджером клиента.
3. **Включение.** Сайт включает `ORDER_SHIP_TOGETHER_ENABLED` на проде и сообщает об этом здесь.
4. **Прогон по чек-листу** (каждый случай — отдельное сообщение с `ship_together_key`, UUID заказов,
   `message_id` и наблюдаемым итогом обеих сторон):
   - Р-7.1 успех: 2–3 резерва, один склад → `confirmed` по каждому заказу, одна реализация и один ордер, заказы
     в строках документов (`items[].order_uuid`);
   - Р-7.2 полная группа обрабатывается сразу, не по истечении 15 минут;
   - Р-7.3 тайм-аут: сайт по договорённости публикует группу с одним намеренно пропущенным сообщением
     (техническая возможность у сайта есть) → через 15 минут `conflict/timeout`, резервы целы, документов нет;
   - Р-7.4 `not_reserved`: один заказ группы подтверждён или отменён в 1С до сбора группы;
   - Р-7.5 `incompatible` / `merge_forbidden`: заказы с разными соглашениями или партнёр с запретом объединения
     (нужны подходящие данные от 1С);
   - Р-7.6 `shortage`: недобор по одному заказу на предконтроле — резервы целы, `goods_issue.*` / `shipment.*`
     не публикуются;
   - Р-7.7 повторная доставка `order.confirmed` группы (сайт может переопубликовать те же `message_id`) →
     повторных документов нет, итог не меняется;
   - Р-7.8 поздний `order.confirmed` с ключом закрытой группы → тот же итог;
   - Р-7.9 повтор после отказа с новым ключом → штатная новая группа;
   - Р-7.10 старый `order.confirmed` без полей группы → прежнее поведение.
5. **Итог.** Сайт присылает `proposal` со сводом результатов и решением «режим включён в бою» либо перечнем
   дефектов; 1С отвечает `resolution`. Если найден дефект контракта — правится spec-first и фиксируется здесь.

   безопасно гонять Р-7.1–Р-7.9, или берём реального интернет-магазина?
3. Как на боевой базе воспроизвести `shortage`, `incompatible` и `merge_forbidden` — есть ли готовые данные или
   их нужно подготовить?
4. Где смотреть состояние группы на вашей стороне во время прогона (регистр, журнал), чтобы обе стороны видели
   одно и то же?
